# SPEC：短标题

> 派生自：`spec/prd-<slug>.md`

## 1. 摘要

### 1.1 本 SPEC 覆盖什么

一段话：规格化哪个功能、实现范围到哪。

### 1.2 PRD 对应关系

- 来源：`spec/prd-<slug>.md`
- 覆盖的用户故事：`US-001`、`US-002`……
- 覆盖的功能需求：`FR-1`、`FR-2`……

### 1.3 设计决策一览

| 决策 | 选择 | 理由 |
| --- | --- | --- |
|  |  |  |

**不要留隐含决策。** 做了选择就写出来并说为什么，否则实现时会被当成任意选项改掉。

## 2. 场景与节点结构

### 2.1 在整体里的位置

这个功能挂在哪个场景下，和哪些既有系统交互。

### 2.2 节点树

新增节点、各自职责与边界。写行为，不写代码。

### 2.3 文件落点

新建哪些文件、修改哪些既有文件。标 `[新建]` 或 `[修改]`。

**先写行为再写落点。** 顺序反了会导致设计被现有代码结构绑住 —— 那是在描述现状，不是设计。

## 3. 数据约定

### 3.1 类型定义

C# 类型、Godot `Resource` 或导出字段。写字段名、类型、取值范围、默认值。

### 3.2 关系

新类型与既有类型怎么关联。

### 3.3 存档与迁移

**开发期不保证旧档兼容**，可以改字段，但必须写明改了什么。发布后再改需要迁移方案。

## 4. 输入与状态机

### 4.1 输入映射

哪些动作、绑定到什么、冲突怎么解。

### 4.2 状态与迁移

状态、迁移条件、守卫、副作用。列成表或状态图。

### 4.3 边界情况

已知边界与各自的处理方式。

## 5. 核心逻辑

关键操作的分步逻辑。可以用伪代码，**不要写实现代码** —— SPEC 描述契约与行为。

不要给没有特殊逻辑的增删改查写完整算法，那是噪音。

## 6. 失败处理

| 失败模式 | 触发条件 | 表现 | 恢复方式 |
| --- | --- | --- | --- |
|  |  |  |  |

资源不足、数据缺失、玩家取消、外部调用失败分别怎么办。缺哪类说明为什么不需要。

## 7. 表现与性能

预期负载（同屏实体数、每帧预算）、优化策略。给不出数字就写「待实测」并说明怎么测。

## 8. 测试映射

### 8.1 自动化覆盖

单元测试、集成测试各测什么，边界在哪。

### 8.2 验收标准对应表

| --- | --- | --- | --- |
| `US-001` |  | 单元 |  |
| `FR-2` |  | 集成 |  |

**每条验收标准至少映射到一个测试，或写明为何只能人工验收。** 按「决策必须有执行体」，说不出执行体的规则等于没落地。

### 8.3 只能实机确认的项

配色、手感、动画节奏、文本排版。列清楚，附实机步骤。
