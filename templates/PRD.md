# PRD：短标题

## 1. 概述

这个需求解决什么问题，以及为什么现在做。用普通话写，假设读者是三周后的自己。

## 2. 目标

具体、可判定的目标。从玩家体验或系统行为描述**结果**，不指定实现办法。

## 3. 上游约束

只**链接**相关正典与已接受的 ADR，并说明各链接约束本需求的哪一部分。不复制正文。

只贴链接不说明约束什么等于没写 —— 读者还得自己读一遍上游再猜关系。

本项目玩法结构已定（见 `canon/gameplay/`），但**数值仍未设计**（`GP-2`）。依赖数值的需求在它归档前无法收敛，此处必须写明依赖关系。

## 4. 用户故事

编号 `US-001` 起，三位数递增。每条应能在一个专注的工作段内完成。

### US-001：短标题

**描述**：作为<角色>，我想要<功能>，以便<收益>。

**验收标准**：

- [ ] 可观察：描述具体的界面状态或系统响应
- [ ] 可测试：有明确的输入输出对
- [ ] 可核对：工具能判定（构建通过、测试通过、检查器 0 FAIL）
- [ ] **界面类故事必须加**：作者实机确认（自动检查判不了配色、手感与排版）

每条验收标准至少满足上面前三项之一，否则算「含糊」必须重写。**「工作正常」「体验良好」「性能优秀」都不可验收。**

### US-NNN：<功能>的端到端验证

**每份 PRD 必须以一条端到端故事收尾**，放在最后。它验证整条链路而不是孤立单元，依赖其余所有故事。

**验收标准**：

- [ ] 自动化测试走完主路径（玩家动作 → 状态变化 → 可见结果）
- [ ] 覆盖至少一条关键失败路径（空数据、极值、取消、资源不足）
- [ ] 测试独立可重复，自己准备和清理数据
- [ ] 纯观感部分列出作者实机确认清单：打开哪个场景、点哪里、该看到什么

## 5. 功能需求

`FR-1` 起递增，每条用「系统必须……」，只描述**一个**行为。不要用「并且」把多个行为塞进一条。

- FR-1：系统必须……
- FR-2：当玩家……时，系统必须……

## 6. 非目标

本需求**明确不做**什么。这一节能省掉后面大量范围争论 —— 实现时顺手扩大范围，通常就是因为没写它。

## 7. 界面与表现考虑

信息层级（什么优先、什么可折叠）、异常态怎么显示、复用哪些既有组件。纯文档或纯逻辑需求写「不适用」。

## 8. 技术考虑

已知约束与依赖。**外部技术事实必须附来源链接**，不凭记忆写 Godot 或 C# 行为；没实测的标「待验证」并给出验证办法。

## 9. 待确认问题（阻塞项）

只列**无法由正典或 ADR 裁决**的产品取舍 —— 口味、玩家体验取向、资源投入优先级。有客观优劣的技术选择自己定并写理由，不要让作者做本该自己做的决定。

每条写成：**问题 + 可选项 + 各自代价 + 我的推荐**。不要只抛问题不给建议。

- [ ] 问题一：……

全部答复后才能把 `status` 改 `approved`。作者只答了一部分就保持 `draft`，不要自己替他补齐剩下的。

> 本节不计入配额。

## 10. 成功判据

怎么算做成了。能量化就给数字，给不出数字就说明这个判断没依据，删掉或改成可观察的行为。
