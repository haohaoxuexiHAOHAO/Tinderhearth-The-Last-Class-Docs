# ADR-0006：工作流骨架对齐上游，纪律留在本项目

## 背景

本项目需要一套「从需求到交付」的工作流，并且要能在切换会话后精确续接。参考实现是 [goal-workflow](https://github.com/smallnest/goal-workflow)（MIT 许可），它有 18 个技能，主线是 `/prd → /prd-to-spec → /to-issues → /loop-it（实现 → /review-it → /ship-it）×N`。

2026-08-25 的第一版改编偏差过大，这不是风格问题，有两个可测量的后果：

- **失去与上游的对照能力。** 18 个上游技能里只有 `humanize-it` 接近原样，5 个被丢弃，1 个（`write-adr`）是发明，其余全部重构并改名。改名之后无法逐份对比，上游更新也无从拉取。
- **进度变得不可见。** 上游 `prd` 的 `US-001` 编号与验收勾选框、`to-issues` 的 `Acceptance Criteria` 复选框被替换成一个 7 取值的 `status` 枚举。结果是 `status: in-progress` 只说明「在实现中」，说不出哪几步做完了 —— 而「切窗口能续接」正是整套流水线要解决的问题。

同时，第一版把权威源指向了并不存在的文件。2026-08-26 实测 `python tools/check_docs.py` 得到 **22 项 FAIL**：`GOVERNANCE.md`、`STATUS.md`、`BACKLOG.md`、`templates/WORKDOC.md`、`templates/DESIGN.md`、`requests/` 全部缺失，而两份 steering 的 `authority` 与 10 份技能共引用它们数十次。设计仓当时**零提交**（`git log` 报 `does not have any commits yet`），说明这些文件从未存在，不是被删。

因此 `ADR-0001` §1／§4、`ADR-0002` §1、`ADR-0004` 的 `STATUS.md` 章节属于**从未生效过的未提交草稿**。本记录直接重写它们的正文，不建立取代链 —— 给没进过 Git 的草稿套 `superseded_by` 会让决策目录看起来经历过不存在的反复。

## 候选

1. **完全自研**（第一版的做法）。贴合项目术语，但已实测出上面两个后果，且脱离上游后每次改进都要自己重新想一遍。
2. **完全对齐上游**。忠实、易跟进，但撞上三处硬冲突：`ship-it` 六步里有五步依赖特性分支、`gh pr create`、`gh issue close`，而本项目是单人 `main`；`modern-go` 的 921 行是 Go 专有规则，没有「通用内容」可改；上游没有 ADR、文档配额与归档蒸馏的概念，采用它等于放弃 `check_docs.py` —— 那是本项目目前**唯一已经在工作**的守卫（22 项 FAIL 都是它抓出来的）。
3. **上游骨架 + 保留本项目三项纪律**（采用）。技能名与分步对齐上游，只替换 Go／gh／PR 相关内容，另加三个上游没有对应项的技能。

「什么都不做」不是选项：没有工作流时每次需求都要重新约定一遍流程，而这已经在第一版发生过一次。

## 决策

1. **技能名与分步对齐上游**，共 10 个：`prd`、`prd-to-spec`、`to-design`、`to-issues`、`loop-it`、`review-it`、`ship-it`、`note-it`、`insight-diagram`、`humanize-it`。只替换与本项目不符的内容，不重命名、不合并、不改变分步结构。
2. **追加三个项目专有技能**：`write-adr`（跨域取舍）、`verify-round`（配额与守卫自证）、`ship-archive`（归档蒸馏）。上游靠 PR 合入天然收尾，没有这三件事的位置。
3. **取消 `STATUS.md` 与根 `BACKLOG.md`**。进度由 `spec/` 下 issue 文件的验收勾选框承载 —— 它同时是检查点和进度视图，比另立一页动态状态少一个会漂移的副本。待办台账移到 `spec/issues/README.md`，编号沿用 `GP`／`NR`／`UI`／`ART`／`ENG`／`DOC` 前缀，因为本决定作出时已有 8 个编号被 6 份文档的正文引用。
4. **不重建 `GOVERNANCE.md`**。进程规则收进 [WORKFLOW.md](../WORKFLOW.md)（配额 150／200 行），具体做法留在技能里。原 `GOVERNANCE.md` 与技能内容大量重复，是第二份会漂移的事实源。
5. **`ship-it` 只保留提交与实现总结两步**。建分支、创建 PR、合入、关闭 issue 四步删除，单人 `main` 不需要。
6. **`to-issues` 固定用上游的 Local 模式**（一条待办一个 Markdown 文件），不用 GitHub Issues。单人开发时一份本地台账比一套工单系统更容易保持真实。
7. **明确不包含**：`code-to-spec`、`refactor`、`smell`、`modern-csharp`、`graph` 五项推迟到 `ENG-2`（代码仓工程底座）落地后再写 —— 代码仓目前是空仓，现在写只能凭空假设代码结构。`design-it`（产出自包含 HTML，与 `to-design` 重叠且逃出 `check_docs.py` 的 `.md` 扫描范围）、`listenhub-tts`、`article-icons` 不建。

## 后果

- **正面影响**：技能名与上游一一对应，可以逐份对照上游改动。`US-NNN` 编号与验收勾选框回来了，进度可见。`check_docs.py` 与 ADR 体系保持在位。整体从 22 项 FAIL 回到 0。
- **代价与风险**：
  - 上游更新仍需**人工**对照，没有自动 diff。技能内容已被改写，`git diff` 对不上。
  - 13 个技能比 10 个多，上下文预算增加。按 `ADR-0002` 的预算约束，技能是按需加载的，所以代价落在检索而不是常驻上下文。
  - `humanize-it` 与上游同名但实现不同 —— 上游那份依赖 `humanizer-zh`、`humanize-chinese`、`technical-writing` 三个子技能，**参考仓里三个都不存在**，照搬会得到调用空气的壳子。同名不同实现有被误以为可直接换用的风险，已在技能正文首段写明。
  - 取消 `STATUS.md` 后，**跨需求的验证基线没有长期落点**。当前只有 `check_docs.py` 一项检查，几秒可复跑，所以不需要。出现跑不起或跑很久的检查（导出冒烟、性能数字）时必须重新引入，触发条件写死为 `ENG-3` 落地。
- **落地要求**：`.kiro/skills/` 下 13 份技能；`.kiro/hooks/` 三个钩子（文档准出、命令守卫、会话基线）；两份 steering 的 `authority` 指向 `WORKFLOW.md`。
- **验证方法**：`python tools/check_docs.py` 0 FAIL；`python tools/selfcheck_docs_guard.py` 全部通过（守卫自证，用真实缺陷形状造违反并确认报错指向正确位置）。技能内容是否真的对齐上游**只能人工验收** —— 没有机器能判断一份改写后的技能是否仍忠于原结构。
