# ADR-0002：代理提醒层最小化与上下文预算

## 背景

`.kiro/steering` 是 Kiro 按文件自动加载的短提醒。前作《火种》里它曾增长到 10 份、517 行，普通场景任务一次载入约 300 行，并出现旧路径、重复的界面规则、互相矛盾的接线状态，以及“本轮／未来”这类动态信息。

关键结构问题是：提醒层位于两个 Git 仓库之外，一旦承载完整事实，就形成**无法随版本审查的第三套事实来源**。它会悄悄与正典和代码漂移，而没有任何检查能发现。

## 候选

1. **让 steering 承载完整规则**：代理不用跨仓读文档，响应快。但提醒层变成第三套事实源，且不受版本控制审查，必然漂移。
2. **完全不用 steering**：零漂移风险，但每个新会话都要重新发现“先读哪份文档”，反复浪费上下文，且容易漏掉高代价约束。
3. **薄提醒 + 权威源在 Git（采用）**：steering 只保存“忘记后代价高”的短清单和路径路由，正文留在 Git 内的权威文档。

## 决策

1. `.kiro/` 只保存**忘记后代价高**的短检查清单、路径路由与工作流技能。产品事实留在正典或专项设计，实现细节留在代码或测试，进行中需求的状态留在设计仓 `spec/`。
2. 自动加载的每条规则必须在文件头声明 Git 仓库内的 `authority`（权威来源）、`owner` 与 `last_verified`。
3. steering 索引使用 `inclusion: manual`，表示只有明确要求时才读取。
4. **上下文预算**：`always` 合计不超过 25 行；单个按文件触发的清单不超过 40 行；任一实际文件触发后 steering 总量不超过 80 行；按文件触发的清单最多 5 份。
5. 新规则只在同类问题**至少复发两次**、后果高，且无法优先用类型约束、测试或静态检查防住时才准入。新增时必须合并或删除等量的低价值提醒，禁止“持续追加”。
6. 提醒层不得维护阶段状态、完成台账、路线图、完整程序接口或故障复盘。
7. `fileMatch`（按文件路径触发）必须命中真实文件。**代码仓尚未建立时不预置打空的清单** —— 打不到文件的规则等于没有，还会让人误以为有护栏。
8. `.kiro/hooks/` 只把生命周期事件接到既有检查命令，不在 hook 里写业务判断。
9. 规则超过 90 天未验证、权威源已覆盖或触发范围失效时，应删除或重写。

## 后果

- **正面**：常用任务只加载预算内的高价值提醒，详细依据按需从 Git 内权威源读取。上下文更稳定、冲突更少。
- **代价与风险**：`.kiro/` 是本机配置，不随任一子仓库版本化。作者已确认近期不换机器，接受这一风险；代价上限是按本 ADR 与 [WORKFLOW](../WORKFLOW.md) 重建，因为正文本身就要求短到可重建。技能正文是例外 —— 13 份 `SKILL.md` 重建成本不低，重建依据是上游 goal-workflow 加 `.kiro/skills/README.md` 的替换表（见 [ADR-0006](./ADR-0006-工作流骨架选型.md)）。
- **落地要求**：[WORKFLOW](../WORKFLOW.md) 承载流程规则的正文，`.kiro/steering/README.md` 只做索引。
- **验证方法**：人工核对预算行数。代码仓建立并出现按文件触发的清单后，再补一个 `check_steering.py` 做机检。
