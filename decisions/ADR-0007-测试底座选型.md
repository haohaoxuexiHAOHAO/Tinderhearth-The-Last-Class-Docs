# ADR-0007：测试底座选型（xunit.v3 打在不依赖 Godot 的规则层上）

## 背景

`ENG-2` 要建测试底座，而 Godot 4 + C# 的测试方案分成两类，混在一起讨论会得出错的结论：

1. **通用 .NET 测试框架** —— 发现、执行、断言、报告。与 Godot 无关。
2. **引擎内测试** —— 把测试体跑在活着的 Godot 进程里，才能碰 `Node`、场景与输入。

两类的成熟度差得很远。第 1 类里 xunit／NUnit 是 .NET 生态的既有轮子；第 2 类的现成方案只有社区插件，落后引擎版本。

作者提出过一个合理的疑问：既然现成方案都或多或少有问题，是不是该自己写一份。这份 ADR 要回答的就是**哪一层该自己写、哪一层不该**。

一条实测事实决定了整个结构：**在引擎外构造 Godot 节点（`new Godot.Node()`）会触发进程级 Fatal error，崩在 `Node..cctor()`，且 `try`／`catch` 抓不住。** 一次手滑不会变成一条失败的测试，而是带走整轮测试的全部结果，还看不出是哪一行造成的。

## 候选

### 谁来当测试框架

1. **自己写一份。** 便宜的部分确实便宜：反射找测试方法、跑、抓异常、算退出码，约 150 行。贵的是三样天天要用的东西 —— 断言的失败信息（每遇一种新类型就得扩一次，写不好只剩「断言失败」四个字）、点一下就能下断点调试（这是协议实现不是几行）、表驱动测试（`GP-2` 的数值规则落地后全是「这组输入应得这个数」）。**更贵的是它自己也得被自证**：按 [WORKFLOW §6](../WORKFLOW.md)，测试框架属于「唯一职责就是可信」的基础设施，自己写就要再写一层「测试框架的测试」，而[踩坑记录 29](../reference/踩坑记录.md) 那种「摘要说通过、有个测试悄悄没跑」的形态正是自造运行器最容易产出的缺陷。省下的只是一行 `PackageReference`。
2. **GdUnit4Net。** 一个包同时覆盖两类，`dotnet test` 可用。已实测**能**在 Godot 4.7.2 + `net10.0` 上跑引擎内测试。但：上游只声明支持 Godot 4.3–4.4.1（我们领先它三个小版本）；最新**稳定**版 adapter 3.1.1 依赖**预发布**的 api 5.1.0-rc5，钉稳定版会 NU1605 报降级，**不存在全稳定版组合**；测试代码必须住在 Godot 工程内，导出时要另外排掉。
3. **xunit.v3 打在不依赖 Godot 的规则层上（采用）。** .NET Foundation 项目，Apache-2.0，直接依赖只有一个。已实测在 `net10.0` 上引用 Godot 工程可跑。它不解决第 2 类，但第 2 类 `ENG-2` 用不到。

### 引擎内测试怎么办

1. **现在就装 GdUnit4Net。** 但本条用不上，等于提前把项目押在预发布包上。
2. **推迟到真需要时再选（采用）。** 需要它是到 `ENG-6` 帧级调优。届时信息更好，且已实测它在 4.7.2 上可用，所以推迟是有依据的推迟而不是赌。
3. **自己写第 4 层。** 约 150 行（一个场景脚本跑程序集、回报结果、设退出码）。**这一层自己写是认真的候选** —— 现成方案在这里确实不成熟。留作 `ENG-6` 的备选。

## 决策

```
规则层测试      xunit.v3（4.0.0 起）
测试范围        判定与结算规则，不含表现层
规则层程序集    不引用 GodotSharp
引擎内测试      本轮不装，到 ENG-6 再选（GdUnit4Net 或自写约 150 行）
跑测试的命令    跑 tests 工程的可执行文件，不用 dotnet test
```

**「不要重复造轮子」这条原则成立，只是它命中的是第 4 层，不是第 1–3 层。** 第 1–3 层是通用件，没有任何游戏因为自研测试运行器而成功；第 4 层是 Godot 特有的，且现成方案确实弱。

**规则层与引擎层必须是两个程序集**，理由是上面那条 Fatal error：不引用 GodotSharp，编译器就不给手滑的机会，这是靠构造保证而不是靠自觉。附带好处是「能不能跑测试」不再依赖「引擎能不能加载程序集」，两个风险被解耦。

顺带一条实测结论备查：Godot 的纯数学结构体（`Vector2I` 之类）在引擎外可用，所以让规则层引用 GodotSharp 技术上行得通 —— 但那会把 `Node` 的门一起打开。要开这个口子须先在代码仓 `ARCHITECTURE.md` 写明开的是哪个口子。

## 后果

- **正面**：绝大多数测试落在最主流、`net10.0` 一等公民、与 Godot 零耦合的框架上。上游风险被围住 —— 万一将来引擎内方案停更，损失只有那一小撮引擎内测试，而那正是值得自己写的 150 行。规则与表现分离本来就是 `ENG-5` 要求的形状，这条选型顺带把它变成结构约束。
- **代价一（已确认）**：**`dotnet test` 用不了。** xunit.v3 生成的可执行文件是 xunit 自己的 in-process 控制台运行器而不是 Microsoft.Testing.Platform 测试模块，`dotnet test` 用 MTP 协议去问它只会得到「Zero tests ran」。四种开关都试过无效，根因与清单见[踩坑记录 30](../reference/踩坑记录.md)。改为直接跑测试工程的可执行文件 —— 这是 xunit v3 的一等路径，退出码两个方向都实测可信（全过 0、有失败 1）。
- **代价二（未验证）**：**IDE 测试资源管理器的集成没验证。** 它依赖 VSTest 或 MTP 协议，而我们两者都不走。这削弱了「选现成框架能点一下调试」这条好处，需要时另查。
- **代价三**：规则层碰不到 Godot 类型，需要向量等类型时要么自定义等价结构体，要么把那部分留在引擎层。这不是纯代价 —— 它逼出的正是规则与表现分离。
- **可撤销性**：测试代码里九成是断言表达式而不是框架 API，换框架是机械替换，动不到被测的规则代码。所以这不是一个需要现在赌对的决定，选现成的正是为了把时间留给真正不可逆的东西（目录结构、规则与引擎的边界、`ENG-5` 的预留）。
- **验证方法**：`dotnet build` 0 警告 0 错误；跑 tests 工程得到预期的测试数量与退出码 0；**核对数量而不只看「通过」**（[踩坑记录 29](../reference/踩坑记录.md)）。故意把配置读来的名册容量写死成常量复跑，确认相关测试会失败 —— 2026-08-30 实测 2 条失败并打出 `Expected: 3, Actual: 9`，证明测试不是空转。
