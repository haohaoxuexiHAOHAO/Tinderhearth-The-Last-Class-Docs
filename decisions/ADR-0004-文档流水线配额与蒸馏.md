# ADR-0004：文档流水线配额与蒸馏

## 背景

前作《火种》的设计仓最终长到 144 份文档。膨胀不是因为内容多，而是因为**过程叙述没有出口**：每次需求的讨论、试错、中间结论都留在活文档里，于是同一件事在工作文档、状态页、变更日志和正典里各写一遍。切换会话时无法判断哪份是现行口径。

整页行数配额也无法发现一类具体问题：某一行被写成整段说明。表格看起来行数正常，实际单元格里塞了三百字。

本项目从十几份文档起步，因此在膨胀之前就装好出口和配额。

## 候选

1. **不设配额，靠自觉**：前作已验证会长到 144 份。
2. **只设总量上限（比如“文档不超过 30 份”）**：数字没有测算依据，且会逼人把内容硬塞进已有文件，让单份文档变成大杂烩。
3. **单向流水线 + 分类配额 + 逐格限制（采用）**：给过程叙述一个明确出口，各类文档按职责设不同阈值，台账另查最长单元格。

## 决策

### 单向流水线

信息只能沿一个方向流动，不允许回流：

`需求描述 → 工作文档（过程） → 正典／ADR／规范（结论） → 归档小结（一处摘要）`

工作文档归档时执行**归档三问**：① 现行事实写入哪份权威源的哪一节（给链接）② 遗留待办进入 `BACKLOG` 哪几个编号 ③ 其余过程叙述是否已**删除**。第三问是关键 —— 不删除就等于没有出口。

**一处摘要 + 两处链接**：归档件保留唯一一份摘要（≤30 行，「教训」不计入）；变更日志加**一行**台账；`STATUS` 的最近归档只加**一个链接**，不复制摘要。

### 规模配额

检查器同时看行数与字符数，前一个是软上限（警告）、后一个是硬上限（失败）。完整表格见 [WORKFLOW §3](../WORKFLOW.md)。要点：普通文档 600／900 行；`WORKFLOW.md` 150／200 行；`spec/` 下的 PRD、SPEC 与 issue 250／350 行。

确需超限时在文件头写 `quota_exempt: <具体理由>`，全库最多三份豁免。**拆分必须沿主题或职责边界**；只有变更日志这类只追加台账可以按时间拆分，正典与现行口径只能按主题拆分。

### 台账逐格限制

变更日志每格不超过 220 字符，待办台账每格不超过 360 字符。超出的解释回到该行链接的正文。

限制按**仓库相对路径**索引而不是文件名 —— 台账现在叫 `spec/issues/README.md`，按文件名会命中每一份 `README.md`。

### 单一待办台账

`type: backlog` 只允许 `spec/issues/README.md` 一处，缺失或出现第二份都判失败。台账编号被正典、制作规格与归档三问跨文档引用，出现第二份会让那些引用指向不确定的地方。

进度**不另立页面**：它是 `spec/` 下 issue 文件的验收勾选框。理由见 [ADR-0006](./ADR-0006-工作流骨架选型.md)。

### 检查时机

一轮工作结束时由 Kiro hook 跑一次整库检查；推送前由 `pre-push` 拦截。本项目单人开发，**不设远程持续集成**。

## 后果

- **正面**：过程叙述有明确出口，活文档只留现行结论。膨胀在发生时就被拦住，而不是事后大扫除。
- **代价与风险**：每次归档要多做三件事（填三问、删过程、加台账行）。写文档时要判断“这条属于哪一层”，比随手写一句话麻烦。软警告会长期存在，需要判断而不能一律忽略。
- **落地要求**：`tools/check_docs.py` 实现文件头、配额、逐格限制、单一台账、断链、入口可达与归档边界检查。
- **验证方法**：`python tools/check_docs.py` 无 `FAIL`；改动检查器后跑 `python tools/selfcheck_docs_guard.py` 自证；规模趋势用 `--report` 观测。
