# ADR-0001：文档事实源与仓库边界

## 背景

前作《火种》起初把进度、待办、路线图和审查稿平铺在设计仓库根目录，同一件事的状态在多处重复维护。切换会话后容易读到旧快照、误建重复文档，或者用实现反推正典。本项目从零开始，因此在第一天就固定边界，而不是等重复出现后再整理。

本项目由单人开发，同时有两个 Git 仓库和一个非仓库的工作区根，三者的职责必须写死，否则代理会把提醒层当成事实源。

## 候选

1. **单仓库**：设计与代码放一起。省去跨仓链接，但正典与实现会互相污染 —— 改代码顺手改正典，正典就失去“产品意图”的定位。
2. **两仓库 + 各自维护状态页**：边界清楚，但两个状态页必然漂移，恢复上下文时不知道该信哪个。
3. **两仓库 + 单一待办台账（采用）**：设计仓答“应该是什么”，代码仓答“现在如何实现”，待办只在设计仓一处，进度不另立页面。

## 决策

1. **设计仓库**以 `README.md` 为唯一入口、`spec/issues/README.md` 为唯一待办台账。进行中需求的过程文件在 `spec/`，稳定事实按正典 `canon/`、专项设计 `design/`、制作规格 `production/`、参考资料 `reference/` 与历史归档 `archive/` 分类。**不设单独的动态状态页** —— 进度就是 `spec/` 下 issue 文件的验收勾选框，理由见 [ADR-0006](./ADR-0006-工作流骨架选型.md)。
2. **代码仓库**只维护实现事实；根部只留 `README.md`、`ARCHITECTURE.md`、`CONVENTIONS.md`，其他工程资料进入代码仓的 `docs/`。**代码仓不设 ADR 目录**，工程性取舍也写在设计仓 `decisions/`。
3. **工作区根**（`.kiro/`）只做提醒、路径路由与生命周期接线，不承载任何一类事实。详见 [ADR-0002](./ADR-0002-代理提醒层最小化与上下文预算.md)。
4. 各类来源分工固定：代码与测试说明**已经实现的行为**；状态为 `accepted` 的 ADR 说明**已经决定的取舍**；正典说明**产品意图**；`spec/` 下的 PRD 与 issue 说明**这一次在做什么、做到哪了**。
5. 冲突时按 `README.md` 的权威层级判断。低层文档只能补充实现细节，不能静默改写高层意图。
6. 不新建“最终版／优化版／综合方案”类文档。跨域冲突写 ADR。
7. 每次文档移动后必须运行 `python tools/check_docs.py` 通过断链检查。

## 后果

- **正面**：新会话读取量小，且不会同时加载多份“当前状态”。恢复上下文的路径唯一：`README → spec/ 下的当前 PRD → 对应 issue 的勾选框`。
- **代价**：跨仓引用要写相对路径（`../Tinderhearth-The-Last-Class/CONVENTIONS.md`），目录名较长。改动必须先改权威源，比直接在状态页写一句话麻烦。
- **落地要求**：`tools/check_docs.py` 负责检查入口可达、无断链、无第二台账、归档不冒充现状。
- **验证方法**：`python tools/check_docs.py` 退出码为 0。
