# ADR-0036：游戏是什么只在 desc 写一份，设计仓只留做游戏要用的文档

> **后续变更，正文不改**：`archive/` 后来也删了，理由与下面「删掉，不挪进 `archive/`」那一条相同：留着的话检查器照样要扫、搜索照样会搜到，git 历史里本来都在。已关闭的编号并成[待办台账](../spec/issues/README.md)「已关闭编号」一张表，一个编号一句话。正文里写到 `archive/` 的几处是那之前的事。

## 背景

工作区根 `desc/` 是作者自己维护的那几份：状态、天赋、技能、角色面板、各类公式计算、人物、剧情、特殊建筑、物品。它们已经是各自那一块的最高权威，正典与系统文档写到这几块时只链过去（[总索引](../README.md)的「权威层级」）。

但同一条规则仍然散在好几处。2026-11 的几轮战斗细化里，改一条规则（例如「出征最晚 10 点回来」「每个学生每关只能倒下一次」）要同时改 desc、正典与三到七份系统文档；一次提交前的评审在这些地方查出四十多处没跟上的旧说法。作者的判断是：文档太多，读不过来，也必然漏改。

2026-11-19 的盘点：设计仓除 ADR 与 `archive/` 外约 190 份、近 200 万字；desc 9 份。`design/` 根下 37 份里，代码仓引用到的只有地块、物品、背包、每日结算、存档、界面、生产系统与数值模型；`reference/godot/` 23 篇里 18 篇的页头写着「战斗的部分还是侧视那一套」。

不作决定的后果：每改一条规则都要追十几处，漏一处就是两种说法，而检查器判不出两句话是不是在说同一件事。

## 候选

1. **两层：desc 写游戏是什么，设计仓只留做游戏要用的（采用）。** 收益：一条规则只有一个家，作者只读 desc 就知道游戏是什么；设计仓要维护的从近 200 份减到十几份加台账。代价：正典里的理由与还没开工的系统的工程设计会删掉，要用时从 git 历史里找。
2. **温和：正典留着只删和 desc 重复的，系统文档全留。** 收益：什么都不删。否决理由：维护面几乎不变，规则照旧散在正典与系统文档两处，漏改的来源还在。
3. **只清过期的：删做完的需求、过时的提案、旧指南。** 收益：最省事。否决理由：最大的两块（正典、系统文档）不动，问题原样留着。

删掉的东西挪进 `archive/` 还是直接删，也比过：挪进去的话检查器照样要扫、搜索照样会搜到，而 git 历史里本来就都在，作者选了直接删。

## 决策

**desc 是唯一写「游戏是什么」的地方**：规则、内容、数值、人物、剧情、世界观。正典里还没进 desc 的规则，搬进 desc 新加的世界观、战斗规则、经营规则，只写规则，不写理由。

**设计仓只留做游戏要用的：**

- 代码在用的系统文档：地块、物品、背包、每日结算、存档、界面、生产系统与数值模型（连同参数表与推演工具）。只写结构、接口、校验与验收；规则与数值以 desc 为准，不另抄。
- 画图规范（`production/`）。
- 作者跟着做、内容还没过期的 Godot 指南，踩坑记录，同类游戏的调研，C# 学习。
- 台账与进行中的需求（`spec/`）、ADR（`decisions/`）、模板与工具。
- 不进 desc 的工程约束（平台、mod 的扩展边界、内容规模基准这类），放进上面留下的文档里。

**删掉，不挪进 `archive/`**：`canon/` 全部；代码不用的系统文档；结论已经迁出的提案；做完的需求与条目文件（台账那一行留一句话，写做完了什么、结论在哪）；内容过期的 Godot 指南；术语表。

**一个系统开工时**，先从 desc 写一份短的系统文档（走 `/prd`），需要时从 git 历史里捞回删掉的那一份参考，不从零开始。

**顺序**：正典等作者看完 desc 新加的那几份之后再删；其余分批删，每批检查过就提交推送。进度在台账 [`DOC-166`](../spec/issues/README.md)。

**本记录取代的**：

- [ADR-0001](./ADR-0001-文档事实源与仓库边界.md) 决策第 1 条里「稳定事实按正典 `canon/`……分类」，与第 4 条「正典说明产品意图」：产品意图改由 desc 说明。
- [ADR-0010](./ADR-0010-文档体裁与系统文档归位.md) 体裁表里「正典」那一行；系统文档那一行的「一个系统一份、系统在它就在」改成「代码开工的系统一份」。

**明确不包含：**

- 不改代码行为。代码仓里引用设计仓的地方改指向，单独一次提交。
- 不改 ADR 正文（它们冻结），也不维护 `archive/`：两处指向被删文件的链接断了就断了，检查器对这两处不再查断链。
- desc 不进任何仓库，作者在工作区根维护，检查器不查它。
- 不规定 desc 怎么写：那是作者自己的文档。

## 后果

- **正面影响**：一条规则一个家，改一次就改完；作者只读 desc 就知道游戏是什么；代理恢复上下文时少读一层。
- **代价与风险**：
  - 「为什么这样定」大多随正典删掉，以后讨论同一件事时，得去 git 历史里翻，或者再问作者。缓解：desc 新加的那几份由代理从正典压缩，作者看完才删正典。
  - desc 不在仓库里，没有版本历史；代码注释只能按名字指它，指不了链接。
  - 还没开工的系统，删掉的那份工程设计（例如状态载体的字段、回合的先后）开工时要重写。
  - 检查器里依赖正典的几条守卫（上游指纹、节名引用、系统文档要有正典引用）要改，改坏了没有自证入口。
- **落地要求**（分批，进度在 `DOC-166`）：
  1. 本记录、WORKFLOW、`.kiro` 规则与两份索引。
  2. desc 新加世界观、战斗规则、经营规则的草稿。
  3. 作者看完之后：删正典、代码不用的系统文档、提案、过期指南与术语表；改留下文档与代码仓里的引用；改检查器。
  4. 清台账：删做完的需求与条目文件，每一行留一句话。
- **验证方法**：设计仓 `python tools/check_docs.py` 0 FAIL；在两个仓里搜被删文件的路径，除 ADR 与 `archive/` 外为零；代码仓 `python tools/verify.py` 全绿。**「同一条规则只写在 desc」查不出来**：两句话是不是在说同一件事，机器判不了，只能靠这条纪律与评审守。
