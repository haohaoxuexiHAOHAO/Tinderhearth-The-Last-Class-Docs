# GP-31：`design/技能系统.md`

> **只读历史归档，不得作为现行依据。** 现行事实在[`技能系统`](../../../design/技能系统.md)。落地顺序按编号活在[待办台账](../../../spec/issues/README.md)。

## 目标

把一个战斗技能要声明的字段写在一处，让加技能变成填表而不是写代码。

## 来源

- PRD：[`prd.md`](./prd.md) 的 `US-004`
- 已有的上游事实散在[角色与成长 · 书 → 学会 → 练熟](../../../canon/gameplay/角色与成长.md)（书学会、实战值练熟、档位解锁宝石孔）与[角色与成长 · 装备：宝物与宝石](../../../canon/gameplay/角色与成长.md)（每技能 2–3 孔、孔位不分类型、正负面词条并存）。

## 依赖

`GP-32`（技能要声明自己打哪一类伤害、带多少穿透，那些量的定义在伤害系统）与 `GP-34`（技能位只装主动、光环不设上限）。

## 验收标准

- [x] 新文档按 [SYSTEM 模板](../../../templates/SYSTEM.md)八节写全，`upstream` 指[角色与成长](../../../canon/gameplay/角色与成长.md)，并被正典链接到。
- [x] 字段表列全一个战斗技能要声明的东西：伤害类型、倍率、元素与施加概率、两种穿透、耗蓝量、读条形态（瞬发或读条）、冷却。
- [x] 写明**每个技能各有自己的冷却下限值**，且下限不得为零。
- [x] 主动、被动与光环三种形态各自占不占槽位写清，与 `GP-34` 收窄后的技能位一致 —— **只有主动占位**。
- [x] 光环不设数量上限，取而代之的约束写全，每条各写自己防的是什么：
  - **同类只取最大，不叠加**；「同类」的判据是**它修饰哪个量**（改物理攻击的算一类、改减伤的算一类），不按技能名也不按元素 —— 不写判据的话，每加一个光环都要重新争一次它算不算同类。
  - **每个光环必须同时带正面与负面影响**，与[角色与成长 · 装备：宝物与宝石](../../../canon/gameplay/角色与成长.md)对宝物宝石那条同理同因。这是替掉数量上限的主力：取舍从「装哪几个」变成「愿意吃哪些代价」，而全开等于把全部负面也一起开。
  - **负面必须可感** —— 不得是「对任何构筑都无所谓」的那一种，判据是它落在这个角色真的会用到的量上。写明这一条**只有人工验收**：能机判的只有「有没有负面项」。
  - 明确**不做总修正上限这类硬钳**（玩家看不出为什么第五个光环没效果），也**不给光环作用半径**（它不是范围效果，开着就生效）。
- [x] 可测试：同类光环叠加被拒 —— 构造两个改同一个量的光环同时在场，生效的只有量级更大那一个。
- [x] 可测试：无负面项的光环定义**载入时被拒**（与[`生产系统`](../../../design/生产系统.md)那条「净产出自己燃料的设备载入时被拒」同一形状）。
- [x] 宝石孔**按实战值档位解锁**、孔位不分类型；宝石改的是机制不只是数字，并给出「改机制」的判据 —— 它换掉了这个技能的某个字段或某条行为，而不是只乘一个系数。
- [x] 边界那一节写明**生活技能不在本页**：「技能」这个词在正典里同时指两类，本页只装战斗技能，熟练度归 `成长系统`。
- [x] 文档里一个玩法数值都没有。
- [x] `python tools/check_docs.py` 0 项必须修复。

## 实现笔记

> 由 `/note-it` 在实现和评审之后填写。

### 设计决策

- **模糊点**：「宝石改机制」这句话怎么才判得了。裁定只说了「不只是数字」。
- **选择**：写成可检验的形式 —— **它换掉了这个技能的某个字段，或加了一条这个技能本来没有的行为**；只在某个字段上乘一个系数的不算。文档里给了正反例。
- **理由**：不给判据，「改机制」就是一句语感，内容审查时没人说得清一颗宝石算不算。给了判据之后它还顺带回答了下一个问题：只动一个系数的东西该做成宝物词条，不该做成宝石。

### 偏离

- **方案怎么说**：验收只要求字段表列全裁定点名的那几项。
- **实际怎么做**：字段表多列了**标识、名称与描述的文本键、效果量**三项，并写明「填不出来也要显式填『无』，不许缺字段靠默认值兜底」。
- **为什么**：前两项是外置数据与存档的前提（存档只存标识，文本走 `ENG-5`）；「效果量」是治疗与屏障的系数，不列它就会有人把它塞进「倍率」，而倍率要进伤害结算、效果量不暴击 —— 混在一起就会出现「治疗暴击」。

### 权衡

光环那一侧考虑过保留槽位上限。取「不设上限 + 必带可感负面」，代价是「负面疼不疼」判不了、只能人工审内容；收益是玩家看得见自己为什么要取舍，而一个数量钳他看不出原因。

「同类光环」的划分考虑过按技能名或按元素。取「按它修饰哪个量」，因为那两种都要维护一张对照表而表会漏；按量分不需要表 —— 加一个光环时它改哪个量本来就得填。

冷却下限考虑过设一个全局值。取按技能各给一个：一个短促的标记与一个大范围控场招，「最快多久能再放一次」本来就不该一样；全局下限要么卡死短招，要么对大招形同不存在。
