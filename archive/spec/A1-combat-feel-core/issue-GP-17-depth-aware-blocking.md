# GP-17：带纵深的实体阻挡

> **只读历史归档，不得作为现行依据。** 随 A1 归档；文中的验收手段（图形探针与守卫）已全部删除。
> 现行事实见[待办台账](../../../spec/issues/README.md)与代码仓。

## 目标

让角色与场景物件在纵深模型下正确地互相阻挡——**只有纵深接近时才挡**，不同排的实体互不妨碍。

## 来源

- 作者 2026-09-09 实机发现：在 `DepthDev` 里主角能直接穿过木桩，走过去能穿、按 E 闪避也能穿。
- 正典：[战斗与关卡 · 空间模型](../../../canon/gameplay/战斗与关卡.md)「场景物件在纵深上作阻挡与掩体，玩家与敌人**绕行而不是跳上去**……它们的职责是让近排与远排之间出现要绕的东西」。绕行成立的前提就是物件真的挡人。

## 依赖

`GP-15`（纵深位置）、**`GP-16`**（它要建的「横向 ＋ 纵深两个条件都成立」那套重叠判定，本条复用同一套，不另写一份）。

## 现状（`ENG-15` 收尾时实测）

碰撞是**单向**的：主角 `CollisionLayer=1`／`CollisionMask=1`（Godot 默认），木桩 `CollisionLayer=4`／`CollisionMask=1`。于是木桩被击退时会被主角挡住（`GP-13` 的 `wall-block` 判据靠这条），而主角穿过木桩。

## 为什么不能「顺手把碰撞层补上」

**这是本条存在的真正理由，不是配置漏填。** 纵深不参与引擎碰撞（`GP-15` 定的：Godot 2D 的两个轴被横向与跳跃高度占满，纵深位置归规则层、只影响绘制）。所以两个角色即使纵深相差满一条带、画面上明显一前一后，它们的 `Position` 仍可能完全重合 —— 在 Godot 眼里是重叠的。

于是给主角加一条 `CollisionMask=4` 的后果是：**站在不同排的两个角色互相挡住**。那比现在能穿过更糟 —— 现在的毛病是「该挡的没挡」，改完的毛病会是「不该挡的挡了」，而后者玩家读不出原因（他看到的是两个明显不在一排的东西卡在一起）。

## 作者裁定（2026-09-09）

**战斗场景按阵营分**：

- **同阵营角色互不阻挡。** 避免队友卡住玩家、敌群互相卡死挤不到玩家面前。
- **中立的场景资源（石头、矿石这类）阻挡。** 与正典的「物件在纵深上作阻挡与掩体、绕行而不是跳上去」一致。

**阵营这个概念不是新造的**：正典[战斗与关卡 · 迷雾与视野](../../../canon/gameplay/战斗与关卡.md)已经用它做敌我判定（「敌人与可交互物件只在**阵营视野并集**内显形」「友方视野取并集，敌方独立取并集」）。但代码里现在**没有**任何阵营数据（`grep` 过 `rules/` 与 `src/`，只有 HUD 的队友列表），所以本条要引入它 —— 这是一处新的数据模型，落点与命名要与将来的感知系统（`玩法定位` 的「感知与视野」）共用一份，不各建一套。

**命名有一条世界观红线要避开**：[世界观](../../../canon/world/世界观.md)明确写了魔化生物「**不是一个阵营**」，理由是「魔化是状态，不是某个族群的天性」，把魔化写成阵营会废掉「魔化可被中断」这条叙事承重项。所以玩法层这个概念表达的是**当前的敌我关系**，不是族群归属；命名与注释都不该让它读成后者。

**敌对双方之间阻挡**（作者 2026-09-09 追加裁定）。这是 belt-scroll 的经典做法：敌群形成需要绕开或打退的「墙」，「被围住」成为真实威胁，而**纵深挪步因此才有意义** —— 因为你需要绕。不挡的话走位更流畅，但位置压力消失，纵深挪步的动机会跟着弱掉。

于是阻挡规则完整了：**同阵营不挡、敌对双方挡、中立物件挡**。

## 阻挡阈值与命中容差是两个数

命中容差（`GP-16`）是「打得着」的宽容量，阻挡阈值是「占同一格」的物理量，同一个数很可能两边都不合适。两者都归 `GP-6` 校准，但**不共用常量**。

## 经营场景的碰撞：本条不做，理由如下

作者提过一个方案：经营场景参考星露谷，角色互相阻挡但持续顶住若干秒后可以穿过。**本条不采纳，也不否定 —— 是现在定不了。**

1. **经营场景还不存在。** 基地场景与建造界面都没立项（代码仓 `ARCHITECTURE.md`：「相机只有行为，没有场景」）。现在定规则没有可实测的对象，属于 `GP-7`「等对应系统存在才能定的其余参数」那一类，那条的理由正是「要等能实测出行为差异时才定得出来」。
2. **计时器式的例外可读性差。** 玩家顶住 NPC 三秒然后穿过去，他读不出「为什么现在能穿了」。这个机制要解决的问题是「NPC 堵住门口过不去」，而那个问题有更可读的解法：**NPC 自己让路**（寻路避让），或者**玩家能推开 NPC**。两者都把因果留在画面上。
3. **星露谷是不是这么做的，我没有依据。** 印象里它的 NPC 会沿自己的路径走开，而不是被顶几秒就可穿透 —— 但这是印象不是事实，不该拿它当依据。真要参考，得实机确认那个游戏的行为再引用。

**结论**：意向记在这里，等经营场景立项时连同 NPC 寻路一起定，届时优先考虑「让路」而不是「计时器例外」。

## 验收标准

- [x] 阻挡判定同时看横向与纵深：纵深差超过阈值时**不挡**，画面上不在一排的实体不会互相卡住
- [x] 判定逻辑复用 `GP-16` 那套带纵深的重叠判定，**不写第二份**
- [x] 场景物件（占一段纵深的巨石／树干占位）挡住角色，角色只能绕行
- [x] 同阵营角色互不阻挡、敌对双方互相阻挡、中立物件阻挡（作者裁定）
- [x] 阵营数据与将来的感知系统共用一份落点，不各建一套；命名不把「当前敌我关系」写成「族群归属」（世界观红线）
- [x] 阈值进 `CombatFeel` 或同级落点，标未校准初值、归 `GP-6`
- [x] 规则层单测：同纵深挡、纵深超差不挡、阈值边界
- [x] 引擎探针：同一横向位置下，纵深对齐时走不过去、纵深错开时走得过去；`GP-13` 的 `wall-block`（击退被实体挡住）复跑不退化
- [x] **阻挡对接近方向不挑**：横向走过去挡得住，**在纵深上（`W`／`S`）走进去也挡得住**。这一条 2026-09-18 补写 —— 原来那句「同一横向位置下，纵深对齐时走不过去」被实现成了只测横向走位，而纵深方向当时是个洞（详见实现笔记）
- [x] 绕行通路仍然通：走到跟前（被挡）→ 挪纵深（允许）→ 从旁边过去。**与上一条配对**，防止「横向重叠就锁死纵深」那种过紧实现

## 实现笔记（2026-09-18）

### 落点

| 那一半 | 落点 |

| 立场数据（三值） | `rules/Foundation/Actors/CombatSide.cs`：`Ally`／`Enemy`／`Neutral` |
| 该不该挡（阵营 ＋ 纵深） | `rules/Combat/DepthBlocking.cs`：`Blocks` 与 `BlocksAtDepth`，复用 `DepthOverlap` |
| 阈值 | `rules/Combat/CombatFeel.cs` 的 `BlockDepthThresholdWorldPx` ＝ 8 |
| 引擎那一半 | `src/World/DepthBlocker.cs`：逐帧增删碰撞豁免、补掩码、报覆盖量 |
| 中立障碍物 | `src/World/SceneObstacle.cs`：静态体、不可受击、刻意不叫「巨石」 |
| 探针 | `src/World/BlockingDev.cs` ＋ `scenes/BlockingDev.tscn` ＋ `tools/blocking_dev.py` |

### 机制：为什么是碰撞豁免

层与掩码是按**类**开关的，表达不了「这一对挡、那一对不挡」，更表达不了纵深。豁免是 Godot 里唯一按**对**生效的开关，所以纵深门控只能落在它上面。横向那一半仍归引擎（碰撞形状与 `MoveAndSlide`），规则层不重算 —— 重算就是第二份事实（`ENG-6`）。

参与者之间的掩码由 `DepthBlocker.Add` 补齐（**只按位或、不覆盖**，否则地形那一位会丢、角色直接掉下去）。让场景自己记得配掩码是一处能忘的注册，而忘了的表现正是本条要修的那件事：该挡的没挡，且不报错。

### 阈值取 8 的算式

依据是正典[战斗与关卡 · 48px 是怎么算出来的](../../../canon/gameplay/战斗与关卡.md)的两个可读性结论：**纵深差 8px 以下基本重叠**、**相邻两排差 16px 仍读得出谁在前**。于是取半排：看上去重叠的两具身体互相挡住（反面正是作者实机撞到的「看着该挡却穿过去」）；隔一排不挡且留整整一倍余量；纵深连续，同排两人各偏半排是常态、最坏差半排，取 8 刚好覆盖满。

**与命中容差不共用常量**，此刻同为 8 是巧合不是等式 —— 两者归 `GP-6` 各自调。另加一条不变量由单测钉着：**阻挡阈值 ≤ 命中容差**，反过来会出现「被挡住却打不着」，玩家贴着一个够不到的东西、读不出原因。

**否掉的另一种推法**：拿影子的纵深厚度（`ShadowHeightWorldPx` ＝ 6）当本体占地。它本身是未校准的审美初值，拿它当阻挡阈值会让**改影子长相就改碰撞行为**，那是不该有的耦合。

### 探针抓到的真实缺陷：挡在已重叠时生效会把人弹开

两个「不能靠推断下结论」的点专门量了，结果一条通过、一条**当场失败**：

1. **逐帧增删豁免是稳的**（此前只在 `_Ready` 里用过一次，无先例）：静止 60 帧零切换，纵深跨过阈值时恰好切换一次。
2. **挡在两者已经重叠时生效会被弹开** —— 先在不同排走到同一个横向位置（此时不挡），再挪进对方那一排，阻挡在两具身体已叠着时才生效。实测 Godot 的脱插**一帧到位**：单帧位移 **17.77px**（约等于整个本体宽 18px），且两具都在 `MoveAndSlide` 的角色此后**锁步一起漂**（60 帧从 X=220 漂到 77.8）。画面上就是「莫名被弹开然后一起滑走」。

修法（作者预先认可的方向）：`DepthBlocker` 加一条迟滞 —— **想挡、但此刻两者已经横向重叠着，就先不挡，等分开了再挡**。也就是把阻挡定义成「不许走进去」而不是「把已经在里面的推出去」。改后实测单帧位移 **0.000px**，迟滞生效 68 次，分开后在 gap＝19.93 重新生效（另有判据 `blocking-resumes-after-separating` 盯住「迟滞不能变成永久的洞」）。

半宽从**引擎实际在用的碰撞形状**上读（`GetShapeOwners`），不让调用方再报一遍宽度；形状假设不成立时当场抛 —— 静默按 0 算会让这条迟滞永远不生效，而那正是它要防的缺陷。

### 第二个缺陷：纵深方向走进去没人拦（作者 2026-09-18 实机发现）

作者实机复核后报：**从正面和后面接近挡得住，从上方和下方（W／S 走纵深）接近却能穿过去。** 这是真缺陷，而且是同一个洞的另一半。

**机制**：上面那套是「用纵深门控**引擎碰撞**」，而引擎碰撞只存在于 Godot 的两个轴上（横向与跳跃高度）——**纵深根本没有碰撞体**，那正是本条的前提。所以 `MoveAndSlide` 物理上拦不住纵深移动，而当时的代码在 `DepthWorldPx` 变化时没有做任何阻挡检查。于是「绕行」形同虚设：换一排走到物件跟前，再在纵深上挪进它体内即可。

**这个缺陷本轮的探针日志里就有，是当时读错了。** `engage-while-overlapping-no-teleport` 那条的输出结尾是 `playerX=220.00 enemyX=220.00` —— 主角在纵深方向挪进敌人后正站在它体内。上一版实现笔记把它写成了「可接受的代价」（站在里面直到自己走出来）。**那个判断是错的**：正典要的是「绕行」，所以走进去本身就该被拦住，而不是只要求进去时别弹开。五条走位判据全都按 `MoveRight`，一条都碰不到纵深方向 —— 那就是它能全绿而缺陷仍在的原因。

**修法**：`DepthBlocker.Resolve` 加一段 `ConstrainDepths`，把在纵深上挤进来的一方夹在阈值边界上；算法是纯函数 `DepthBlocking.ClampDepthOutOf`（规则层，可单测）。三条约束：只对**横向重叠**的对生效（正好贴住时纵深必须自由，否则绕行那一步就没了）、**只拦往里不拦往外**（否则把已经在里面的关死）、夹的是**边界**而不是「上一帧位置加位移」（某一帧位移再大也不穿到另一侧）。滞后一帧、最多插进 1px，因为纵深每帧最多走 1 世界像素。

**新判据三条**：`depth-approach-front-blocked`／`depth-approach-back-blocked`（两侧各一条，只测一侧会漏掉符号写反的那一半）、`go-around-path-open`。**第三条是配对的正面判据**，不是凑数：光有「挤不进去」会让「横向重叠就一律锁死纵深」那种过紧实现也全绿，而那会把玩家钉在物件跟前，正典要的绕行反而做不到。实测 `closestDepthGap` 前侧 7.00／后侧 8.00（阈值 8，容一帧 1px），夹逼生效 89／91 次。

**顺带修掉探针自己的一个假绿**：迟滞那一段把「按住纵深键」写在方法开头，于是分离段还在每帧重按，纵深键一直没松 —— 主角在随后每一轮走位里都往带后沿飘，纵深差一拉开就没人挡它，五条走位判据会一起变成「都走得过去」。是诊断输出里 `playerDepth` 停在 22 而不是 24 才看出来的（两次运行数字逐位相同，说明是确定性缺陷而不是环境抖动）。按住那一句已挪进靠近段内部。

**迟滞的地位随之下降**：加了纵深夹逼之后，「整个人挪进对方体内」正常操作已经到不了，所以迟滞从常规路径变成安全网（摆位、出场与将来的击退仍可能造出重叠状态）。那一条判据也改成量「正常操作能到达的最坏情形」：横向完全叠着、纵深正好顶在阈值上。

### 验收结果

`verify.py` 6/6、测试 **352**（原 328，新增 24 条）；新探针 `blocking_dev` **19/19**、`--smoke 120` 无错。现有四个探针无回归：`player_dev` 43/43、`hit_feedback` 82/82（`--no-shake` 也 82/82）、`combat_debug` 11/11、`depth_dev` 16/16。

**探针必须在跑起来之后不再执行前台命令**，否则 `focus-kept` 会以「玩法坏了」的形状连带毁掉需要输入的判据 —— 本轮把这条收窄成了可操作的规程（归 `ENG-14`）。**该规程已随 [ADR-0009](../../../decisions/ADR-0009-编辑器主导的开发模式.md) 作废**：图形探针全部删除，已无适用对象。

**现有四个探针不装这个组件**，所以它们里的碰撞关系一点没变（`GP-13` 的 `wall-block` 靠木桩 `Layer=4`／`Mask=1` 那条单向关系，本条不动它）。阻挡由场景显式装配，训练房与 `BlockingDev` 装。

### 训练房摆了两个沙包（作者 2026-09-18 定）

一个我方、一个敌方，分开站。走一趟就能连着撞出两种结果：我方那个穿得过去，敌方那个挡住、得往纵深挪半步才绕得过。原先主角与靶那条写死的互免碰撞删掉了 —— 它当初的两个理由（不看纵深地挡更糟、挨打时挤开）现在都由判定本身兑现。

阈值 8 与「站进敌人身体里要自己走出来」这两件事只能实机看。**手感确认不在本条**，归 `GP-6`。
