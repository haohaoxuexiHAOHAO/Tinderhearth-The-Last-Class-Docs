# PRD：两种视角各自的尺度与人物本体尺寸

> **历史背景·非依据。只读归档件，不得作为现行依据。** 现行事实见下面「归档三问」列出的落点；待办见[待办台账](../../../spec/issues/README.md)。

## 归档三问

**一、本轮现行事实落在哪：**

- [玩法定位 · 视角规则](../../../canon/gameplay/玩法定位.md)：两种视角的相机都不缩放、各自一屏装多少格、俯视相当于星露谷的哪一档远近。侧视 2 倍拉近与「同一套素材两处复用」两句都已作废。
- [玩法定位 · 像素基准](../../../canon/gameplay/玩法定位.md)：基础单位与瓦片单格、俯视与侧视人物各自的本体尺寸、体型三档、素材按视角分两套、哪些角色要几套。
- [玩法定位 · 核心循环](../../../canon/gameplay/玩法定位.md)：补进接委托、粮食与吃饭、治疗与照护三个环节，闭合点从四处变五处（粮食单独一条，它的失败方式与金钱材料不同）。
- [战斗与关卡 · 可行走纵深是怎么算出来的](../../../canon/gameplay/战斗与关卡.md)：按新本体尺寸重算的那笔账 —— 同深度间距、一排几人、排距、纵深、几排、站位总数与纵向预算，以及命中纵深容差取半个排距。纵深值的家在这一节，别处只写链接。
- [人物 · 可读性规则按视角分](../../../canon/characters/人物.md)：两种视角各自哪些细节读得出来，以及靠小道具建立特征的角色必须另有主剪影钩子。
- [场景绘制约定](../../../production/场景绘制约定.md)：俯视 45 度的投影规矩、地面分层判据、双网格与四边拼接各管什么与怎么选、地形交接用配对法、光影归属、基地要画哪几套、耕地干湿两套、侧视背景按组件分层拼、动态水用静态瓦片加逐格帧动画而不写扰动着色器。
- [像素绘制原则 · 12. 逐帧交付与脚底锚点](../../../production/像素绘制原则.md)：帧框按角色各自实测、声明四项含锚点列、朝向目录分层，以及动作帧可以超出精灵格、本体不行。
- [ADR-0020](../../../decisions/ADR-0020-侧视不拉近而把角色画大一档.md)：拉近倍数与本体高度是同一个取舍的两半，以及 LF2 的纵深占比在 16:9 上装不下的那笔纵向预算账。
- [ADR-0021](../../../decisions/ADR-0021-每个朝向各画一套不做水平翻转.md)：每个朝向各一套素材、代码不翻转、没有「这个角色翻不翻」的开关，以及它换来的那几处简化。
- 只改指针不改结论的三处：[关卡系统](../../../design/关卡系统.md)、[学生群像](../../../canon/narrative/学生群像.md)、[ADR-0013](../../../decisions/ADR-0013-战斗片段就是一屏.md) 里指向改过名的那两个节名。

**二、本轮新记的欠账：** 六个新编号 `ART-15`（世界侧配色）、`ART-17`（试片实机确认尺度）、`ENG-24`（代码侧尺寸常量与朝向按新口径落地）、`ENG-25`（双网格实现）、`GP-86`（地形渲染将来要一份系统文档）、`NR-26`（剪影复核按新基准重审），各在台账有自己一行；`DOC-101` 添了两项作者实读；`ENG-16` 与 `ART-6` 只更新备注、条目不关闭。另记下一条修根办法：给 `tools/check_docs.py` 加按格量长度的判定，等作者定。

**三、检查：** `python tools/check_docs.py` 0 FAIL 0 提示；`python tools/simulate_week.py --check-doc` 无分叉。

## 1. 概述

作者要开始画正式美术，而画之前有一批尺寸没有定：**俯视场景的相机远近、俯视角色画几个方向、俯视 45 度怎么画、侧视角色画多大。** 现在能查到的只有基础单位 16px、逻辑分辨率 640×360 与侧视 2 倍拉近这几项，其余要么散在代码里当字面量，要么整个不存在。

同时要改一条已经写下来的结论：正典现在写着**侧视拉近 2 倍、同一套素材两处复用**，而两处复用本来就名不符实（俯视要四向、侧视要一整套动作，没有一张图真能共用），拉近 2 倍的全部理由又只是「32px 的角色在屏上太小」。作者定的方向是**把角色画大到本体 48px、同时取消侧视拉近** —— 换来的是一屏容得下的活动区域大出一截，也就是[待办台账](../../../spec/issues/README.md) `ENG-16` 那条「作者两次实机都反馈活动区域偏窄、上下留白多」要的东西。

**这一轮是纯文档批次。** 它定口径，不画素材、不调手感、不改代码 —— 现有代码里那几个尺寸常量是旧工作方式的遗留，按新口径落地跟真正开发那一轮一起走。

## 2. 目标

- 作者拿着文档就能开始画俯视与侧视两侧的素材，不用再回来问尺寸。
- 两种视角的相机远近各有一个文档里的家，代码不再是唯一出处。
- 侧视那笔几何账按新的本体尺寸重算一遍，结论仍然自己成立。
- 体型不一的角色与会伸出本体的动作帧有一条通用做法，不必每加一个怪物重定一次。
- 核心循环图补上正典别处写了、图上没画的那几个环节。
- 文档与代码的差距记进台账一处，不留静默分叉。

### 作者已经定下的口径

**这一批值本轮要写进正典与制作规格；落进去之后本节就是历史、不作依据。**

| 项 | 值 |
| --- | --- |
| 俯视相机 | 不缩放 |
| 侧视相机 | 不缩放（原先的 2 倍拉近取消） |
| 俯视人物 | 本体 32px 高，精灵格 32×32，画四个方向 |
| 侧视人物 | 本体 48px 高、宽不超过 32px |
| 体型分档 | 小 ≤32px 高、人 48px 高、大 64–80px 高（按素材实测） |
| 帧框 | 按角色从素材实测算出，不写死；作者只要画完不截 |
| 素材套数 | 两套。主角与学生各两套；敌人与怪物只要侧视，城区 NPC 只要俯视 |
| 已画好的土对草 | 是**天然裸土**对草，走双网格；已耕地另是一套、走四边拼接 |
| 可行走纵深 | 本体高的四倍 |
| 场景地面 | 用瓦片集拼，不整片手工画 |
| 瓦片单格 | 与基础单位同宽，所以半格偏移落在整数像素上 |
| 自然地形瓦片 | 双网格：显示层相对数据层偏移半格，一种交接一套 16 张 |
| 功能性格状态瓦片 | 同一网格上的四边拼接，一种状态一套 16 张（引擎原生模式，不偏移） |
| 地形交接的画法 | 本轮用配对法：会挨着的每一对各一套 16 张 |
| 耕地 | 干与湿各一套 16 张，形状相同只换色带 |
| 场景背景 | 按组件分层拼，同类地形在片段之间复用 |
| 动态水 | 静态水面瓦片 ＋ 引擎原生的逐格帧动画；不写扰动着色器 |

**表里没有的那几个量是派生的，由 US-002 按既有算法算出来**：同深度相邻间距、一排装得下几个、相邻两排纵深差、可读排数与站位总数。它们的输入就是上表的本体尺寸与逻辑分辨率。

**背包与界面图标不在本轮范围内，也不受影响** —— 界面画在逻辑分辨率上，从不跟相机缩放走。**侧视关卡里的树干、宝箱、石头这类物件同样不受影响**，它们按大件画、不受基础单位约束。

## 3. 上游约束

- [玩法定位 · 像素基准](../../../canon/gameplay/玩法定位.md)：基础单位 16px、逻辑分辨率与它的两条推导、动作帧可以大于精灵格。**这一节是本需求主要要改的地方** —— 侧视缩放与「同一套素材两处复用」在这里，俯视缩放本该在这里而现在没有。
- [玩法定位 · 视角规则](../../../canon/gameplay/玩法定位.md)：战斗与出征一律侧视、基地与城区一律俯视 45 度，无例外。**约束本需求只碰尺度，不碰视角归属。**
- [玩法定位 · 核心循环](../../../canon/gameplay/玩法定位.md)：那张图与它下面的闭合点。**约束补环节时要连闭合点那句一起看，不能只往图里加框。**
- [战斗与关卡 · 可行走纵深是怎么算出来的](../../../canon/gameplay/战斗与关卡.md)：那笔几何账的算法（本体尺寸 → 相邻间距 → 一排几人 → 排距 → 纵深）。**约束重算要沿用同一套算法，只换输入，不换方法。**（那一节原先的名字里带着旧带宽，改名也在本需求内。）
- [战斗与关卡 · 战斗关卡的空间模型：带纵深的横版](../../../canon/gameplay/战斗与关卡.md)：纵深连续、角色不因远近缩放、绘制按纵深排序。**这三条一个字不改**，本需求只改那条带宽。
- [人物 · 可读性规则按视角分](../../../canon/characters/人物.md)：面部细节在 32px 画不出来、主记忆点落在剪影与签名色上。（那一节原先的名字里带着俯视那个数，改名也在本需求内。）**它是第 2 级正典，层级高于玩法定位** —— 侧视本体改成 48px 会让那一节里「屏幕上占 64px、素材只有 32px」这句不再成立，所以要配 ADR。
- [像素绘制原则 · 动作帧可以超出精灵格，本体不行](../../../production/像素绘制原则.md)：帧框尺寸从实测极值算出、不写死；作者只要画完不截。**这条思路不变，本需求把它从「全项目一个帧框」扩到「每个角色各自一个」。**
- [ADR-0009](../../../decisions/ADR-0009-编辑器主导的开发模式.md)：素材裁切与导入归作者在 Godot 里做；参数唯一来源是场景与资源，代码不留能用的默认值。**约束帧框那条口径要写明缺声明当场报错**，也约束本需求不替作者决定任何一张图长什么样。
- [ADR-0013](../../../decisions/ADR-0013-战斗片段就是一屏.md)：一个战斗片段就是恰好一屏，而「一屏」指侧视有效视野、那两个数的家在像素基准。**它刻意没有复述那两个数，所以本需求改缩放之后它自动跟着变，一个字不用改。**

## 4. 用户故事

### US-001：正典定下两种视角各自的尺度

**描述**：作为要开始画素材的作者，我想在正典里查到两种视角各自的相机远近与人物本体尺寸，以便不用翻代码也不用问人。

**验收标准**：

- [ ] 可核对：同一节写明**侧视相机同样不缩放**，原先那句 2 倍拉近及其「同一套素材两处复用、不另画战斗素材」一并删除
- [ ] 可核对：同一节写明两种视角的人物本体高度各是多少，并写明它们不相等的理由
- [ ] 可核对：同一节给出体型三档（小、人、大）的本体高度口径，并写明大型按实测、在站位上按占两个算
- [ ] 可核对：同一节写明素材分两套，以及哪几类角色只需要其中一套
- [ ] 可核对：[玩法定位 · 内容规模基准](../../../canon/gameplay/玩法定位.md)加一行**基地的天然地形种类**，并写明这个量要撑起什么（两种才试得出双网格一对，三种才试得出「哪几对会挨着」那条纪律）

- [ ] 可核对：全库搜不到「同一套素材两处复用」这一类说法（搜两个仓加 `.kiro`）

### US-002：侧视几何账按新本体尺寸重算

**描述**：作为要摆敌人与互动物件的人，我想要一张按新本体尺寸重算过的几何账，以便知道一屏里到底站得下多少个、纵深该做多宽。

**验收标准**：

- [ ] 可核对：[战斗与关卡 · 可行走纵深是怎么算出来的](../../../canon/gameplay/战斗与关卡.md)那一节整体重写，**节名不再带旧带宽那个数**，并把全库指向它的引用一起改指新节名
- [ ] 可测试：表里每一行都给出算式与依据，且逐行算得通 —— 本体尺寸 → 同深度相邻间距 → 一排装得下几个 → 相邻两排纵深差 → 可行走纵深 → 可读排数与站位总数
- [ ] 可测试：纵向那笔账也给出来（最近的脚、最远的脚、最高的头、角色带高度、上方留给背景与 HUD 的余量），且各数加起来等于逻辑分辨率的高度
- [ ] 可核对：站位总数容得下同屏敌人上限加一支满编队伍，并留得出互动物件的位置
- [ ] 可核对：那一节仍然写明**这是几何账不是好玩账**，密度成不成立归实机，`ENG-16` 的验法照旧
- [ ] 可核对：命中的纵深容差写明它是半个排距，与新排距对得上

### US-003：场景绘制约定成文（两种视角合一份）

**描述**：作为要画基地、城区与关卡片段的作者，我想要一份场景画法约定，以便画出来的地面、背景、建筑与人物能拼到一起，也知道一种地形要画多少张。

**合成一份而不是两份**，因为瓦片集与拼接那套做法两种视角共用 —— 分两份就要把同一套解释写两遍。俯视 45 度的投影规则是其中只管一侧的那一节。

**验收标准**：

- [ ] 可核对：`production/` 下新增一份场景绘制约定，文件头齐全、被设计仓 README 的文档地图链着
- [ ] 可核对：写明俯视的地面格是正方形、不是等距菱形，并给出格边长的来源（不复述那个数，写链接）
- [ ] 可核对：写明俯视的立面不做纵向压缩 —— 一格高的墙、树干这类竖直面按整格高度画
- [ ] 可核对：写明**建筑贴图允许高于占地**（屋顶往上伸出），占地仍按既有规则取整数格；并写明这与动作帧超出精灵格是同一个形状
- [ ] 可核对：写明俯视角色画四个方向，以及为什么不做八向
- [ ] 可核对：写明俯视的前后遮挡按脚底位置排序，并与侧视那条按纵深排序的规则互相指认
- [ ] 可核对：写明自然地形走**双网格**：数据层一格一个地形、显示层整体偏移半格，每张显示贴图管四个角的组合，因此一套 16 张

- [ ] 可核对：写明**两种 16 张的分工与判据** —— 判据是「这一格是不是玩家单独操作的对象」；是就走同一网格上的四边拼接（边界落在格边线，引擎原生模式），不是就走双网格（边界落在格中线）

- [ ] 可核对：写明地面分层，判据是**谁决定它在哪** —— 作者画在地图里的天然地形走双网格，玩家自己改出来的（已耕地，以及若做的装饰性铺地）走四边拼接
- [ ] 可核对：写明**天然裸土与已耕地是两样东西**，各走一种拼接；并写明装饰性铺地**若做**才有，它归的编号写链接不复述状态

- [ ] 可核对：写明本轮**保持配对法**与理由，并写明切到叠加法时要动的只有「对方长出来的东西」那几笔

## 6. 非目标

- **不改代码。** 现有那几个尺寸常量是旧工作方式的遗留，按新口径落地跟真正开发那一轮一起走；本轮只把落点记进台账（US-007）。
- **不画任何素材。** 重画角色动作帧、画俯视四向、画瓦片集、画关卡片段背景都归作者，各自记条目。
- **不实现双网格。** Godot 不原生支持它，要两层图层加一段把数据层翻译成显示层的脚本 —— 那是代码，归开发那一轮，落点记进台账（US-007）。**功能性格状态那一套不在此列**，它走引擎内置模式、没有要写的东西。
- **不定手感值。** 顿帧、击退、闪避冷却、纵深移动速度照旧归实机收敛，本需求一个都不碰。
- **不改视角归属。** 哪些场景俯视、哪些侧视一个字不动。
- **不改基础单位与逻辑分辨率。** 它们是本需求全部推导的输入，动它们要另立需求。
- **不改纵深连续、角色不因远近缩放、绘制按纵深排序**这三条空间模型结论。
- **不改同屏敌人上限。** 新的站位账要容得下它，而不是反过来削它。
- **不碰界面与背包图标。** 界面画在逻辑分辨率上、不跟相机缩放走，取消拉近碰不到它。
- **不碰侧视关卡里那些大件物件的尺寸。** 树干、宝箱、石头按大件画，本来就不受基础单位约束。
- **不定世界侧的配色。** 角色、地形与物件的色板现在全库没有家（有色板的只有界面那一侧），而它是画正式美术的另一个前置。**另立一轮**，理由是它要在编辑器里看着定、反复试，而本轮全是算得出来或查得到的口径 —— 两类混一批会让这批收不了尾。**本轮只在台账记一条编号。**
- **不做俯视场景本体。** 基地、城区与建筑室内的节点树归各自的条目。
- **不开地形渲染的系统文档。** 能写下来的都在制作规格与正典里，实现那一半现在只有「两层图层加一段映射」这一句 —— 开一份九节骨架会有一大半写「待定」，而那正是文档漂移的来源。触发条件记进台账（US-007）。
- **不定城区与侧视关卡的地面材质。** 只定基地那一张；城区那批人造地面归城区分图那条待办，关卡的按遗址各自定。
- **不画装饰性铺地，也不定它做不做。** 正典只写了「装饰性建造（美化，无功能收益）」，没说包不包括地面铺装，而且那一条明确后置。约定里它只占一句「若做，走四边拼接」。
- **不切到叠加法。** 本轮保持配对法，只把切换判据与「切的时候要动哪一部分」写下来。
- **不定关卡片段的具体张数与内容。** 只定一屏有多大。
- **不碰俯视的移动速度与经营侧动作机。** 尺度变了之后那些量要复看，但归它们自己的条目。
- **不替作者判观感。** 角色在屏上够不够大、场面够不够宽敞只能实机看。

## 7. 界面与表现考虑

- **HUD 的可用面积变了**：侧视不再缩放之后，角色带与上方余量都按新的纵向账算，顶部那条 HUD 与角色头顶的距离会变。排布本身不在本轮改，但重算那笔账时要把留给 HUD 的余量写出来，否则下一个人只能猜。
- **世界空间那些元素反而变简单**：读条圆环、精英血条、伤害数字原先要按侧视缩放换算，两种视角同尺度之后那层换算没有对象了。这是开发那一轮的收益，本轮只记在台账上。
- **界面本身没有任何改动**：图标两档、排版栅格、字号行高都不受影响。
- **异常态**：帧框那条口径写明缺声明应当报错而不是画一个占位框 —— 这是 [ADR-0009](../../../decisions/ADR-0009-编辑器主导的开发模式.md) 的要求，静默兜底会让「作者忘了填」变成一个查不出来的问题。

## 8. 技术考虑

- **代码侧的落点已经收得很窄**，因为那几个数各自只有一处：侧视缩放在 `rules/Ui/UiMetrics.cs`、两种视角的分叉在 `rules/Ui/CameraRig.cs`、纵深带宽在 `rules/Combat/DepthBand.cs`、命中容差在 `rules/Combat/CombatFeel.cs`、阻挡阈值在 `rules/Combat/DepthBlocking.cs`、帧框在 `src/World/PlayerActor.cs`。乘缩放的调用方在 `rules/Ui/HudLayout.cs`，死区的注释在 `rules/Ui/CameraFeel.cs`。**这一轮只把这份清单记进台账，不动它们。**
- **文档与代码会有一段口径差，这是刻意的。** 代码改完而素材还是旧尺寸时，角色会在一屏里显得偏小、纵深带多出一片空地 —— 那不是缺陷，但它长得像缺陷，而实机看是这件事唯一的验收手段。差距靠 US-007 那条台账记着，不靠记忆。
- **`ENG-16` 那条实机验收不关闭。** 本需求给的是一个算得出来的新值，仍然没有证明「打起来爽」；那条验收换个对象继续用。
- **既有测试里钉着旧数字的那些留到开发那一轮改**，包括钉住侧视有效视野是逻辑分辨率一半的那条、以及按旧排距推容差关系的那条。改测试不是绕过测试 —— 它们钉的是「两个数之间的关系」，关系不变、输入变。
- **外部参照均已核过，附来源**：星露谷的图块 16×16 与角色 16×32 见 [modder 指南](https://stardewvalleywiki.com/Modding:Modder_Guide/Game_Fundamentals)；屏上一格 64 像素见 [TMXTile](https://github.com/Platonymous/TMXTile) 的 `tileSize`；标准农场可耕格数见 [Farm Maps](https://stardewvalleywiki.com/Farm_Maps)。LF2 的窗口 794×550 与场景纵深默认区间见开源复刻 [F.LF](https://github.com/Project-F/F.LF) 的 `global.js` 与 `background.js`；它的精灵格按文件各自声明、每帧另带锚点，见 [Firen 的数据](http://lf2.fandom.com/wiki/Firen.dat)与 [Julian 的投射物](https://lf2.fandom.com/wiki/Julian_ball2.dat)。CPS-1 的 384×224 见 [Capcom Database](https://capcom.fandom.com/wiki/CP_System)。星露谷缩放条的下限 75% 只有社区来源（[玩家指南](https://stardewguide.com/uncategorized/how-to-easily-zoom-out)），**标「待验证」** —— 验证办法是实机拉一次缩放条看最小档。上述外部内容为合规做过改写。
- **LF2 那套按文件声明格子加每帧锚点的做法，与本项目现有的脚底锚点管线是同一招**，差别只在本项目在导入时就把锚点解析成一个统一帧框。所以 US-004 是把既有做法从「一个帧框」推广到「每角色一个」，不是换方案。
- **双网格的数目有出处**：显示层偏移半格之后每张贴图管四个角，一种地形一套 16 张，而同一网格上的传统八邻域自动拼接要 47 张 —— 见 [Unity 侧的原始实现](https://github.com/jess-hammer/dual-grid-tilemap-system-unity)与[偏移半格那段说明](https://github.com/starburst997/Unity.DualGrid/blob/master/Documentation~/user-guide.md)。**Godot 不原生支持**，社区有现成实现（[Godot 版](https://github.com/jess-hammer/dual-grid-tilemap-system-godot)、[TileMapDual 节点](https://github.com/jeffbdavenport/TileMapDual_godot_node)），内置与否仍在[提案讨论](https://github.com/godotengine/godot-proposals/discussions/10422)里。
- **动态水按星露谷那条路走，它的做法有官方出处**：标了 `Water` 的瓦片由游戏**另画一层动画覆盖**，而把值设成 `I` 就只保留水的逻辑、不画那层动画（[Modding:Maps 的瓦片属性表](https://stardewvalleywiki.com/Modding:Maps)）。所以水面瓦片本身是静的，动画不必给那 16 张边缘各做一套。
- **引擎这一侧现成**：Godot 的瓦片图集支持逐格动画帧（`TileSetAtlasSource` 的动画帧数与速度，见[类文档](https://docs.godotengine.org/en/4.4/classes/class_tilesetatlassource.html)），所以「静态边缘 ＋ 水面那一格几帧动画」不需要写任何着色器。
- **功能性格状态那一套引擎也原生支持**：同一网格上按四条边拼接正好是 16 张，对应内置地形模式里的 Match Sides（[官方论坛那句「只有 16 张就选 Match Sides」](https://forum.godotengine.org/t/how-to-paint-terrain-for-auto-tile-of-tilemap/55366)；三种模式的对照见[这份地形文档](https://github.com/dandeliondino/godot-4-tileset-terrains-docs)）。所以耕地那一侧不需要插件也不需要偏移层 —— **只有自然地形那一侧要写脚本**。
- **星露谷的耕地在观感上就是逐格对齐的那一种**，但它的实现没核到源码级别，**这一句是推断**；不影响本轮的结论，因为引擎这边的做法不靠它成立。
- **噪声扰动那条刻意不选。** 它最省素材，但扰动出来的采样落在非整数像素上，与本项目的最近邻、整数缩放与「只许全透明或全不透明」三条硬规则直接冲突；要用就得把位移量化到整像素（[texel 量化那类做法](https://godotshaders.com/shader/texel-space-quantization/)），而在瓦片图层上还要先把图层塞进子视口再挂着色器（[现成的像素水着色器](https://godotshaders.com/shader/pixel-art-water/)就是这么装的）。收益是省几帧素材，代价是一条会破坏像素纪律的新通路 —— 留作以后的润色项，不进本轮。上述外部内容为合规做过改写。
