# GP-24：`design/装备系统.md`

> **只读历史归档，不得作为现行依据。** 现行事实在[`装备系统`](../../../design/装备系统.md)，两条取舍的依据在 [ADR-0011](../../../decisions/ADR-0011-纯增益装备的窄例外.md)与 [ADR-0012](../../../decisions/ADR-0012-宝石的两个镶嵌目标.md)，加成的出口在[`成长系统`](../../../design/成长系统.md)的派生表、载体在[`状态效果系统`](../../../design/状态效果系统.md)的永久项。**这个编号还没做完** —— 文档已交付而代码一行都没写，落地顺序与状态在[待办台账](../../../spec/issues/README.md)，不在本文。

## 目标

把「一件宝物是什么、词条什么时候掷、装上去那份加成怎么进派生表、强化改哪一部分、谁来配」写进一处，加一件宝物时只是填表。

## 来源

- PRD：[`prd.md`](./prd.md) 的 `US-004`
- 起因：这批东西现在无家可归，而下游已经在引它 —— [`成长系统` · 它读谁](../../../design/成长系统.md)那张表里「宝物与宝石给的加成」一栏直接指向本条（那一栏原来写的是「饰品」，本批统一成「宝物」），[`背包系统` · 一格一堆，堆的标识是「种类 ＋ 品质」](../../../design/背包系统.md)写明「装备栏那一侧怎么存归本条」，[`技能系统` · 宝石：改机制，不只是改数字](../../../design/技能系统.md)持有孔位怎么开却把「宝石自己是什么」留给了这一批。
- 上一批刚落地的生活技能专长又一次用了同一个永久载体，**装备是那个载体最后一个缺席的来源**。

## 依赖

`GP-48`（用词与清单）、`GP-46` 与 `GP-47`（两条取舍的依据）。**与 `GP-48` 互相引用，一起验。**

## 验收标准

**先答一个结构问题，答案与过程都写进本条的实现笔记：** 装备系统装着宝物栏、专属栏、宝石与孔位、强化、主副词条这几组东西，**该不该拆成几份**。按[`生产系统` · 什么时候拆出去单独成篇](../../../design/生产系统.md)那条判据（**它有没有自己的状态机**）逐组判一遍 —— 不默认拆，也不默认不拆，并写明结论将来被重判的条件。

- [x] 按 [SYSTEM 模板](../../../templates/SYSTEM.md)八节写全，`type: system`、文件名以「系统」结尾、`upstream` 指[角色与成长](../../../canon/gameplay/角色与成长.md)，**并在 `GP-48` 这一轮就被正典链接到**。
- [x] 拆不拆的判断逐组记进本条实现笔记。
- [x] **一件宝物要声明哪些字段写成一张表**，至少覆盖标识、名称与描述的文本键、稀有度、固定主词条、副词条候选池、基础孔数、能不能被强化、是不是纯增益那一类。写明**哪些字段属于[`物品系统` · 物品定义的字段：只写「它是什么」，不写「它能干什么」](../../../design/物品系统.md)那张表、本页不复述**，两张表的分工写成一句判据。
- [x] 写明**副词条条数由稀有度给、不写在每件宝物身上**（写在每件上就是同一个事实两个家）。
- [x] **一颗宝石要声明哪些字段写成一张表**，含**属性侧**与**机制侧**两块，**两块都可以为空但不能都为空**；机制侧要写明它换掉的是[`技能系统` · 一个战斗技能要声明的字段](../../../design/技能系统.md)里的哪一格。
- [x] 写明**孔的种类由宝石的声明决定**，镶进没声明那一侧的孔时被拒；这不是分类规则，而是声明推出来的（指 `GP-47`）。
- [x] 写明**一颗宝石只能在一处**、**宝物被卸下时镶在它身上的宝石跟着它走**、**镶进去的宝石不单独占背包格**。
- [x] **宝物孔数写成两段相加**（稀有度给基础、强化给附加），并写明**宝物孔同样不分类型**；**孔数上限是接口常量**，每档给几个归 `GP-7`。
- [x] **宝石与两种孔的接缝各指对方**：技能孔怎么开在 `技能系统`，宝物孔怎么开与宝石自己是什么在本页。两处都要有指向对方的一句。
- [x] **词条分两类并各写生成时机**：固定主词条在定义里写死，随机副词条**在实例产生那一刻掷定、之后不再变**；**不做重掷与洗练**并给理由。
- [x] **正负面写成可判定的形式**：没有负面项的宝物与宝石定义**被拒**，**唯一放行的是纯增益那一类且必须带唯一性标记**（指 `GP-46`）。同一处写明「这个负面疼不疼」**永远没有机器判据**。
- [x] 写明**宝石的两侧效果各自必须带负面**（只在机制侧写负面，那颗宝石镶进宝物就是纯增益，例外会从宝石这边整个漏掉）。
- [x] 写明**固定主词条一律正面，负面只出现在副词条里**，并给理由。
- [x] **装上与卸下走同一条载体接口**：装备时往[`状态效果系统` · 载体的字段](../../../design/状态效果系统.md)加永久项并带**来源标签**，卸下时按同一个来源显式移除。写明**不新建修饰表**，理由指[玩法定位 · 跨系统约定](../../../canon/gameplay/玩法定位.md)那条点名。

- [x] 写明**词条能改哪些量的判据**：它改的量必须指得到一个已声明它的系统，**填不出归属的量不许当词条**；不做全局轴表，理由与专长那条同源。

- [x] **强化作用在宝物与宝石两样上、各有自己的等级**，写成一张表；写明**对副词条只拉伸、不重掷、不改条数**。
- [x] 写明**级数上限必须存在且与品质无关**（品质管量级不管结构），**上限是接口常量**、每级幅度归 `GP-7`。

## 实现笔记

> 由 `/note-it` 在实现和评审之后填写。

### 设计决策

**先记拆篇判断，那是本条要先答的结构问题。**

按[`生产系统` · 什么时候拆出去单独成篇](../../../design/生产系统.md)那条判据（**它有没有自己的状态机**）逐组判：

| 组 | 有没有自己的状态机 | 为什么 |
| --- | --- | --- |
| 宝物栏与专属栏 | **没有** | 装上与卸下是瞬时的，没有「正在装备」「装备冷却」这类中间态。一件宝物要么在容器里、要么在某个栏位上 |
| 宝石与两种孔 | **没有** | 孔是「未开 → 已开」的单向门，不是流转；而技能孔那道门的条件（实战值档位）在成长与技能那一侧，不在本页 |
| 词条 | **没有** | 实例产生那一刻掷定，之后不再变。生成是一次性的函数，不是状态 |
| 强化 | **本来会有，但被答复排掉了** | 只要强化可以失败并降级，它就有「尝试 → 失败 → 降级」的流转。作者定了**不会失败**，于是它只是一个单调递增的整数字段 |

**结论：不拆，一份 `design/装备系统.md` 装全。** 五组东西没有一组有自己的状态机，而它们共享同一个载体（状态载体的永久项）、同一条容器判据（实例唯一永不合堆）、同一条支出管道（强化）。拆开会让「一件宝物的加成从哪来」有两份文档，而那正是这一批要消掉的毛病。

**这个结论将来会被重判的条件写死两条**：①**强化改成可失败并降级**（那时它有了流转，该拆出去，而本页只留接口）；②**词条出现重掷或洗练**（那时词条有了「可变」这个状态，同理）。

---

- **模糊点**：来源标签的粒度 —— 载体本来就有「来源」字段，但没说粗到什么程度。
- **选择**：粒度必须指得到**「哪一件的哪一条」**，不能只标「装备」。
- **理由**：卸下必须按来源整批撤，而两件宝物都加物理防御时，只标「装备」会把另一件的也撤掉 —— **而那种错不报错**。这条给出了一条能写的反证：卸一件之后，同时在场的另一件那一批一条不少。

第二处：**「词条能改哪些量」不做全局轴表，改成一条判据** —— 它改的量必须指得到一个已经声明过它的系统。理由与上一批的专长轴同源：全局表一定留下填不了的格，而填不了的格会被「等效物」塞满。

第三处：**强化同时吃钱与材料。** 只吃钱会让强化变成一个把钱换成战力的转化器，而挖矿与采集挖出来的东西需要一个去处 —— 宝石本身就是灵能结晶，那条链的下游不该只有「卖掉」。

### 偏离

- **方案怎么说**：本条只写 `design/装备系统.md`，`GP-48` 另改正典。
- **实际怎么做**：两条是同一轮做完并一起验的，本条的文档链了正典那一节、正典那一节也链了本文档。
- **为什么**：**两份互相引用的文档不可能各自独立跑绿** —— 长期规格没有正典引用会当场 FAIL，而正典要指得到系统文档才说得清「细节在哪」。**所以本条的「`check_docs` 0 FAIL」是与 `GP-48` 合并之后才成立的**，写在这里免得被当成单独跑绿了。

第二处：**顺带改了三份别人的文档**，都不在本条的验收清单里，但它们指的就是本批定下的东西 —— [`技能系统`](../../../design/技能系统.md)（宝石那一节收窄成技能孔、分工措辞改成按孔的种类分）、[`成长系统`](../../../design/成长系统.md)（派生表那一栏补上宝石经宝物孔进来这条路、「不持有装备」改成指本文档）、[`背包系统`](../../../design/背包系统.md)（「装备栏那一侧怎么存归 `GP-24`」改成指本文档，并补一句宝物与宝石都不占格）。不改的话，那几处就是指向一个已被回答的问题的指针。

第三处：**`数值模型` 里那半句「大头来自饰品、宝石……」跟着改了名**，而它触发了一个新坑，见下面「待确认」。

### 权衡

「拆成 `装备系统` 加 `宝石系统` 两份」考虑过 —— 宝石现在有两个镶嵌目标，看起来够独立。没选：判据问的是「有没有自己的状态机」，宝石没有；而且宝石的属性侧只有装在宝物孔里才生效，拆出去之后「宝物给了多少属性」要跨两份文档才读得全。

「把强化写成一份自己的文档」考虑过。没选：同上判据，而且它只是一条支出加一个整数字段 —— 那一节现在的篇幅远没到其余各节之和。

「给装备开一张自己的词条修饰表」考虑过，实现最省事。没选：那会让「同时生效的修饰」又多一个来源，而正典那条「全部临时性与持续性效果走同一套状态系统」正是为这个写的，并且**点名把「宝物的负面词条」列在里面**。

「让装备自己算派生量」考虑过（少一层转发）。没选：派生表就不是下游唯一入口了，而玩家问「这 47 点防御从哪来」时会有两个答案，其中一个查不到出处。

### 待确认

**一处是推断，未实测**：「装备的逻辑在代码仓一处都没有」这句写进了下游同步那一节，**但没有搜过代码仓确认**。验法很简单，实现前搜一遍；写明它是推断，因为本批一个 `.cs` 都没动、没有跑 `python tools/verify.py` 的对象。

**一条落地前置**：永久项那一档现在**还不存在** —— 载体是定长两槽、只有帧这一种时长单位（`rules/Combat/StatusEffects.cs`）。所以本页写的「装上加永久项」这条接法要等 `GP-18` 的载体扩容，落地顺序里已写明。
