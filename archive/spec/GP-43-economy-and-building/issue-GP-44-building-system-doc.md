# GP-44：`design/建造系统.md`

> **只读历史归档，不得作为现行依据。** 现行事实在[`建造系统`](../../../design/建造系统.md)：两套网格与同一份冲突判定、摆位四条拒绝路径（含门前一格）、施工状态机与取消、升级／拆除／移动三条路径、仓库格数与室内摆位两个挂点。**这个编号还没做完** —— 文档已交付而代码一行都没写，落地顺序与状态在[待办台账](../../../spec/issues/README.md)，不在本文。

## 目标

把「一栋建筑摆得下摆不下、升级是什么形状、室内的格子怎么算」写进一处，并让仓库扩容与设备摆位各有一个指得到的挂点。

## 来源

- PRD：[`spec/prd-economy-and-building.md`](./prd.md) 的 `US-004`
- 起因：[时间与经营 · 建造](../../../canon/gameplay/时间与经营.md)定了尺寸、建筑类别、施工占天、可拆可移与每栋都有室内，但**网格上怎么摆、升级是什么形状、室内的摆放网格是什么，一条都没定**。
- 两处在等它：[`背包系统` · 两个容器，分它们的判据是「跟着人走还是跟着建筑走」](../../../design/背包系统.md)的仓库扩容，与[`生产系统` · 设备：它买的是自动化，不是便宜](../../../design/生产系统.md)的设备摆位 —— 后者已经写着「建筑与室内的摆放网格结构归将来的建造系统」。

## 依赖

`GP-39`（开荒清理物的对应）、`GP-43`（花费走它那条支出管道）。**与 `GP-43` 互相引用**，两条一起写完一起验。

## 验收标准

- [x] 按 [SYSTEM 模板](../../../templates/SYSTEM.md)八节写全，`type: system`、文件名以「系统」结尾、`upstream` 指[时间与经营](../../../canon/gameplay/时间与经营.md)，**并在本条这一轮就被正典链接到**。
- [x] **两套网格分清并各写职责**：地面网格（可建造区那一套，地块与建筑共用，指回[`生产系统` · 地块：唯一一条有自己状态机的渠道](../../../design/生产系统.md)）与**室内网格**（每类建筑各自声明、与外观占地无关）；写明室内那套与外观脱钩的理由。
- [x] **摆位判定写成可判定的清单**：占地范围、不许越出可建造区、不许与已有建筑或地块状态冲突、**门前一格必须留空**；不满足时**下单当场被拒并说清是哪一种原因**。
- [x] 写明**门前那一格计入占地**，并写明它替代的是什么：**不做整片连通性判定**，理由与它挡不住的那种形状都写出来，真出现了再补 —— 那时是加法。

- [x] 写明**施工可以取消，取消的返还与拆除走同一条规则**；理由写清。

- [x] 写明**移动仍然要过全部摆位判定**（含门前那一格），所以「免费」只是免代价、不是免规则。
- [x] **仓库扩容接在这里**：仓储建筑的级数 → 仓库格数，写明这是[`背包系统`](../../../design/背包系统.md)那一侧唯一的扩容入口，**格数的值归 `GP-2`**。
- [x] **设备摆位接在这里**：设备占室内格子、不占派工位（指回[`生产系统`](../../../design/生产系统.md)），室内摆放的冲突判定与地面那套同源。

## 实现笔记

> 由 `/note-it` 在实现和评审之后填写。

### 设计决策

- **模糊点**：升级要不要重走摆位判定 —— 验收只要求「原地升级、里面的东西不动」。
- **选择**：**外观占地不随级数变**，所以升级不重走摆位判定。
- **理由**：占地随级数涨的话，玩家会遇到「升不了级，因为旁边盖满了」—— 而那是一条查不到原因的拒绝（他升的是这栋楼，被拒的理由在别的楼上）。容量靠室内承担与正典那条「小建筑加大画布」同向，所以这条不是妥协。

第二处：**拆除前要先清空。** 仓储里有东西、室内摆着设备时不许拆 —— 否则就要回答那些东西去哪，而[`背包系统`](../../../design/背包系统.md)整页都在拒绝「替玩家丢东西」。

第三处：**两套网格用同一份冲突判定**，只是作用在不同坐标空间里。写明这一点是为了不出现两份「重叠了吗」的实现。

### 偏离

- **方案怎么说**：本条只写 `design/建造系统.md`，`GP-43` 另写经济那份。
- **实际怎么做**：两条同一轮做完并一起验，本条的文档直接链了 `经济系统`。
- **为什么**：与 `GP-43` 那条相同 —— **互相引用的两份系统文档各自独立跑不绿**。**所以本条的「`check_docs` 0 FAIL」也是合并之后才成立的。**

第二处：**「门前一格必须留空」这条同时写进了正典。** 条目只要求写进系统文档，但它是一条玩家会直接撞上的摆位规则（不是一个字段）—— 玩家摆不下去时看到的提示来自它。写进[时间与经营 · 建造](../../../canon/gameplay/时间与经营.md)一句，是为了让「为什么摆不下」在正典层就答得出来；同一处指明细节在本页。

第三处：**顺带把[`生产系统`](../../../design/生产系统.md)三处「将来的建造系统」占位改成了实链接**，另有[`背包系统`](../../../design/背包系统.md)的仓库扩容那一格。它们不在本条验收里，但它们等的就是本条。

### 权衡

「做整片连通性判定」考虑过，它能把「门被堵住」挡得更干净。没选：要算全图连通、还要回答「哪一扇门走不到」，是这一节最贵的一项。门前留一格用**一格占地**换掉了绝大多数真会发生的情况；**它挡不住的形状写明了**（拿建筑围一圈把某栋圈在中间），真出现再补 —— 那时是加法，不推翻任何一条。

「施工中不占地」考虑过，更灵活。没选：同一块地能叠着下好几单，冲突要留到建成那天在结算里解决 —— 那是最难查的一类错，而且它发生在玩家不在看的时候。

「不许取消施工」考虑过。没选：那会把一次摆错变成两倍材料的惩罚，而摆错位置是必然会发生的事。给取消另定一套返还比例也被排掉 —— 那要回答「取消比拆除该多返还还是少返还」，而那个问题没有正确答案。

「移动占天或花钱」考虑过。没选：有代价的移动会让玩家干脆不动它，于是布局在第一次摆完之后冻住，而布局优化是经营类游戏的长期留存点。**但「免费」只是免代价** —— 移动仍要过全部四条判定，这条单独写了一句，因为它是最容易被实现成后门的地方。

「仓储也可多建」考虑过（与畜舍对称）。没选：再造一个仓库就绕开仓库满那条压力，而[`背包系统`](../../../design/背包系统.md)已经为同一件事裁过一次（室内那排箱子是装饰）。

### 待确认

**一处是推断，未实测**：「建造的逻辑在代码仓一处都没有」写进了下游同步，**但没有搜过代码仓确认**（与 `GP-43` 同一处疏漏）。验法：实现前搜一遍。

**另一处留给实机**：门前留一格这条规则玩家理不理解，只能作者摆一遍看 —— 已写进本页的实机确认清单。
