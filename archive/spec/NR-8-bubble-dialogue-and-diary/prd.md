# PRD：气泡对话与日记

> **只读历史归档，不得作为现行依据。** 现行事实在[`气泡对话系统`](../../../design/气泡对话系统.md)与[`日记系统`](../../../design/日记系统.md)，玩法规则那几节在[玩法定位](../../../canon/gameplay/玩法定位.md)与[角色与成长](../../../canon/gameplay/角色与成长.md)。**未完的部分不在本文** —— 按编号活在[待办台账](../../../spec/issues/README.md)。

## 1. 概述

正典把这两样的**要求**写全了，缺的是它们**是什么**。

**气泡那一侧**：不接管输入、不暂停世界、内容按情境预写随机挑选，外加五条一起成立的约束（上下文键要细、说过的进冷却池、密度有上限、优先级与丢弃、**不承载必要信息**）。缺的是那几条约束的**结构形状**：一条语料条目要声明什么、五个上下文键怎么匹配、额度与丢弃发生在哪一层、冷却池活多久。

**日记那一侧**：每个角色都有、模板打底加预写文本、**读日记能发现需求进而解锁小事件**、受最小必要原则保护**非解锁不可翻**。缺的是一条条目长什么样、需求那条链的形状、解锁读什么、多少东西要进存档。

**日记的形状本批收窄了一次，所以正典那一句要同批改写。** 正典原来写「玩家视角的行为日志 ＋ 角色视角的私人日记**两者都做**」，读起来像两本册子；现在收成**每个角色一本日记，条目按类别分**。理由是那两个「视角」并不是两套存储，而是同一本里两种条目的区别（一种记发生了什么、一种记他怎么看）；做成两本的代价是同一次远征要在两处各写一条，而**「每个人的看法不同」恰恰要求它们并排放在同一个人名下才读得出来**。日记的作用是让这个世界的角色显得活着，而那要靠「同一件事在不同人笔下不一样」，不靠册子分家。

**为什么现在做，而且排在存档之前。** 上一批按判据把这两样显式推到了外面：气泡进不了[`剧情演出系统`](../../../design/剧情演出系统.md)（正典禁止它与正式对话合成一个系统），也进不了[`事件系统`](../../../design/事件系统.md)（记账语义相反 —— 引导是「首次之后不再主动出现」，气泡是「说过了进冷却池、还会回来」，同一份存储装不下两种）；日记被[`人际系统`](../../../design/人际系统.md)与[`事件系统`](../../../design/事件系统.md)两处显式推开，**多读者无主**。而它们各自要往存档里放什么（气泡的冷却池、日记的条目与已发现的需求）**是存档那一批的输入** —— 排在存档之后就要回头改那一批。

**本批不重写正典。** 气泡那五条约束、日记那三句要求都已在正典写全，本批只决定它们各自落在哪、长什么样。

**已经判过的一件事：写成两份文档，不是一份。** 按[`生产系统` · 什么时候拆出去单独成篇](../../../design/生产系统.md)那条判据（**有没有自己的状态机**）两样都没有，所以真正要问的是上一批留下的那条补充：**它有没有宿主页。** 上一批已经排掉了演出与事件两个候选，所以剩下要判的是**这两样能不能互为宿主** —— 答案是不能。它们看起来同类（都是按键取文的叙事文本载体），但每一条要紧的性质都相反：一个自发推送、一个按需翻阅；一个没有解锁门、一个有制度性的门；一个的记账是「说过了会回来」、一个是「写过就一直读得到」；一个只有读出口、一个有运行时写入口；一个刻意没有任何机制作用、一个的机制作用（解锁小事件）是它存在的理由。**合成一份的后果是那些相反的性质都要写成表格上的分支**，而分支一多，「气泡不承载必要信息」与「日记非解锁不可翻」这两条就会各被读成另一条的例外。判断过程记进条目。

## 2. 目标

- **气泡的五条约束各有一处结构落点**，而且落点之间说得出先后：额度闸门在选句之前、冷却池只在真说出口之后才记。
- **日记一条条目就是一本里的一行，类别只决定它怎么生成与谁翻得开**，且「重建出来的和当时看到的一样」这件事有依据，不靠承诺。
- **条目不按天生成，按「发生了值得一记的事」生成** —— 于是条数是派生量（跟着事件与派工走），而不是随天数线性长；这同时是它读起来像活人而不像考勤表的原因。
- **「读日记 → 发现需求 → 解锁小事件」这条链在文档层面走得通**，并且它不是第二套触发 —— 它是[`事件系统` · 关系小事件也是一条事件](../../../design/事件系统.md)那张表里已经留好的一格。
- **「非解锁不可翻」有可判定的判据**，而且判据指回它的制度来源，不是凭手感定的一道门。
- **两份文档都不新建第二条取文管线、不新建时间单位、不新建通知渠道。**
- 正典那两处「还没有落点」改成指落点，**状态仍然只写在台账一处**。

只链接，不复制正文；每条写明它约束本需求的哪一部分。

- [人物 · 台词、命名与原创表达红线](../../../canon/characters/人物.md)：台词文明度、**声线靠语速、句长、抢话习惯区分而不靠脏话**、禁译表与母语审校。**约束「说话者」与「文本键」必须是两个字段（声线属角色、文本属内容），也是气泡允不允许一小串这个问题的来源。**
- [人物 · 教师权力、同意与关系红线](../../../canon/characters/人物.md)：私人信息遵循最小必要原则、不得变成战术奖惩资源。**这是「非解锁不可翻」的红线一侧。**

- [玩法定位 · 成就要靠统计事件总线，不能事后补埋点](../../../canon/gameplay/玩法定位.md)：值得记录的行为都向总线发事件。**约束本批两份各留一个挂点，不等成就系统存在。**
- [玩法定位 · 内容规模基准](../../../canon/gameplay/玩法定位.md)：那张表是全部平衡判据的算账基准，改它要回头看判据前提。**本批要判气泡语料与日记条目各要不要补一行。**
- [`剧情演出系统` · 文本一律按键取，日记与事件回看共用同一条](../../../design/剧情演出系统.md)：管线只在那一份展开、三处共用、缺键报错不退化成显示键名。**本批两份都写链接不复述 —— 再写一遍就是第三份副本。**
- [`事件系统` · 呈现与回看走已有渠道](../../../design/事件系统.md)：事件发生时往日记写一条回看记录，落在行为日志那一半；日记本体不在那一页。**这是本批要接住的那个接口，形状已定。**
- [`事件系统` · 关系小事件也是一条事件](../../../design/事件系统.md)：小事件的前置条件读关系档位、可加一个读日记的条件，后果是播一段演出。**「读日记发现需求」是那一格的精确化，不是第二套触发。**
- [`事件系统` · 持续引导：同一条管道，两条出口](../../../design/事件系统.md)：引导提示是必要信息、**不参与任何丢弃**，所以两者不共用一条呈现队列。**这是气泡那条呈现边界的另一侧。**
- [`人际系统` · 谁改它、谁读它](../../../design/人际系统.md)：气泡语料的选择已经是登记在册的读者、档位是一个上下文键；那一份明确不做日记。**约束本批不新开读者行，只把已有那几格接到落点。**
- [`活跃失衡系统` · 对外只有档位，没有精确值](../../../design/活跃失衡系统.md)：读口只有档位与总量、就近读，气泡语料的选择是登记在册的读者之一。**同上。**
- [`生产系统` · 什么时候拆出去单独成篇](../../../design/生产系统.md)：拆篇判据是**它有没有自己的状态机**。**本批两样都没有，所以真正要判的是上一批留下的那条补充：它有没有宿主页。**
- [`数值模型` · 尚未给值的量，各自写明校准办法](../../../design/数值模型.md)：值的唯一来源是参数表，文档只写量纲与约束形式。**约束本批新增的量一律进那张表，并写明给值那一轮必须同时把判据接上。**
- [ADR-0014](../../../decisions/ADR-0014-对话是演出脚本的一类指令.md)：正式对话是演出脚本上的一类指令，**气泡不共用这份格式**，判据落在接不接管输入上。**本批只能加强这条位置上的分隔，不能绕过它。**
- [ADR-0009](../../../decisions/ADR-0009-编辑器主导的开发模式.md)：参数唯一来源是场景与资源、代码不留能用的默认值；表现与手感由作者实机验收。**约束条目缺字段当场报错，也约束本批不把「气泡好不好看」写成机器判据。**
- [ADR-0010](../../../decisions/ADR-0010-文档体裁与系统文档归位.md)：体裁按寿命分、位置就是体裁、系统文档八节一节不少且必须有正典上游。**约束本批产出的形状与归位。**

## 4. 用户故事

### US-001：气泡对话落成一份系统文档

**描述**：作为实现者，我想要一份说清「一条语料条目声明什么、一次气泡怎么被选出来、什么时候不说话」的文档，以便不用在基地、关卡与每个角色身上各长一套挑句子的逻辑。

**验收标准**：

- [ ] 按 [SYSTEM 模板](../../../templates/SYSTEM.md)八节写全，`type: system`、文件名以「系统」结尾，`upstream` 指[玩法定位](../../../canon/gameplay/玩法定位.md)，**并在同一批被正典链接到**。
- [ ] **一条语料条目要声明什么写成一张表**，至少覆盖：标识、说话者要求、上下文键要求、优先级档、文本键；**缺任一必填项载入报错**。
- [ ] **上下文键表按正典那五个封口**（场景、当前状态、说话者、与在场者的关系、所在区的失衡档位），并写明**加一个键是填这张表、不是改选句规则**。
- [ ] **匹配规则写死成「条目声明了的键必须相等，没声明的视为任意」**，同一处写明为什么不做全五键匹配（配不出内容）也不做打分取最像（说不清为什么选了这句）。
- [ ] **候选集里怎么挑写成两级排序**：先按优先级档、再按条目声明的键数（专用的先说）；同级再随机。写明这让「专用句盖过通用句」不需要一个额外字段。
- [ ] **额度闸门排在选句之前**，且**被额度挡下的那一次不进冷却池**（承重项，有反证）—— 否则一句从没说出口的话被标记成说过了，而它不报错。
- [ ] 写明**没有队列**：额度满时低优先级的直接丢弃、不延后，也**不撤掉已经在显示的**；代价写明（挤不进来的剧情台词说不出口），并指回「气泡不承载必要信息」这条正典。
- [ ] **冷却池按「角色 × 条目」记、跨场景保留**，并写明它**进临时续玩点、不进正式存档**，理由指回存档时机（睡眠 ＝ 新的一天，那一刻重置正好对上语义边界）。
- [ ] 写明**同一条目在短时间内不许由不同角色说出**，理由是听到两个人说同一句话是明显的破绽。
- [ ] **与引导提示不共用呈现队列**，理由指回[`事件系统` · 持续引导：同一条管道，两条出口](../../../design/事件系统.md)，本页不重写。
- [ ] **文本一律按键取，写链接不复述管线**（[`剧情演出系统` · 文本一律按键取，日记与事件回看共用同一条](../../../design/剧情演出系统.md)）。
- [ ] 挂载点列全并写明「到此为止」，至少覆盖关系档位读口、失衡档位读口、当前状态读口、文本管线、呈现层、统计事件总线、临时续玩点。
- [ ] 边界那一节写明**不持有**：正式对话与演出脚本、语料内容、引导提示、必要信息的表达、气泡长什么样与飘多久的表现、任何数值。
- [ ] 文档里一个玩法数值都没有。
- [ ] `python tools/check_docs.py` 0 项必须修复（与 US-002、US-003 合并之后才成立）。

### US-002：日记落成一份系统文档

**描述**：作为实现者，我想要一份说清「一本日记里有哪些条目、各怎么生成、各存多少、谁翻得开」的文档，以便「读日记发现需求」这条链有一处可实现的形状，而不是散在人际、事件与界面三处。

**验收标准**：

- [ ] 按 [SYSTEM 模板](../../../templates/SYSTEM.md)八节写全，`type: system`、文件名以「系统」结尾，`upstream` 指[角色与成长](../../../canon/gameplay/角色与成长.md)，**并在同一批被正典链接到**。
- [ ] **一本日记按角色各一本、主角也有一本**；写明它**不是一本全局流水**，理由是同一件事在不同人笔下不一样，而那份不同只有并排放在各自名下才读得出来。
- [ ] **条目的类别写成一张开口的表**，起步两类：**纪事**（发生了什么，模板打底＋参数快照，自动写入）与**心声**（他怎么看，预写文本，由关键事件与关系档位触发）。同一处写明**加一类是填这张表**，以及类别只决定「怎么生成、谁翻得开」这两件事，不决定它存在哪。
- [ ] **条目不按天生成，按「发生了值得一记的事」生成**；写明为什么不做每天一条的摘要（每天一条会让一半条目是「今天没什么事」，而日记的作用恰恰是让角色显得活着），并写明由此条数是派生量。
- [ ] **纪事类条目 ＝ 模板文本键 ＋ 一组参数快照 ＋ 日期 ＋ 类别**，**不存渲染好的句子**；理由写准 —— 省的不是体积（一句渲染好的中文与一个键加几个参数差不多大），而是**正确性**：存渲染结果会让改模板或改语言之后旧条目还是旧样子，而它不报错。同一处写明参数是**当时的快照**而不是读取时现查（现查会让「那天他还只是熟悉」在今天变成信赖）。
- [ ] **一件事可以往多本日记各写一条**，各取那个角色自己的文本变体；**变体缺失时按条目声明的通用变体取，而通用变体缺失时报错** —— 写明这是**声明式回落**，不是「缺键退化成显示键名」那种静默降级。
- [ ] **心声类条目自带声明**（哪个角色、由什么触发），**不做「角色 × 事件」或「角色 × 关系档」那种二维索引表**；理由写明：交叉表要求每个格都有内容，而内容是分批铺的。
- [ ] **需求那条链写成「日记条目上的一个标记」**：一条条目可以声明它揭示哪个需求标识，读到那一条时那个需求进「已发现」集合；**小事件的前置条件读的是需求标识**。同一处写明为什么不用「读过某人的日记」当条件（翻开一次就解锁全部，于是「发现需求」退化成「点开过那一页」）。
- [ ] **「非解锁不可翻」按本判，不按类别判**：**主角自己那本一律可翻**（最小必要原则保护的是第三方的私人信息，理由指回制度来源）；**别人那本读关系档位**。
- [ ] 同一处写明**事件回看因此永远查得到**：凡是走过手环通知的事，主角那本里都有一条纪事；别人那本里的是「他怎么看这件事」，那一份才受解锁门管。**这是[`事件系统` · 呈现与回看走已有渠道](../../../design/事件系统.md)那个接口在新形状下的落点。**
- [ ] 同一处写明**主角不在场的、别人之间的事照样记**（记进当事人那本），**记与读是两件事** —— 写入不看解锁，解锁只管玩家翻不翻得开。这条让「都记下来」与最小必要原则同时成立。
- [ ] 同一处写明**不读「某条小事件演过没有」当解锁条件**：小事件本来就读关系档位，用它当门是把同一个条件绕一层，还会让解锁链成环。
- [ ] **存法按「参数化的存参数、静态的只存标识」写死**：纪事类条目进正式存档（模板键 ＋ 参数 ＋ 日期 ＋ 类别），心声类只存「哪些条目已被写出来」的标识集合（正文从内容数据重建，重建结果与当时一致，因为正文是静态的），**已发现的需求集合进正式存档**，**解锁状态不单独存**（它读关系档位，是派生量）。
- [ ] 写明**不设条目保留上限**，代价写准：正典写明**无全局日期上限**，所以条目总量没有上界，存档体积随游玩时长线性长。同一处写明**为什么仍然不设**（设了就查不到老事件，而回看正是为了让玩家不把事件当 bug），以及**要不要设、设多少登记成一个等实测的量** —— 判据是实测存档体积，不是估算。
- [ ] **日记是弹出界面所以它暂停世界**，判据指回[玩法定位 · 弹界面接管输入就暂停世界，世界里的动作不暂停](../../../canon/gameplay/玩法定位.md)，与气泡刚好是同一条判据的两侧；**关卡内只许查看**。
- [ ] **文本一律按键取，写链接不复述管线**（同 US-001）。
- [ ] 挂载点列全并写明「到此为止」，至少覆盖事件回看的写入口、日常动作（派工、出征、上课这一类）的写入口、关系档位读口、需求集合的读口（给[`事件系统`](../../../design/事件系统.md)）、文本管线、手环、统计事件总线、存档。
- [ ] 边界那一节写明**不持有**：日记文本内容、小事件的触发与后果、需求满足之后怎么样、翻页与排版、任何数值。
- [ ] 文档里一个玩法数值都没有。
- [ ] `python tools/check_docs.py` 0 项必须修复（合并之后才成立）。

## 5. 功能需求

- FR-1：气泡那份文档必须给出一条语料条目的字段表，且**缺任一必填项时载入报错**，不留能用的默认值。
- FR-2：气泡的上下文键表必须与正典那五个键逐一对上，且**不在那之外新开一个键**。
- FR-3：匹配必须是严格的 —— 条目声明了的键必须相等；**没声明的键视为任意**，不做打分近似。
- FR-4：一次询问里有多条候选时，必须按「先优先级档、再声明键数、同级随机」挑出一条。
- FR-5：额度闸门必须排在选句之前；**被额度挡下的那一次不得进入冷却池**。
- FR-6：系统必须没有气泡队列 —— 额度满时低优先级候选直接丢弃，且不撤掉已在显示的气泡。
- FR-7：冷却池必须按「角色 × 条目」记、跨场景保留，并且**只进临时续玩点、不进正式存档**。
- FR-8：气泡必须不接管输入，因此**不得暂停世界**。
- FR-9：气泡必须与引导提示分属两条呈现通道，引导提示**不参与任何丢弃**。
- FR-10：日记必须按角色各一本，主角也有一本；**不得做成一本全局流水**。
- FR-11：条目必须声明它的类别，类别表必须是开口的；类别只决定生成方式与可读性，**不得决定条目存在哪**。
- FR-12：条目必须在「发生了值得一记的事」时生成，**不得按天固定生成一条**。
- FR-13：纪事类条目必须存成「模板文本键 ＋ 参数快照 ＋ 日期 ＋ 类别」，**不得存渲染后的句子**；参数必须是当时的快照，不得在读取时现查。
- FR-14：一件事往多本日记写入时，各本必须能取到那个角色自己的文本变体；**变体缺失时按条目声明的通用变体取，通用变体也缺失时报错**。
- FR-15：心声类条目必须由条目自己声明它属于哪个角色、由什么触发，**不得引入二维索引表**。
- FR-16：当玩家读到一条声明了需求标识的条目时，系统必须把那个需求记入「已发现」集合。
- FR-17：关系小事件的前置条件必须读**需求标识**，不得读「读过某人的日记」这种整本粒度的条件。
- FR-18：主角自己那本必须一律可翻；别人那本必须按关系档位判解锁。**写入不得看解锁** —— 记与读是两件事。
- FR-19：「已发现的需求」集合必须进正式存档；日记的解锁状态**不得单独存**。
- FR-20：日记打开时必须暂停世界（它接管输入），且在关卡内**只许查看**。
- FR-21：两份文档都必须按键取文，且**不得各写一套取文办法** —— 管线只在[`剧情演出系统`](../../../design/剧情演出系统.md)展开一次。
- FR-22：两份文档都不得出现任何玩法数值；量纲与约束形式留文档，值进参数表并登记进尚未给值表。
- FR-23：一条气泡语料条目必须能声明一小串（同一人连说，或两人一来一回）；**条件不再成立时整串中止、不补演**，已说出口的照常进冷却池。
- FR-24：主角必须与其他角色共用同一套气泡规则，**不得为他砍掉任何优先级档**。

## 6. 非目标

本需求**明确不做**：

- **不写语料与日记文本。** 台词与日记正文是内容，一律数据外置（`ENG-5`），设计仓只持有格式与约束。
- **不碰正式对话与演出脚本。** 它们的家在[`剧情演出系统`](../../../design/剧情演出系统.md)，而气泡与它的分家判据已由 [ADR-0014](../../../decisions/ADR-0014-对话是演出脚本的一类指令.md)落成位置上的分隔。
- **不重写正典那五条气泡约束与那三句日记要求。** 本批只定它们的结构形状。
- **不做小事件的触发与后果。** 结构在[`事件系统`](../../../design/事件系统.md)，本批只提供它读的那个需求标识。
- **不做需求满足之后怎么样。** 需求被发现 → 解锁一条小事件，那条链到小事件为止；「需求被满足」是那条小事件自己的后果。
- **不做日记的搜索与筛选。** 类别与按本分是本批定的两层索引，怎么翻、要不要搜，归界面侧。
- **不定条目的保留上限。** 现在只登记它是一个等实测的量。
- **不做界面。** 日记挂手环哪一页、怎么翻、气泡框长什么样、飘多久、字号多大，归界面侧与作者实机定。
- **不做本地化流程。** 禁译表与母语审校在[人物 · 台词、命名与原创表达红线](../../../canon/characters/人物.md)，本批只保证存的是文本键。
- **不设计存档序列化格式。** 只定「哪些东西进正式存档、哪些进续玩点、哪些不存」，格式归存档那一批。
- **不定任何数值。**
- **不为气泡新建通知渠道。** 手环是唯一的事件通知渠道，气泡不是通知。
- **不给气泡承载必要信息。** 这是正典那条最要紧的约束，本批连接口都不留。
- **不做主角自己的私人日记之外的「他人内心读口」。** 读日记是唯一渠道，不另做「好感提示面板」一类东西。

## 7. 界面与表现考虑

**界面不在本批范围内**，但本批要定下的硬约束落进文档，界面侧照它做：

- **气泡与引导提示必须在形状上不一样，不能只靠颜色。** 气泡按说话者上色是很自然的做法，但那会把颜色这一维用满 —— 于是「另一种颜色的气泡」就再也分不出是提示还是闲聊，而提示不许被漏掉。这条与 `UI-18` 那条同源，本批不新开一条。
- **说话者靠位置认，颜色是辅助。** 气泡挂在说话者头上，那本来就是最强的指认手段；颜色好认但不能是唯一手段（色盲玩家之外，同色系角色多了也认不清）。另有一条既有硬约束：色值不带 alpha，像素只许全透明或全不透明。
- **一本日记里两类条目要看得出分别。** 纪事是「发生了什么」、心声是「他怎么想」，混排会让解锁门看起来像 bug（同一页里有的能读有的不能）。
- **被锁住的那本要说得出「为什么锁着」。** 只显示一把锁等于让玩家以为是坏的；说「你们还不够熟」才让它变成一个目标。
- **读到一条揭示需求的条目时要有一处看得见的落点**（见待确认问题四）。
- **气泡在关卡里不能挡住该看的东西**（正典那条）。位置、层级与避让都是表现，作者实机看。

信息层级、字号与色板沿用已有的排版单位与色板欠账，本批不定。

## 8. 技术考虑

- **文本管线已经落地**：代码仓 `data/text/zh-CN.json` 与那条文本外置预留（`ENG-5`）。本批两份只定「怎么从它取文」，不新建管线。
- **关系档位读口已经存在**（[`人际系统` · 谁改它、谁读它](../../../design/人际系统.md)），气泡与日记都只是加一个读者，不是加一条接口。
- **失衡档位读口已经存在**（[`活跃失衡系统` · 对外只有档位，没有精确值](../../../design/活跃失衡系统.md)），且气泡语料的选择已经是登记在册的读者。
- **暂停闸门已经存在**（复用顿帧那个「当帧不推进」的闸门），日记打开时用它，气泡不用它。
- **气泡的选句与额度判定不需要引擎**，所以它落规则层；呈现落引擎层。日记的条目与解锁判定同理。**这一条是推断** —— 实现前要先搜一遍代码仓确认这两侧真的是空的。
- **两份文档互相引用**，所以它们一起写完一起验：单独跑任何一份都会有指向另一份的断链。这一点写进条目的「偏离」。

## 9. 待确认问题（阻塞项）

**无。** 答案都已写进正文，这里只留它们各自落在哪，免得再翻一遍：

| 问过什么 | 定成什么 | 落在正文哪 |
| --- | --- | --- |
| 气泡允不允许一小串 | 允许；条件不再成立时整串中止、不补演 | `FR-23`、`US-001` |
| 日记的解锁档位 | 中段那一档（值仍归 `GP-7`） | `US-005` |
| 日记是一本还是按角色 | **按角色各一本，主角也有**，条目按类别分 | 概述、`US-002`、`US-003`、`FR-10` |
| 揭示需求时要不要提示玩家 | 给一条克制的提示，不写成任务条目 | 界面与表现考虑 |
| 主角自己那本写不写 | 写 | `US-002`、`FR-10` |
| 收不收主角不在场的别人之间的事 | 照样记；**记与读是两件事**，读由解锁门管 | `US-002`、`US-003`、`FR-18` |
| 主角会不会冒气泡 | 会，三档都冒；他的性格补进正典 | `US-003`、`FR-24` |

答复连带定下两件本来要问的事，按既有规则裁得出来，所以直接定了、没有再开一轮：

- **名字用「日记」不用「日志」。** 正典与[`事件系统`](../../../design/事件系统.md)已经在用前者，改名要连着动正典与两份系统文档；而「日志」在本项目里另有所指（工具自己写的那种）。两份文档的「同名不同物」那一节写明这一点。
- **谁有日记由角色定义上的一个声明项决定**，起步铺主角与学生、常驻 NPC 的格子留着。理由与内容分批铺同一条：写成「全体都有」会让常驻 NPC 缺内容时无声地显示一本空册，写成声明项则「他还没有日记」是数据里看得见的事实。**这条同时是[待办台账](../../../spec/issues/README.md) `DOC-35` 那张角色定义字段表要收的一格。**
## 10. 成功判据

- **两份系统文档各自八节写全、各被正典链接到、各自说得出「不持有什么」**，且 `python tools/check_docs.py` 0 项必须修复（看它自报的覆盖量，不只看退出码）。
- **正典与另外四份系统文档里，「气泡／日记还没有落点」这个说法一处不剩**（按编号搜两个仓加 `.kiro` 的结果为零）。
- **气泡那五条正典约束逐条指得到一处结构落点**，且落点之间的先后说得出来（额度在选句之前、冷却只记真说出口的）。
- **日记那三句正典要求逐条指得到一处结构落点**，其中「非解锁不可翻」的判据指回制度来源而不是手感。
- **正典那两处改写都落进了正典本身**（日记收成一本、主角性格），而不是只活在系统文档里；改写只动了该动的那句，三条要求与笑脸面具那段一个字没改。
- **「读日记 → 发现需求 → 解锁小事件」这条链在文档上从头走到尾**，并且[`事件系统`](../../../design/事件系统.md)那一侧只改了一处措辞、没多一个字段。
- **本批新增的量都在尚未给值表里**，各有量纲、校准办法与归属；现在就判得到的那几条约束形式已经写出来。
- **本批没有把状态写进散文**：进度仍只在台账，两份新文档与正典都只写链接。
