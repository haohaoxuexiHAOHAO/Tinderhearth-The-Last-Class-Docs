# PRD：数值模型（`GP-2`）

> **本文件已归档，只读，不得作为现行依据。** 现行的公式与判据见[数值模型](../../../design/数值模型.md)，值见 `design/numeric-model-params.json`，当前实测值跑 `python tools/simulate_week.py`。现行待办见[台账](../../../spec/issues/README.md)。

## 1. 概述

玩法结构已定（`GP-1` 已归档），但**没有一个数字**。四份正典把数值指向 `GP-2` 的地方有十几处：属性公式、成长曲线、判定公式、时间与体力消耗、经济与定价、容量、AI 阈值。在它们落地之前，任何玩法实现要么停工，要么现场编数字 —— 后者更坏，因为编出来的数字会以「配置」的样子留在仓库里，看不出是猜的。代码仓 `ARCHITECTURE.md` 现在刻意不含任何玩法数值，就是为了不让这件事发生。

**现在做的理由是它挡住了所有玩法实现。** 剩余待办里 `GP-4`、`GP-5`、`ENG-5` 的后续部分、`ENG-6` 的实际调参都在它后面。

本轮**只产出设计**，不落代码。这不是省事：判定公式的最终值依赖实机手感，而手感调优的工具还没选（`ENG-6`），现在写进 `data/*.json` 只是把猜测伪装成配置。

## 2. 目标

- 玩法实现需求开工时，**不必再自己编数字** —— 每个量都能在数值模型里查到，或者查到「它为什么还不能定，以及怎么定」。
- 正典[留给 `GP-2` 的六条数值前提](../../../canon/gameplay/玩法定位.md)每条都有一个**算得出来的数**，而不是一句形容。
- 第一周的可玩性**在纸面上就能判断**：时间装得下、粮食不断、现金流不负、出征划得来。
- 正典里那些定性硬约束（「精准防御回蓝不得高于进攻回蓝」这类）变成**可检验的判据**，而不是留在散文里等人自觉。

## 4. 用户故事

### US-001：定下量级、单位与硬约束清单

**描述**：作为后续故事的作者，我想要先有一份量级与单位约定，以便所有公式写在同一把尺子上。

**验收标准**：

- [ ] 可核对：文件里写明 HP 三位数（100–999）、伤害两位数的量级选择及理由
- [ ] 可核对：列出全部量的单位（游戏小时、体力点、货币单位、格、帧）
- [ ] 可核对：正典里的定性硬约束逐条抄成编号判据，每条写明「怎么算才算没违反」
- [ ] 可测试：每条判据给出一个数值例子，说明违反时会算出什么

### US-002：四项属性到各自作用项的量化映射

**描述**：作为玩法实现者，我想要知道一点力量到底改变什么，以便实现属性时不必猜。

**验收标准**：

- [ ] 可核对：力量、敏捷、体力、智力各自的作用项都有公式，覆盖正典点名的全部方向（含体力的日体力上限、智力的阅读速度两条经营侧作用）
- [ ] 可测试：给出 1 级与满级两组输入的完整计算结果
- [ ] 可测试：满级角色对新手角色的战力差落在 **4–6 倍**区间，给出算法与结果
- [ ] 可核对：写明单一属性堆到极限时**为什么仍不能解释胜负**，并给出该情形下的数值证明

### US-003：成长曲线

**描述**：作为玩法实现者，我想要等级、属性点与天赋点的分配曲线，以便实现升级与训练。

**验收标准**：

- [ ] 可测试：给出等级上限、每级经验需求与每级给出的属性点与天赋点
- [ ] 可测试：天赋点总量 ÷ 节点总数给出具体比例，且比例 < 1
- [ ] 可测试：给出出征经验、训练经验（含每日上限）与未出战者补偿比例三个量，并验证「训练收益明显低于出征」
- [ ] 可测试：给出技能实战值的累积速率与档位阈值的量纲

### US-004：战斗判定公式的结构与硬约束

**描述**：作为战斗实现者，我想要伤害、暴击、闪避、硬直与防御的公式结构，以便不等帧数校准就能先把结构搭对。

**验收标准**：

- [ ] 可核对：伤害、暴击、闪避、硬直抗性、SP 消耗与回复各有公式，且**不含任何须实机校准的帧数**
- [ ] 可测试：验证「精准防御的回蓝效率不得高于进攻回蓝」—— 给出两条途径的每秒回蓝量并比较
- [ ] 可测试：给出主角攻击招与学员输出的伤害比，验证主角显著更低
- [ ] 可核对：待实机校准的量逐条列出（顿帧、精准防御窗口、连段帧数、读条时长），各自写明量纲、允许区间与校准办法

### US-005：时间与体力预算表

**描述**：作为经营实现者，我想要一天 19 小时里每个动作占多久、耗多少体力，以便派工与出征结算有依据。

**验收标准**：

- [ ] 可测试：浇水、走路、一次出征（按三类委托与三档委托档位）、读技能书、加工、训练各自的耗时与耗体力都有数字
- [ ] 可测试：把这些数字代入 19 小时，给出至少两种成立的一日安排
- [ ] 可测试：熬夜两档（22:00–24:00 轻度、24:00–25:30 重度）对次日体力上限的下降量
- [ ] 可测试：体力上限的四个来源（体力属性、吃饭、住宿等级、健康状态）各自的贡献量

### US-006：开局配置与前期现金流

**描述**：作为玩家，我想要开局刚好能开始，以便第一天知道该干什么又不觉得东西已经给全了。

**验收标准**：

- [ ] 可测试：起始资金、起始粮食、债务本金三者的具体值与比例
- [ ] 可测试：至少一种作物的生长周期 ≤ 4 天，给出全部第一版作物的周期
- [ ] 可测试：粮食储备撑到第一次收获后**仍余 1–2 天缓冲**
- [ ] 可测试：按季计息的季利率，并验证第一季免息后第二季的利息额不超过一条低难度委托报酬的某个倍数（给出该倍数）

### US-007：出征与治疗的性价比

**描述**：作为玩家，我想要「出征值不值得」和「花钱快治是不是真的可选」都有明确答案，以便这两个决策不是假选择。

**验收标准**：

- [ ] 可测试：一次低难度委托的报酬 ÷（耗时 + 耗体力）给出具体比值，并说明它为什么让出征划得来
- [ ] 可测试：治疗费用 ÷ 委托报酬给出具体比值，并验证「花钱快治」在第一周就是一个真实可选项而不是奢侈品
- [ ] 可测试：给出免费慢养与花钱快治的天数差

### US-008：定价三层的幅度与材料分级

**描述**：作为玩家，我想要「这季种什么」每季都重新成为问题，以便经营不是一次性算完就照抄。

**验收标准**：

- [ ] 可测试：基础价、需求系数（季度偏好溢价）、供给系数（批量递减）三层各自的幅度
- [ ] 可测试：验证偏好溢价足以让「按偏好种」优于「按最高基础价种」，给出两种策略的一季收入对比
- [ ] 可核对：材料分级 —— 哪些基础材料可直接购买、哪些进阶材料必须经加工
- [ ] 可核对：每个影响价格的因子都写明「玩家在手环里能查到的当前值与原因」是什么

### US-009：背包与仓库容量

**描述**：作为玩家，我想要一次出征回来需要做一次「带什么回去」的取舍，但不被频繁迫使丢弃。

**验收标准**：

- [ ] 可测试：背包各级格数与仓库各级容量
- [ ] 可测试：用 US-005 的一次典型出征产出量验证「需要一次取舍」，并给出产出量与容量的比值
- [ ] 可核对：写明这个比值为什么不会导致频繁被迫丢弃

### US-010：七天纸面推演

**描述**：作为作者，我想要看到前七天逐日的四条曲线，以便判断第一周到底可不可玩。

**验收标准**：

- [ ] 可测试：逐日给出时间、体力、现金流、粮食四条曲线，共 7 天
- [ ] 可测试：六条数值前提逐条判定通过或失败，失败的指出是哪个参数
- [ ] 可核对：推演由 `tools/` 下的入口重算，不是一次性手工表格
- [ ] 可测试：改动任一参数后重跑，四条曲线随之变化

### US-011：数值模型的端到端一致性验证

**描述**：作为三周后的自己，我想要确认设计文件与推演互不矛盾、且任一参数改动都能重算，以便这套数值是可维护的而不是一次性的。

**验收标准**：

- [ ] 可核对：推演入口跑一次，六条前提全部判定通过，退出码 0
- [ ] 可测试：关键失败路径 —— 故意把一条作物周期改成 > 4 天，重跑，确认对应前提判定为失败且指出是哪个参数
- [ ] 可测试：故意把治疗费改成高于委托报酬，重跑，确认对应前提判定为失败
- [ ] 可测试：推演入口自报覆盖量（算了几天、判了几条前提），并在参数缺失时判失败而非用默认值静默补齐
- [ ] 可核对：设计文件里出现的每个数字都能在推演的参数表里找到同名项，不存在两处不同的值
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL，数值模型文件已接入 README 文档地图

## 5. 功能需求

- FR-1：数值模型必须给出四项属性到各自作用项的量化映射。
- FR-2：模型必须给出等级、属性点与天赋点的成长曲线。
- FR-3：天赋点总量与节点总数的比例必须使玩家无法点满全部小树。
- FR-4：模型必须给出战斗判定公式的结构与量纲。
- FR-5：模型必须把须实机校准的量单独列出，并给出各自的量纲、允许区间与校准办法。
- FR-6：模型必须给出 19 游戏小时内每个动作的耗时与耗体力。
- FR-7：模型必须给出至少一种生长周期不超过 4 天的作物。
- FR-8：模型必须给出起始资金、起始粮食与债务本金三者的比例。
- FR-9：模型必须给出一次低难度委托的报酬与其时间体力消耗之比。
- FR-10：模型必须给出治疗费用与委托报酬之比。
- FR-11：模型必须给出定价三层各自的幅度。
- FR-12：模型必须给出背包与仓库的各级容量。
- FR-13：模型必须把正典的每一条定性数值约束转成带编号的可检验判据。
- FR-14：推演必须逐日给出时间、体力、现金流与粮食四条曲线。
- FR-15：推演必须能在参数改动后重算。
- FR-16：推演必须在任一数值前提不成立时判失败并指出对应参数。
- FR-17：模型文件必须接入 README 文档地图。

## 6. 非目标

- **不产出 `data/*.json` 参数文件，也不实现规则层公式。** 落地跟着各玩法实现需求分批走，与 `ENG-5` 的推进方式一致。
- **不定顿帧时长、精准防御判定窗口、连段帧数与读条时长。** 正典写明这些只能实机逐帧调，工具选型归 `ENG-6`。本轮只给量纲、允许区间与校准办法。
- **不定异常状态的具体持续时间与叠加规则。** 依赖统一状态系统的设计，那属于实现需求。
- **不定队友 AI 四档的具体实战值阈值与警戒传播的范围与延迟。** 本轮给实战值累积速率与阈值量纲，具体阈值等 AI 实现能实测行为差异时再定。
- **不定星火积分的兑换上限具体值。** 二周目第一版不做，本轮只给「上限必须存在」的约束形式。
- **不做界面与手环的显示设计。** 归 `UI-1` 与 `DOC-2`。
- **不改任何正典。** 正典明确写「数值一律不在正典」，所以本需求的产出落在 `design/`，不上升。
- **不改第一版内容规模表。** 它是范围约定，数值按它设计而不是反过来。

## 7. 界面与表现考虑

数值本身不是界面，但正典有三条要求会反过来约束数值设计，必须现在满足：

- **每个影响价格的因子都要能在手环里查到当前值与原因。** 所以定价的每一层都必须是**可命名、可解释**的，不能是一个合成系数。
- **体力上限变化必须有可见反馈与原因。** 所以上限的四个来源必须各自独立可显示，不能先加总再存。
- **伤害数字默认关闭、杂兵不给血条。** 所以数值量级主要服务于调试可读性，不服务于玩家阅读 —— 这是选小数值的一条理由。

界面排版与具体控件归 `UI-1`，本需求不涉及。

## 8. 技术考虑

- **产出落点**：数值模型写成 `design/` 下的**长期常驻条目**。依据是 `design/README.md` 的分工表 ——「一个系统的完整规则、会被多次改动反复引用」正是它。有一处要写明：该 README 说「设计稳定后结论上升进正典」，但[玩法定位](../../../canon/gameplay/玩法定位.md)明确写「数值一律不在正典」，**所以数值模型是这条上升规则的例外，永久留在 `design/`**。这条不写清，以后会有人来做一次错误的上升。
- **推演做成 `tools/` 下的 Python 入口，不是手工表格。** 理由是 [WORKFLOW §5](../../../WORKFLOW.md)「会做第二次的操作写成 `tools/` 下的 Python 入口」—— 推演一定会重算，每次调参数都要。手工表格的结论三周后没人能验，改一个数就得全部重算，而这正是「结论必须有依据」要防的形状。
- **推演脚本的退役条件要写在它自己里。** 它在游戏没有实现之前是唯一能算的地方；一旦规则层实现了公式，两处会出现漂移风险。届时要重新判断：退役，还是改成读同一份参数表来交叉验证实现。这个判断本身要记账。
- **不引入任何新依赖。** 推演只用标准库，与 `check_docs.py`、`setup_godot.py` 一致。
- **战力差 4–6 倍这个目标是本轮定的口味，不是正典事实。** 正典只约束方向（属性不得解释全部胜负），幅度由作者 2026-08-30 选定。写进设计文件时要标明来源是本 PRD 而不是正典。

## 10. 成功判据

- 六条数值前提**每条都有一个算得出来的数**，且推演逐日结果与之一致。
- 推演入口重跑一次得到相同结果；改一个参数后四条曲线随之变化；任一前提不成立时它判失败并指出是哪个参数。
- 第一周推演里：粮食在第一次收获时仍余 **1–2 天**缓冲、现金流未出现负值、19 小时装得下正典要求的日常动作且至少有两种成立的安排。
- 满级角色对新手角色的战力差落在 **4–6 倍**。
- 天赋点总量 ÷ 节点总数 **< 1**，且给出具体比例。
- 正典的定性数值约束逐条有编号判据，推演里没有一条被违反。
- `python tools/check_docs.py` **0 FAIL**，数值模型文件从 README 可达。

## 11. 归档小结

**范围**：产出了公式与理由（`design/数值模型.md`）、全部值（`design/numeric-model-params.json`）、推演入口（`tools/simulate_week.py`）与七天推演结论。**没动**任何正典、没产出游戏侧 `data/*.json`、没实现规则层公式、没定任何须实机逐帧校准的帧数。

**结论**：四项属性只解释一半胜负 —— 从 1 级练到满级战力涨 **4.35 倍**，而操作与构筑造成的差距远大于此。派生公式一律一次式，减伤用软化分母自然递减。六条正典数值前提与九条附加约束写成 16 条编号判据，由推演入口自动判定，当前 16/16。设计文件刻意不重复数字，值只在参数表里，所以「不存在两处不同的值」是构造保证而不是靠人核对。
