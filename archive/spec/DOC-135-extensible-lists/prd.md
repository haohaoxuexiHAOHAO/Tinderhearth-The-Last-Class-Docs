# PRD：哪些清单能加东西，加的人是谁

> **只读历史归档，不得作为现行依据。** 现行事实的落点清单在本页末尾的「归档三问」；状态与剩余动作在[待办台账](../../../spec/issues/README.md)，不在本页。**本页里描述「现在是什么样」的那些句子说的是改之前**，它们是立项理由，不是现状 —— 尤其「概述」那几处举出来的缺陷都已经改掉了。

## 1. 概述

`design/` 下三十多份系统文档里，「某一栏能填哪些值」这件事没有统一口径。有的写得很开（[`状态效果系统` · 载体的字段](../../../design/状态效果系统.md)明写种类可扩、不是定长枚举的固定索引），有的写成死名单（[`技能系统` · 一个战斗技能要声明的字段](../../../design/技能系统.md)的元素那一格只有火、冰、灵能、无），有的说了「这张表是开口的」却没说开口通向数据文件还是通向代码。

原因是现有两条政策各答一半：[ADR-0018](../../../decisions/ADR-0018-内容定义按声明扩展.md) 答「一个条目有哪些格」，[ADR-0022](../../../decisions/ADR-0022-内容清单的家是数据文件.md) 答「有哪些条目」。**没人答「一格能填哪些值，谁有权往里加一个」**，于是每份文档各推了一遍，推出了不同结论。

后果已经出现：同一份取值集在几处各有一份副本，而且有的已经对不上 —— [`战斗AI系统` · 预警与对策：都是出手定义上的显式声明](../../../design/战斗AI系统.md)列的对策带「打断」，而[战斗与关卡](../../../canon/gameplay/战斗与关卡.md)与[玩法定位](../../../canon/gameplay/玩法定位.md)两处列的都没有。没有任何检查能发现这种分叉。

本需求做三件事：把那条缺的政策立下来；按它把已经写偏的地方归位；顺带定下装备那几个谁都没定过的上限，并给出同稀有度下的平衡与爽感方案。

## 2. 目标

- 加一种新东西时，「它算数据还是算代码、谁有权加」有唯一答案，不用重新讨论。
- 元素、恶劣天气、建筑类别、生产渠道、委托类型这几样，加一种只要多一条数据，不改代码。
- 装备那几个决定界面画几格的上限各有唯一的家与值，实现时不必现场拍数。
- 同一稀有度的两件宝物差距小到不会「开出废品」，而拿到好东西仍然有即时可见的惊喜。
- 作物的生长阶段数由每种作物自己定，「最快几天成熟」这个会被抄错的数字不再存在。
- 已经对不上的那几处口径统一，且统一之后有检查盯着。

## 3. 上游约束

- [ADR-0018](../../../decisions/ADR-0018-内容定义按声明扩展.md)：约束本需求那条新政策的形状 —— 它只补「一格能填哪些值」，**不动**「一个条目有哪些格」与那三种必填级别。
- [ADR-0022](../../../decisions/ADR-0022-内容清单的家是数据文件.md)：约束归为内容型的那几样落在代码仓 `data/`，系统文档只写选取判据、不列名字。
- [ADR-0009](../../../decisions/ADR-0009-编辑器主导的开发模式.md)：约束装备那几个上限由作者填值、代码不留能用的默认值；也约束作物素材的交付归作者在 Godot 里做。
- [ADR-0011](../../../decisions/ADR-0011-纯增益装备的窄例外.md)：约束「特别强力的装备」走已有那条窄例外（纯增益必带唯一性标记），本需求不为它新开机制。
- [ADR-0012](../../../decisions/ADR-0012-宝石的两个镶嵌目标.md)：约束宝石的分类由声明推出，本需求的孔数上限要与它算得出的孔数对得上。
- [玩法定位 · mod 的扩展边界](../../../canon/gameplay/玩法定位.md)：内容外置、规则不外置。**本需求对技能的作用目标与形态那两格显式收窄这条承诺**，所以要在文档里写明这处例外。
- [角色与成长 · 装备：宝物与宝石](../../../canon/gameplay/角色与成长.md)：宝物栏格数、每个技能的孔数、宝物孔两段相加的形状都已在那里。本需求只补那几个还没有值的上限，**不改已有的任何一个数**。
- [`物品系统`](../../../design/物品系统.md)：稀有度答「有几条副词条」、品质答「每条有多强」。本需求的平衡方案全部搭在这条分工上，不新开第三条轴。
- [战斗与关卡](../../../canon/gameplay/战斗与关卡.md)：每一招可不可打断由它自己声明，而那一格与「对策」是同一格。**这是「对策」统一成含打断那一份的依据。**

依赖关系：装备那几个上限之外的值（各档给几个基础孔、强化每级的幅度与代价、副词条取值区间）仍归 `GP-7`，本需求不给。

## 4. 用户故事

### US-001：那条规矩立成一份决策记录

**描述**：作为以后要加新东西的人，我想要一条现成的判据，以便不用每次重新讨论「这份清单该放哪儿」。

判据一句话：**加一个取值，要不要写新代码。** 三种归属各有自己的家 —— 不用写代码的落数据文件、要写代码的落系统文档与代码、是个数的落唯一一处由作者填值。另有一类是只有在 Godot 里才看得出来的（素材、摆位、手感），归作者。

**验收标准**：

- [ ] 可核对：`decisions/` 下多一份已接受的 ADR，接进 [决策索引](../../../decisions/README.md)。
- [ ] 可核对：那份 ADR 里写明它**不取代** [ADR-0018](../../../decisions/ADR-0018-内容定义按声明扩展.md) 与 [ADR-0022](../../../decisions/ADR-0022-内容清单的家是数据文件.md)，而是补上它们之间那一格。
- [ ] 可核对：被放弃的候选写明了，含「每处各自判断」这一条与它的代价。
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL。

### US-002：五样东西改成加一种只要多一条数据

**描述**：作为以后要加内容的人，我想要元素、恶劣天气、建筑类别、生产渠道、委托类型都能只靠加数据扩展，以便不为了一种新天气去改代码。

**验收标准**：

- [ ] 可核对：[`技能系统`](../../../design/技能系统.md)的元素那一格不再是定长取值，改成指一份「元素 → 它施加哪条状态」的外置声明。
- [ ] 可核对：[`天气系统`](../../../design/天气系统.md)与正典两处对恶劣天气的说法改成只写起步量与选取判据，名字不再当成封闭清单。
- [ ] 可核对：[`建造系统`](../../../design/建造系统.md)的建筑类别改成内容，而**带新功能读口的那一半仍归代码**，两者在文档里分得开。
- [ ] 可核对：[`生产系统`](../../../design/生产系统.md)的渠道与[`任务系统`](../../../design/任务系统.md)的委托类型各写明加一种要填哪几格、不改判定。
- [ ] 可测试：委托那条按名字写的编队规则（哪一类允许主角单人）改成由委托类型自己声明，构造第四类时它答得出来。
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL。

### US-003：两样东西写明是代码的事，mod 加不了

**描述**：作为读文档的人，我想要知道技能的作用目标与形态加一个取值必须写代码，以便不去数据文件里白试一遍。

**验收标准**：

- [ ] 可核对：[`技能系统`](../../../design/技能系统.md)对这两格写明它们是代码结构、加一个取值算一次改设计。
- [ ] 可核对：那处对 mod 承诺的收窄**显式写出来**，并指回 [玩法定位 · mod 的扩展边界](../../../canon/gameplay/玩法定位.md)。
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL。

### US-004：装备那几个上限定下来，各有唯一的家

**描述**：作为要画装备面板的人，我想要知道一件宝物最多几条词条、几个孔、能强化到几级，以便界面上格子数有依据。

定值：主词条 1 条；副词条最多 3 条；宝物孔最多 3 个；强化最多 5 级。

**验收标准**：

- [ ] 可核对：这几个数各只写在一处，[`装备系统`](../../../design/装备系统.md)的边界那一节不再说「家在正典与本页」两处都有。
- [ ] 可核对：每个数旁边写明它为什么是这个数，其中宝物孔那一条要指得回宝石的起步量。
- [ ] 可核对：各档稀有度给几个基础孔、强化每级开几个附加孔仍留在[数值模型](../../../design/数值模型.md)的尚未给值表，本需求不给。
- [ ] 可测试：宝物孔数超过上限的定义载入被拒；强化到上限后再强化被拒。
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL。

### US-005：同稀有度差距小，而拿到好东西仍然爽

**描述**：作为玩家，我想要同一稀有度的宝物不会开出废品，同时拿到好东西那一下有看得出来的惊喜，以便刷装备既不挫败也不无聊。

原则：**随机决定「你拿到的是什么」，不决定「它有多少」。**

**验收标准**：

- [ ] 可测试：副词条里正负各几条**按稀有度固定、不随机** —— 低档 1 条负面，中档 1 正 1 负，高档 2 正 1 负；负面永远只有 1 条。构造一件正负条数不符的实例时被拒。
- [ ] 可核对：[`装备系统`](../../../design/装备系统.md)立一条约束形式 —— 单条副词条的掷定波动不得大到让同稀有度同品质的两件差出一个品质级差。
- [ ] 可核对：同一份里立第二条 —— 品质的级差必须大于同级内的掷定波动，否则「这件是传奇」在面板上看不出来。
- [ ] 可测试：宝物定义的光环必须是机制而不是「某属性加一个百分比」，只声明数值修饰的光环载入被拒；判据与[`技能系统`](../../../design/技能系统.md)那条「改机制不只是改数字」同一条。
- [ ] 可核对：[`界面系统`](../../../design/界面系统.md)写明品质与稀有度要在掉落那一刻就看得出来，不用进背包比对。
- [ ] 作者实机确认：掉落一件高品质与一件普通品质，不点开就分不分得出来。
- [ ] 可核对：那两条新约束登记进[数值模型](../../../design/数值模型.md)的尚未给值表，值归 `GP-7`。

**最低那一档是过渡品，这是刻意的。** 它只有一条正面主词条与一条负面副词条，净收益可能接近零 —— 所以玩家一眼看得出该早点换掉，而「稀有度」这条轴从第一件宝物起就有分量。**不给它开纯增益的口子**：那会撞破 [ADR-0011](../../../decisions/ADR-0011-纯增益装备的窄例外.md) —— 那条窄例外的对象是几件唯一装备，而最低档是一整档。**也不靠「把负面幅度压得很小」来缓解**：那是个值不是结构，压多小要等 `GP-7`，于是「低档有没有用」在给值之前一直没有答案。

### US-006：作物阶段数由每种作物自己定

**描述**：作为要加作物的人，我想要一种作物自己声明它有几个生长阶段，以便做得出三天成熟的速生菜。

形状：阶段序列第一个必须是种子、最后一个必须是成熟可收，中间几个由这种作物自己定，最少就这两个。成熟是终态、不带天数。

**验收标准**：

- [ ] 可测试：只声明种子与成熟的作物载入成功；少于两个阶段、第一个不是种子、最后一个不是成熟，三种各一条载入被拒。
- [ ] 可核对：[`地块系统`](../../../design/地块系统.md)里「最短生长周期」那个算出来的数字**删掉**，它由每种作物自己的声明算出来。
- [ ] 可核对：[数值模型](../../../design/数值模型.md)那一行不再要求「五个阶段各几天」，也不再复述最短周期。
- [ ] 可核对：[场景绘制约定](../../../production/场景绘制约定.md)的作物交付改成「按它声明的阶段数各一张，加一张枯死」，节名不再带张数，引用它的地方一并改过。
- [ ] 可测试：声明的阶段数与交付的素材张数对不上时报错，并说清缺哪一张。
- [ ] 可核对：`python tools/check_docs.py` 0 FAIL。

**描述**：作为以后要做回收机的人，我想要它现在就有编号与一条护栏，以便本轮定下的那几个数不会把它堵死。

## 5. 功能需求

- FR-1：系统必须为每一份取值集写明它归数据、归代码、归一个数还是归作者。
- FR-2：归数据的取值集，系统文档必须只写选取判据、不列名字。
- FR-3：归代码的取值集，系统文档必须写明加一个取值要改哪里。
- FR-4：是一个数的取值，必须只写在一处，且代码不留能用的默认值。
- FR-5：元素必须声明它施加哪一条状态，缺声明载入报错。
- FR-6：建筑类别必须与建筑的功能读口分开，前者是内容、后者是代码。
- FR-7：委托类型必须自己声明它允不允许主角单人出征。
- FR-8：一件宝物必须恰好有一条固定主词条。
- FR-9：一件宝物实例的副词条正负条数必须由它的稀有度决定，不随机。
- FR-10：一件宝物实例的负面副词条必须恰好一条。
- FR-11：一件宝物的光环必须改变一条机制，只给数值修饰的定义载入被拒。
- FR-12：掉落那一刻必须能看出这件东西的品质与稀有度。
- FR-13：一种作物必须声明一个以种子开头、以成熟结尾的阶段序列。
- FR-14：成熟阶段必须不带天数。
- FR-15：作物素材的张数必须等于它声明的阶段数加一。
- FR-16：全部敌人定义合起来必须覆盖到每一种对策，缺一种载入报错并说清缺哪一种。

## 6. 非目标

- **不改代码。** 本轮全部产出是文档与决策记录；载入校验与那几条测试各归自己的落地编号。
- **不做装备回收机的设计。** 只立编号与护栏（US-008）。
- **不给那几个上限之外的装备数值。** 各档基础孔数、强化每级幅度与代价、副词条取值区间都仍归 `GP-7`。
- **不改已有的任何一个接口常量。** 宝物栏格数与每个技能的孔数照[角色与成长 · 装备：宝物与宝石](../../../canon/gameplay/角色与成长.md)不动。
- **不做重掷与洗练**，也不做「刷到极品」那条路。这是本轮平衡方案刻意放弃的一样东西，理由在 US-005：波动窄换来的是不开废品，两者只能选一个。
- **不逐处清理自计数与副本。** 普查时查出一批验收里写着条数的地方（加一个取值后它照旧通过、只是保证范围静默变窄），以及品质级数、委托档位这类在几处各有一份的散文副本。它们不致命，本轮不动，另行记账。
- **不动 `archive/` 与已接受 ADR 的背景。**
- **不改内容规模基准里的任何起步量。** 装备件数会长，但那是内容，归 `GP-89`。

## 7. 界面与表现考虑

- 装备那几个上限直接决定面板要画几格：一件宝物旁边是一条主词条、最多三条副词条、最多三个孔位。排版归 `UI-16`，本需求只给数。
- 掉落那一刻要看得出品质与稀有度（FR-12）。具体怎么显示（描边、底色、图标角标）归[`界面系统`](../../../design/界面系统.md)与作者实机定；本需求只要求「当场看得出」，不指定做法。
- 作物阶段数放开之后，同一片地里不同作物的阶段数不一样，所以「这一格熟没熟」不能靠阶段序号判，只能靠「到了成熟那一阶段」。这条[`地块系统`](../../../design/地块系统.md)已经是这么写的，本需求不改它。

## 8. 技术考虑

- 那条新政策**只约束数据的形状，不约束 C# 怎么建模** —— 与 [ADR-0018](../../../decisions/ADR-0018-内容定义按声明扩展.md) 同一条边界，要显式写上，否则那份 ADR 会被读成一条代码规范。
- 归为内容型的那几样落在代码仓 `data/`，而那条载入路径本身还不存在，进度查[待办台账](../../../spec/issues/README.md)。**所以本轮只定形状，不写数据文件** —— 往没有读者的文件里写内容等于白写。
- 元素改成外置之后，正典那条「异常状态与元素一样多」的推论仍然成立（它本来就不自己写一个数），不需要跟着改。
- 一个观察，**是推断未实测**：按本轮定的上限，一个角色满配的孔位总数远多于宝石的起步量，所以起步内容下多数孔会空着。这不是本轮的问题（起步量归 `GP-89`），但给值那一轮要看一眼，否则「强化开孔」这条回报摸不到。验证办法是等宝石内容存在后数一遍。
- 改[`地块系统`](../../../design/地块系统.md)与[场景绘制约定](../../../production/场景绘制约定.md)会动到被按名引用的节名，所以要跟着扫一遍引用；`python tools/check_docs.py` 的节名引用那一条会报出漏改的。
- 动了正典节的正文之后，上游指纹会报「引它的那几处要复核」，复核完跑 `--repin` 重录。

## 9. 待确认问题（阻塞项）

**无。** 最低那一档宝物的定位已经答掉，结论与被放弃的两条路都写在 US-005 里。

## 10. 成功判据

- 随便挑一份系统文档里的一格取值集，照那条新判据能在一次问答内定出它归谁，不用翻别的文档。
- 本轮归为内容型的那几样，各自能写出一句「加一种要填哪几格」，而那句话里不含「改代码」。
- 装备那几个上限在全库各只出现一次，`python tools/check_docs.py` 的节名引用与代码路径两条都不报。
- 「对策」这个词在正典与设计侧指的是同一份取值，搜两个仓加 `.kiro` 没有短一项的副本。
- 本轮结束时 `python tools/check_docs.py` 0 FAIL，且本轮新立的编号在台账里各有一行。
