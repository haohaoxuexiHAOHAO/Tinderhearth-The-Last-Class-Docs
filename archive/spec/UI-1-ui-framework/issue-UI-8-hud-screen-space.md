# UI-8：关卡 HUD 的屏幕空间部分

## 目标

侧视关卡里玩家能一眼看清自己的资源、技能位、目标进度与队友状态，且这些东西不压掉屏幕中间那块该看角色的区域。

## 来源

- PRD：[`spec/prd-ui-framework.md`](prd.md) 的 `US-007`（屏幕空间那一半；世界空间部分在 `UI-9`）
- 取 HUD 当样板界面由作者 2026-08-30 定。理由：它落在全游戏最挤的一块地方 —— 640×360 在侧视 2 倍缩放下有效视野只有 320×180。

## 依赖

`UI-6`（层级与排版单位）、`UI-7`（修饰键组合的当前组数据）、`ART-4`（占位素材）。

## 第一步：验收脚手架（2026-08-31 已落地）

HUD 要加在一个**有会动的世界**的场景上，而本条自己的验收标准就写着「看 12px 文字**在动态下**
读不读得清」—— 没有那个场景，这条签不掉。同一个场景也是 `UI-5`（相机取景与手感）、`UI-7`
（知道自己按的是哪个技能）、`ART-4`（占位件在 640×360 下看得出布局意图）三条实机确认的落点，
所以它先做，作为本条的第一步而不是另立编号（作者 2026-08-31 定）。

已落成 `src/World/CameraHarness.cs`：可拼接地面、5 格／20 格的格线（横向移动没有它看不出来，
是存图看出来的）、画出来的地图边界与可建造区边界与推镜触发带、15 个 32×32 剪影（数量按本条
「同屏 10–15 个敌人时 HUD 不遮挡」那条取）、一个走 `InputRouter` 移动的角色（侧视用侍武士精灵
表、俯视用占位剪影），加一排调试键（`F1` 视角／`F2` 建造／`F3` 震一下／`F4` 震动开关／`F5` 敌群
聚拢／`F6` 打印 HUD 排版／`F7` 队友数 4↔0／`O` 目标进度三态／`G` 手柄预览（不接手柄也能看手柄呈现）／
`F9` 演出／`F10` 打印数值／`F11` 调试文字）。存图入口 `python tools/harness_shot.py` 两种视角各存一张，
**排 HUD 时靠它复核**。

> 目标态用 `O` 而不是功能键：原先押 `F8`，而 `F8` 是 Godot 编辑器「停止运行项目」的快捷键、
> **游戏窗口有焦点时也照样生效**（[godotengine/godot#94713]），于是从编辑器起工程一按 `F8`
> 进程就直接关掉，看起来像程序自己崩了（作者 2026-08-31 实机撞到）。这些调试键不过 `InputMap`，
> 绑定表那套核对管不到，故另加守卫 `check_input_map.py::check_harness_debug_keys` 盯着，见「偏离」。

## 验收标准

- [x] 有一个能走能打的验收场景，两种视角都跑得起来且引擎无报错 —— 见上，`harness_shot.py` 存图复核
- [x] 主角 HP／SP／MP 与体力常驻可见 —— 四条一行一根，标签沿用正典缩写加「体力」
- [x] 6 个技能位可见并有冷却表现；手柄修饰键按下时显示当前那一组对应哪三个技能 —— 一行横排分两组，按住扳机时那一组三格连着高亮，记号由绑定表推出
- [x] 目标进度常驻可见（还差几个素材、还剩几个来源点）；为 0 或已达成时仍显示而不隐藏（[战斗与关卡](../../../canon/gameplay/战斗与关卡.md)要求始终可见）—— 三种态各有判据
- [x] 队友状态可见，容纳编队上限 4 名学员；队友为 0（单人采集）时该区收起而不是留空槽
- [x] 同屏 10–15 个敌人时 HUD 不遮挡角色所在的可读区 —— 脚手架 `F5` 把 15 个剪影收拢到视野里，存图与「四块都不压角色可读区」判据两头核
- [x] 显示的数值全部由视图模型传入，代码里没有任何写死的数字（`GP-2` 的参数表不在本条落地）—— 静态核加行为核，见实现笔记
- [x] 没有绝对像素坐标，全部锚点与容器 —— 撑开逻辑宽度后逐块量位移
- [x] 作者实机确认：打开样板场景，看 12px 文字在动态下读不读得清、HUD 有没有压掉该看的东西 —— 2026-08-31 作者实机（键鼠）确认：动态下 12px 中文可读、四块 HUD 未压角色可读区，「除按 `F8` 外没发现问题」。`F8` 是脚手架调试键撞了编辑器停止键、不是 HUD 缺陷，已定位根因并修掉（见「偏离」）。同一轮作者要求技能栏去数字并收紧，已改（见「设计决策」）；键鼠模式（作者所测）现在是干净图标无数字，**手柄面键提示叠图后的可读性尚未用手柄实机看过**，记为待确认第 4 条

放置与配色已定（见「设计决策」），存图在代码仓 `logs/art/harness-{TopDown,SideView}-*.png`。

## 实现笔记

### 设计决策

**像素字体与主题先落地。** `assets/fonts/fusion-pixel-12px-proportional-zh_hans.ttf`（[ADR-0008]
选定款，版本与 SHA256 都钉在素材登记表里）。十项渲染属性**设在 `.ttf.import`、期望在
`rules/Ui/PixelFont.cs`、实际值由引擎自己报** —— 三处独立才互为量具，同源的守卫改错设置时判据会
跟着一起改掉。字体装成 `ThemeDB.FallbackFont`（全局回退），于是忘挂主题的界面也拿到像素字体而不是
悄悄退回引擎默认字体。

**量在规则层，节点在引擎层。** 排版量落 `rules/Ui/HudLayout.cs`（块尺寸、贴哪条边、占屏比例、
可读横带、角色可读区），显示的量走 `rules/Ui/HudViewModel.cs` 传入，占位配色落
`rules/Ui/HudPalette.cs`，按键记号落 `rules/Ui/InputHints.cs`（**从绑定表推**，改键位提示自动跟着改）。
结果是 `src/UI/LevelHud.cs` 里**除 0 与 1 之外一个数字字面量都没有** —— 于是「界面里没有写死的数」
从一句自觉变成可以机器扫的规则。

**两条会静默退化的规则各有两道核**，执行体 `tools/check_hud.py`（自证 `selfcheck_hud.py`）：

| 规则 | 静态核 | 行为核 |
| --- | --- | --- |
| 没有绝对像素坐标 | 扫界面源码：无位置类 API、无逻辑分辨率常量、无 `TextureFilter` 覆盖 | 把窗口改成 1298×720（逻辑 **649**×360，奇数）再逐块量位移：左锚点应 0，右锚点应 Δ；四块全落整数像素 |
| 数值全部由视图模型传入 | 扫界面源码：除 0 与 1 外无数字字面量 | 灌三份不同的量，核条长等于自己算的期望像素数 |

只有静态核不够：界面完全可以拿视图模型当摆设、画一根固定长度的条。只有行为核也不够：它证明不了
「下一个人不会顺手写个 100 进去」。

**放置取四角贴边**（作者 2026-08-31 从两套候选里选定，另一套是「底边一条、技能居中」）：目标左上、
队友右上、资源左下、技能右下。两条好处是算出来的 —— 贯通两端的可读横带 **640×238**（占屏高 66.1%），
HUD 占屏 **9.05%**；而且**一个居中锚点都不用**，于是任何逻辑宽度下四块都落在整数像素上，判据从
「只允许居中有半像素」变成「一个都不许有」，判得更死。没选的那套**连代码一起删掉了** ——
留一个死方案在枚举里，迟早有人以为它还在用。

**6 个技能位一行横排**（同日作者定，此前是两行三列）。`FR-17` 靠两样东西成立：按住修饰键时那一组
**三格连着高亮**（横排下比两行更像「一组」），加每组前面的「L」「R」记号列告诉玩家没按住时哪三个归
哪个扳机。横排后技能块从 80×76 变成 160×40，压在屏幕底边、与资源块同一条基线 —— 底边那条线本来就
被资源块占着，技能条贴上去不多占纵向空间，可读横带因此从 234 涨到 238。

**键鼠去数字、去「L」「R」记号列，技能块两步收紧到 112×24**（作者 2026-08-31 两次实机后定，尺寸演进
全程可复算：两行三列 80×76 → 横排带数字与记号列 160×40 → 去键鼠数字 136×40 → 去提示行 136×24 →
去记号列 112×24）。

第一步**键鼠不画数字键**：数字键 `1`–`6` 与六个槽位从左到右一一对应，再在每个槽下画一遍数字只是给
屏幕底边添一行字；而冷却中的槽记号本就为空，那一行于是显示成「1 3 4」这种断号，比不画更糟。故键鼠
模式下六个槽**一个记号都不画**（数字绑定仍由绑定表持有，改键位后手柄提示与实际按键照样同源）。手柄
不同，`LT`／`RT` 加面键推不出来，那个方向记号照画，但**叠进 16px 图标内**而不另占一行。

第二步**去掉两组前的「L」「R」记号列**：那两个 12px 的列在键鼠下永远是空的（作者盯着的正是这块空白）。
去掉后手柄辨「哪三个归哪个扳机」靠三样 —— 两组之间那一个栅格的间隔（看得出是 3+3）、按住扳机时那一组
三格连着高亮（`FR-17`）、每个图标内叠的面键记号；左组＝左扳机、右组＝右扳机是位置约定，按住任一扳机时的
高亮会当场教会玩家。**这一步把 `FR-17` 的呈现从「显式文字标签」改成「间隔＋高亮＋约定」**，是可回退的取舍：
不清的话把记号列加回来即可（见待确认 4 的退路）。

两步之后技能块由 160×40 收到 **112×24**，HUD 占屏从 9.05% 一路降到 **7.43%**。可读横带仍是 640×238 ——
底边被 40px 高的资源块占着，技能块变矮不改变那条线。

**配色按占位那套走**（作者 2026-08-31 认了推荐）。六色（暖炭底／面板／边／正文／次要／强调）
**沿用 [ADR-0008] 那套字体对比工程的配色**，理由是连续性 —— 作者判定「12px 可读」时看的就是那个
背景上的那个字色。四条资源色是新加的，按[像素绘制原则 §4]「明度先于色相」挑，四档明度两两差
≥ 0.115（有测试盯着），于是红绿难分的人也分得出来。**它仍标为占位、仍归 `DOC-2` 定稿**：认的是
「先按这套走」，不是「这就是最终色板」。`PixelColor` 类型**刻意没有 alpha 字段**：半透明遮罩画上去
就是屏幕上的插值像素，与半透明素材同一后果。所以冷却表现用**不透明色遮住一部分**而不是压暗。

**`ART-3` 本轮做掉了，不记账。** 它原先卡在「依赖字体进仓」，而字体今天进仓 —— 如果只记账，从今天起
发行包里就是「有字体没许可证」的状态，那不是将来的风险而是当下的缺陷。落点本来就存在（`verify.py`
已在解 `.pck` 逐条看清单），加一条判据加一条自证用例即可。

### 偏离

**队友格里没有名字。** 20px 的头像框装不下 12px 的两个汉字，而 [ADR-0008] 已排除更小的字号。
识别改由头像本身承担 —— 那正是[人物 · 形象记忆点设计]要求每个角色有独立剪影与签名色的用处。
于是倒地状态另加一个记号盖在头像上，不只靠颜色（§4：相反语义要有不同符号）。

**脚手架的调试文字改成默认隐藏**（`F11` 打开）。本条要判的正是「HUD 有没有压掉该看的东西」，
而那块文字自己就压着左上角 —— 它在场，那条判断就做不了。数值仍可按 `F10` 打进日志。

**目标态调试键从 `F8` 换成 `O`，并补了守卫。** 作者 2026-08-31 从编辑器起工程、按 `F8` 想切目标
进度三态，进程却直接关掉 —— 看起来像程序崩了。**修根前先定位根因**：脱开编辑器单独跑（`--diag-keys`
自注入 `F8` 与 `O` 两个事件），两键都正常触发目标态轮换、进程退出码 0，证明处理器本身无辜；问题在
键位 —— `F8` 是编辑器「停止运行项目」，游戏窗口有焦点时仍生效（[godotengine/godot#94713]）。诊断代码
验完即删。这些调试键在 `_UnhandledKeyInput` 里直接匹配原始键码、**不过 `InputMap`**，绑定表那套「一份
来源 + 逐条核对」一条都管不到，谁挑了一个编辑器要用的键也没人拦。于是加执行体
`check_input_map.py::check_harness_debug_keys`（自证 `selfcheck_input_map.py` 两条新用例）：调试键
**登记制** —— 每个键写明用途，代码里多一个或少一个都判失败；押在编辑器要用的键（`F8`）上直接判失败。
只列黑名单挡不住下一个人挑另一个坏键，登记制会逼着他在守卫里写一行。这是脚手架键位第一个执行体，
按「输入键」的性质挂在 `UI-7` 的输入守卫里，而非另立文件。

**`UiRoot.Register` 顺带修了根。** 它原先靠「先设锚点再 `AddChild`」这个顺序才铺得满，
而顺序本身没有任何东西守着（详见[踩坑记录 40](../../../reference/踩坑记录.md)）。改成
`SetAnchorsAndOffsetsPreset` 之后与顺序无关。这不是顺手扩范围：本条的 HUD 撞的就是同一个机制，
不修根的话下一个面板会再犯一次。

**`gen_placeholders.py` 顺带修了根。** 它每次重新拼一份完整登记表，会**静默抹掉**手工维护的
段落 —— `ART-4` 那段「可进发行包」判据说明与本轮新加的「字体」一节，跑一次生成器就没了。
改成只重写「生成槽位」那一节。

**守卫自己有过一个盲区，是自证撞出来的。** 「排版算式与实现漂移」这条原先只比**实际矩形与预测
矩形**，而那个比对**只对贴下边或贴右边的块有效**：贴上边的块偏移与尺寸无关，算式偏大时块只往下
多长几像素、位置一点不变，两边照样对得上。自证用例第一版恰好挑了贴右上的队友块，于是它通不过 ——
守卫真的漏了。补法是加一条**病根级判据**：规则层的算式与**容器自己要的**最小尺寸逐块相等
（`Control.GetMinimumSize()`，不含 `CustomMinimumSize`）。补完之后任何一块的漂移都逃不掉，
与贴哪个角无关，而且两条用例（贴下边一条、贴上边一条）各撞一次证明了这件事。

### 权衡

**目标进度块按最长那句定宽（11 个全宽汉字 = 160px 外框，占逻辑宽度四分之一）。** 好处是达成态
不会被截断，而那正是最需要看清的时刻；代价是常态显示「素材 2／5」时右边空着一大截，看起来偏空。
另一条路是让它随内容伸缩，代价是占屏与可读区的预测失效，而那两个数是选放置方案的依据。
**这一条是可以改的排版取舍，归 `DOC-2`。**

**块尺寸取定值而不是随内容伸缩。** 定值让规则层的预测等于实际，于是占屏与可读区算得出来也测得出来。
内容比框长时截断。

**居中锚点会落在半个逻辑像素上，这条留了个记录但没测完。** 逻辑宽度是奇数时（`UI-3` 实测 3840×2130
得到 649×360）居中偏移必然是 .5 —— 这一半**实测过**：删掉之前那套候选前量到技能块落在 −35.5。
「×2 下正好 1 物理像素没后果、×3 下是 1.5 会让素材边界离开物理像素格」这一半**是推断，没实测**，
验证办法照 `CameraProbe` 那套：在 ×3 窗口下给居中块截图量最小同色跑长。四角这套一个居中锚点都不用，
所以本条不受影响；将来真要用居中，先补那次测量。记录写在 `HudAnchor` 的注释里，加一条测试挡住
「有人把居中加回来」。

### 待确认

1. ~~字体算不算「发行包只允许作者自绘」那条的例外~~ **已定案（作者 2026-08-31 确认：字体算例外）。**

   登记表的 `可进发行包` 字段判而不是按目录判，否则会把字体一起拦掉。**这条不取消 OFL 义务** ——
