## 实现笔记

### 设计决策

- **模糊点**：次日的天气该在结算的哪一步定下来。那串步序里没有一步天生属于天气。
- **选择**：并进「日期推进，可能翻季或翻年」那一步。
- **理由**：天气是那一天的一个属性，与日期同时成立。放到后面任何一步都会出现「这一天已经开始了但还不知道它的天气」那个空窗，而那一步之后就有东西要读它。

另一处：侵袭档挂事件的**前置条件**而不是权重。权重那一格已经有失衡档位这一个来源，再挂一个就要定「两个偏移怎么合」；前置条件本来就是一组判断，多一条不改变它的形状。代价是档位对频率的影响成了阶梯式而非连续 —— 反而更容易被玩家读出来。

### 偏离

- **方案怎么说**：PRD 把正典改动与索引登记分给 `DOC-109` 与 `DOC-111`，排在本条之后。
- **实际怎么做**：那两条与本条同一轮做掉了。
- **为什么**：检查器有两条判定卡在那里 —— 一份长期规格必须被至少一份正典链接到、每份文档必须从 README 走得到。本条交付的文档不接上正典与索引就过不了门禁，所以它们不是「之后」而是「同时」。

### 权衡

考虑过让天气声明自己的新量（一个「能见度」或「湿滑度」），写起来最直接；放弃它是因为那等于每加一种天气都可能往战斗里加一条轴，最后没人说得清一个角色的输出由多少来源决定。改成只许引用派生表里已有的量之后，表达力少一点，而「一个量只有一个家」保住了。

也考虑过给天气新建一个状态载体，放弃理由在文档的取舍那一节。

### 待确认

无。六条玩法取舍与抗性、设备两处都由作者定过。剩下的全是要等实现或等作者实机看的，各自挂在台账上。
