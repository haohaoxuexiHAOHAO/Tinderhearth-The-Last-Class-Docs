# PRD：剩下那批设计空白，分批补完

## 1. 概述

系统文档的文档侧已经全部交付（进度看[待办台账](./issues/README.md)的「系统深化顺序」）。剩下没写的东西分三类：**具体内容**（有哪几种作物、哪几件宝物这类）、**系统文档自己写明还没定的洞**、**叙事里只划了空间没写内容的那几处**。它们散在十几份文档里，没有一份总览，所以每次要问「接下来写什么」都得重新扫一遍全库。

**但这一轮真正要修的不是任何一项空白，而是一个机制性漏洞。** 全库有两处按类型点名内容的地方 —— [玩法定位 · 内容规模基准](../canon/gameplay/玩法定位.md)那张表给每类内容定起步量，而台账 `ENG-5` 那份「要外置的内容类型」名单点名另一批。**两份的行对不上，差集里的那几类既没有清单也没有任何编号在等它们**，而这件事没有任何东西查得出来。不先堵这个洞，后面每批补完内容，下一次往基准表加一行还是会掉。

## 2. 目标

- **基准表的每一行都指得到一个台账编号**，而且「某一行没人接」这件事由检查器判得出来 —— 从查不出来的错变成查得出来的断链。
- 现在掉在地上的那几类内容各有一个编号，备注写明它缺什么、卡在谁。
- 剩下的空白按批次归好，每批有写得出来的边界与卡点，作者可以逐批决定做不做。

## 3. 上游约束

- [玩法定位 · 内容规模基准](../canon/gameplay/玩法定位.md)：那张表给各类内容定起步量，并写明它是全部平衡判据的算账基准。**这是本需求第一批要对齐的对象** —— 对齐动的是「谁在等它」，**那张表里的量一个都不改**。
- [玩法定位 · mod 的扩展边界](../canon/gameplay/玩法定位.md)：内容一律数据外置、规则不外置。**约束内容清单最终落在哪一层**，也是下面待确认问题三的依据。
- [ADR-0018](../decisions/ADR-0018-内容定义按声明扩展.md)：内容定义按声明扩展、一张表、缺字段报错。**约束新点名的内容类型要按同一形状声明，不为它们另开结构。**
- [ADR-0010](../decisions/ADR-0010-文档体裁与系统文档归位.md)：文档体裁按寿命分、位置就是体裁。**约束这一轮新增的文字往哪写**；它**没有回答内容清单该落哪儿**，那正是待确认问题三。
- [ADR-0009](../decisions/ADR-0009-编辑器主导的开发模式.md)：参数唯一来源是场景与资源，素材与摆位归作者。**约束分工** —— 后面批次里凡是素材与实机验收那一半都归作者，本 PRD 不把它们写成代码任务。
- [待办台账](./issues/README.md)：**全库唯一的状态所在处**。本 PRD 一处都不复述进度与卡点，只写链接。

## 4. 用户故事

**本节只覆盖第一批。** 后面几批的边界在「11. 批次」那一节，各自开始时再写自己的故事 —— 一份 PRD 装八批的故事会让它变成一份查不动的清单，而那与它要修的毛病同形。

### US-001：基准表每一行都指得到一个编号

**描述**：作为三周后要接着写内容的人，我想打开基准表就看出每一行由哪个编号在等，以便不用重新扫全库才知道「这一类有没有人接」。

**验收标准**：

- [x] 可核对：逐行核过，**每一行的说明里都有一个反引号里的台账编号**
- [x] 可核对：对齐只加编号引用，那张表里的**量一个都没改**（`git diff` 里没有数字变动）
- [x] 可观察：编号指向的台账行真的存在（不是写一个还没开的号）

### US-002：掉在地上的那几类内容各有一个编号

**描述**：作为作者，我想知道技能书、知识书、宝物副词条候选池、家畜、鱼、料理配方与设备这几类各归谁，以便决定什么时候写它们。

**验收标准**：

- [x] 可观察：台账里各有一行，状态词取自那张状态词表（不自造第六个）
- [x] 可核对：每一行的备注写明**它缺什么**与**卡在谁**，不复述基准表里的量
- [x] 可核对：这几行都被基准表对应那一行引用（与 `US-001` 互为对账）

### US-003：`ENG-5` 写明它覆盖到哪里

**描述**：作为实现内容外置的人，我想知道 `ENG-5` 那份名单是不是全部内容类型，以便不把「它没点名」误读成「它不用外置」。

**验收标准**：

- [x] 可核对：`ENG-5` 的备注写明它覆盖哪一批、**没覆盖的由哪几个编号接**
- [x] 可核对：那句话里不列具体类型清单（清单的家是基准表，这里写链接）

### US-004：守卫 —— 基准表有一行没人接就报失败

**描述**：作为把这个洞堵上的人，我想让检查器判出「某一行没有编号引用」，以便下一次往基准表加一行时漏登记会当场被拦住。

**验收标准**：

- [x] 可核对：`python tools/check_docs.py` 里新增一条检查，正常情况 0 FAIL
- [x] 可测试：**从某一行里去掉编号引用之后检查器报失败**，补回来就过（失败路径与成功路径各撞一次）
- [x] 可观察：它像其余检查一样自报覆盖量（核了多少行），而不是只在失败时说话

### US-005：手环示意底图有个家

**描述**：作为将来要画那张底图的人，我想找到一个编号在等它，以便它不再是两份文档都委托出去、两侧都没接的状态。

**验收标准**：

- [x] 可观察：台账里有一行等它
- [x] 可核对：[`地图与导航系统`](../design/地图与导航系统.md)里那句委托改成指那个编号，而不是指「界面侧与美术侧」

### US-006：下雨算不算自动浇水在正文里也有落点

**描述**：作为读地块那一份的人，我想在正文里就看到这件事还没定，以便不把「文档没写」读成「它不存在」。

**验收标准**：

- [x] 可核对：[`地块系统`](../design/地块系统.md)的边界那一节写明它未定并指到编号
- [x] 可核对：那句话里不复述天气系统的进度（状态只在台账）

### US-007：端到端 —— 这个洞真的堵上了

**描述**：作为要相信这一轮有效的人，我想验证「往基准表加一行却没人接」从此查得出来，以便下次不靠人记。

**验收标准**：

- [x] 自动化：`python tools/check_docs.py` 0 FAIL，且新守卫的覆盖量大于零（**覆盖量为零等于它什么都没判**）

## 5. 功能需求

- FR-1：[玩法定位 · 内容规模基准](../canon/gameplay/玩法定位.md)那张表的每一行必须有一个台账编号引用它。
- FR-2：检查器必须判得出「某一行没有编号引用」。
- FR-3：检查器必须自报这条检查核了多少行。
- FR-4：现在没有编号的那几类内容必须各有一行台账条目。
- FR-5：`ENG-5` 必须写明它覆盖哪些内容类型、其余由哪几个编号接。
- FR-6：手环示意底图必须有一个台账编号。
- FR-7：「下雨算不算自动浇水」必须在 `design/` 正文里有一处落点。
- FR-8：本轮新增的编号不得复用任何已删除或已关闭的号。

## 6. 非目标

- **不写任何一类内容的具体清单。** 这一批只动「谁在等它」，写清单是批 4 起的事。
- **不定任何数值。** 参数表与[数值模型](../design/数值模型.md)这一轮一个字不改。
- **不改代码仓的 `.cs`。** 作者明确要求这一轮先把文档写全；`tools/check_docs.py` 是设计仓的检查器，不在这条里。
- **不改基准表里的任何量。** 改量要重跑推演，那是另一回事。
- **后面几批的用户故事不在本 PRD 里**，见「11. 批次」。
- **不动已关闭的编号。**

## 7. 界面与表现考虑

不适用 —— 这一批全是文档与检查器。后面批次里凡涉及界面与素材的，各自那一批再写，且实机确认一律归作者（[ADR-0009](../decisions/ADR-0009-编辑器主导的开发模式.md)）。

## 8. 技术考虑

- 新守卫加进 `tools/check_docs.py`。那个脚本已经有几条同形检查（节名引用、已关闭编号、术语覆盖），新增一条按同一套路自报覆盖量。
- **怎么认出「基准表的一行」需要先读那个脚本**：它有没有按节取 markdown 表格的现成办法我还没核，**待验证** —— 实现前先读 `check_docs.py`，有现成的就复用，没有就新写一小段并说明为什么不能复用。
- **编号引用的形状可以复用**：「已关闭编号」那条守卫已经在扫反引号里的编号，认法应该能共用，同样**待验证**。
- 一条要当心的：新守卫**不能只在失败时说话**。覆盖量为零的守卫比没有守卫更坏 —— 它会让人以为这件事被守住了。

## 9. 已裁定的三条取舍

**待确认问题已全部答复，本节留答案。** 三条都是产品取舍，不是技术选择。

**一、那几类内容的编号开在 `GP` 域，不新开内容前缀。** 编号前缀那张表是接口 —— 加一个前缀要改那张表、改检查器认的前缀集合，还要换掉全库的引用习惯，换来的只是分类看起来清楚一点。代价写明：`GP` 域会更长，但它本来就是最大的域。

**二、批次照「11. 批次」那一节的顺序走。** 前两批看不见画面，但每一批都在给后面解卡点；而批 2（城区分图）本身就是作者能直接开始画的输入 —— 它排第二不是巧合。

**三、内容清单的家是代码仓 `data/` 下的数据文件，设计仓不写第二份清单**；而「为什么选这几种」写进对应那份系统文档。放弃的两条：`canon/` 下新开内容目录（要改 [ADR-0010](../decisions/ADR-0010-文档体裁与系统文档归位.md) 与检查器的体裁规则，而且数据文件与它迟早对不上）、写进各自的系统文档（那几份自己写着「不定内容」，等于翻掉它们的边界）。

> **第三条要一份 ADR，而且要在批 4 开始之前写完** —— 它影响多个系统且难撤销：选错之后要把全部内容清单搬一遍。那笔账记在 `GP-88`（批 4 的编号），不另开编号，因为它是那一批的前置而不是独立待办。

## 10. 成功判据

- 基准表逐行都有编号引用，**且去掉任一行的引用会让检查器报失败**（这条是承重的 —— 没有失败路径就等于没有守卫）。
- 现在掉在地上的那几类内容都有编号，备注答得出「缺什么、卡在谁」。
- `python tools/check_docs.py` 0 FAIL，新守卫自报的覆盖量与基准表的行数一致。
- 三个月后往基准表加一行时，漏登记会被检查器拦住，而不是靠有人记得。

## 11. 批次

**每批一个批次号，顺序即建议的先后。** 各批的进度**一律看[待办台账](./issues/README.md)**，本节只写边界与它为什么排在这个位置 —— 状态写在这里就会有第二个家。

| 批 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| **1** | 内容账目对齐与守卫（**本 PRD 的用户故事就是它**）：基准表逐行接编号、掉地那几类各开编号、`ENG-5` 写明覆盖面、加守卫，外加示意底图与下雨那两笔小账 | 它决定后面每一批的编号往哪落。先做别的，那批新编号还要回头重新归位 |
| **2** | 城区分图与命名（`NR-28`） | 它是[`地图与导航系统`](../design/地图与导航系统.md)那张写死拓扑**唯一缺的输入**，也是作者搭城区场景的输入。不卡任何人，而下游最多 |

| **4** | 经营侧内容清单：作物、家畜、鱼、料理、设备、加工配方 | 它们互相咬 —— 料理要吃鱼与作物，设备要烧燃料。**这一批要连着定一批数值**，所以排在它们各自的产量校准基准存在之后 |
| **5** | 战斗侧内容清单：技能、宝物、宝石、特质、天赋、敌人、异常状态、副词条候选池、两类书 | 量最大且要连着定数值。排在经营侧之后，是因为经营那批能先把「内容清单怎么写」这条路走通 |
| **6** | 事件与叙事载体的内容：小事件、随机事件、气泡语料、日记条目、演出脚本 | 它们的内容要引用前面几批的东西（事件后果调已有入口、日记写的是发生过的事） |
| **7** | 关卡与场景内容：关卡片段、资源点、委托模板 | 片段要作者搭，所以它天然排在俯视与侧视场景本体之后 |
| **8** | 界面剩下那几页：更新公告、开界面的键、设置那几组 | 它们各自读的系统落地了才写得出来；更新公告那一页的「显示什么」其实可以提前 |

**这张表不是范围承诺。** 每批开始前各自确认，作者可以跳过或重排；重排时要连着看上面那一列理由，因为几处先后是输入关系而不是偏好。

## 12. 批 1 顺带查出来的两处

**这一批要修的那个漏洞有第三个实例，做的时候才撞到**，记在这里是因为它证明这个洞不是偶然：

- **[玩法定位 · mod 的扩展边界](../canon/gameplay/玩法定位.md)那句也抄了一份类型清单**，而它同样比基准表短。它是那个清单**该有的家**（正典是最高层），所以没有删掉它，而是写明了两处的行刻意不同、差集在哪、为什么现在不收平 —— 收平归 `DOC-106`。
- **`ENG-5` 备注里那份清单删掉了**：它既不是家（正典那句才是），又比基准表短，属纯副本。
- [ADR-0018](../decisions/ADR-0018-内容定义按声明扩展.md) 的背景里也有同一份清单，**那一份冻结不改** —— 它写的是当时的背景，不是现行事实。

**所以同一份事实原先有四处**：正典那句、`ENG-5` 备注、`ADR-0018` 背景、基准表那些行。删掉一处、写明两处的关系、给差集记了账；`ADR-0018` 按体裁规则不动。
