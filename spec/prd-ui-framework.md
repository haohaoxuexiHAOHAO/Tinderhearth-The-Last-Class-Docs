# PRD：逻辑分辨率与界面结构骨架（`UI-1`）

## 1. 概述

定下逻辑分辨率、缩放链路、相机行为与界面结构骨架，并用**关卡 HUD** 这一个样板界面把骨架验到能实机验收。

现在做的理由有三条，都不是"排到它了"：

1. **`ART-2` 刚把它解锁。** [ADR-0008](../decisions/ADR-0008-中文像素字体选型.md) 给了字号下限 12px、必须整数缩放、以及 Godot 4.7.2 下十项已实测的像素完美字体属性 —— 分辨率的下限从此有依据。
2. **它卡着两件事。** `DOC-2`（界面色彩、尺寸与放置清单）明写依赖本条；美术素材也要等分辨率定了才知道图标画多大、边距留多少。
3. **工程里现在的状态会静默毁掉像素素材。** 2026-08-30 读 `project.godot` 实测：**没有 `window/size/viewport_width/height`**（还是引擎默认 1152×648）、**没有 `window/stretch/scale_mode`**（默认 `fractional`）、**没有 `rendering/textures/canvas_textures/default_texture_filter`**（默认线性过滤）。这三项不改，第一张素材进去就是糊的，而且不会报错。

作者已在立项对话里定了五项，本文按这些写：**逻辑分辨率 640×360**；**范围是骨架 + 一个样板界面**；**手柄 6 技能位走修饰键组合**；**手环是统一容器带标签页**；**建造不做缩放，靠相机滚动与边缘推镜**。

## 2. 目标

- 像素素材与 12px 中文进到工程里就是清晰的，且这件事有可复跑的判据，不靠"看着还行"。
- 相机的五项行为一次定完。正典已点名它们并写明[行为不定下来两种视角会各写一套](../canon/gameplay/玩法定位.md)。
- 界面结构骨架就位：层级与导航栈、栅格与安全边距、锚点规范、输入映射。后续每个界面照它做，而不是各自发明一套。
- 关卡 HUD 做到作者能在实机上判"这一屏读得清"。
- 交出 `DOC-2` 需要的输入：栅格单位、安全边距、字号与行高、图标尺寸档位。

## 4. 用户故事

### US-001：逻辑分辨率与缩放链路落进工程

**描述**：作为开发者，我要让工程按 640×360 的逻辑分辨率整数放大到窗口，以便像素素材与像素字在任何常见分辨率下都不变形。

**验收标准**：

- [ ] 可核对：`project.godot` 有 `viewport_width=640`、`viewport_height=360`、`stretch/scale_mode="integer"`、`default_texture_filter=0`，且 `stretch/mode="canvas_items"` 与 `aspect="expand"` 未被改动
- [ ] 可测试：窗口分别设为 1280×720、1920×1080、2560×1440、3840×2160 时，实际缩放倍数分别是 2、3、4、6，且无非整数倍
- [ ] 可观察：窗口拉成非 16:9 时可视区域按 `expand` 伸缩，界面元素不被裁掉
- [ ] 作者实机确认

### US-002：像素字在 `canvas_items` 下的实测与定论

**描述**：作为开发者，我要确认 12px 中文在 `canvas_items` 拉伸模式下仍是块状像素而不是被重新光栅化成平滑字形，以便 ADR-0008 的结论在真实工程里也成立。

**为什么单独一条**：ADR-0008 的实测是在 `stretch/mode="viewport"` 下做的，而工程用的是 `canvas_items`。两者的文字光栅化路径不同 —— 前者先画 640×360 再整数放大，后者按最终屏幕尺寸画字形。**这是本需求唯一的技术未知项**，且它一旦不成立会推翻整套配置。

**验收标准**：

- [ ] 可测试：同一段中文在 ×2／×3／×4 下截图，字形轮廓的每个像素块边长恰好等于缩放倍数（不出现 1 物理像素宽的笔画）
- [ ] 可核对：结论与所用的字体属性取值写回 ADR-0008 的"未验证"段，成立就划掉，不成立就写明改用哪条路径
- [ ] 可测试：若 `canvas_items` 下无法保住块状字形，改用的替代路径同样跑一遍上面两条
- [ ] 作者实机确认

### US-003：相机五项行为

**描述**：作为玩家，我要相机在两种视角下行为一致且可预期，以便我不会因为镜头突然移动而失去对角色的判断。

**验收标准**：

- [ ] 可观察：俯视跟随主角，有死区（角色在死区内移动时镜头不动）
- [ ] 可观察：侧视为 2 倍整数缩放，有效世界视野 320×180
- [ ] 可测试：相机在场景边界处被钳制，视口不越出地图，边界处不出现空白
- [ ] 可测试：屏幕震动可在设置里关闭，关闭后重击不产生任何位移
- [ ] 可核对：演出镜头能由脚本接管并归还控制权，归还后跟随行为与接管前一致
- [ ] 作者实机确认

### US-004：界面层级、导航栈与手环容器骨架

**描述**：作为玩家，我要打开面板、层层深入再逐层退回时行为一致，以便我永远知道按返回键会回到哪。

**验收标准**：

- [ ] 可核对：层级自下而上固定为 世界 → 世界空间 UI（读条、血条、气泡）→ HUD → 面板 → 弹窗 → 过场遮罩，且有一处集中定义而非各场景自行摆放
- [ ] 可测试：导航栈支持压入与弹出，返回键逐层退出；栈空时返回键不吞掉输入
- [ ] 可测试：手环容器有标签页，且**关卡内操作类标签页被禁用、查看类可用**（正典约束）
- [ ] 可测试：关卡内打开背包时游戏**不暂停**，HUD 仍可见且世界仍在运行
- [ ] 作者实机确认

### US-005：栅格、安全边距与锚点规范

**描述**：作为美术与后续界面的实现者，我要一套写下来的排版单位，以便每个界面不各自发明边距。

**验收标准**：

- [ ] 可核对：给出栅格单位、面板内边距、元素间距、屏幕安全边距四个数，且都是整数并与 16px 基础单位对齐
- [ ] 可核对：给出图标尺寸档位（至少 16px 与 32px 两档），与[像素绘制原则](../production/像素绘制原则.md)的 16px 图标条款一致
- [ ] 可测试：样板界面里没有任何绝对像素坐标，全部由锚点与容器定位（改窗口宽高比后布局不错位）
- [ ] 可核对：这四个数与图标档位同时交付给 `DOC-2`

### US-006：输入映射（键鼠与手柄）

**描述**：作为玩家，我要键鼠和手柄都能完整操作战斗与界面，以便我用哪种设备都不残缺。

**验收标准**：

- [ ] 可核对：`InputMap` 覆盖轻攻击、重攻击、防御、闪避、冲刺、跳跃、交互与 6 个技能位，键鼠与手柄各一套
- [ ] 可测试：手柄的 6 个技能位按**修饰键组合**触发（两个扳机 × 三个面键，作者 2026-08-30 定），且修饰键按下时 HUD 显示当前那一组是哪三个技能
- [ ] 可测试：面板导航在手柄上可用 —— 列表与标签页走焦点移动，网格摆放（建造）走光标移动
- [ ] 可观察：按键提示图标随最后使用的设备切换
- [ ] 作者实机确认

### US-007：关卡 HUD 样板

**描述**：作为玩家，我要在侧视关卡里一眼看清自己的资源、目标进度和队友状态，以便我不必停下来找信息。

**为什么用它当样板**：它落在全游戏最挤的一块地方（侧视 2 倍缩放后有效视野只有 320×180），且约束最密。骨架在这里成立，其余面板就是排版工作。

**验收标准**：

- [ ] 可观察：主角 HP／SP／MP 与体力常驻可见；6 个技能位含冷却表现
- [ ] 可观察：目标进度常驻可见（还差几个素材、还剩几个来源点）
- [ ] 可观察：队友状态可见，容纳编队上限 4 名学员
- [ ] 可测试：读条画在**执行者身上**（世界空间），随角色移动，不在界面角落
- [ ] 可测试：血条只对精英与 BOSS 出现，杂兵没有血条
- [ ] 可测试：伤害数字默认关闭，设置里可开
- [ ] 可测试：同屏 10–15 个敌人时 HUD 不遮挡角色所在的可读区
- [ ] 作者实机确认：打开样板场景，看 12px 文字在动态下读不读得清、HUD 是否压掉了该看的东西

### US-008：端到端验证

**描述**：作为开发者，我要一条走完整条链路的验证，以便这套骨架不是各自单测通过而合起来不成立。

**验收标准**：

- [ ] 自动化测试走完主路径：进入侧视场景 → HUD 出现 → 打开背包（不暂停）→ 打开手环（操作页禁用）→ 逐层返回 → HUD 恢复
- [ ] 覆盖失败路径：导航栈为空时按返回、窗口尺寸小于逻辑分辨率、队友数为 0、目标进度为 0／已完成
- [ ] 测试独立可重复，自己准备与清理场景数据
- [ ] 代码仓 `python tools/verify.py` 全绿（构建、测试、导出、跑产物）
- [ ] 作者实机确认清单：跑导出产物 → 全屏 → 在 1080p 与 1440p 各看一遍 → 确认字清晰、缩放为整数倍、HUD 不挡人

## 5. 功能需求

- FR-1：系统必须以 640×360 为逻辑分辨率渲染。
- FR-2：系统必须只以整数倍把逻辑分辨率放大到窗口。
- FR-3：系统必须对所有纹理使用最近邻过滤。
- FR-4：系统必须保持 `stretch/mode="canvas_items"` 与 `aspect="expand"` 不变。
- FR-5：系统必须让 12px 中文在任何整数缩放下保持块状像素边缘。
- FR-6：俯视相机必须跟随主角并带死区。
- FR-7：侧视相机必须使用 2 倍整数缩放。
- FR-8：相机必须在场景边界处被钳制。
- FR-9：屏幕震动必须可在设置中关闭。
- FR-10：演出脚本必须能接管相机并在结束时归还。
- FR-11：界面层级必须在一处集中定义。
- FR-12：导航栈必须支持逐层返回。
- FR-13：关卡内打开背包时系统必须不暂停世界。
- FR-14：关卡内手环的操作类页面必须禁用。
- FR-15：界面元素必须由锚点与容器定位，不得使用绝对像素坐标。
- FR-16：手柄的 6 个技能位必须由修饰键组合触发。
- FR-17：修饰键按下时 HUD 必须显示该组对应的技能。
- FR-18：按键提示图标必须随最后使用的输入设备切换。
- FR-19：读条必须绘制在执行者所在的世界位置。
- FR-20：血条必须只对精英与 BOSS 显示。
- FR-21：目标进度必须常驻可见。
- FR-22：伤害数字必须默认关闭且可在设置中开启。
- FR-23：基地建造时相机必须支持滚动，并在角色接近可建造区边缘时自动推镜。
- FR-24：可建造区尺寸必须从配置读取，不得写死在代码里。

## 6. 非目标

- **不做除关卡 HUD 之外任何界面的排版。** 手环只做容器与标签页骨架，页内内容跟着各自功能的实现需求走。派工、名册、建造、背包、角色面板、委托板、对话、存档、设置一律不在本条。
- **不做界面色彩、具体尺寸与放置清单** —— 那是 `DOC-2`，它依赖本条的交付物。
- **不改基地可建造区的 40×30 格**。它是正典的场景规模，属经营系统范围；是否扩大已记 `GP-8`。
- **不做其他宽高比与设备适配** —— `UI-2`。按 16:9 设计与验收。
- **不定任何数值**。HP／SP／MP 上限、体力、冷却时长一律引用 `GP-2` 的参数表。
- **不做技能轮盘**。手柄走修饰键组合，轮盘方案已被排除（它要么暂停要么减速，与"关卡内不暂停"冲突）。
- **不做无障碍字号缩放**。设置里那一组归后续；本条只保证 12px 这一档成立。
- **不做持续引导与教学提示层**（正典第一版为否）。

## 7. 界面与表现考虑

**信息层级（自下而上）**：世界 → 世界空间 UI（读条、精英血条、气泡）→ HUD → 面板 → 弹窗 → 过场遮罩。读条与血条刻意归在世界空间层而不是 HUD 层，因为正典要求它们跟着角色。

**侧视的空间预算是本条最紧的约束**：640×360 在 2 倍缩放下只剩 320×180 世界像素（20×11 格）。HUD 必须把中间那块留给角色与敌人，资源与技能位靠边贴角。

**异常态**：目标进度为 0 或已完成时仍显示（显示"已达成，返回入口点撤离"），不隐藏 —— 正典要求进度始终可见。队友为 0（单人采集）时队友区收起而不是留空槽。

**复用**：手环容器与导航栈是后续所有面板的共用件，本条把它们做成可复用节点而不是 HUD 的私有实现。

## 8. 技术考虑

**技术未知项（`US-002`，2026-08-30 已验完，结论如下）**：`canvas_items` 拉伸模式下 12px 字**仍是块状**，×2／×3／×4 的最小同色跑长恰为 2／3／4。所以不必回退 `viewport`。

**承重项与立项时的推测不同**：当时以为靠字体的 `oversampling=1.0`，实测是**最近邻纹理过滤**在起作用 —— 不钉 `oversampling` 结果逐字节不变，而把纹理过滤改成线性则三档最小跑长全部塌到 1。这条对后续界面有直接后果：`default_texture_filter=0` 不只是给精灵用的，它同时是文字清晰的唯一依靠，**任何界面节点局部覆盖 `texture_filter` 都会静默毁掉文字**（已记 `ENG-13`）。

**已实测可用**（2026-08-30，Godot 4.7.2）：`FontFile` 的十项像素完美属性全部存在；`Window.content_scale_stretch = INTEGER` 配 `CONTENT_SCALE_MODE_VIEWPORT` 与 `ASPECT_KEEP` 时整数缩放成立，全屏自动挑最大整数倍并留黑边。这两条来自 `tools/font-preview/` 那套工程的实际运行。

**工程现状**（2026-08-30 读 `project.godot`）：逻辑分辨率、`scale_mode`、纹理过滤三项都还没设，见第 1 节。

**依赖**：`ENG-5` 已落地的"配置从数据读"接缝（`Foundation/Config/GameConfig.cs` + `data/config/game.json`）是 FR-24 的落点，不必新建机制。

**占位素材**：本条的界面素材是占位件，最终由作者用自己的像素资源按槽位替换。三条约束：

1. **开发期不限授权，发行包只允许作者自己的素材与 CC0 素材。** 代码仓是私有单人仓库（作者 2026-08-30 确认），私有持有不构成再分发；真正的分发行为是发行包。所以守卫落在**导出**而不是入仓：`verify.py` 已在解 `.pck` 逐条看清单（`ENG-3`），加一条"包里出现登记为占位的素材即判失败"。
2. **能生成的优先生成。** 面板底、九宫格边框、图标槽位用脚本产出纯色几何件 —— 零授权问题，且一眼可辨是占位，不会被误当成品。真正需要下载真素材的只有角色精灵与动画（手感与 32px 剪影可读性得靠真东西验）。CC0 来源候选：Kenney 全站素材为 CC0（[Kenney · Support](https://kenney.nl/support)）。
3. **占位件的尺寸、帧数与锚点必须就是最终规格**，否则替换等于重做。由素材槽位登记表约束：路径、用途、尺寸、帧数、来源与授权、是否待替换。

`ENG-10`（假像素守卫）的时机因此提前到本轮：台账原文写它"须在第一张素材进仓前就位"，而本条就是放第一批素材的地方。登记表同时补上它缺的那一半（尺寸与槽位比对）。

**HUD 显示的数值从视图模型传入**，UI-1 不读也不搬 `GP-2` 的参数表 —— 那属于各玩法实现需求。测试里注入假值，实机演示用一份明确标为演示的数据。
