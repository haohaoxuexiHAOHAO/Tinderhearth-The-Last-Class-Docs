# PRD：天气

## 1. 概述

正典很早就写下「天气与节日可以晚做，但时间系统必须先为它们留数据钩子」，还定了恶劣天气的起步种类 —— 因为穹盾有一项改造专门削减它们，一个「削减恶劣天气」的东西必须有削减的对象。但天气本身**一个字的设计都没有**：全库三十多份系统文档里只有两处提到它，一处是刻意没答的问题（下雨算不算自动浇水），一处是等它才能给值的参数。

于是现在有三样东西悬在那里：学生日程少了正典点名的那一维、穹盾那项改造说不出效果、地块那条欠账答不了。这一轮把天气做到闭环 —— 它是什么、谁决定它、谁读它、四种恶劣天气各自改什么，全部有落点。

**节日不在本需求内**，它与天气唯一的共同点是都挂在时间上：节日挂日期，天气挂概率，形状不一样。它另有编号。

## 2. 目标

1. 天气有一份系统文档，回答「一天的天气从哪来、存在哪、谁读它」。
2. 四种恶劣天气各有一组**落在既有量上**的影响，玩家在关卡里和基地里都感觉得到。
3. 玩家能提前规划：今天就知道明天是好天还是坏天，装了设备之后还知道是哪一种。
4. 穹盾那项改造有说得出的效果。
5. 地块那条欠账（下雨算不算自动浇水）在这一轮被答掉。
6. 天气不夺走玩家的任何选择 —— 恶劣天气改的是划算不划算，不是能不能做。

## 3. 上游约束

只链接，并写明各自约束本需求的哪一部分。

- [时间与经营 · 作息与熬夜](../canon/gameplay/时间与经营.md)：天气与节日可以晚做但时间系统要先留数据钩子；恶劣天气的起步种类；学生完整日程按季节、日期与天气三维排布。**这是本需求存在的理由，也是那几种天气的唯一出处 —— 本需求不改那几个名字、不加第五种。**
- [时间与经营 · 结算顺序（固定，不得改动）](../canon/gameplay/时间与经营.md)：那串步序一步不许增。**约束「明天什么天气」只能并进已有的某一步。**
- [时间与经营 · 时间](../canon/gameplay/时间与经营.md)：时间单位只有天、季、年三级。**约束天气的粒度是一天一种。**
- [世界观 · 穹盾](../canon/world/世界观.md)：天气保护改造削减恶劣天气的侵袭。**约束本需求必须持有一个「被削减的东西」。**
- [玩法定位 · 随机事件：事件可以晚做，扩展点现在就留](../canon/gameplay/玩法定位.md)：触发钩子的位置已经定死那几处。**约束天气事件只能挂在既有钩子上，不许为天气新开一处。**
- [`伤害系统` · 状态线：抗性减的是施加概率](../design/伤害系统.md)：抗性按状态各一份、没有元素抗性这一层。**约束「雨天不容易被点着」写成灼烧抗性，而不是火抗。**
- [`成长系统` · 派生表](../design/成长系统.md)：那张表是战斗侧读角色数据的唯一入口。**约束天气的修饰只能落在表里已有的量上。**
- [`装备系统`](../design/装备系统.md)：装上加项并打来源标签、卸下按来源整批撤。**约束进关卡加、离关卡撤走同一条既有路径，不新建载体。**
- [`地块系统` · 边界与非目标](../design/地块系统.md)：那一份刻意没答「下雨算不算自动浇水」，把账记在台账。**约束本需求必须答它。**
- [`活跃失衡系统`](../design/活跃失衡系统.md)：总量是三层之和、它没有按天到期的项也没有自然漂移。**约束天气不直接进失衡，只能通过境况事件间接推。**
- [`战斗AI系统`](../design/战斗AI系统.md)：不给敌人开专用通道。**约束天气的修饰敌我同吃。**
- [`存档系统` · 进哪一侧：判据一句话](../design/存档系统.md)：跨过一次睡眠还成立的进正式存档。**约束天气进正式存档。**
- [ADR-0009](../decisions/ADR-0009-编辑器主导的开发模式.md)：参数唯一来源是场景与资源，代码不留能用的默认值。**约束本需求一个数都不定，缺配置要当场报错。**
- [ADR-0010](../decisions/ADR-0010-文档体裁与系统文档归位.md)与 [ADR-0019](../decisions/ADR-0019-系统文档骨架加术语一节.md)：交付物是 `design/` 根下一份 `type: system`，骨架与术语节按模板。**约束交付物的形状。**

**依赖关系写明**：天气修饰的**幅度**、各天气的**出现权重**、侵袭档的**削减率**都要等给值那一轮，归属见[待办台账](./issues/README.md)；本需求只定量纲与约束形式。落地那一半还依赖状态载体的扩容（现在那份载体只有帧这一种时长单位，而天气修饰要的是「在场期间」那一档），编号同上。

## 4. 用户故事

### US-001：天气系统文档的主体

**描述**：作为三周后回来看的自己，我想要一份说清「一天的天气从哪来、存在哪、谁读它」的文档，以便加一种天气或接一个读者时不用重新推一遍。

**验收标准**：

- [ ] `design/天气系统.md` 存在，`type: system`、文件名以「系统」结尾，骨架与术语节过 `check_docs.py` 的判定
- [ ] 文档里答得出这几个问题：一天有几种天气、明天的那一种什么时候定下来、它存在哪、谁读它、四种恶劣天气各改什么
- [ ] **全文一个玩法数值都没有**（可核对：搜不到幅度、权重与削减率的具体值）
- [ ] 至少被一份正典链接到（`check_docs.py` 的长期规格上游判定）

### US-002：正典侧按新结论改，并挂上落点

**描述**：作为读正典的人，我想要「天气可以晚做」这句话不再挂在一个已经有设计的东西上，以便正典不说过期的话。

**验收标准**：

- [ ] [时间与经营 · 作息与熬夜](../canon/gameplay/时间与经营.md)那句「可以晚做」缩到只剩节日，并指得到新文档
- [ ] 两条玩法立场进正典：**恶劣天气不拒绝任何玩家动作**、**天气的修饰敌我一视同仁**
- [ ] 那几种恶劣天气的名字与条数**一个字未改**（可核对：`git diff` 里那一行只增不改）
- [ ] 改动之后跑 `check_docs.py`，被惊动的上游约束逐处复核过再 `--repin`

### US-003：地块那条欠账被答掉

**描述**：作为在雨天对着一片地发愣的玩家，我不想还得拎桶浇一遍水。

**验收标准**：

- [ ] `design/地块系统.md` 那条「不答下雨算不算自动浇水」换成答案，并指得到新文档
- [ ] 答案落成一条可测的行为：降雨类天气那天，那一格的浇水累计按浇过算，玩家再浇一次**被拒**且不重复计数
- [ ] 台账里那笔账（记在生产那条编号的备注里）改成已答

### US-004：数值与内容量各归其位

**描述**：作为将来给值的人，我想要天气新增的每个量都已经登记在册并写明校准办法，以便不用回头猜它是什么量纲。

**验收标准**：

- [ ] [数值模型](../design/数值模型.md)的尚未给值表加天气那一组：各天气的出现权重、各修饰的幅度、侵袭档的削减率，每项写明量纲、校准办法与归属
- [ ] **预报那两档不新增任何量** —— 分档读的是「装没装那台设备」这个既有事实
- [ ] 至少立一条约束形式（不是值），例如「恶劣天气造成的产出损失不得高于一整天的产出」这一类可判的形状
- [ ] [内容规模基准](../canon/gameplay/玩法定位.md)那张表**逐样重判**：补行或不补行都要写明理由
- [ ] `python tools/simulate_week.py --check-doc` 无分叉

### US-005：索引与台账

**描述**：作为按编号找东西的人，我想要天气这件事在台账上只有一处状态，以便不出现两份说法。

**验收标准**：

- [ ] [系统文档与提案索引](../design/README.md)加天气那一行，摘要写得出它持有什么、不持有什么
- [ ] 台账里天气那条编号的状态按结果改，**节日另有一条自己的编号**
- [ ] 本轮新记的欠账（落地依赖、要作者实机看的那几项）在台账各有一行
- [ ] 按编号搜**两个仓加 `.kiro`**，提到那几个编号的地方一起改掉

### US-006：端到端 —— 一条天气从生成走到玩家看得见

**描述**：作为验收的人，我想要走一遍「明天下雨 → 今天就看得见 → 出征时全场吃到修饰 → 回来地已经浇过了」这条链，以便确认各处接得上而不是各自成立。

**验收标准**：

- [ ] 文档层面走通整条链：跨日定下明天的天气 → 预报读口报出来 → 进关卡施加修饰 → 离关卡按来源撤掉 → 地块那天算浇过 → 天气事件按既有钩子被问一次
- [ ] 覆盖至少一条失败路径：**缺配置当场报错**（某种天气没声明修饰组、或设备级别读不到时不许静默兜底）
- [ ] 交叉核对分三轮：按词（旧说法在活文档里零残留）、按量级数字（天气那几个数只有一个家）、按不变式（结算步数一个未增、事件钩子一处未加）
- [ ] 两个入口都跑过：`check_docs.py` 0 FAIL、`simulate_week.py --check-doc` 无分叉
- [ ] 作者实机确认清单（**这一批全部要等实现**，本轮只列出来）：四种天气在画面上认不认得出、预报那两档读起来够不够用、雨天全场修饰感不感觉得到

## 5. 功能需求

- FR-1：系统必须为每一天持有恰好一种天气。
- FR-2：系统必须在跨日那一刻定下次日的天气。
- FR-3：系统必须把定天气这件事并进每日结算已有的某一步，不得新增步骤。
- FR-4：系统必须把当天与次日的天气写进正式存档。
- FR-5：系统必须让每种天气声明一组修饰，而那组修饰只许引用派生表里已有的量。
- FR-6：进入关卡时，系统必须把当天那组修饰施加给场内全部角色，敌我一视同仁。
- FR-7：离开关卡时，系统必须按来源整批撤掉那组修饰。
- FR-8：系统不得因天气拒绝任何玩家动作。
- FR-9：当天气是降雨类时，系统必须把当天视为已浇水。
- FR-10：系统必须持有当天的侵袭档。
- FR-11：当穹盾的天气保护改造建成时，系统必须降低侵袭档。
- FR-12：天气相关事件必须挂在正典已定的钩子上，系统不得新开钩子。
- FR-13：系统必须让天气事件的前置条件读得到当天的天气与侵袭档。
- FR-14：系统必须提供一个读口，回答「明天是好天还是坏天」，且这一位永远是准的。
- FR-15：当基地装了那台灵分析设备时，系统必须让同一个读口额外回答「明天具体是哪一种」。
- FR-16：系统必须让全世界同一天只有一种天气，不得按场景各存一份。
- FR-17：系统不得持有任何天气数值。
- FR-18：当某种天气缺少修饰组声明时，系统必须在载入时报错，不得按无修饰兜底。

## 6. 非目标

- **不做节日。** 它另有编号。
- **不做天气的画面与音效。** 那是作者在编辑器里的工作，音频另有编号。
- **不定任何数值。** 幅度、权重、削减率、设备级别全归给值那一轮。
- **不做一天之内的天气变化。** 粒度是一天一种。
- **不做按地点分的天气。** 全世界共享同一天那一种。
- **不做学生日程 AI。** 天气这一维就位之后它才有输入，但它仍然后置。
- **不碰元素抗性那条结论。** 没有火抗这一层，天气用的是既有的状态抗性。
- **不让天气直接改活跃失衡。** 只允许境况事件间接推。
- **不做预报那一页的界面排版。** 它跟手环那一页的落地编号走。
- **不实现任何效果。** 本需求交付的是文档与接口形状。

## 7. 界面与表现考虑

- 预报进手环：低档只报「明天好天还是坏天」，高档报具体种类。**低档那一位必须准** —— 如果做成「可能变差」这种模糊话，它和不知道没区别。
- 关卡里那组修饰要让玩家知道它在生效，但**具体怎么呈现不在本需求**：世界内那一层已经有自己的清单，天气项按同一条办。
- 四种天气在画面上认不认得出来只能实机看，归作者。

## 8. 技术考虑

- **落地依赖状态载体的扩容**：天气修饰不是倒计时项，是「在场期间」那一档，而现有载体只有帧这一种时长单位。编号见台账。
- **设备没有级别，装了就算。** 核过 `生产系统` 的设备那一节：设备是摆放物，占室内格子、不占派工位、添料是一次交互，声明项里没有级数。所以预报分档读的是「装没装那台设备」，**不新开级别量**。
- **那台设备不进渠道表。** 生产那张表里的设备是产出执行体，而灵分析设备不产物品，所以它不走那条产出管道 —— 这一点要在天气那一份里写明，否则读者会去渠道表找它。
- **天气的随机源**：存结果不存种子 —— 算法将来若改，旧存档里那个「明天下雨」仍然成立。
- **天气与季节是两个量**：正典写季节只影响三处，天气不在其内，所以它们不合并成一个字段。

## 9. 待确认问题（阻塞项）

无。六条取舍都已定：不拦动作、下雨算满浇水、不直接进失衡（只走事件）、穹盾削的是侵袭程度、预报分两档、全世界一种天气；抗性那一侧用既有的状态抗性，承载预报精度的是基地里那台灵分析设备。

## 10. 成功判据

- `design/天气系统.md` 交付，过骨架、术语与上游引用三条判定。
- 四种恶劣天气各有落点，且**没有一条落在派生表之外** —— 可核对：搜不到任何新增的战斗量。
- 地块那条欠账有答案，对应台账编号的备注改掉。
- 天气新增的每个量都在尚未给值表里，各写了量纲、校准办法与归属。
- 每日结算的步数一个未增、事件钩子一处未加 —— 两条不变式，用 `git diff` 为空作证。
- `check_docs.py` 0 FAIL，`simulate_week.py --check-doc` 无分叉。
- 作者实机确认项只列清单、不在本轮勾选（它们都要等实现）。
