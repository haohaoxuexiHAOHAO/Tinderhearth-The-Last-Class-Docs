# PRD：战斗手感核心（进攻侧竖切片 + 帧调优工具）

## 1. 概述

这是第一个**玩法实现**需求，它故意先攻项目最大的风险：逐拍的战斗手感成不成立。正典把整个游戏押在这句话上——「战斗手感是本作的核心，玩家不出门这游戏就没了」（[玩法定位](../canon/gameplay/玩法定位.md)）。地基已经铺完（`UI-1` 的相机／HUD／输入／世界空间 UI、`ENG-2`／`ENG-3` 的工程与测试底座、`GP-2` 的数值），但**一行玩法都还没实现**。

本切片（内部代号 A1）只做一件事：一个侧视训练房，玩家操作主角对**不还手的木桩**做移动／跳／轻重攻击／闪避／冲刺，配打击反馈四件套（顿帧／闪白／击退／屏幕震动），并建起 `ENG-6` 的最小帧调优工具，把手感调到作者认可。**纯运动手感——不接任何资源（HP／SP／MP），不消费 `GP-2` 数值。** 防御、敌人 AI、目标、关卡拼装都是下一切片（A2）的事。

现在做的理由不是「排到它了」：核心手感是一次成败的赌注，越早摊开看越好；而 `UI-1` 建的侧视相机、输入映射与 HUD 就是为战斗关卡建的，正空等着它。

### 范围变更：加入纵深轴（作者 2026-09-09 确认）

**本 PRD 立项时假设的是单平面横版**，`GP-10`～`GP-13` 的实现与机器验收都建在那个假设上。2026-09-09 作者裁定战斗关卡是**带连续可行走纵深的横版**（belt-scroll，48 世界像素纵深带），并删除多层平台；正典见[战斗与关卡 · 空间模型](../canon/gameplay/战斗与关卡.md)。

**为什么在本切片内改而不是推给 A2**：纵深容差直接决定「打得着／打不着」，与顿帧同级。在会被推翻的空间模型上收敛手感等于调两遍，而本切片的全部价值就是那次收敛。

**受影响的范围**：运动模型（原单水平轴 + 重力 + 地板／天花板碰撞）、命中判定（加纵深容差）、绘制顺序（按纵深排序）、影子（由代码持有，作纵深与高度提示）。**不受影响、已完成的部分保留**：连段状态机、统一状态载体、命中结算、顿帧计时、输入门面、素材导入管线、闪白与震屏。改造条目：`GP-15`、`GP-16`、`ENG-15`、`ENG-16`。

**已通过的机器验收要重新理解**：`GP-12` 的 41 项、`GP-13` 的 62 项都是**单平面模型下**通过的，不能当作纵深模型也已验过。

## 2. 目标

- 主角在侧视场景里能被流畅操作（移动／跳／攻击／闪避／冲刺），**操作结果与输入意图一致**。
- 命中有「打得实」的反馈，不靠伤害数字传达。
- 手感帧数（前后摇／无敌帧／顿帧时长／击退量）是**可调的**，且这一版调过什么可复核。
- 有一套够用的帧调优工具（帧步进 + 判定框可视化），并给出 `ENG-6` 现成方案的评估结论。
- 战斗结算逻辑（连段状态机、无敌与硬直窗口）落在规则层，可脱离引擎单元测试。

## 4. 用户故事

### US-001：侧视训练房与主角移动

**描述**：作为玩家，我要在侧视训练房里流畅地移动和跳跃主角，**并能在纵深上前后走动**，以便判断基础移动手感。

**验收标准**：

- [ ] 可核对：训练房是侧视场景，用既有 `GameCamera`（2 倍整数缩放、跟随）；主角由 `IActorController` 的本地玩家控制器驱动
- [ ] 可核对：输入全部经 `InputRouter`，`src/` 无直接 `Input` 轮询（`check_input_map` 已守此约束）
- [ ] 可观察：主角能左右移动、跳跃、落地；移动与跳跃的加减速为可调参数
- [ ] 可测试：移动与跳跃的运动学（加速度、跳跃初速、重力）在规则层可测
- [ ] 作者实机确认：移动与跳跃「跟手」

### US-002：轻重攻击的固定连段

**描述**：作为玩家，我要轻重攻击打出有节奏的固定连段（含空中连击），以便判断攻击手感。

**验收标准**：

- [ ] 可观察：轻攻击、重攻击各有多段固定连段；离地时可打空中连击
- [ ] 可核对：连段状态机（每段的前摇／命中／后摇帧、连段衔接窗口）在规则层，帧数是可调数据
- [ ] 可测试：连段状态机的推进（输入 → 段切换、超时回落待机、落地打断空中连击）有单元测试
- [ ] 可核对：不做取消与派生（`GP-4`）、不做倒地追打（需可击倒目标，随 A2）
- [ ] 作者实机确认：连段的前后摇与衔接节奏「打起来顺」

### US-003：闪避与冲刺

**描述**：作为玩家，我要闪避带无敌帧、冲刺是显式高速位移，以便判断走位手感。

**验收标准**：

- [ ] 可观察：闪避是带无敌帧的短距闪步（quickstep，非翻滚）；冲刺是无无敌帧、按住冲刺键期间移动的高速位移
- [ ] 可核对：闪避取方向读「按下瞬间的输入状态」（`GP-9`），闪避状态机直取 `InputRouter` 当前轮询、不引入缓冲窗口
- [ ] 可核对：闪避无敌作为一个「无敌」状态经统一状态载体表达，不用 ad-hoc 计时器
- [ ] 可测试：无敌窗口的起止帧、闪避位移曲线在规则层可测
- [ ] 作者实机确认：闪避的无敌感与冲刺的「显式」感成立

### US-004：打击反馈四件套

**描述**：作为玩家，我要命中木桩时有「打得实」的反馈，以便不靠数字也知道打中了、打得重不重。

**验收标准**：

- [ ] 可观察：命中瞬间顿帧（双方短暂静止）；受击者闪白；击退位移随轻重攻击不同；重击触发屏幕震动
- [ ] 可核对：木桩受击进入「硬直」状态，经统一状态载体表达
- [ ] 可测试：顿帧时长、击退量、硬直帧数为可调参数；屏幕震动可在标志位关闭，**关闭后重击零位移**
- [ ] 可核对：不显示伤害数字（默认关）、木桩不显示血条（正典：杂兵靠受击表现）
- [ ] 作者实机确认：四件套合起来「打得实」，且顿帧不长到打断连击的输入节奏

### US-005：帧调优工具与可调参数存证

**描述**：作为开发者，我要能逐帧步进看判定框与状态、并留下调参存证，以便手感调整有依据、可回归。

**验收标准**：

- [ ] 可核对：有帧步进能力（暂停 / 单帧前进）与判定框／受击框可视化叠层（默认关，仅调试开）
- [ ] 可核对：给出三个现成候选（引擎自带碰撞框可视化 / `animated-shape-2d` / `Fray`）在 4.7.2 + `net10.0` 上的评估结论——各能做什么、为何自建最小工具补哪一层，结论写回 `ENG-6`
- [ ] 可核对：手感可调参数集中在一处，能导出一份参数快照落 `logs/`
- [ ] 可测试：帧步进不改变结算结果（步进与实时跑同一份规则层状态机）
- [ ] 作者实机确认：用这套工具能把 US-001~004 的手感调到位

### US-006：端到端与手感实机确认

**描述**：作为开发者，我要一条走完整链路的验证，以便这套手感核不是各部件单测过、合起来却不成立。

**验收标准**：

- [ ] 自动化测试走完主路径：待机 → 触发连段各段 → 命中判定产生硬直与顿帧触发 → 闪避进入无敌窗口 → 回到待机；条数与 `verify.py` 静态计数一致
- [ ] 覆盖失败与边界路径：连段超时回落、无方向输入时闪避方向取值、屏幕震动关闭时零位移、空中连击落地打断
- [ ] 可核对：代码仓 `python tools/verify.py` 全绿（构建／测试／导出／跑产物），`temp/` 干净
- [ ] 作者实机确认清单：打开训练房 → 移动跳跃跟手 → 轻重连段与空中连击顺 → 闪避无敌＋冲刺显式 → 命中四件套「打得实」且顿帧不断节奏 → 用帧步进工具复核一遍；在 1080p 与 1440p 各看一遍字与像素清晰
- [ ] 可核对：本轮调到的那一版参数快照与帧步进截图存证已落 `logs/`

## 5. 功能需求

- FR-1：系统必须提供一个侧视训练房场景，使用既有 `GameCamera` 的侧视 2 倍整数缩放。
- FR-2：系统必须让主角由 `IActorController` 的本地玩家控制器驱动。
- FR-3：系统必须只经 `InputRouter` 查询输入。
- FR-4：系统必须支持主角左右移动与跳跃。
- FR-5：系统必须提供轻攻击的固定连段。
- FR-6：系统必须提供重攻击的固定连段。
- FR-7：系统必须支持空中连击。
- FR-8：闪避必须带无敌帧。
- FR-9：闪避取方向时必须读按下瞬间的输入状态，不引入缓冲窗口。
- FR-10：冲刺必须由移动修饰键显式触发，不得自动进入。
- FR-11：命中必须触发顿帧。
- FR-12：受击者必须显示闪白。
- FR-13：击退位移必须随攻击轻重不同。
- FR-14：重击必须触发屏幕震动。
- FR-15：屏幕震动必须可关闭，关闭后不产生任何位移。
- FR-16：木桩受击必须进入硬直状态，且该状态经统一状态载体表达。
- FR-17：闪避无敌必须作为无敌状态经统一状态载体表达。
- FR-18：连段帧数、无敌窗口、顿帧时长与击退量必须是集中的可调参数，不得作为魔法数散落。
- FR-19：系统必须提供帧步进与判定框／受击框可视化。
- FR-20：战斗结算规则（连段状态机、无敌与硬直窗口、闪避方向取值）必须在规则层，不引用 Godot。
- FR-21：系统不得显示伤害数字，木桩不得显示血条。
- FR-22：系统必须能把当前手感参数快照导出到 `logs/`。
- FR-23：角色必须能在连续的纵深上移动，纵深位置钳在 48 世界像素带内。
- FR-24：横向、纵深与跳跃高度必须三轴分离；离地期间纵深锁定，落地后解锁。
- FR-25：命中必须同时满足横向范围与纵深容差，任一不成立即不命中。
- FR-26：绘制顺序必须按纵深排序，且与命中判定使用同一份纵深值。
- FR-27：角色影子必须由代码绘制、不进精灵帧；跳跃期间影子留在地面作高度提示。
- FR-28：纵深移动速度与纵深容差必须是集中的可调参数，标为未校准初值。

## 6. 非目标

- **不做防御**（普通／精准防御）与 SP 失衡——需会攻击的目标才测得了，随 A2。
- **不做任何资源**（HP／SP／MP／体力）。纯运动手感；资源与 `GP-2` 消费随 A2 的真实敌人一起进来。
- **不做敌人 AI、队友 AI、感知与视野**（A2）。木桩不还手、不移动、不死。
- **不做委托目标、失败判定、撤离**（A2）。
- **不做关卡片段拼装**。训练房是固定手工场景、不是委托关卡；片段拼装架构随真正的关卡（A2+）再建。
- **不做多层平台**——正典 2026-09-09 已删除该系统（见[战斗与关卡 · 多层平台已删](../canon/gameplay/战斗与关卡.md)）。地面起伏与跳跃照旧，但没有「悬在半空的第二层地面」。
- **不做纵深密度的好玩判断**。本切片只做纵深轴本身；48px 够不够要满编实机看，归 `ENG-16`。
- **不做招式取消与派生（`GP-4`）、倒地追打、场景物件可拿（`GP-5`）**。
- **不做技能（6 技能位）、光环、真实形态**。
- **不做完整状态系统**——本切片只用硬直与无敌两种状态，走最小统一载体；异常状态种类与叠加／覆盖／过期规则随后续需求扩展同一载体。
- **不定也不消费 `GP-2` 数值**。手感帧数属 `GP-6`，值持在代码不进数值模型。
- **不做设置界面**——屏幕震动开关本切片用一个可切换标志即可，完整设置界面另计。
- **不替换占位美术**——用 `ART-4` 已登记的下载 samurai 精灵，发行前由作者自绘替换（`ENG-12` 守发行包）。

## 7. 界面与表现考虑

- 本切片无资源，故**不接关卡 HUD 的资源条**；世界空间 UI 的伤害数字默认关、不启用。屏上反馈纯靠角色与木桩的受击表现（顿帧／闪白／击退）加屏幕震动。
- 判定框／受击框可视化是**开发者叠层**，默认关、仅调试开启，不作为发行包表现。
- 相机沿用 `GameCamera` 侧视 2 倍缩放与跟随；**顿帧期间相机与角色一同静止**。
- 占位 samurai 精灵的动作帧（待机／走／跳／轻攻击／重攻击／闪避）决定手感能不能验；帧不够时补生成占位或明确标注缺口。

## 8. 技术考虑

- **分层**：连段状态机、无敌与硬直窗口、闪避方向取值以帧为单位建在 `rules/Combat`（纯 C#、可单元测试，帧数是数据）；命中检测（`Area2D` 交叠）、动画播放、顿帧（引擎时间冻结）、闪白（`modulate`）、击退（速度）、屏幕震动（相机）在 `src/` 引擎层，读规则层决策驱动表现。手感**逻辑**可测、手感**表现**实机调。
- **输入**：轻／重攻击、闪避、冲刺、跳跃已在 `UI-7` 的 `InputBindings` 映射；经 `InputRouter` 查询（`check_input_map` 守直接轮询）。
- **统一状态载体**：硬直与无敌是本项目首批临时状态。正典要求「同一套状态系统现在就成立」，故本切片建一个最小状态载体（带「可否解除」属性，本切片两种都不可解除）供两者注册，而非各写计时器；完整状态系统随后续需求扩展同一载体。
- **`ENG-6` 工具**：先评估三候选——Godot 自带运行时碰撞框可视化（引擎能力）、`animated-shape-2d`（逐帧判定框编辑，插件）、`Fray`（战斗状态机 + 输入缓冲，GDScript 插件，从 C# 调需互操作）。**三者均未在 4.7.2 + `net10.0` 实测，须先实测再定**，评估后自建补缺的最小帧步进与判定框叠层，结论写回 `ENG-6`。
