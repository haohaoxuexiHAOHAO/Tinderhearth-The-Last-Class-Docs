# ENG-22：新的可建造区尺寸落到配置与相机判据

## 目标

把 80×60 落进配置，并把相机那条按旧宽度算的判据重算 —— 代码里一个尺寸都不写死。

## 来源

- PRD：[`spec/prd-base-and-production.md`](../prd-base-and-production.md) 的 `US-001`
- 现状：尺寸已经是配置项（`rules/Foundation/Config/GameConfig.cs` 的两个字段，无默认值、缺字段当场报错），所以扩大是改数加延伸地图。

## 依赖

依赖 `GP-25` —— 正典先定尺寸，配置才有依据可改。

## 验收标准

- [x] `data/config/game.json` 的两个尺寸字段改成新值（80／60），注释里那笔「60 格 = 960px」的账跟着重算
- [x] 规则层测试跟着改：`tests/Foundation/Eng5ReservationTests.cs` 原来断言 40×30，现在断言 80×60，并写明「改画布只需改这里的期望值」
- [x] `rules/Ui/CameraFeel.cs` 里建造滚动速度那条「640px 宽走完 2.5 秒」的判据按新宽度重算：速度 256 → 384，横穿 3.3 秒、纵穿 2.5 秒，注释里写明**宽度不是常量**
- [ ] 边缘推镜的余量（格）复看 —— 它用的是格而不是像素，画布变大不改变「离边几格开始推」的含义，所以值没动；**推不推得舒服要实机看**，归 `UI-12`
- [x] `python tools/verify.py` 五步全绿（347 条测试、0 失败）
- [ ] 作者实机确认：打开基地场景看取景与滚动手感

## 实现笔记

### 设计决策

- **模糊点**：滚动速度那条判据是「横穿可建造区不该久到让人不耐烦」，画布翻倍之后原速度要走 5 秒。
- **选择**：速度 256 → 384（横穿 3.3 秒、纵穿 2.5 秒），并在注释里写明**判据里的宽度不是常量**，画布再改要重算这笔账。
- **理由**：3.3 秒与原来那版「640px 走 2.5 秒」是同一个量级；手感本身归 `UI-12` 由作者实机调，这里只保证判据的算法还成立。

### 偏离

- **方案怎么说**：写一条「比对装进相机的可建造区与配置一致」的规则层测试。
- **实际怎么做**：改的是既有测试的期望值（40×30 → 80×60），没有新增测试。
- **为什么**：那条测试已经在做这件事 —— 它比对「配置给什么、读出来就是什么」，而相机侧的 `CameraRig.BuildableWidth` 本来就是给这种比对用的。再加一条同形状的测试只是重复。

### 权衡

边缘推镜的余量没动：它的单位是**格**不是像素，画布变大不改变「离边几格开始推」的含义。舒不舒服要实机看，归 `UI-12`。

### 待确认

无。取景与滚动手感等作者实机。
