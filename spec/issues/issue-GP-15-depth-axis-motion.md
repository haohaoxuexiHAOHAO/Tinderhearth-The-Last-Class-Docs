# GP-15：规则层纵深轴运动

## 目标

把主角运动从单平面改成带连续可行走纵深的模型：横向、纵深、跳跃高度三轴分离，纵深带 48 世界像素。

## 来源

- 正典：[战斗与关卡 · 战斗关卡的空间模型](../../canon/gameplay/战斗与关卡.md)（作者 2026-09-09 定）
- PRD：[`prd-combat-feel-core.md`](../prd-combat-feel-core.md) 的 `US-001`、`US-003`（2026-09-09 范围变更）
- SPEC：[`spec-combat-feel-core.md`](../spec-combat-feel-core.md) 的运动模型一节

## 依赖

`GP-10`（已完成，`MotorState` 与 `CombatFeel` 在那里）。**这是对 `GP-10` 已实现模型的改造**，不是新建：`GP-10`／`GP-12`／`GP-13` 的机器验收都是在单平面模型下通过的。

## 验收标准

- [x] 纵深是**连续**的，不是固定轨道；纵深位置钳在 48px 带内
- [x] 三轴分离：横向速度、纵深速度、跳跃高度互不串。**空中不改纵深**（离地期间纵深锁定），落地后恢复
- [x] 纵深移动速度作为独立可调量进 `CombatFeel`，标未校准初值、归 `GP-6`
- [x] 出招时纵深与横向一同定身（沿用 `GP-10` 的 `attacking` 封锁口径）
- [x] 闪避方向取按下瞬间的输入（`GP-9` 口径不变），但方向现在是**横向与纵深的二维输入**
- [x] 规则层单测覆盖：纵深钳制、空中锁纵深、落地解锁、三轴不串、出招定身
- [x] `rules/Combat` 仍不引用 Godot

**手感不在上面这些勾里，而且现在还看不了。** 纵深走得跟不跟手、48px 挪起来够不够、纵深闪避有没有分寸，全部归 `GP-6` 实测收敛 —— 但**本条完成时纵深在画面上是不可见的**：引擎层一次都没读 `DepthWorldPx` 去改绘制位置、绘制顺序或影子（那是 `ENG-15`），所以实机按 W／S 时角色在屏幕上原地不动，纵深只在规则层里动。

**这意味着本条不产出「待作者实机确认」项。** 要让纵深变成能看、能判断的东西，最少要 `ENG-15` 的两件：角色绘制按纵深偏移并排序、影子留在地面。在那之前对纵深手感的任何判断都没有依据可看。本条交出的是「按登记的数逐帧算对了」，验它的是机器判据而不是眼睛。

## 实现笔记

### 设计决策

- **模糊点**：纵深位置该由谁持有。既有契约是「规则层持速度，引擎层持位置」（`GP-12` 的运动帧契约），纵深照这条走，48px 带的钳制就落到引擎层。
- **选择**：**纵深的速度与位置都归规则层**（`MotorState.DepthWorldPx`），引擎层只读。
- **理由**：Godot 2D 只有两个轴，已被横向与跳跃高度占满，纵深在引擎侧没有可借的位置量；纵深上本轮也没有碰撞体（物件在纵深上的阻挡归关卡实现）。若让引擎持纵深位置，钳制只能写在引擎层或两处各写一份，而钳制正是本条要能脱引擎单测的东西。代价与执行体写进代码仓 `ARCHITECTURE.md`：引擎层绝不许再积分一遍纵深速度（两倍位移且不报错），写入口由 `private set` 守、逐帧步长由图形探针守，「引擎另建一份影子纵深」扫不出来、留作 `ENG-15` 的人工评审项。

- **模糊点**：48px 该不该进 `CombatFeel`。
- **选择**：另立 `rules/Combat/DepthBand.cs`。
- **理由**：`CombatFeel` 持的是「只能实机逐帧调」的手感初值，48px 不是那类东西 —— 它是正典从视野、本体尺寸与排间距算出来的几何账。混进去，下一个人会以为它可以凭手感改，而它一改「几排装得下 20 个」要重算。同时它也不是不可改：`ENG-16` 可能回改，所以要有**一处**常量而不是散落的字面量。

- **模糊点**：纵深闪避用什么速度。
- **选择**：新增 `DodgeDepthSpeedPixelsPerSecond`（90），不复用横向闪避的 168。
- **理由**：168 是按 320px 宽的横向视野定的，18 帧走 50.4px；放到 48px 带上一次闪避就超过整条带，于是每次纵深闪避都撞在带沿上，**落点由钳制决定而不是由输入决定**，「往里挪半步」与「翻到最里侧」变成同一个结果。90 在 60Hz 下是 1.5px／帧、18 帧走 27px（约 1.7 排），出了当前这一排又离带沿有余量。这条关系（一次纵深闪避走不完整条带）由 `CombatFeelTests` 判死。

### 偏离

- **方案怎么说**：SPEC §3.1 的输入类型是 `CombatInput(int MoveSign, …)`，`MoveSign` ∈ {−1,0,+1}「侧视只用左右」。
- **实际怎么做**：改成 `CombatInput(int HorizontalSign, int DepthSign, …)`，并把 `Direction` 拆成 `HorizontalDirection` 与 `DepthDirection`，另加 `HasDirection`。
- **为什么**：加了纵深之后 `MoveSign` 会读成「移动轴」，而纵深也是移动 —— 「把纵深接到横向字段上」就成了一个看不出来的错。这是破坏性签名改动，**故意不做兼容重载**：参数个数从 6 变 7、第二位是 `int` 而不是 `bool`，所以每个既有构造点都必须重新编译并表态，不存在「恰好还能编过、语义已错位」的中间地带（构建 0 错误 0 警告即为证）。SPEC 已同步。

- **方案怎么说**：验收标准只要求纵深移动速度进 `CombatFeel`。
- **实际怎么做**：进了两个（行走与闪避各一）。
- **为什么**：见上面第三条决策。不是加了一个可调项，是把「纵深闪避该走多远」从钳制手里拿回来。

### 权衡

- **纵深不做加速曲线**，横向做。纵深速度直接取目标值，因为整条带只有 48px，横向那条 6 帧起步的曲线会在到速之前吃掉 8px（六分之一条带），「挪半步」会变得不跟手。代价是横纵同按时两轴的手感不同源，实机若觉得纵深起步太生硬，加一条曲线是 `GP-6` 的改动。
- **不做对角归一**。两轴各走自己的速度，斜走的合速度（√(104²+60²) ≈ 120px/s）比纯横向快 15%。归一化会让两个轴互相牵制，与「三轴分离」相反；belt-scroll 那一类作品普遍不归一。**未验证这在实机上是否显眼**，列入待确认。
- **冲刺只加横向**。按住冲刺 + 只按纵深不进 `Dash` 相位、纵深仍走行走速度。冲刺是沿横向轴的突进，再加一个「纵深冲刺速度」就是第四个没有设计需求的未校准量。
- **闪避途中掉出平台，纵深当帧起锁住**，横向位移照给满。闪步不是纵深的豁免 —— 否则「空中不改纵深」会有一个用闪避就能绕开的口子。
- **`IsDepthAirLocked` 名字里带 Air 是评审改的**。原名 `IsDepthLocked` 会读成「纵深现在动不了」，而出招定身时纵深速度也是零、这个标志却为假，看起来就是矛盾。定身与离地锁是两条不同的封锁口径，名字得自己说清是哪一条。

### 待确认

- 纵深行走 60px/s、纵深闪避 90px/s 都是**未校准初值**，归 `GP-6`。纵深挪步与命中容差（`GP-16`）是一对：容差一改，速度大概要跟着重调。
- 斜走比纯横向快 15%（不归一的代价）在实机上是否显眼 —— 未验证，验法是实机斜走横穿一段直线走廊看有没有「斜着更快」的感觉。
- 纵深带的默认出生点取带中线（24px）。关卡按站位摆纵深要走 `MotorState.PlaceDepth`，本轮引擎层一次都没调它，调用方只有单测 —— `ENG-15`／`GP-16` 接摆位时要确认这个入口够用。
- **`GP-12`／`GP-13` 的历史机器验收要按新模型重读**：两者的判据是单平面下写的，本轮复跑全绿，但那证明的是「纵深没有破坏既有两轴」，不是「它们已经验过纵深」。纵深的绘制与命中分别归 `ENG-15`、`GP-16`。

**新增的 4 条图形判据钉的是引擎那一段接线**，三轴分离本身由规则层单测钉：

| 判据 | 钉住什么 | 检出什么形状的失效 |
| --- | --- | --- |
| `depth-front` | 按住向前键：纵深逐帧步进恰好一格、走到前沿被钳住、钳后速度归零；同时逐帧核引擎持有的 X 与 Y 一像素都没动 | 接线断（纵深不动）、符号写反（走向后沿）、纵深串进 X／Y、步长错（例如被二次积分成两格） |
| `depth-back` | 同上反向，走到后沿 | 同上 |
| `depth-air-lock` | 离地期间纵深一帧都不变且锁标志为真（另核真的离地够久、起跳时纵深还没贴前沿，否则是空判） | 空中还能挪纵深 —— 那会让「跳起来躲横扫」与「往里挪半步躲横扫」失去区别 |
| `depth-land-unlock` | 落地后**同一份按住的输入**立刻又生效（落地帧本身不推进，两帧走两格），跳跃轴回到同一块地面并静止 | 落地后纵深不解锁、要重按一次才动 |

阶段长度、推进帧数下限与容差**全部由 `DepthBand` 与 `CombatFeel` 导出**，探针里不写死像素或帧数（踩坑记录 48 同一条理由）：速度归 `GP-6` 调、带宽可能被 `ENG-16` 回改，写死的判据只对今天这一版成立。

排缺陷记一笔：`depth-land-unlock` 首轮失败，加临时诊断输出后定位到唯一不成立的合取是 Y 容差 —— 落地静止的 Y 与起跳前差 0.025px，那是 `CharacterBody2D` 自己的碰撞安全边距（`SafeMargin`，引擎默认 0.08）。容差改成取引擎自报的那个边距、另加「竖速归零」，诊断输出已删。教训记进[踩坑记录 49](../../reference/踩坑记录.md)。

**`focus-kept` 的一个观察，未证明因果。** `--no-shake` 档跑的 4 次里有 2 次 `focus-kept` 失败（`focusLost=1`），另外 62 条玩法判据每次都全过 —— 也就是失败的是「这一轮算不算」的前提判据，不是被测行为。两次失败都发生在**紧接着上一个 Godot 探针进程启动**的那一次；留 20 秒间隔单独跑的 2 次都通过。**这是相关，不是已证明的因果**：样本只有 4 次，而 `--probe` 档也有紧邻启动的情形却没失焦。验证办法是固定间隔与不固定间隔各连跑若干次比失焦率。它属于 `ENG-14`（探针互不污染）的范围，本条不改探针 —— `focus-kept` 报「这一轮不能算」正是它该做的事，把它调松才是错。
