# UI-34：随身栏那条六格

## 目标

玩家不打开任何界面就看得到随身的那几样东西，并且换得动手上那一样。

## 来源

- PRD：[`spec/prd-carry-slots.md`](../prd-carry-slots.md) 的 `US-001`、`US-002`、`US-006`
- 上游：[那份键位提案](../../design/proposals/键鼠技能位挪到右手.md)里「数字键那一排空出来，刻意不补」
  那一节 —— 它为本条留了键位，原话是留给「将来真要一条快捷道具栏」

## 依赖

`UI-14`（键鼠战斗键位重排）。**六个技能位现在仍然绑在数字键上**，不挪走就与本条抢同六个键。

## 验收标准

- [x] 六格显示在常驻那一层，每格能显示一个图标与一个数量；数量为 1 时不显示数字
- [x] **不新增 HUD 块** —— `rules/Ui/HudLayout.cs` 里 `HudBlock` 的取值个数不变
- [x] 那一块的宽度与六个技能位那一块**相等**，且宽度按同一个数算出来（不是两处各写一个常量）
- [x] `HudLayout.BlocksOverActorBand` 在 640×360 与拉宽的窗口下都返回空
- [x] 按 `1`–`6` 分别选中第 1–6 格，选中序号与按的键一一对应
- [x] **空格子也选得中** —— 那等于「手上没东西」，不是拒绝换格
- [x] 选中的那一格与其余五格当场分得出来
- [x] 手柄上十字键左右能移动选中位，且六格都到得了
- [x] 手柄那套切换不与两个扳机冲突（扳机现在切两组技能位）
- [x] 每个新动作在两个设备族上要么有绑定、要么有一条带理由的豁免登记（这条已有测试盯着）
- [x] 输入一律经 `src/UI/InputRouter.cs` 那个门面，没有直接轮询引擎输入
- [x] 存档为本条新增的字段**恰好一个**（当前选中第几格）
- [x] 代码仓 `python tools/verify.py` 五步全绿
- [ ] **接进一个真场景** —— 现在 `scenes/` 下只有启动场景与训练房，**没有俯视经营场景**，
      所以那条栏还没有地方挂。视图类已经写好（`src/UI/CarrySlotBarView.cs`），作者搭出场景之后
      是接一下的事。**卡在 `ENG-21`／`GP-87` 的作者那一半。**
- [ ] **作者实机确认**：格子边框、选中框、数量角标在 16px 图标上分不分得清
- [ ] **作者实机确认**：左手按住移动键时右手够不够得到那六个键
- [ ] **作者实机确认**：手柄上切到最远那一格要按几下，烦不烦

## 实现笔记

### 设计决策

- **模糊点**：「不新增 HUD 块」与「那一块的宽度与技能位那一块相等」放在一起读不通 ——
  说「相等」意味着两块，说「取值个数不变」意味着一块。
- **选择**：**是同一块**，把 `HudBlock.Skills` 改名成 `HudBlock.ActionBar`（底边右侧那条六格横排），
  关卡里装技能位、经营场景里装随身栏。取值个数一个没变。
- **理由**：俯视场景没有技能位，那一块在那里本来就空着。共用一块之后「同宽」不是一条要维护的
  约束，而是**同一个东西** —— 于是那条「不许压角色可读区」的既有硬判据输入一个字没变，
  随身栏进来时不用重跑一次占屏账。改名是因为 `Skills` 那个名字会让「经营场景里这一块装什么」
  读不出来。

- **模糊点**：格数从哪来。
- **选择**：`CarrySlotBar.SlotCount` 读 `InputActions.Skills.Count`，`HudLayout.CarrySlotCount`
  再读前者 —— **一条链到底，中间一处都没有抄出来的 6**。
- **理由**：抄一个 6 的后果是改格数时两种内容的宽度悄悄分叉，而分叉只在拉宽窗口时看得出来。

- **模糊点**：随身栏六格紧邻是 96px，而那一块的内容宽 104px（技能位两组之间有一道 8px 分界）。
- **选择**：六格在容器里**居中**，多出来的那一格空隙留在两侧。
- **理由**：这样两种内容的格子落在同一批横坐标上，换场景时格位不跳。让随身栏也带一道中间分界
  是另一条路，但那道分界在随身栏上不表示任何东西 —— 无意义的视觉分组会被玩家读成有意义的。

- **模糊点**：`Select` 越界该抛、该钳，还是该拒。
- **选择**：拒（返回 `false`）且**选中位不动**；而从存档恢复用另一个入口 `Restore`，越界时退回
  第一格并说得出它退过。
- **理由**：两处输入的来源不同。按键来自当场的操作，钳到两端会让「按了第 7 格」看起来像
  「按了第 6 格」；存档来自一个**没人修得了的文件**（旧版本格数可能不同），而 [ADR-0015]
  对旧版本的口径是补默认值、不是报错 —— 报错等于让玩家的档打不开。

### 偏离

- **方案怎么说**：验收里第一条是「六格显示在常驻那一层」。
- **实际怎么做**：视图类写完了，但**没有接进任何场景** —— `scenes/` 下只有启动场景与训练房，
  俯视经营场景还不存在。
- **为什么**：接进启动场景会让它与关卡那条技能栏抢同一个角（两者共用 `ActionBar` 那一块），
  而那个场景演的是关卡。硬接上去只能看到一条假的经营 HUD，换不来任何真信息。
  **三条实机确认因此一并等场景**，这与 `GP-130` 和 `GP-87` 是同一个处境。

### 权衡

**数字键那一排在同一轮里被删掉又加回来。** `UI-14` 按提案把六个 `Digit` 符号连同绑定一起删了
（理由是「留着等于留六个看起来可绑的位」），而本条又把它们加回来 —— 因为那份提案同时写明这一排
「刻意不补，留给将来真要一条快捷道具栏」，而本条就是那条道具栏。**两步都照各自的规格做对了**，
中间那个「一排空着」的状态是 `UI-14` 真实交付的形状，不是一次返工。

**手柄那一侧没给六格直选键。** 手柄上凑不出六个空位（扳机当修饰键，四个面键、两个肩键与左摇杆
按压都有归属），所以改成 D-pad 左右挪选中位、绕回。代价是切到最远那一格要按几下 ——
经营侧不赶时间，这个代价落在最便宜的地方。

### 待确认

**D-pad 那两个方向有一份还没落地的重叠主张**，已按超边界记成 `UI-36`：代码注释与那份键位提案都
写着「D-pad 留给队友三指令」，而队友指令现在一条绑定都没有。三条指令加两个挪位键大于四个方向，
所以 `GP-36` 落地时必须有人让一步。**今天不冲突，而那一天不会静默过去** —— 绑定表有一条测试钉着
「同一个物理位不被两个动作抢」。

**「按场景分动作集」这一层不存在**，本条没有造它。锄地在关卡里没有意义、队友指令在基地里没有意义，
这个缺口迟早要答，而 `UI-36` 是它第一次真的挡住人。
