# GP-41：`design/任务系统.md`

## 目标

把「一条任务记在哪、目标怎么表达、完成与失败各结算什么、谁能加一条」写进一处，加一类任务时不用重新发明一遍进度。

## 来源

- PRD：[`spec/prd-quest-and-level.md`](../prd-quest-and-level.md) 的 `US-002`
- 起因：正典写清了三类委托**怎么算通关**，但没有一处写清一条任务被接下来之后**是什么** —— 而委托只是任务的一类，主线任务与个人请求同样有目标与进度，现在各自无家可归。

## 依赖

`GP-40`（要按步名引那两步，也要用它封掉的三处边界写接口表）。

## 验收标准

- [x] 按 [SYSTEM 模板](../../templates/SYSTEM.md)八节写全，`type: system`、文件名以「系统」结尾、`upstream` 指[战斗与关卡](../../canon/gameplay/战斗与关卡.md)，**并在本条这一轮就被正典链接到**（检查器对长期规格有「必须被正典链接到」的硬判定，链接不在就当场 FAIL —— 不要攒到 `DOC-27`）。
- [x] **判据写在最前面**：有目标与进度、有完成与失败结算的是**任务**；没有目标、只有「触发 → 后果」的是**事件**。写明它要能回答「新东西该进哪一边」，而不是靠记清单。
- [x] 三类任务（委托、主线任务、个人请求）列成一张表，**只列它们在哪几格上不同**（占不占额度、有没有截止、失不失败、能不能重试、谁触发），共用的字段不各写一遍。
- [x] 写明**一条任务持有一到多个目标条目**，全部达成才算达成；理由指回正典（主线任务可以是任意一类委托**加**附加剧情目标）。
- [x] 目标条目的**类型按[完成标准](../../canon/gameplay/战斗与关卡.md)分**，每类写明进度怎么计数、上界从哪来，并写明「清理区域读的是指定目标而不是全歼」。
- [x] 写明**采集类目标的进度不区分物品来源**（资源点、容器、掉落都计数），理由是正典要求玩家随时知道还差多少。
- [x] 写明**进度的呈现接已有的那个 HUD 目标视图，不新建第二份**（`rules/Ui/HudViewModel.cs`），并写明多目标时 HUD 显示**当前未达成的那一条**、其余进手环。理由：两个来源里必有一个查不到出处。
- [x] 写明**关卡内只许查看、不许操作**（[玩法定位 · 手环的管理功能在关卡内不可用](../../canon/gameplay/玩法定位.md)）。
- [x] 委托实例的字段写全，至少覆盖来源、类型、目标条目、档位、上板日期与截止日期、报酬引用、编队限制。**报酬只存引用，不存数额。**
- [x] **作废有两条路径且后果相同**：失败与超期都让这条委托作废且不可重试；主线是唯一例外，个人请求根本没有这条路。
- [x] **达成与结束是两件事**：达成不结束关卡，返回入口撤离才结束；达成后返回算成功、未达成返回算撤退（奖励作废、已获物品保留）。写明两条走同一个动作，判据是「达成没达成」。
- [x] 结算那一节写明**完成结算各调哪个已有系统**，列成表：时间与精力扣除、奖励入背包、关系增量、经验与未出战补偿、统计事件总线。**每一格都指向已有系统，本页一个效果都不实现。**
- [x] 写明**时间与精力的消耗按「类型 × 档位」查表，委托模板不各自声明一遍**，理由是那是量纲不是内容。
- [x] 挂载点列全并写明「到此为止」，至少覆盖委托板（基地那块，以及城区建成后的两处）、事件系统往板上加一条、剧情节点触发主线任务、手环的通知与查询、统计事件总线、存档。
- [x] 边界那一节写明**不持有**：关卡怎么拼、敌人种类与行为、奖励数额与定价、剧情内容、事件触发机制、主线节点之间的解锁条件。
- [x] 文档里一个玩法数值都没有；「三类委托」「3 条额度」「3 天截止」这些量写链接不复述。
- [x] `python tools/check_docs.py` 0 项必须修复。

## 实现笔记

> 由 `/note-it` 在实现和评审之后填写。

### 设计决策

- **模糊点**：多目标任务在 HUD 上显示哪一条 —— 已有那张目标视图一次只装一条。
- **选择**：显示**当前未达成的那一条**，全部条目进手环。
- **理由**：那一格的标签宽度有上限（数在 `rules/Ui/HudLayout.cs`），装不下两条；而「还差几个」这条信息一次也只需要一条。轮显被排掉 —— 玩家扫一眼 HUD 的时候它可能正好在另一条上。

第二处：**失败不没收已获物品。** 正典只对「撤退」写明保留，对失败没写。按「失败比撤退付得更多」推的话反而更该保留 —— 失败已经付了时间、精力与伤病，再倒空背包就是把一次失手变成不可控的损失。

### 偏离

- **方案怎么说**：本条只写 `design/任务系统.md`，`GP-42` 另写关卡那份。
- **实际怎么做**：本条的文档里直接链了 `关卡系统`，而那份是在 `GP-42` 那一轮才落地的 —— 两条实际上是同一轮做完并一起验的。
- **为什么**：**两份互相引用的系统文档不可能各自独立跑绿。** 任务把类型、档位与遗址交给关卡，关卡把「采到了什么」报回任务 —— 接口表两边都要指到对方。可选项只有两个：其中一份先写成不带链接的散文、下一轮再补（那是两次工，而且中间那一版的接口表读起来像缺了一半），或者一起写完一起验。取后者，代价是本条的「`check_docs` 0 FAIL」是与 `GP-42` 合并之后才成立的，**写在这里免得被当成跑绿了却没跑**。

### 权衡

「委托与主线任务各成一份系统文档」考虑过。取一份，因为两边的目标、进度、达成判定与结算调用完全同形，差别只有几格 —— 分两份等于同一套逻辑维护两遍，而它们迟早分叉（一边加了多目标另一边没加）。

「时间与精力的消耗写进委托模板」考虑过，模板本来就是外置内容，看起来顺手。没选：那是量纲不是内容，写进模板之后调一次平衡要改几十个文件，而且内容作者无从判断一条委托「该耗多久」。

「给进度加百分比」考虑过（画进度条方便）。没选：目标条目是计数或布尔，折算成百分比传达的信息比「还差 3 个」少。

### 待确认

**一处是推断，未实测**：那句「HUD 那一格装不下两条」是从 `rules/Ui/HudLayout.cs` 的标签宽度上限推出来的，**没有实机量过**。验法写在文档的实机确认清单里 —— 作者摆一条长标签看看。
