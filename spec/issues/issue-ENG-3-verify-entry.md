# ENG-3：建立验收总入口

## 目标

代码仓有一条命令能完成整轮验收，且**每一步都不只看退出码**。

## 来源

不来自 PRD —— 本条是工程基础设施，在[台账](./README.md)直接立项。三条设计要求取自台账原文，继承前作已验证的做法。

两个必须覆盖的具体形状来自本项目自己踩的坑：[踩坑记录 29](../../reference/踩坑记录.md)（摘要说通过、有测试没跑）与[同 33](../../reference/踩坑记录.md)（导出泄漏不报错）。

## 依赖

`ENG-2`（已归档）—— 要先有工程、规则层与测试底座才有东西可验。

`ENG-11`（行尾守卫覆盖到代码仓）**不是**本条依赖，反过来它可以接进本入口。本轮刻意不做，理由见「权衡」。

## 验收标准

- [x] 一个总入口串联构建、测试、导出、跑产物，门禁只调它
- [x] 每步日志落盘；标准输出每步只有一行
- [x] 写一份带起止时间戳的运行摘要
- [x] 测试：断言运行器报的条数等于预期条数，光看「Passed」不算
- [x] 导出：校验产物确实生成、实际运行产物、并看包内清单有没有泄漏
- [x] 上一轮那个一次性的五步导出校验脚本被收编成 `tools/` 下的入口
- [x] 守卫自报覆盖量，并用真实缺陷形状自证（[WORKFLOW §6](../../WORKFLOW.md)）

## 实现笔记

### 设计决策

- **模糊点**：台账只说「一个总入口」，没说放哪个仓、叫什么。两仓各有一个 `tools/`。
- **选择**：代码仓 `tools/verify.py`，并让它启动时确认同级有 `project.godot` 与 `.sln`，不在就拒绝执行。
- **理由**：被验收的对象全在代码仓，三条命令的工作目录也都是代码仓根。放设计仓要跨目录找兄弟仓，等于让守卫依赖工作区布局，而设计仓 `check_docs.py` 的 `ROOT` 是刻意钉死在自己仓内的。防混淆不靠命名靠**落点自检** —— 命名依赖记性，自检能自动检出。

- **模糊点**：「预期的测试数量」从哪来。
- **选择**：从测试源码数 `[Fact]` 与 `[Theory]` 的 `[InlineData]` 行推出来，不写死常量；静态数不出来（`[MemberData]`／`[ClassData]`）时直接判失败要求显式登记。
- **理由**：两个数字必须来自互相独立的来源，否则拿运行器证明运行器等于没证明。而且死数字已经烂过一次 —— [ADR-0007](../../decisions/ADR-0007-测试底座选型.md) 里记的是 8 条，现在实际 10 条。**少算比不检查更危险**：期望值偏小时「有测试没跑」也能对得上。

- **模糊点**：怎么保证不是「跑在旧产物上」。
- **选择**：导出前把 `export/` 清空，于是「文件存在」直接等于「本轮生成」。
- **理由**：比对 mtime 要求脚本自己定义「多新才算新」，多一个会错的判断；清空之后存在性本身就是证据。`export/` 已被 `.gitignore` 忽略且每轮重建，清它没有代价。

- **模糊点**：怎么观察导出产物真的起来了。release 包没有控制台包装器（预设 `debug/export_console_wrapper=1` 只给 debug），而 GUI 子系统的 exe 在本机不往管道写东西（`setup_godot.py` 早前记下的同一条事实）。
- **选择**：用引擎自己的 `--log-file <路径>` 把日志落盘再读，断言启动阶段的三个标记都出现、无错误行。
- **理由**：不动产物、不动预设，也不依赖管道行为。标记钉在 `src/Main.cs` 那个脚手架上，所以入口会先确认标记还在源码里 —— 脚手架被替换时当场说清要同步改，而不是报一句看不懂的「没找到标记」。

- **模糊点**：局部跑怎么给。
- **选择**：`--upto build|test|export|smoke`，前置步骤一定跟着跑；范围不完整时摘要写明「不能当一次验收」，标准输出也打 `[WARN]`。
- **理由**：`--only test` 那种形态能跑出旧产物，`--upto` 结构上就跑不出来。局部跑成功仍返回 0，否则 `--upto` 没法用于调试；防误用靠摘要标注与 `runs.log` 记下的范围。

### 偏离

- **方案怎么说**：台账原文「标准输出只打一行摘要」。
- **实际怎么做**：**每步一行**（四行）加末尾的覆盖量与结果行。
- **为什么**：整轮只有一行时，看不出是哪一步失败，必须先打开日志才能定位 —— 而这条入口的用途正是快速判断能不能收。作者 2026-08-30 确认按本作的形态定，不对齐前作。

- **方案怎么说**：本条只做串联、日志与产物校验，不做新检查。
- **实际怎么做**：额外加了 `tools/.gdignore`，并让入口现场补 `logs/.gdignore`。
- **为什么**：这两个目录是本条自己往 `res://` 下加的。按踩坑记录 33 的判据，不放 `.gdignore` 就是下一次泄漏的来源 —— 等于本条一边加泄漏检查一边制造泄漏源。不算新检查，算不给自己挖坑。

- **方案怎么说**：台账没提自证。
- **实际怎么做**：多做了 `tools/selfcheck_verify.py`。
- **为什么**：[WORKFLOW §6](../../WORKFLOW.md) 对守卫的要求是硬的 ——「改了守卫必须自证」且「必须自报覆盖量」。**一个什么都不检的脚本也会全绿**，所以「跑过一次全绿」不构成它可信的证据。设计仓的同类要求已经做成了入口（`selfcheck_docs_guard.py`），这里照同一形态办。

### 权衡

**入口放哪**（三选一）：

| 方案 | 结果 |
| --- | --- |
| 代码仓 `tools/verify.py` | **采用。** 自包含，只 clone 代码仓也能验收 |
| 设计仓 `tools/` 里再加一个 | 否决：要跨仓找兄弟目录，守卫会依赖工作区布局 |
| 工作区根做成两仓共用 | 否决：工作区根不属于任何仓库，脚本不入库、不被 review。工作区本身是稳定的，所以理由**不是**怕丢，而是丢了可复核性 |

**包内清单怎么读**（二选一）：解导出日志，还是解 `.pck`。选了解 `.pck` —— 日志的详细程度随引擎版本与开关变，而清单是产物本身。代价是要自己实现格式解析，而第一版就解错了（见「待确认」下面那条已解决的记录）。

**`ENG-11` 是否顺手一起做**：否决，单独一轮。两条理由：本条自己已有两处必须用真实缺陷形状自证的判定，再塞一个守卫的自证会让验收报告长到没人逐条核；而 `ENG-11` 还有个未定取舍（抽成两仓共用 vs 代码仓建等价入口），那是「三周后会有人问当时为什么这么定」的东西。接口成本为零：本入口的步骤表加一步即可。

**测试步是否用 `dotnet test`**：无可选项 —— [ADR-0007](../../decisions/ADR-0007-测试底座选型.md) 与[踩坑记录 30](../../reference/踩坑记录.md) 已经裁定它在本项目跑不通，只能跑测试工程的可执行文件。

### 待确认

- 冒烟会用到 `%APPDATA%\Godot\app_userdata\Tinderhearth-The-Last-Class\` 的 `mods` 与 `saves`（`ENG-1` 那轮就已建）。入口只在摘要里报路径、**不删** —— 那将来是玩家真正的存档目录，验收工具去删它是个难坑。**作者 2026-08-30 确认按此办。**
- `export/` 里上一轮的产物会不会被下一次导出打进包：**推断不会**（都不匹配预设的 `export_filter="all_resources"` 与 `include_filter="data/*.json"`），**未实测**。要实测得手工连导两次不清目录。入口每轮清空 `export/`，让这问题不会发生。
- `.pck` 格式版本升到 5 时，`parse_pck()` 会**报错而不是猜着解**，需要人工照实测布局更新。这是有意的失败方向，不是缺陷。
- 构建那一步「认不出 `dotnet build` 输出形状」与导出那一步「产物缺失或空壳」两条分支**没有自证用例**，理由登记在 `selfcheck_verify.py` 的 `UNPROVEN_BRANCHES` 里（要伪造假输出，而伪造出来的不是真实缺陷形状）。
