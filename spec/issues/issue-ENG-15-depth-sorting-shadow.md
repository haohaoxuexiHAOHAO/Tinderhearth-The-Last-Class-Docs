# ENG-15：纵深排序与代码影子

## 目标

引擎层按纵深排序绘制，并由代码持有角色影子——它是纵深与跳跃高度的主要提示。

## 来源

- 正典：[战斗与关卡 · 战斗关卡的空间模型](../../canon/gameplay/战斗与关卡.md)「绘制按纵深排序」（作者 2026-09-09 定）
- SPEC：[`spec-combat-feel-core.md`](../spec-combat-feel-core.md) 的绘制顺序与影子一节
- 素材侧口径见 [`issue-ART-6`](./issue-ART-6-role-action-frames.md)：**影子不画进帧里**

## 依赖

`GP-15`（要有纵深位置才排得了序）、`GP-12`（主角节点）。

## 验收标准

- [x] 纵深靠后的先画、靠前的压在上面；同纵深时按脚底位置排。排序**与命中判定用的是同一份纵深值**，不许各存一份
- [x] 影子由代码绘制，不进精灵帧：位置取角色的**地面投影点**（纵深位置），不随跳跃升高
- [x] 跳跃时影子留在地面，并按高度变化（缩小或变淡），作为高度提示
- [x] 影子参数（尺寸、透明度、随高度的变化）集中进 `CombatFeel` 或同级落点，标未校准初值
- [x] 引擎探针判据：两角色纵深交换时绘制顺序随之交换；跳跃全程影子的地面位置不变；落地后影子与脚底重合
- [x] 不新增 `Camera2D` 派生类，不破坏 `Main.tscn` 探针链与既有相机专项

**这一条是纵深第一次能用眼睛看。** 但「好不好读」仍归作者实机：影子多大、缩多少、48px 带在满编时够不够看清排位，都不是机器判据能答的（密度归 `ENG-16`，尺寸与缩放归 `GP-6`）。

## 实现笔记

### 设计决策

- **模糊点**：排序用什么机制。Godot 有现成的 `y_sort_enabled`。
- **选择**：排序算在规则层（`rules/Combat/DepthRendering.cs`），引擎层只把序号写进 `z_index`。
- **理由**：正典要的是**两个键**（纵深为主、同纵深时脚底为次），而 `y_sort` 只按节点屏幕 Y 排一个键 —— 而屏幕 Y 里混着跳跃高度与纵深偏移，于是「跳起来」会被排成「往里走」，地形起伏也会把纵深主键压过去。正典点名这条是承重项：排错了，玩家看到的前后关系会与命中判定（`GP-16`）的前后关系相反，而这件事不报错。算在规则层的附带好处是它能脱引擎单测，引擎层只剩三件事：找出参与者、写 `z_index`、报覆盖量。

- **模糊点**：影子随高度「缩小或变淡」选哪个。
- **选择**：只缩小，不变淡。
- **理由**：不是偷懒 —— [像素绘制原则 §9](../../production/像素绘制原则.md) 把「透明度只使用完全透明或完全不透明」定为绝对规则，代码侧的落点是 `rules/Ui/HudPalette.cs` 的 `PixelColor` **连 alpha 字段都不给**（冷却遮罩因此用不透明色遮住而不是压暗）。半透明影子画上去就是屏幕上的插值像素，与半透明素材同一后果。缩小是像素风该有的做法：层次靠形状与色阶。

- **模糊点**：碰撞地面对应纵深带的哪个位置。
- **选择**：**带中线**，绘制偏移 = 纵深 − 24。
- **理由**：站在默认纵深的角色，绘制位置与物理位置重合。取带后沿（偏移恒为正）也能用，但那样所有角色会整体下移半条带，`GP-13` 那些按屏幕位置取像素的判据会量错地方 —— 它们量的是颜色，位移会让它们报出与颜色无关的失败。**代价一并记下**：地形也得画成一条 48px 厚的带子，否则角色在带内前后走时脚会离开画出来的地面线。

- **模糊点**：探针放哪。
- **选择**：新开 `scenes/DepthDev.tscn` 与 `tools/depth_dev.py`，13 条判据。
- **理由**：本条要验的两件事都需要专门摆位（两个角色重叠站在不同纵深、一次干净的跳跃），塞进 `PlayerDev` 或 `HitFeedbackDev` 的连续时序会踩到它们正在测的东西；而且判断「谁压在谁上面」要靠截图数像素，需要画面里没有别的东西在动。

### 偏离

- **方案怎么说**：条目只要求「引擎按纵深排序绘制，并由代码持有影子」。
- **实际怎么做**：另外改了 `TrainingDummy` 的画法（两个 `_Draw` 矩形改成挂在可视根下的 `Polygon2D`，闪白从换填充色实现），并给它加了纵深字段与 `PlaceDepth`。
- **为什么**：排序要两个角色，木桩必须有纵深。而木桩原来的身体画在自己的 `_Draw` 里，`_Draw` 不跟着子节点走 —— 纵深偏移就会漏掉它。把身体搬进可视根之后，**纵深偏移只有一处来源**（可视根的 `Position`），新增角色时漏不掉。闪白刻意**不用** `Modulate`：那是乘法，白色乘原色还是原色，闪白会静默失效（画面上木桩根本不变白，而所有逻辑判据照旧全绿）。

### 权衡

- **影子跟着宿主的 `z_index`，不单独一层。** 于是靠前角色的影子会压在靠后角色的身体上。正典没要求影子单独分层，单独分层要再引入一层 z 段位与它的分配规则。满编时若显得脏，那是 `ENG-16` 该看的。
- **射线每帧问一次地面，不用「记住上次在地面的高度」。** 记忆式做法在跳过坑时会把影子留在坑沿的高度，那时影子指的位置是错的、而画面上只是「影子有点怪」。代价是每个角色每帧一次射线查询。
- **射线的层掩码用 1，而主角也在层 1。** 层 1 是地形层，但木桩的 `CollisionMask=1` 靠主角在那一层实现「击退被主角挡住」（`GP-13` 的 wall-block 盯着）。所以射线只排除宿主自己，另一个角色若正好压在宿主正下方仍会被当成地面。本轮场景里不会发生（角色各自站在地面上），**要多角色叠在一起时得给地形一个专属层** —— 那要动 `GP-13` 的碰撞关系，归 A2 记账。
- **`z_index` 从 8 起（`DepthSortedLayer.ActorZBase`）**，给将来按纵深插进角色之间的前景装饰留出层号，本轮不预设分层规则。
- **`PlayerDev` 与 `HitFeedbackDev` 的地面没有改成带状。** 它们是单平面时代的探针，纵深在那里只是数值；改了会动它们正在测的画面。**代价**：在那两个场景里按 W/S 走纵深，角色看起来会浮在地面线上下。要看纵深就看 `DepthDev`。
- **`DrawOrder` 每帧分配一个下标数组与一个比较委托。** 评审时算过：同屏 20 个角色约 100–150 字节／帧，60fps 下约 9KB/s，离 .NET 的 gen0 阈值（几 MB）差几个数量级，一次 gen0 回收也是亚毫秒。**没改成传入复用缓冲区**：那会让规则层的纯函数形态变成带出参的过程，可测性变差，而换来的是量不到的收益。A2 满编实测若真出现 GC 尖峰再改，那时有实测数据可依。

### 待确认

- 影子的四个初值（宽 16、厚 6、最小 50%、缩到底的高度 32）全是未校准初值，归 `GP-6`。缩放曲线现在是线性，曲线形状要实机看才定得出来。
- 纵深带的地面配色沿用了开发场景的 `485750`，影子借 `HudPalette.Charcoal`（整屏最暗一档）。**世界侧的正式配色没有条目** —— `DOC-2` 覆盖的是界面色彩。等真美术进来时要一起定。
- 满编（15 敌 + 5 角色）时排序与影子还读不读得清，归 `ENG-16`。本条只证明了两个角色的情形。
- **影子只随离地高度缩放，攻击与闪避时形状不变**（作者 2026-09-09 实机报的：「看上去很奇怪」）。**不是缺陷，是当前设计的边界** —— 影子承担的是「站在哪一排」与「离地多高」两件事，姿态不在其中。但反馈成立：闪避翻滚时身体形状变化很大，脚下却是个一动不动的椭圆。三条候选各有代价：按当前动作查表给不同的椭圆宽（最省，但要维护一张表）；从精灵帧的 alpha 边界算出本体宽度（数据已经由 `ART-6` 的导入器量过，但它在 `tools/` 里、运行时读不到，得在载入时重算一遍）；把精灵压扁成剪影再画一次当投影（自动跟姿态，**但非整数缩放会破坏像素对齐**，与 `UI-3`／`ENG-13` 的整数缩放与最近邻冲突，除非压到 1/2 这类整数比例）。**作者 2026-09-09 选第二条并已实现**（从精灵帧算本体宽度），口径是「保留基本的阴影细节就好，不需要太细」。只让影子的**宽度**跟着当前帧变，形状仍是椭圆、中心仍在脚底 —— 不做压扁投影，因此不碰整数缩放那条铁律。

实现与两次实测修正：

1. **逐帧取，不按动作取最大值。** 先做了后者（同一动作内影子恒定，理由是躲开待机呼吸的抖动），**截图当场否掉**：轻击整段影子都是伸出后的 26px，而前摇帧身体只有 19px，影子比身体宽出一截、看起来像影子偏了。而实测 `idle` 的逐帧宽度是 `[19,19,19,19,19,19]` —— **我担心的呼吸抖动根本不存在**，那个权衡建立在没量过的假设上。
2. **宽度有下限，取角色实体宽（18px，与碰撞框同一常量）。** 逐帧数据暴露了另一件事：`walk` 是 `[18,11,13,18,20,11,13,17]`，因为整帧不透明宽度**含四肢**，手臂前后摆会让它掉到 11px。照抄会让影子以每四个物理帧一次的节奏缩到一半，而角色占的那块地没变。影子代表占地，所以取「实体宽与当前姿态宽的较大者」：走动时稳定（实测 16.20–18.00），出拳时跟着伸（待机 17.10 → 轻击命中帧 26.10）。
3. **宽度表按精灵表缓存，不按角色实例算。** 不缓存的话每个角色都重扫一遍：探针 spawn 六个替身就是 45 万像素，正典的同屏 20 个角色会是 150 万，而那是同一批图。**这个开销没有任何判据会报**（它只让载入变慢），发现它靠的是启动日志里同一行打了六遍 —— 所以宽度那行只在真正扫的时候打，打的次数本身就是「扫了几次」的量具。

**一个意外的交叉验证**：运行时用 C# 逐帧量出的最大值（19／20／25／20／27／29／36）与登记表「角色本体 最宽」逐个相同。两套独立实现（Python 导入器与引擎）互为量具，这比任何一边自证都强。
- **`DepthDev` 里打不着木桩**（作者 2026-09-09 实机报的）。本条只接了绘制，场景里**没有判定框与命中结算** —— 主角挥拳有动画、木桩没反应。刻意不在本轮补：现在接上会是单平面判定，纵深差满一条带也照样打中，那正是 `GP-16` 要改的错误行为，让作者先体验一遍反而添乱。`GP-16` 的验收标准最后一条（「同一横向距离下，纵深对齐时打到、纵深错开时打空」）需要的就是这个场景，接命中连纵深容差一起做。
- **作者实机怎么看**：`python tools/run_local_check.py depth_dev.py`（不带 `--probe`）。进场即是可读摆位 —— 主角在带中线、木桩在带前沿（更靠下、压在前面），两个影子各自落在自己那一排。A／D 横走，**W／S 走纵深**，空格跳（跳起来影子留在地面并缩小）。交互模式带相机跟随；探针模式刻意不带，因为它靠世界坐标当屏幕坐标取像素。

`Main.tscn` 的探针链未受影响，证据是 `verify.py` 的「跑产物」一步：导出产物启动后 `[启动]` 10 行、0 错误。

13 条判据分两组。**排序四条**：`sorted-count`（层自报覆盖量，漏挂一个角色不报错，所以要它）、`order-back-first`、`order-swaps`、`overlap-front-visible`。最后那条**去屏幕上数像素**而不是信 `z_index` 自报的数：z 写对了但绘制顺序没跟着变（比如两个角色不在同一层下、或被别的 z 值压过），排序判据照样全绿而画面上前后关系是错的。实测数值：木桩在前时重叠区有 306 个木桩色像素，交换纵深后降到 98。

**影子与偏移八条**：`depth-offset-signed`（往前画得更低、往后更高、带中线为零，全部从规则层导出）、`shadow-foot-on-land`、`shadow-follows-depth`、`shadow-ground-fixed`（跳跃全程逐帧核，滞空 32 帧）、`shadow-shrinks-in-air`（最小缩放实测 0.500，正好是登记的下限）、`shadow-restored-on-land`、`shadow-width-floor`（走满一整轮行走循环，宽度不掉到实体宽以下）、`shadow-width-follows-action`（**在 Active 帧量**，前摇帧的姿态与待机几乎一样、那时比较是空判）。另加 `screenshot` 与两条前提判据（`tick-frame-1to1`、`focus-kept`）。

**作者实机报的第三件：只按 W／S 走纵深时角色没有行走动画**（站着不动地在纵深上滑）。这是本轮遗漏的真缺陷 —— `PlayerActor.UpdateVisual` 选动作时只看 `HorizontalVelocity`，而纯纵深移动时它是 0，于是动作落到 `idle`。**不缺素材**：走纵深复用侧面行走姿态，belt-scroll 那一类作品都是这么做的（没有「往里走」的专用动画），正典也定了角色不因远近缩放、朝向只有左右两面。改成两个轴任一在动就算「在走」，并加判据 `depth-walk-visual`（`player_dev.py` 的纵深阶段本来就在按 W／S，逐帧核纵深在动时的动作名）。**用真实缺陷形状反证过**：把修复临时还原，该判据当场变红；恢复后 46/46。

这条的教训与上面那条影子偏移同源：**位置在变、判据全绿、只有眼睛看得出来。** 三轴分离改了运动模型，而动画选择是另一处按单轴写的代码，没人提醒它要跟着改。

**排缺陷记两笔。**

一是**机器判据全绿但画面是错的**：13 条判据首次全过之后看截图，木桩的影子落在脚底下方 24px。根因是射线挂在带纵深偏移的可视根下，起点已经偏移过一次；纵深往前（偏移为正）时起点落进地面碰撞体内部，`HitFromInside` 让命中点等于起点，于是量出来的「地面」也带着那次偏移，画影子时又加一次。**判据没抓到是因为它只核了主角**，而主角当时的偏移为负、射线起点在地面之上，那个方向恰好是对的。修法：射线挂宿主（地面是物理量，与绘制偏移无关），并把 `shadow-foot-on-land` 与 `shadow-follows-depth` 都改成**两个角色一起核**，一个偏移为负、一个为正。教训是「一个判据只覆盖了参数的一侧」这类漏洞看不出来 —— 得让判据自己跨过零点。

二是**前提判据失败时我查错了方向**：`player_dev.py` 一度报 `depth-back`、`depth-land-unlock`、`focus-kept` 三条失败，我先去查前两条玩法判据，加了诊断才发现诊断一次都不触发 —— 真正的原因是 `focus-kept` 报的那件事：窗口失焦时 Godot 释放全部按下的动作，探针合成的「按住」被悄悄松开，纵深于是停在半路。**前提判据失败时应当先重跑，而不是查下游判据**，这正是把它单列出来的用处。记进[踩坑记录 50](../../reference/踩坑记录.md)。
