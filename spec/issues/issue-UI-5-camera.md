# UI-5：相机五项行为

## 目标

俯视跟随、侧视 2 倍缩放、边界钳制、屏幕震动、演出镜头五项行为一次定完并落成一份两种视角共用的实现。

## 来源

- PRD：[`spec/prd-ui-framework.md`](../prd-ui-framework.md) 的 `US-003`
- [玩法定位 · 系统清单](../../canon/gameplay/玩法定位.md)点名这五项并写明"**行为不定下来，两种视角会各写一套**"

## 依赖

`UI-3`（侧视 2 倍缩放的有效视野是逻辑分辨率的一半，得先有分辨率）。

## 验收标准

- [x] 俯视跟随主角且有死区：角色在死区内移动时镜头不动 —— 硬死区，出了死区镜头只挪到"目标刚好
      贴在死区边上"；启动自检在两种视角下各验过"贴边不动、出一像素跟一像素"
- [x] 侧视为 2 倍整数缩放，有效世界视野 320×180 —— 缩放取 `UiMetrics.SideViewZoom`，不另定义；
      守卫拿正典写死的期望值核引擎自报的实际值
- [x] 相机在场景边界处被钳制，视口不越出地图，边界处不出现空白 —— 判据是**视口**在边界内而不是
      相机在边界内；视野比地图宽时改为居中（`expand` 下真会发生，见下）
- [x] 基地建造时相机可滚动，角色接近可建造区边缘时自动推镜（作者 2026-08-30 选的方案：不做缩放）
      —— 滚动经 `InputRouter` 读方向，推镜按可建造区四条边触发；**没有任何改缩放的入口**
- [x] 屏幕震动可在设置里关闭；关闭后重击不产生任何位移 —— 判据是**恒零位移**而不是"幅度调小"。
      设置界面归后续那一组，本条交出开关与它的判据
- [x] 演出脚本能接管相机并在结束时归还，归还后跟随行为与接管前一致 —— 取"凭据"形状，见设计决策三
- [x] 两种视角共用同一份相机实现，不是各写一套 —— 两道执行体：静态核"派生 `Camera2D` 的类型恰好
      一个且 `sealed`"，行为核"两种视角的判据名字集合完全相同"
- [ ] 作者实机确认 —— **攒到 `UI-8` 一起看**：真镜头 + 真 HUD + 插手柄，一次把 `UI-5`、`UI-7`、
      `UI-8` 三条签掉。单独看相机没有 HUD 参照，判不出取景挤不挤

### 立项前后的引擎实测（2026-08-31，Godot 4.7.2 mono，1280×720 窗口）

**一、相机落在分数像素上并不会破坏像素对齐。这条推翻了立项时的假设。**

做法：世界里铺一张 1px 棋盘格纹理，量"最小连续同色跑长"—— 每个世界像素在 ×N 下应当摊成 N 个
物理像素。三次截图（视口缩放 ×2、相机缩放 ×2，期望跑长 4）：

| 状态 | 最小同色跑长 | 与基线逐像素比 |
| --- | --- | --- |
| 相机位置 0（基线） | 4（统计 103,341 段） | —— |
| 相机位置 +0.125 世界像素（＝ 0.5 物理像素） | **4，一点没变** | **一模一样** |
| 相机缩放改 1.25（总缩放 2.5，非整数） | **2** | 被切开 |

原因算得出来：总缩放是整数 S 时，第 k 个世界像素的屏幕跨度是 `[kS+d, (k+1)S+d)`，它恰好包住
S 个像素中心，**与偏移 d 无关**。所以整数总缩放下平移多少都不改变采样结果。真会把像素块切成
宽窄不一的条的是**总缩放不是整数**，而那正是代码挡住的东西（缩放只收正整数）。

**所以相机位置取整的理由不是清晰度，是取景与运动可预期**，这条得改写下来：

- 0.5 物理像素的位移**渲染结果完全一样**，也就是说小于一个物理像素的镜头移动**根本不显示**。
  而物理像素的大小随窗口变（×2 到 ×6），于是同一个分数世界像素的位移在小窗口上看不见、在大
  窗口上看得见 —— 表现为"这台机器上镜头会抖，那台不会"。整数世界像素的位移在任何整数缩放下都
  是整数物理像素，两台机器上一样。
- 震动幅度同理：小于 1 世界像素的幅度在小窗口上等于没震。所以 `CameraFeel` 的屏幕像素量都要求
  能被侧视缩放整除，`CameraRig.Shake` 对除不尽的幅度直接抛。

**二、`Camera2D` 的内置钳制默认值是 ±10000000，不是 `int` 的极值。** 守卫核"没启用内置钳制"时
拿一台**引擎自己新建的** `Camera2D` 当期望值，不写死这几个数 —— 各版本改过它们，写死会让这条
检查在某次升级后静默变成永远通过。

**三、`--headless` 下取不到视口纹理。** `GetViewport().GetTexture()` 返回空（dummy 渲染后端），
硬取会灌一串 `Parameter "t" is null` 加 NullReference，而 `verify.py` 的跑产物那步正是 headless
—— 那些 ERROR 会让门禁判失败。所以像素实测在无渲染设备时显式跳过并打出理由，守卫（不带
`--headless`）反过来把"跳过"判成失败。

**四、`aspect="expand"` 让"视野比地图还宽"成为常态而不是边角情况。** 可建造区 40×30 格 ＝
640×480 世界像素，而俯视 1 倍缩放下逻辑视野宽度的**下限**就是 640 —— 宽窗口上视野一定比可建造
区宽。实测 3840×2130 的窗口得到逻辑 649×360。

### 设计决策

**一、一份实现，视角是构造参数。** `CameraRig` 一个类服务两种视角，视角只影响 `Zoom` 与由它换算
出来的可视尺寸和死区，其余判定逐字相同。引擎层 `GameCamera` 是 `sealed` 的 —— 派两个子类正是
"各写一套"最自然的形态，封起来让那条路在编译期就走不通。

执行体想清楚了才写的（这条规则本来最容易悄悄退化）：

| 退化形态 | 谁拦 |
| --- | --- |
| 新建一个平级的 `Camera2D` 派生类 | 静态：`src/` 下派生 `Camera2D` 的类型必须恰好一个 |
| 给 `GameCamera` 派子类 | 静态：必须 `sealed` |
| 规则层另建一套几何 | 静态：`rules/` 下带 `Camera` 字样的类型必须是登记在册的那四个 |
| 在编辑器里往场景拖一台裸相机 | 静态：`.tscn` 里的 `Camera2D` 必须挂 `GameCamera` |
| 某个行为只在一种视角下成立（另一边悄悄没跑） | 行为：两种视角的判据**名字集合必须完全相同** |

最后那条是关键：只核"两边都跑了"不够，得核"跑的是同一批"。`selfcheck_camera.py` 用真实缺陷
形状把每条都拦过一遍（11 条用例，覆盖守卫里全部 10 个检查函数）。

**二、死区写成屏幕像素，除以缩放得世界像素。** 一个数服务两种视角，取景因此一致 —— 实测两边都是
48×32 屏幕像素（俯视 48×32 世界像素、侧视 24×16）。这是"共用同一份实现"在数值上的形态；给某一
种视角单独设一个死区，规则层测试与守卫会同时失败。代价是屏幕像素量必须能被缩放整除，有测试盯着。

**三、演出接管取"凭据"，不取标志也不取调用方自存快照。** 这项是技术选择，不问作者：

| | 形状 | 为什么不选 |
| --- | --- | --- |
| 甲 | `rig.IsCutscene = true` … `= false` | 不阻止忘记复位；分不清"两段演出同时接管"与"接管了两次"；归还后的状态是"碰巧剩下什么"，而验收要求的是"与接管前一致" |
| 乙 | `var s = rig.Snapshot(); … rig.Restore(s)` | 比甲好，但快照会丢 —— 跨帧的演出得把它存成字段，存漏了不报错 |
| 丙（采用） | `var lease = rig.TakeOver("用途")` … `lease.Release()` | 见下 |

丙的四条性质都对着一个具体故障：接管那一刻由**相机自己**存下行为参数、归还时自己还原，演出脚本
记不住也没关系；凭据实现 `IDisposable`，`using` 让中途抛异常的演出也归还（演出最容易出错的地方
正是中途抛）；重复接管**抛异常**而不是静默覆盖，因为第二段悄悄顶掉第一段之后镜头会归还到错的
状态而没人知道；接管期间 `Follow` 与 `SnapTo` 都不许直接驱动镜头，要动只能经凭据 —— 于是"谁在
开镜头"在类型上就是明确的。接管必须写明用途，卡住时它是唯一能指认责任方的东西。

归还的语义定成：**还原行为参数（缩放、震动开关、边界），并让下一次跟随直接对准目标**。不补间 ——
演出可能把镜头带到很远，硬死区跟随会在第一帧补上整段位移，看起来是一次莫名的横移。想要软归还的
演出应当自己先把镜头摇回来再归还，那时它还握着凭据，做得到。

**四、硬死区，不做位置平滑。** 平滑要引入一个时间常数，那是第五个只能实机收敛的数；而且它算出的
是分数位置。正典要求相机行为可预期，硬死区的位移完全由目标位移决定。`PositionSmoothingEnabled`
有判据盯着必须为假。

**五、钳制自己实现，不用 `Camera2D.Limit*`。** 两个理由：内置钳制不启引擎测不了，而"钳制少一边"
的表现是"地图边上偶尔露白"，属于要凑巧遇到才看见的失效；更要紧的是 `expand` 撑出的"视野比地图
宽"局面下内置钳制会把镜头顶到一边、白边全挤到另一侧，而规则层那份显式改成**居中**，让露白对称。
`Limit*` 因此必须保持引擎默认，有判据核 —— 两份钳制同时生效会互相拉扯。

**六、钳制边界与可建造区是两个矩形。** 一开始想合成一个，算了一遍不成立：拿可建造区当钳制边界的话
横向根本不存在滚动（视野下限 640 ＝ 可建造区宽 640），宽窗口上视野还会更宽。所以钳制用地图
（可建造区加周边地形），推镜用可建造区。**这是"按 640 算钳制范围会错"的具体后果。**

**七、可建造区尺寸从 `game.json` 读，判据是"装进相机的那个值"。** 打印配置里的值只能证明配置读到
了，代码里另写死一份照样通过；所以 `CameraRig` 把装进去的尺寸暴露出来，守卫拿它与 Python 自己解
的 JSON 比对 —— 两个独立来源。自证里有一条"读错配置字段（宽度当高度用）"，它没有字面量、配置也
读到了，只有这个判据拦得住。

### 偏离

**一、相机代码放 `Rules.Ui` 而不是 `Rules.Foundation`。** 正典把相机归"跨系统基础设施"，照代码仓
`ARCHITECTURE.md` 那张表应进 `Foundation`。实际放 `Ui`，理由是依赖方向：相机的量全部从
`UiMetrics` 推导（缩放与有效视野来自逻辑分辨率与侧视 2 倍，死区写成屏幕像素再除以缩放），照表放
会让 `Foundation` 依赖 `Ui`，基础层依赖上层。输入（`UI-7`）此前已是同样的处理。**偏离已写进
`ARCHITECTURE.md`**，不是漏改。

**二、顺手给 `GameConfig` 的既有字段也加了校验。** 本条要加两个可建造区字段，写的时候实测确认了一件
事：位置参数 `record` 配 `System.Text.Json` 时 JSON 缺字段**不报错**，会拿 `default(int)` ＝ 0 填
进构造函数。0 格可建造区表现为"钳制退化、建造区不存在"，0 名册容量表现为"谁都招不进来"，两者都不
报错。这是同一个机制，改法是每个字段一行，所以三个字段一起校验了，并补了一条测试钉住"缺字段当场
抛而不是静默填零"。**严格说 `RosterCapacity` 超出本条范围**，但按"修就修根"处理：只修我加的那两个
字段等于留着那个机制。

**三、`CameraFeel` 的值是初值，没有实机收敛过。** 见待确认。

### 权衡

- **震动波形是占位的方波**（幅度线性衰减到 0、按固定频率换向、两轴换向速率差一倍走遍四象限），
  不做噪声。要保住的不变量只有两条：位移恒为整数世界像素、关掉时恒为 0。波形本身等实机收敛。
- **建造滚动经 `InputRouter.MoveDirection()` 接线，而建造界面还不存在。** 这条接线是能力演示：
  真正的建造界面要决定方向轴是驱动格子光标还是驱动镜头（`PanelNavigation` 的注释说的是跟着光标
  滚动），那是建造实现的事。现在这样至少证明了"相机读输入走门面"这条约定成立（`check_input_map.py`
  扫过 `src/` 确认没有直接轮询引擎）。
- **演出只做接缝，没有演出系统。** 正典要求第一版有剧情演出，复杂度限于"镜头 + 站位 + 对话 + 简单
  动作"，那是叙事侧。本条交出的是"能接管、能归还、归还后行为与接管前一致"。
- **`CameraProbe` 是脚手架**，与 `Main.ProbeUiSkeleton`、`InputProbe` 同一性质，`UI-10` 的端到端
  测试会替换它。引擎内测试底座还不存在（`ENG-6`），在它到位前"判据打进日志、Python 读回来判"是
  唯一能自动化的形态。

### 待确认

四个问题都是**只能实机收敛的手感数值**，已确认设计仓里没有归属：`design/数值模型.md` 与
`design/numeric-model-params.json` 里一条相机项都没有（搜过"相机／镜头／震动／死区／推镜"零命中），
`GP-6` 明写的四项是顿帧时长、精准防御判定窗口、连段帧数、读条时长，相机不在其中。

代码里已按算得出来的区间给了初值并由测试钉住量纲，所以**改这几个数不需要改结构**：

| 量 | 单位 | 允许区间与算法 | 当前初值 |
| --- | --- | --- | --- |
| 跟随死区半宽／半高 | 屏幕像素 | 下限一个栅格 8（更小就每帧拖镜头）；上限视野半宽的一半，横 160 竖 90（角色始终留在画面中间那一半）。须能被侧视缩放 2 整除 | 48×32（侧视换算 24×16 世界像素） |
| 震动幅度 | 屏幕像素 | 下限 2（＝ 1 世界像素 × 侧视缩放，比这更小在整数网格上表达不出来）；上限死区半高 32（别把角色晃出死区）。须能被 2 整除 | 4 |
| 震动时长 | 秒 | 0.05–0.25。下限一个震动周期（更短只看到一次跳动）；上限受正典那条邻居约束管着——顿帧不能长到打断连段输入节奏 | 0.12（换向 30Hz） |
| 边缘推镜触发余量 | 格 | 1–9 格。上限须小于侧视视野半宽 10 格，否则一进场就在推镜 | 3 格（48 世界像素） |
| 边缘推镜速度 | 世界像素／秒 | 须小于手动滚动速度——推镜是提示不是操作 | 128（8 格／秒） |
| 建造手动滚动速度 | 世界像素／秒 | 下限按"横穿 640 世界像素不超过 4 秒"取，即 ≥160 | 256（2.5 秒横穿可建造区） |

**这几个数该记在哪，推荐新立一条待办（`UI-12`：相机手感的实机校准），照 `GP-6` 的形状办** ——
本条给量纲、区间与校准办法，那条只做实测收敛。三条理由：不进 `design/数值模型.md`，因为那份持有
的是六组**平衡量**、每一项都进得了某条不等式判据并能被 `simulate_week.py` 重算，相机手感一条公式
都不进，混进去会稀释那份文档的可信度来源；不进 `game.json`，因为它是表现规则不是内容，正典的
"内容外置，规则不外置"把它划在外面，而且外置意味着 mod 能把死区改成 0；不并进 `GP-6`，因为那条
依赖 `ENG-6` 的逐帧工具与战斗实现，而相机手感现在就能靠"走两步看镜头跟不跟手"收敛，不必等。

另一条待确认：**建造模式下方向轴驱动格子光标还是驱动镜头。** 归建造界面实现，本条只留了两条能力。
