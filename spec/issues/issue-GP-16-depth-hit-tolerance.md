# GP-16：纵深容差命中判定

## 目标

命中改成必须同时满足横向范围与纵深容差两个条件，并让容差成为可调手感量。

## 来源

- 正典：[战斗与关卡 · 打击反馈](../../canon/gameplay/战斗与关卡.md)「命中要同时满足横向与纵深两个条件」（作者 2026-09-09 定）
- PRD：[`prd-combat-feel-core.md`](../prd-combat-feel-core.md) 的 `US-004`
- SPEC：[`spec-combat-feel-core.md`](../spec-combat-feel-core.md) 的命中判定一节

## 依赖

`GP-15`（要有纵深位置才谈纵深差）、`GP-11`（命中结算）、`GP-13`（现有命中检测与四件套，**其判定是单平面的，本条改它**）。

## 验收标准

- [x] 命中条件是横向与纵深**两个都成立**；任一不成立即不命中
- [x] 纵深容差进 `CombatFeel`，标未校准初值、归 `GP-6`
- [x] 击退方向按攻击者朝向沿横向施加；**纵深方向不施加击退**（除非后续设计明确要求），理由写进笔记
- [x] 同一次挥击对同一受击框仍只结算一次（`GP-13` 口径不变）
- [x] 规则层单测：横向够近但纵深超差不命中、纵深够近但横向超范围不命中、两者都够才命中、容差边界值
- [x] 引擎探针行为级判据：同一横向距离下，纵深对齐时打到、纵深错开时打空

## 实现笔记

### 设计决策

**1. 「两个条件都要」落在哪一层、以什么形状存在**

- **选择**：新建 `rules/Combat/DepthOverlap.cs`。纵深那一半是 `Within(a, b, 容差)`，两条件合判是
  `WithHorizontal(横向重叠, a, b, 容差)`；横向那一半以 `bool` 参数传进来。
- **理由**：横向重叠是引擎能力（`IntersectShape`），在规则层把矩形与旋转再实现一遍就是第二份事实；
  纵深反过来**只能**在规则层判（Godot 2D 两个轴被横向与跳跃高度占满，纵深不参与引擎碰撞）。所以
  本类的价值不是「算得更准」，而是**让「都要」有一个具名落点**：问「这一下算不算重叠」只有
  `WithHorizontal` 一条路，于是「只判了一个轴」写不出来。少了它，漏判纵深的代码与单平面时代的代码
  长得一模一样，而它不报错，只表现为隔着一排也能打中。它同时是那四条规则层单测（四种组合）能存在
  的前提 —— `tests/` 引不到 `src/`，横向那一半必须能当参数喂进来。

**2. 容差初值取 8，是算出来的**

- **选择**：`CombatFeel.HitDepthToleranceWorldPx = 8`，等于半个排间距。
- **理由**：正典几何账里有两个可读性结论（[战斗与关卡 · 48px 是怎么算出来的](../../canon/gameplay/战斗与关卡.md)）
  ——「纵深差 8px 以下基本重叠」、「相邻两排差 16px 时 30px 高的精灵仍读得出谁在前」。于是有一句能
  写成算式的话：**看上去重叠的打得到，看得出一前一后的打不到**。三条都对得上：差 ≤ 8 是正典说的
  重叠区；差 16（一整排）打不到且离容差有整整一倍余量，不会在浮点末位上摇摆；纵深连续不是轨道，
  同一排上两人各偏半排是常态，最坏差一排的一半，容差取半排刚好覆盖满。
- **算式只证明「有依据」，不证明「手感对」**：正典点名这条两个方向都会坏，哪边更难受只能实机看，
  归 `GP-6`。单测钉的是**关系**（隔一排打不到、带内存在打不到的位置），不是 8 这个数。

**3. 去重排在纵深判定之后**

- **选择**：候选先过纵深条件，通过了才进「本次挥击已命中集合」。
- **理由**：**打空不是打过。** 横向那一半本来就是这个口径 —— 框外的候选压根不出现在查询结果里，
  也就不会被登记；两个轴的口径必须一致，否则纵深会多出一条只在特定顺序下才看得出来的规则。反过来
  的形状是「贴着敌人挥空一次之后，站对了也还是空」，玩家会归因于判定不准而不是站位。这条由
  `depth-realign-hits-same-swing` 单独守着 —— 反证时把去重挪到纵深之前，它是 70 条里**唯一**变红的
  一条，其余 69 条（含 63 条既有判据）全绿。

**4. 纵深值经 `IDepthActor` 取，让编译器守住**

- **选择**：`Hitbox.Connects(bool, IDepthActor, IDepthActor)`，两个参数都是接口类型。
- **理由**：正典要求绘制排序与命中判定用同一份纵深值（排错了，玩家看到的前后关系会与判定相反），
  `ENG-15` 已把那句话落成这个接口。参数写成接口，本类就没有第二份纵深可用 —— 想另存一份得先改签名，
  那是改得见的。代码仓 `ARCHITECTURE.md` 原先记着「引擎层另建一份纵深变量，静态检查扫不出来，只能
  人工核」；这一条把命中这条路上的那一半变成了编译期约束，已同步改那份文档。

**5. 命中容差与阻挡阈值不共用常量**

- **选择**：`DepthOverlap` 本身不持有任何数，容差一律由调用方传入。
- **理由**：作者已裁定 `GP-17` 复用同一套重叠判定，但「打得着」的宽容量与「占同一格」的物理量是两件
  事，共用一个数会让一边调另一边跟着坏。两个数都归 `GP-6` 校准，各自独立。

**6. 非法容差抛异常**

负容差与 NaN 都让「差 ≤ 容差」恒为假，于是**每一次攻击都静默打空**、一行报错都没有，玩家读到的是
「判定不准」，查起来会先去翻判定框和动画。这类「配错了就全体失效」的量必须响着坏。`WithHorizontal`
里刻意先算纵深那一半再取合，不写 `横向 && Within(...)` —— 短路会让非法容差等到有人真站到面前才暴露。

**7. 击退为什么不给纵深（验收标准点名要写的理由）**

- 正典给击退的职责是「位移量随攻击轻重变化，让轻重攻击在手上有区别」，那是**沿攻击方向**推开；而
  攻击方向是横向 —— 侧视精灵只有左右两面，朝向本来就不含纵深（`GP-15` 定：纵深输入不改朝向）。
- 纵深位置是玩家的**站位决策**（正典：往里挪半步躲开）。被打一下就换排，等于攻击方替被攻击方做了
  站位决定，而那正是纵深挪步这个机制要交给玩家的东西。
- 纵深上没有碰撞体，纵深位移**挡不住**：横向击退有 `wall-block` 兜着，纵深上会把人推进物件里
  （`GP-17` 之前甚至推到带沿靠钳制兜）。
- 真要做还得新增一个「纵深击退量」未校准量，而现在没有任何设计需求要它。将来若有击飞／横扫类招式
  要在纵深上位移，那是**招式设计**，不是命中结算的默认行为。

代码上「不给」＝ `TrainingDummy.Receive`／`AdvanceCombat` 一行都不碰纵深（现状即如此），执行体是
`knockback-horizontal-only`：反证时让击退也推纵深，它当场报 `depth=32→40`。

### 偏离

- **方案怎么说**：SPEC §8.2 只要求纵深容差命中有规则层单测与引擎探针判据。
- **实际怎么做**：多加了两条**前提判据**（`probe-depth-rows-derived`、`depth-probe-fresh-swing`）与
  一个量具（`Hitbox.RejectedAsAlreadyHit`）。
- **为什么**：实现途中 `depth-off-row-miss` **假绿**过一次。它断言「纵深错开时 `Resolve` 返回 0」，
  而那个 0 是被上一阶段留在去重集合里的脏值挡下来的，不是纵深挡的 —— 判据声称测了纵深，其实没测。
  根因是 `Resolve` 的每挥击去重集合靠「相邻两次调用之间的 Active 上升沿」清空，而探针手动驱动连段、
  稀疏调用，跨挥击那次清空没发生（诊断输出证据：`hitSetSize=1`、`alreadyHit=True`）。所以补了
  「这个 0 是纵深造成的」的量具，并把契约写进 `Resolve` 的注释。详见[踩坑记录 52](../../reference/踩坑记录.md)。

第二条偏离：`knockback-horizontal-only` 的横向比较**用引擎自报的 `SafeMargin` 当容差**，不是自己挑
的 0.002。木桩受击时正贴着主角（探针的 `NearX` 是两个 18 宽实体刚好不互插的间距），第一次
`MoveAndCollide` 带一次脱离接触的推出，实测 `dx=8.0748` 对 8 —— 超出量落在 `SafeMargin`（0.08）以内。
挑一个刚好能过的数就是量具骗自己（[踩坑记录 49](../../reference/踩坑记录.md)）。纵深那一半仍按**精确
相等**判：纵深位置在规则层、没有引擎介入，本该分毫不动。两个轴量具不同是因为两个轴的所有权不同。

### 权衡

- **`Hitbox.Resolve` 的挥击身份是推断出来的，没改。** 去重集合的生命周期挂在**调用节奏**上，不挂在
  挥击本身上。生产路径每个非顿帧物理帧调一次，所以是对的（顿帧期间不调也安全，那几帧连段没推进）；
  稀疏调用就会拿到脏集合，表现是攻击静默不生效。要改根得让挥击的拥有者显式告知「新挥击开始了」，
  那是动连段机接口，而 63 条既有判据都建在现行行为上 —— **超出本条边界，记进「待确认」**。本轮做了
  三件替代：契约写进 `Resolve` 注释、`RejectedAsAlreadyHit` 让违反变成查得出来的、探针加
  `depth-probe-fresh-swing` 当执行体。
- **纵深容差只能在形状查询之后筛。** 候选集合按横向算，纵深超差的目标仍会被查出来再丢掉 —— 同屏满编
  时是白算的一点开销，量级归 `ENG-16`。靠碰撞形状表达不出来（纵深上没有轴、没有碰撞体）。
- **「纵深对齐时打到」这一头没有单独判据。** 它已被 60 多条既有判据全体覆盖：本场景两个角色都在带
  中线，纵深条件一旦漏判它们会成片变红。反证第一轮（`Connects` 退回单平面）确实是这个形状。新加的
  判据因此只覆盖既有判据盖不到的四种形状：错开一排打空、同挥击挪回同排打中、正好差一个容差打中、
  击退不碰纵深。

### 待确认

1. **容差 8 的手感（`GP-6`）。** 正典点名两个方向都会坏（太小＝玩家觉得判定不准；太大＝纵深挪步失去
   意义）。它与 `CombatFeel.DepthSpeedPixelsPerSecond` 是一对：容差一改，纵深挪步速度大概要跟着重调。
   本轮**未实机**，纵深容差在画面上要靠「挪半步就打不到」才感觉得到，宜与 `ENG-16` 满编探针同轮看。
2. **`Hitbox` 的挥击身份要不要显式化**（见「权衡」第一条）。`GP-17` 与 `GP-14` 接手命中循环时要先看
   `Resolve` 的调用契约那段注释。
3. **纵深上不施加击退这条是本轮按空间模型推出来的，作者未表态。** 理由列在「设计决策 7」，若作者要
   改成「重击也把人推开半排」，那是新的未校准量与新的招式语义，不是回改本条。

### 反证（七条新判据里反证了五条）

每一轮都是干净轮次（`tick-frame-1to1`、`focus-kept` 两条前提判据均通过），验完立刻还原。

| 注入的缺陷 | 预期变红 | 实际 |
| --- | --- | --- |
| `Connects` 退回单平面（忽略纵深） | `depth-off-row-miss` | FAIL，并级联 `depth-realign-hits-same-swing`（68/70） |
| 去重挪到纵深判定之前 | `depth-realign-hits-same-swing` | FAIL，且**是 70 条里唯一一条**（69/70） |
| 容差边界由「含」改成「不含」 | `depth-tolerance-edge-hit` | FAIL，唯一一条（69/70） |
| 击退也推纵深 | `knockback-horizontal-only` | FAIL，日志报 `depth=32→40`（60/67） |
| 容差调到一整排（16） | `probe-depth-rows-derived` ＋两条单测 | 三者全 FAIL，且前提判据先说清原因（67/70） |

剩下两条**没有做注入反证**，各有理由，不算已反证：

- `depth-probe-fresh-swing`：它是**实现途中真踩出来**的那个形状的执行体，证据是
  `logs/hit-feedback/20260911-125155` 与 `20260911-125557` 两份日志（`depth-off-row-miss` 假绿、
  下游三条同时变红）。真实故障比注入更强，但它证的是判据的**必要性**，不是「判据会变红」——
  要造那个形状得让上一阶段停在 Active 上，而上一阶段是 `ART-6` 的，动它超出本条边界。
- `depth-probe-restored`：清场判据，作用是别让本阶段留下的状态去毁下一条取色判据
  （`restored-pixel`）。它失败的形状就是「`restored-pixel` 因为无关原因失败」，而那条是既有判据 ——
  单独注入证不出新东西。

**未验证**：容差 8 的实机手感（归 `GP-6`）；满编密度下纵深容差够不够用（归 `ENG-16`）。
