## 一、界面与本地化

### 3. 同一页面的数据变化要就地重绘

- **症状**：操作已成功，但当前页面仍显示旧数量、旧选择或旧状态；切走再回来才更新。
- **根因**：只改了逻辑对象，没有重新生成当前内容区。
- **处理**：页面入口统一登记重绘方法；小范围更新用局部 `Rerender()` 清空并重建内容区，标题或整体形态改变时才重开整窗。
- **守卫**：页面刷新契约守卫测试检查页面刷新契约。

### 4. 容器和叶子控件承担不同职责

- **症状**：多行卡片重叠、标签高度为 0、子控件吃掉整卡点击。
- **根因**：`Button`、裸 `Control` 等不会根据任意子节点自动排版或上报正确最小尺寸。
- **处理**：多控件卡片用 `PanelContainer`、`MarginContainer`、`VBoxContainer` 等容器；可点击卡片走项目的可点击卡片组件。会换行的 `Label` 同时设置横向约束，卡内纯展示子控件使用 `MouseFilter.Ignore`。

### 6. 修改图片后先处理导入缓存

- **症状**：源码 PNG 已替换，截图或游戏仍显示旧图。
- **根因**：Godot 使用 `.godot/imported` 中的导入产物，不直接读取刚改的源文件。
- **处理**：通过项目既有导入/验证入口刷新缓存，再检查截图。导入前后都查看 `project.godot` 差异；`godot --import` 可能按当前引擎默认值重写配置，必须由项目配置守卫测试复核。

## 二、探针与引擎侧验证

### 7. 探针必须证明自己到达了目标

- **症状**：报告全是 `[OK]`，实际目标页没有打开，测到的是空根节点或上一个页面。
- **处理**：每个目标同时输出目标标识、可见控件数和关键节点；登记深层入口后先重建 C# 工程，再跑引擎侧检查。入口调用失败、目标控件为 0 或预期标题缺失都应失败。
- **原因**：托管回调异常可能只写引擎日志，不会传播给驱动；“进程还活着”不能证明页面完成初始化。

### 8. 一个进程只测一个场景或目标

- **症状**：单独运行通过，全量串行运行失败，或后一个目标继承前一个窗口最小尺寸、浮层和延迟释放节点。
- **处理**：场景冒烟和 UI 探针按目标分进程；驱动侧设超时，失败后单独复跑归因。报告必须说清是全量、分批还是单独运行。

### 9. 几何探针不能替代观感验收

- **能回答**：是否溢出、截断、缺焦点、嵌套滚动、弹窗尺寸是否越档。
- **不能回答**：配色、动效舒适度、像素缩放是否好看、焦点顺序是否顺手、音效是否刺耳。
- **处理**：自动报告与作者实机走查分别记录结论，不把“几何通过”写成“界面验收通过”。

## 三、逻辑、随机与存档

### 10. 周期结算按跨过的边界计算

- **症状**：一次推进多天时漏结算月度事件，或刚好落在边界时重复结算。
- **处理**：比较推进前后跨过的周期编号，逐个结算边界；不要只写“如果天数等于某值”。为跨零个、一个和多个边界分别测试。

### 11. 运行时状态要走完整存档链

- **症状**：当前会话正常，读档后字段归零、关系丢失或任务状态倒退。
- **处理**：新增持久状态时逐项检查：数据对象字段 → `Capture` → JSON 往返 → `Rebuild` → 当前版本回归。槽位档与传承档走各自的迁移路径分别管理，不能混迁。
- **边界**：存档契约守卫测试只证明数据对象与 JSON 完整，不自动证明业务对象映射完整。

### 12. 事件结算必须幂等

- **症状**：重进场景、重复信号或读档恢复后同一奖励发两次。
- **处理**：先以稳定 ID 或完成事实判断是否已结算，再执行副作用，最后记录完成。为重复调用写回归，第二次调用不得再次发奖或推进。

### 13. 显示值必须与实际生效值同源

- **症状**：面板显示基础值，战斗实际使用装备、难度或天赋修正后的值。
- **处理**：把“实际值”收敛到单一计算入口，界面和结算都调用它；不要在界面复制一套近似公式。

### 14. 随机性要沿完整数据流传递

- **症状**：测试传入固定种子，深层方法却新建随机数生成器，导致结果仍不可重放。
- **处理**：受保护随机走世界种子派生的随机流并传递子流；刻意允许读档重掷的入口才用独立的易变随机源。测试固定业务规模，只改变随机种子，不把种子误传成半径或数量。

### 15. 静态初始化不要依赖声明顺序

- **症状**：目录类加载时出现空引用，但相关静态表明明写在同一文件里。
- **根因**：静态字段按声明顺序初始化；前面的字段构造函数读到后面尚未初始化的表。
- **处理**：把依赖项声明在使用者之前，或改成显式延迟初始化；为目录完整性写直接回归。

## 四、测试、守卫与工具

### 16. 守卫必须用真实缺陷形状自证

- 先制造一处与历史缺陷结构相同的临时违反，强制重建测试程序集，确认守卫 `[FAIL]`；还原后再确认通过。
- 不用“看起来差不多”的假样例代替。守卫若只扫字符串字面量，就不能拿运行时拼接的样例证明它失效。
- 报告覆盖量时由守卫现场统计；不要把某次扫描的文件数、属性数或目标数写成永久契约。

### 18. 结果分类和缓动量要用合适判据

- 原因分类的数量相加必须等于总量；对不上说明分类漏项或重复，不应当作“有趣数据”。
- 带动画、阻尼或缓动的量不能用单帧精确相等判断。等待稳定窗口，或检查误差持续收敛且最终落入容差。

### 20. 进程、编码和日志以当前环境为准

- 交互终端出现过旧输出复用、退出码异常、GBK/UTF-16 重定向和续行状态残留；**2026-08-15 在 Kiro 交互终端再次复现**（卡在 `>>`、逐字符回显、成功命令报 `-1`），处置步骤见代码仓 `CONVENTIONS.md` §17.1，但仍不得反推为所有终端的固定行为。
- **2026-08-30 又添一种形态：长输出会被截断。** 跑 `ENG-3` 的自证（约两分钟、十来轮验收）时，终端显示到第 4 条用例就停住并给出退出码 `-1`，而工具实际跑完了全部 10 条。**输出截断处看起来就像执行结束**，据此判定会得出「卡在第 4 条」这种错的结论。可推广的处置：**会跑很久或输出很长的工具必须自己写日志，结论从文件里读**，别指望终端把话说完；调试期需要看进度时用后台进程再轮询。
- 当前规则：工具自行用 UTF-8 写具名日志并输出 `[OK]`、`[FAIL]` 或 `EXIT=`；同时核对进程结果与日志时间戳。两者冲突时先查原因，不重复粘贴长命令。
- 后台进程只用于确有持续运行需求的工具；收尾只结束本轮自己启动的进程。

### 21. 一种量具的"没报错"不是反证

- 2026-08-15 同一屏上，试玩桥看到"日志入口从可见控件消失"，几何探针却报"越界 0"。当时任一侧单独看都会给出错误结论：只看试玩桥会当确凿缺陷、只看探针会判没问题。
- 规则：两种量具结论冲突时，**先查明为什么，不选一个相信**；查明前两侧都不得作为结论依据，也不得互相反证。
- 结论写法上要区分"某工具测到"与"缺陷成立"，并写明另一侧为何测不到。

### 22. 固定帧数收敛不等于界面已停下

- 探针原先等固定帧数就开测，量到的是"正好那一帧的样子"。同一份代码连跑三次，教学战屏的可见控件在 238/244 之间跳，据此做的跨运行对照全是噪声（曾因此报出一个"少 21px 可用高度"的差值并撤回）。
- 现行做法：UI 探针的「安静已稳定」检查要求连续 6 帧「可见控件数 + 根视口内容最小尺寸」不变才开测；等到上限仍在变就照当前帧测量但**记一项问题**并标注「不可跨运行比较」，绝不静默打 `[OK]`。
- 更要紧的判据：**内容本身随机的屏，跨进程 A/B 在原理上就无效**（深层目标每组一个独立进程）。教学战出手顺序随机 ⇒ 当前行动者的技能数不同 ⇒ 控件数必然不同。要比较就先固定该场的随机源，或只比与行动者无关的不变量。
- 排查这类问题时，第一步是**补对照条件**（例如"只起战斗、不点任何东西"那一组），否则分不清变化来自你的动作还是来自场景本身。

### 23. 目录层直接拼玩家可见文本＝绕过本地化

- 前作目录层曾直接返回玩家可见的格式化字符串（如「受伤 +25%」、「策略点 1」），这些字符串**没有文本键**，所以多语言界面照样显示原文，且任何翻译覆盖率守卫都看不见。
- **判据**：逻辑层与数据目录只提供事实（数值、成本、冷却），**显示串一律在表现层由单一渲染器按文本键生成**；同类缺口目前**没有自动守卫**能发现，新增玩家可见短串时人工核对。

### 24. 往有配额的文档补内容前先估长度

- **属机制类，直接生效**：划掉专有名词后剩下的判断仍然成立 —— 有配额的文档补内容前先估长度，别用一个警告换掉另一个。

### 25. 蒸馏文档必须逐段对原文，不能凭记忆重建

- 规则：整份重写前后都要与 `HEAD` 版本逐节比对，尤其是模板化小节（归档三问、验收标准）。压缩允许删过程，不允许改口径。

### 26. 用 git 取文件清单必须关掉 `core.quotepath`

- 2026-08-25 写 `check_docs.py` 的 `--changed-only` 时，用 `git status --porcelain` 取改动清单。git 默认 `core.quotepath=true`，会把非 ASCII 文件名转义成 `"canon/world/\344\270\226..."` 这种八进制。按原样拼路径得到不存在的文件，于是**全部中文名文档被静默跳过** —— 检查器报「0 项必须修复」，实际只看了 12 份中的 ASCII 那一半。本项目文档大半是中文名，等于检查器假装在工作。
- 发现它的唯一原因是**自报覆盖量**：输出里印了「扫描 12 份／全库 24 份」，数字对不上才查出来。没有这一行，这个缺陷会一直潜伏。
- 现行做法：① 取路径用 `git -c core.quotepath=false status --porcelain -z`，`-z` 的 NUL 分隔还能避免文件名里的空格与引号切错字段；② 重命名（`R`/`C`）在 `-z` 模式下会多输出一个原路径字段，要跳过；③ 问不出清单（没装 git、不是仓库）时**退回全量扫描并打印警告**，不能当成「没有改动」。
- 可推广的判据：**任何“只处理一部分”的优化，都必须同时打印实际覆盖量与应覆盖量。** 静默漏检比慢一点坏得多，因为它把「没检查」伪装成「检查通过」。

### 27. 用 shell 管道读命令输出的中文＝读乱码

第 26 条的另一半：那条讲 git **输出的文件名**被转义，本条讲**输出的内容**被重编码。

- **症状**：2026-08-29 做文档评审时用 `git diff | Select-String` 取被删除的行，拿到的中文全是 `缁ф壙杈圭晫` 这类乱码。同一条 `git diff` 直接执行时显示正常，一进管道就坏。
- **根因**：PowerShell 在进程间传递时按控制台代码页重新编码，git 的 UTF-8 输出被破坏。同一现象也出现在 `python xxx.py | Select-Object` 上 —— 脚本自己 `reconfigure(encoding="utf-8")` 也救不了，因为破坏发生在管道那一端。
- **危害不是不好看，是结论失真**：评审规则要求「逐段对照原文、不许凭记忆」，而据乱码做的对照**既不是对照原文也不是凭记忆，是凭猜** —— 而且它看起来像做过了。本次靠它才发现自己漏改了一处正典，若继续用乱码对照就会漏掉。
- **处理**：需要读取命令输出的**内容**时，写一段 Python 用 `subprocess` 直接拿 `bytes` 再 `decode("utf-8")`，自己 `print`，**不经过 shell 管道**；取文件名另加 `-c core.quotepath=false`（第 26 条）。一次性用完即删，不留在 `tools/`。
- **守卫**：`.kiro/hooks/command_guard.py` 的「管道 + python/git → 作者确认」规则（`DOC-8`，2026-09-01 上线）。拦截形态：命令同时含管道符与 `python`/`git` 关键字则转作者确认，不直接拦下——因为「git log | head」这类不含中文输出的命令不必拦，让作者看一眼命令自己判断。自证见 `selfcheck_command_guard.py` 的「管道+python」与「管道+git」两条用例。

### 28. 编辑工具可能把整个文件的行尾改成 CRLF

- **症状**：2026-08-29 验收时 `git diff --check` 报 `reference/踩坑记录.md` 的 CRLF 将被替换为 LF。对照 `git show HEAD:<路径>` 后确认：HEAD 版本 191 行纯 LF，编辑后变成 **201 行全 CRLF** —— **整个文件**被转换，不只是改动的那几行。同一轮里另外 12 份 md 用同样方式编辑却保持了 LF，所以这不是必然发生，而是**偶发且无提示**。
- **规模比当时以为的大**：2026-08-30 行尾守卫上线后第一次全库扫描，当场揪出**三份此前一直没人发现的全 CRLF 文件**（`production/像素绘制原则.md` 167 行、`production/文案写作规范.md` 186 行、`reference/学习CSharp-Java程序员向.md` 700 行），三者在 HEAD 里都是纯 LF。也就是说这不是「偶发一次」，而是**长期存在且从未被察觉**。
- **为什么要紧**：本仓库 `.gitattributes` 钉了 `* text=auto eol=lf`，所以提交时索引会被规范化，仓库内容不受影响 —— 单个 md 文件的工作区行尾是低危的。**但同一个机制作用在 `.githooks/pre-push` 上就是高危**：那是 `#!/bin/sh` 脚本，带 `\r` 时 Git Bash 报 `bad interpreter: /bin/sh^M` 直接不执行，**文档准出检查静默失效**。那次故障是这份 `.gitattributes` 存在的原因，见文件内注释。
- **`git diff --check` 比「只给 warning」更不可靠**：上面那三份文件被发现时，`git status --porcelain` 把它们报成**未修改**，`git diff --check` **一个字都不输出**、退出码 0。原因是 `eol=lf` 让 git 比对前先把工作区内容规范化，于是**压根不存在 diff**。所以它不是「警告了但退出码为 0」，而是对「整份转 CRLF 且无其他改动」这种形状**结构性失明** —— 2026-08-29 那次能看到警告，只因为那份文件同时有内容改动。**任何依赖 `git diff --check` 判行尾的做法都不成立。**
- **处理**：跑 `python tools/check_docs.py`，行尾不合规直接判 FAIL；要修就跑 `python tools/check_docs.py --fix-eol`（按 `.gitattributes` 声明的方向改，两个方向都管）。不要再现场写一次性替换脚本。
- **守卫**：`check_docs.py` 的 `check_line_endings`（`ENG-9`，2026-08-30 上线）。策略不在 Python 里复述，而是用 `git check-attr` 问 `.gitattributes` 要 —— 改了声明，守卫自动跟着变。它按字节数 `\r`，二进制按 git 自己的判据（前 8000 字节内有 NUL）跳过；这条不可省，实测 `git check-attr eol -- x.png` 因为 `*` 通配也返回 `lf`，而 PNG 文件头本身就含 `\r\n`。自证见 `selfcheck_docs_guard.py` 的七条行尾用例（含「二进制未被误报」与「`.bat` 必须 CRLF」两个反向断言）。

### 29. 测试摘要说「通过」，可有一个测试压根没跑

- **症状**：2026-08-30 试 GdUnit4Net 时，`dotnet test` 打的是 `Passed! - Failed: 0, Passed: 1, Skipped: 0, Total: 1`，**退出码却是 1**。工程里明明有 2 个测试，其中那个 `[RequireGodotRuntime]` 的引擎内测试连不上引擎（日志里有 `Failed to connect: Connection timeout`），然后**从计数里整个消失** —— 既不算失败，也不算跳过，`Total` 直接从 2 变成 1。
- **为什么要紧**：这是[WORKFLOW §7](../WORKFLOW.md)「退出码为 0 不等于成功」的**反面形态**，也更阴险：摘要说通过、退出码说失败。只看摘要会放过它；只看退出码会知道失败但不知道少了什么。**一个没跑的测试被当成了没问题。**
- **本例的根因是布局**：测试工程当成 Godot 工程的兄弟目录时连不上；测试代码放进 Godot 工程内部就正常（2 个全过、退出码 0）。所以它不是「4.7.2 不兼容」—— 我第一次就差点写成那个结论，是靠退出码与摘要矛盾才没写错。
- **处理**：**核对数量，不看结论。** 预期几个测试就断言报告里是几个，对不上直接判失败。退出码与摘要矛盾时，先信矛盾本身：一定有东西没跑。
- **守卫**：代码仓 `python tools/verify.py` 的测试那一步（`ENG-3`，2026-08-30 上线）。期望条数**不写死**，从测试源码里数 `[Fact]` 与 `[Theory]` 的 `[InlineData]` 行推出来，跟运行器报告的 `Total` 比 —— 两个数字来自互相独立的来源，而运行器自己的发现流程正是本条里失灵的那一环，拿它证明自己等于没证明。死数字也已经烂过一次：ADR-0007 里记的是 8 条，现在实际 10 条。静态数不出来（`[MemberData]`／`[ClassData]`）时直接判失败要求显式登记，不静默少算。自证见 `selfcheck_verify.py` 里那条「源码里有测试没被编译进去」的用例。

### 30. .NET 10 上 `dotnet test` 与 xunit.v3 跑不通，改直接跑测试可执行文件

- **症状一（两条协议不能共存）**：给 `net10.0` 工程同时装 `xunit.v3`（自带 Microsoft.Testing.Platform，简称 MTP）和 `Microsoft.NET.Test.Sdk` + `xunit.runner.visualstudio`（VSTest 那条路），`dotnet test` 直接构建失败：`Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later`。**同一个测试工程里只允许一条测试协议。**
- **症状二（换成 MTP 后零测试）**：只留 `xunit.v3`，再按官方文档在 `global.json` 写 `{"test":{"runner":"Microsoft.Testing.Platform"}}`，VSTest 那个错没了，但结果是 `Zero tests ran`、退出码 5 —— 而同一个程序集用 `dotnet run` 跑得出 8 个测试。
- **根因**：`xunit.v3` 4.0.0 生成的可执行文件是**xunit 自己的 in-process 控制台运行器**，不是 MTP 测试模块 —— 拿 MTP 的列测试选项去问它会得到 `unknown option`。于是 `dotnet test` 在用 MTP 协议对一个不说 MTP 的程序说话，自然一个测试都发现不了。
- **试过但无效的四种开关**（记下来免得再试一遍）：MSBuild 属性 `TestingPlatformDotnetTestSupport`、`UseMicrosoftTestingPlatformRunner`、仓库根 `dotnet.config` 的 `[dotnet.test.runner]`、`global.json` 的 `test.runner`。前三个无效，第四个能切到 MTP 但换来症状二。
- **处理**：**不用 `dotnet test`，直接跑测试工程的可执行文件**（`dotnet run` 指定测试工程）。这是 xunit v3 的一等路径而不是绕路 —— 它的测试工程本来就是可执行文件，退出码两个方向都实测可信（全过 0、有失败 1）。代价是 IDE 测试资源管理器的集成**未验证**，需要时另查。
- **顺带一条实测**：`gdUnit4.test.adapter` 3.1.1（当时的最新**稳定**版）依赖 `gdUnit4.api >= 5.1.0-rc5`，是**预发布**版；把 api 钉在稳定的 5.0.0 会直接 NU1605 报降级 —— **不存在全稳定版组合**。选它就得接受预发布依赖。
- **守卫**：**只能人工留意。** 值得记的判据有两条：**一个测试工程只允许一条测试协议**；**换测试框架或升 SDK 后，先确认测试数量不是 0** 再相信任何「通过」。

### 31. `ImplicitUsings` 让 Godot 的几个类型名变歧义

- **症状**：`ENG-2` 建工程时写 `FileAccess.Open(...)` 直接编译失败：`error CS0104: 'FileAccess' is an ambiguous reference between 'Godot.FileAccess' and 'System.IO.FileAccess'`。
- **根因**：`ImplicitUsings` 会自动引入 `System.IO` 等命名空间，而 Godot 有若干同名类型。`FileAccess` 是撞得最狠的一个，`Error`、`Environment`、`Path`、`Color` 之类也都有撞的可能。
- **处理**：在**用到它的那个文件**顶部取别名（`using FileAccess = Godot.FileAccess;`），不要为此关掉 `ImplicitUsings`。理由是范围：关掉会让全仓每个文件都要手写一堆 `using`，而别名把歧义在真正出现的地方解决一次，读代码的人还能一眼看出用的是哪个。
- **守卫**：**编译器就是守卫** —— 这条会当场报错，不会静默。记在这里只为省下第二次查它的时间。

### 32. 「导出后 `res://` 只读」是错的，而且它写起来还报成功

- **实测**：2026-08-30 用导出产物（Windows、非嵌入 pck）往 `res://zz-probe.txt` 写文件，句柄**非 null**、`GetOpenError()` 返回 **Ok**，也就是**写成功了**。文件落在**可执行文件同级目录**里 —— 不是项目根，也不在 `.pck` 内部。同一次运行里 `user://` 写入也成功。
- **所以那条流传很广的说法要改**：只有**已经打进 `.pck` 的条目**才真正改不了；`res://` 这个前缀本身在导出后是可写的。此前本项目文档按「导出后 res:// 只读」写过 mod 路径的理由，那个理由不成立。
- **为什么要紧**：这类错误结论会静默地把决定建在空气上。本例里**结论（mod 放 `user://`）是对的，但理由是错的** —— 而错理由会在下一个决定里被复用。正确的理由是三条：exe 同级目录不按用户区分（多用户共享安装时互相干扰）；真实安装位置常常写不了或会被抹掉（`C:\Program Files` 要提权，Steam 的「验证文件完整性」会清掉不在清单里的文件，玩家 mod 会莫名消失）；Steam 云存档要求可预测的按用户位置。
- **可推广的判据**：**「写不了」这种否定式结论必须实测，不能靠常识推。** 而且要连「它失败时是怎么表现的」一起测 —— 本例中失败与成功的返回值完全一样（都是非 null + Ok），只看返回值根本分不出来，得去文件系统里找那个文件到底落在哪。
- **守卫**：**只能人工留意。** 但有一条便宜的做法：凡是「某处不可写／不可改」的假设，验证时都去文件系统确认文件的实际落点，而不是只看 API 的返回值。

### 33. Godot 会把 `res://` 下所有子工程的源码与构建中间产物打进发行包

- **症状**：2026-08-30 首次导出，日志里逐个列出被打包的文件，其中有 `rules/**/*.cs`、`tests/**/*.cs`、`rules/obj/project.assets.json`、`tests/obj/...`、`*.deps.json`。资源包 **182 KB**，而实际该发行的内容只有 **8.5 KB**。
- **根因**：Godot 工程根就是仓库根，而导出预设的 `export_filter="all_resources"` 会把 `res://` 下的一切资源打包 —— Godot 把 `.cs` 当 `CSharpScript` 资源，`obj/`／`bin/` 里的 JSON 则是普通文件。这些目录被 `.gitignore` 忽略**不影响 Godot**，两者是各自独立的忽略机制。
- **泄漏的到底是什么**：`.cs` 条目在 `dotnet/include_scripts_content=false` 下是空占位（改完后在包里搜方法名与 `using Godot;` 都未命中），所以主要泄漏物是**构建中间产物**，其中 `project.assets.json` 含**本机 NuGet 绝对路径**。附带是 95% 的体积浪费。
- **处理**：在每个不需要被 Godot 看见的子目录放一个 `.gdignore`（本项目是 `rules/`、`tests/` 与 `tools/`；`logs/` 不入库，那份由 `verify.py` 现场补）。它只挡 Godot 的资源扫描，不影响 MSBuild —— 程序集照旧通过 csproj 的 `ProjectReference` 参与构建与导出，实测导出与运行都正常。
- **可推广的判据**：**新增任何不含 Godot 类型的子工程时，同时放一个 `.gdignore`。** 并且验收导出时要**看包内清单**，不只看包能不能生成 —— 泄漏不会报错。
- **守卫**：代码仓 `python tools/verify.py` 的导出那一步（`ENG-3`，2026-08-30 上线）。它自己解 `.pck` 读包内清单，不看导出日志 —— 日志的详细程度随引擎版本和开关变，而清单是产物本身。`.cs` 单独判，因为它有一种合法形态：`src/**/*.cs` 一定在包里但只是 1 字节空占位（`dotnet/include_scripts_content=false`），所以判据是「`src/` 以外出现 `.cs`」或「任何 `.cs` 带内容」。解析失败一律报错而**绝不返回空清单** —— 空清单会被读成「0 条泄漏」，那是比不检查更坏的失效方向。自证用的就是本条的真实形状：把 `rules/.gdignore` 挪走再导，实测当场揪出 20 条泄漏。

### 34. 提交信息第一行后面没有空行，整条信息都会变成标题

- **症状**：2026-08-30 提交 `ENG-9` 时把标题和正文各写一行、中间没留空行，git 把**全部 862 个字符都当成了标题**，正文为空。`git log --oneline` 会渲染成一行 862 字符，历史直接不可读。编码没问题（UTF-8 正常），坏的只是结构。
- **根因**：git 的「标题」定义是**第一个空行之前的全部内容**，并把其中的换行替换成空格。不是「第一行」。
- **处理**：标题后**必须空一行**，段落之间也空行。用 `-F <文件>` 传信息时尤其容易忘，因为文件里看着已经分段了。提交后用 `git log -1 --format=%s` 复核标题长度 —— 这是唯一能当场发现的办法，`git commit` 自己的回显看不出来。
- **守卫**：**当前只能人工复核。** 值得注意的是这条缺陷**提交时不会有任何报错**，和第 28 条同一类：声明看着对、实际不对、而且没人提醒。

### 35. 自证工具的「还原」必须覆盖被测系统的副产物，否则它自己留下的垃圾没人看得见

- **症状**：2026-08-30 写 `ENG-3` 的自证入口时，有一条用例故意挪走 `rules/.gdignore` 来复现第 33 条那种泄漏。还原时我把 `.gdignore` 放了回去，但 Godot 在那段时间里已经把 `rules/**/*.cs` 当资源扫了一遍，生成 **8 个 `.cs.uid`** 留在仓库里。
- **为什么没被发现**：自证的最后一步是「还原后复验」，而复验判据是「完整验收重新变绿」。那 8 个文件**不会被打进发行包**，所以复验确实全绿 —— **自证工具自己造的垃圾，恰好落在它自己的判据看不见的地方。** 最后是 `git status` 里多出 8 行未跟踪文件才暴露的。
- **可推广的判据**：「注入 → 验证 → 还原」这套做法里，**还原要撤的不只是你写过的文件，还有被测系统在注入期间产生的副产物。** 判断办法很便宜：还原后看一次版本库状态，多出来的东西就是漏收的。
- **顺带一条更一般的**：一个工具的「自己验自己」总有盲区，因为盲区正是它判据的补集。所以自证之外还要有一个**判据不同**的检查（这里是 `git status`），否则盲区永远不会被看见 —— 与第 21 条「一种量具的没报错不是反证」是同一件事的两种形态。
- **守卫**：**只能人工留意。** 让检查器去判断「哪些文件是某次注入的副产物」需要它理解被测系统的行为，代价远高于收益。可观察形式是**每轮验收报告版本库状态**。

### 36. 导出产物的输出读不到，因为 release 包没有控制台包装器

- **症状**：2026-08-30 做 `ENG-3` 的冒烟步骤时要读导出产物打印的启动日志，用 `subprocess` 开管道拿到的是**空的**，而产物退出码是 0 —— 「退出码 0 加零输出」看起来像跑通了，实际什么都没证明。
- **根因两层**：导出预设的 `debug/export_console_wrapper=1` 是「只给 debug」，所以 release 产物**没有** `*.console.exe`；而 GUI 子系统的 exe 在本机不往继承来的管道写东西（同一条事实早前在 `setup_godot.py` 取编辑器版本号时就撞过，那里的处置是改用 `*_console.exe`）。
- **处理**：用引擎自己的 `--log-file <路径>` 把输出落盘再读，配 `--headless --quit-after <帧数>`。**不动产物、不动预设、不依赖管道行为**，而且日志是 UTF-8，中文不会坏。
- **可推广的判据**：**「进程还活着」和「退出码是 0」都不能证明它干了活，得看它自己说了什么。** 反过来，一个程序的输出取不到时，先问它是不是压根没往你监听的那个地方写 —— 别急着怀疑它没跑。
- **守卫**：`verify.py` 的冒烟步骤断言启动阶段的标记逐个出现且无错误行；**产物一个字都没输出时直接判失败**，不接受「退出码 0」这一个证据。

### 37. 数值算错好查，度量算错查不出来

- **症状**：2026-08-30 做 `GP-2` 的七天推演，「粮食缓冲」判定报 0.67 天（要求 1–2 天）。第一反应是起始粮食给少了，但翻代码发现是**度量写错了**：我在收获那一刻先扣掉当天的口粮再算缓冲，而收获送达时当天的饭还没吃 —— 于是缓冲少算了整整一天。真实值是 1.67 天，参数本来就是对的。
- **为什么危险**：算错的数**看着完全正常**。0.67 天是个合理的数，如果判据的区间当初定成 0.5–2 天，它就直接通过了，而所有下游结论都会建在一个错的度量上。数值错了容易被判据拦住；度量错了会连判据一起骗过去，因为判据也用同一个度量。
- **本轮另有两处对照**：战力差 8.62 倍与主角轻攻击 3.4 点伤害都是**参数**错，判据一跑就拦下。只有这一处是度量错，靠的是我去核算式才发现。
- **可推广的判据**：**一个判定不成立时，先问「这个量的定义对不对」，再问「参数对不对」。** 顺序反了会去调一个本来正确的参数，把度量错误固化成「调好了的数」。判断办法很便宜：手工复算一个最小例子（三个人吃三天饭），看算式给的数和你数手指头得到的数一样不一样。
- **守卫**：**只能人工留意。** 检查器判不了「这个量的定义符不符合意图」—— 它只能验算式自身一致。可观察形式是每条判据都写出算式与一个数值例子，让读者能自己核一遍（`design/数值模型.md` 的判据表就是按这个写的）。

### 38. 探针在被测节点的上游改状态，会被它自己的每帧同步抄回去

- **症状**：2026-08-31 做 `UI-5` 的反证，探针把相机位置挪到分数像素后截图，量出来「像素块一点没变」。看起来像引擎自己会做像素吸附，而项目设置里吸附是关着的 —— 结论直接反了。
- **根因**：探针是父节点、被测相机是子节点，Godot 按**父先子后**的顺序调 `_Process`。探针在自己那一帧改的位置，被相机紧接着的每帧同步（把规则层算出的整数抄进节点）覆盖掉了。也就是说那一帧渲染的**根本不是**探针以为的状态。
- **为什么危险**：它不报错，而且失败方向是「测出了想要的结论的反面」或者更坏 ——「测出了想要的结论」。本例侥幸测出了反面才引起怀疑；如果当初想证明的是「分数位置没问题」，这次空转会直接被当成证据。
- **处理**：量之前先停掉被测对象自己的每帧逻辑（`SetProcess(false)`），并且**把注入后的实际状态一起打进日志**，让「注入生效了」本身成为一条判据。本例的判据是「两次截图的相机位置一个整数一个分数」，缺了它，「引擎不受影响」与「注入没生效」在日志里长得一模一样。
- **可推广的判据**：**注入型探针必须先证明注入生效，再报被测量。** 只报被测量的探针分不清「系统不受影响」和「我没碰到系统」。
- **守卫**：`tools/check_camera.py` 的 `check_pixel_alignment` 逐条核注入后的实际状态；`tools/selfcheck_camera.py` 用「棋盘格没铺满就去量」这条用例证明它拦得住空转的量。

### 39. Godot 打开一次工程就会吃掉 `project.godot` 里的注释

- **症状**：2026-08-31 作者在编辑器里打开工程看了一眼，`git diff project.godot` 里冒出三处改动：加了 `config/features` 的 `"C#"` 标记、`[rendering]` 的键被重排、**`[importer_defaults]` 上面那段六行解释注释被整段删掉**。没有任何提示。
- **根因**：`project.godot` 是引擎自己维护的配置文件，它按内部数据结构重新序列化，注释不在那个结构里。文件开头那句「best edited using the editor UI」说的就是这件事，但它没说清代价是注释会消失。
- **为什么危险**：被吃掉的恰好是**「为什么是这个值」**。值还在、守卫也还在，所以什么都不会失败；但下一个人看到 `compress/mode: 0` 没有理由，很可能顺手「清理」掉。这是一类特殊的静默失效：坏的不是行为，是行为的依据。
- **处理**：**「为什么」不写在会被工具重写的文件里。** 理由挪进代码仓 `ARCHITECTURE.md`，配置文件里只留值。同时确认那些值有独立的执行体 —— 本例是 `tools/check_assets.py` 逐个读素材的 `.import` 核三项，项目级设置只影响将来新导入的文件，所以真正的判据比那三行更强。
- **可推广的判据**：**一份文件如果有工具会重写它，就不要把只有人读的信息放进去。** 判断办法：这个文件有没有「用编辑器改而不是手改」的说明？有就当它随时会被重排。
- **守卫**：**只能人工留意**（不值得为它写检查器：注释被删不改变任何行为，机器判不出「这段注释本该在」）。可观察形式是提交前看一眼 `git diff project.godot` —— 编辑器的改动与人的改动长得不一样，重排与删注释是它的签名。

### 40. 加进树之后再设锚点预设，Control 铺不满

- **症状**：2026-08-31 做 `UI-8`，HUD 根节点在 `_Ready` 里调 `SetAnchorsPreset(FullRect)`，存图出来**只有左上角那一块**，另外三块不见了。诊断输出显示：锚点确实是 0,0,1,1，视口是 640×360，而根节点的尺寸是 **0×0**，偏移被改成了 −640,−360。
- **根因**：`set_anchor` 的 `keep_offset` 参数含义与名字给人的印象**相反** —— 传 `false`（默认）时引擎会**改写偏移以保住当前那个矩形**，而 `_Ready` 那一刻矩形还是 0×0。所以「设了铺满的锚点」并不等于「铺满」。加进树之前调它碰巧没事：那时 `_size_changed` 早退，偏移原样留着，进树时才按真实父矩形算一次。
- **为什么危险**：不报错，而且**只表现为「少了几块」**。贴左上角的子节点用的是锚点 0，任何父尺寸下位置都对，看起来一切正常；贴下边与贴右边的子节点落到负坐标、画在屏幕外。于是「界面没写完」和「界面写错了」长得一模一样。原先 `UiRoot.Register` 把那行写在 `AddChild` 之前，也就是说它的正确性依赖**两行代码的先后顺序** —— 那种正确性迟早被一次无害的重排毁掉。
- **第二层**（同一天撞的另一半）：`set_offsets_preset` 按**内容最小尺寸**算偏移，实际尺寸却按「内容最小与 `CustomMinimumSize` 取大」定。两者不等时块会整体偏出安全边距几像素 —— 本例是容器行距写 0 而尺寸算式按一个间距，块低了 4px。
- **处理**：要铺满就用 `SetAnchorsAndOffsetsPreset`，它显式设偏移、与调用顺序无关。块的尺寸算式与容器的实际排法（间距、内边距）必须逐项对上。
- **可推广的判据**：**「我设了这个属性」不等于「它生效了」—— 属性写完要把实际几何读回来核一遍。** 判断办法：这个 API 有没有「保住当前状态」这类隐含行为？有就说明它依赖调用时刻的状态，而那个状态未必是你以为的。
- **守卫**：`src/UI/HudProbe.cs` 打「HUD 根节点铺满视口」与「四块的实际矩形与规则层预测逐块一致」两条判据，`tools/check_hud.py` 读回来判；`tools/selfcheck_hud.py` 用「尺寸算式与实现漂移 4px」这条用例证明它拦得住。

### 41. 改了 `.import` 的参数却没重新导入，跑的还是上一次烘出来的产物

- **症状**：2026-08-31 把字体 `.ttf.import` 的 `[params]` 里四项改成 ADR-0008 要求的值，跑起来引擎报的仍是旧值（抗锯齿仍是灰度、系统回退仍开着）。四项里另外六项「通过」，因为它们本来就是默认值 —— 所以看起来像「大部分对了」。
- **根因**：`.import` 是**导入器的输入**，真正被加载的是 `.godot/imported/` 下烘出来的产物。游戏运行（`--path .`）不重新导入，只有编辑器或 `--headless --import` 会。第 6 条记的是「改了 PNG 源文件要刷缓存」，这一条是它的参数变体：**源文件没动，参数动了，缓存同样是旧的**。
- **为什么危险**：抗锯齿开着只表现为 12px 中文多一圈半透明脏边 —— 画面「有点糊」，不报错，而且改过参数的人会认为自己已经改好了。
- **处理**：改完 `.import` 跑一次 `<Godot> --headless --path . --import`，再让守卫核**引擎自报的实际值**而不是 `.import` 的文本。设置、期望与实际三处分开：设置在 `.import`，期望在 `rules/Ui/PixelFont.cs`，实际由引擎报 —— 三处独立才互为量具，同源的守卫等于没有守卫。
- **可推广的判据**：**凡是「有中间产物」的配置，判据必须取自运行时的实际值，不能取配置文本。** 判断办法：这个文件旁边有没有 `.import`／`.md5`／缓存目录？有就说明它不是最终生效的东西。
- **守卫**：`tools/check_hud.py` 的字体那一组逐项比对引擎自报值与期望值，条数也核（漏测一项不报错）；`tools/selfcheck_hud.py` 用「期望值与引擎实际不符」这条用例证明它拦得住。

### 42. `stretch/aspect="expand"` 下逻辑分辨率有一维是变量，按定值写缩放校验会误判

- **症状**：2026-08-30 做 `UI-3`，缩放守卫原按「1280／1920／2560／3840 各窗口缩放倍数恰为 2／3／4／6」写。前三档过，4K 档预期 ×6 怎么都对不上 —— 实测逻辑尺寸是 649×360、缩放 ×5（本机屏幕装不下 4K，系统把窗口裁成 3840×2130）。
- **根因**：`stretch/mode="canvas_items"` + `aspect="expand"` 把**短边锁在逻辑值**（这里高 360）、**长边按窗口宽高比撬开**。所以逻辑分辨率只有高是定值 360，宽是随窗口比例变化的变量（16:9 时约 640，更宽的窗口更大）；缩放倍数是「物理高 ÷ 逻辑高」向下取整。
- **为什么危险**：按定值写的判据在最常见的几档（严格 16:9）会全过，只在非严格 16:9 或屏幕装不下时才失败 —— 于是它长期看着对，换一台屏幕或一次全屏就崩，而且失败时报的是「缩放不对」，指向错的方向（其实是判据的定值假设错了，不是缩放错了）。
- **处理**：判缩放守**不变量**而不是定值 —— 缩放为整数、两轴倍数相等、逻辑尺寸不小于设定的 640×360。这三条对任意窗口都成立，也正是 `aspect="expand"` 承诺的东西。
- **可推广的判据**：**自适应／拉伸布局下，先分清哪一维是定值、哪一维是变量，校验只钉不变量。** 判断办法：这个模式的名字里有没有 `expand`／`fit`／`aspect` 这类词？有就说明至少有一维会随容器变，别拿它当常数。
- **守卫**：代码仓 `tools/check_scaling.py`（`UI-3`）。四档窗口从引擎 `--log-file` 读回实际逻辑尺寸与缩放倍数，判整数、两轴相等、逻辑不小于 640×360；一档都没读到就判失败（避免空转全绿）。它是量具不是守卫（判据全来自引擎自己写的日志），故无独立自证。

### 43. `detect_3d/compress_to` 默认会把像素图静默重导成 VRAM 压缩

- **症状**：2026-08-30 做 `ART-4` 生成占位件时，纹理导入默认带 `detect_3d/compress_to=1`。一旦某张纹理被引擎判定用在 3D 场景，它会被**自动重新导入成 VRAM 压缩格式**，像素图的硬边与配色当场毁掉 —— 导入期干的、运行时才看到糊，不报错。
- **根因**：Godot 默认导入设置假设项目是 3D 或混合项目，`detect_3d` 在检测到 3D 用法时切换压缩模式。纯 2D 像素项目里这是纯破坏，但默认值站在多数项目那边。
- **为什么危险**：它在**导入期**触发、由**使用位置**决定 —— 同一张图 2D 用没事、被 3D 引一次就变质；改的人没动过这张图却发现它糊了，最难往「导入参数」上想。
- **处理**：设项目级 `[importer_defaults]` 的 `texture`：`detect_3d/compress_to=0`、`compress/mode=0`、`mipmaps/generate=false`，让新导入的纹理默认无损。已有的 `.import` 不会自动跟着变，要删掉重导。
- **可推广的判据**：**纯 2D 像素项目第一件事就是关掉一切「检测到就自动压缩／生成 mip」的默认。** 判断办法：导入参数里凡带 `detect_`／`compress`／`mipmap` 的，问一句「它什么时候会自己动，动了会不会毁像素」。
- **守卫**：代码仓 `tools/check_assets.py` 把这三项导入参数纳入 `--check`（`ENG-10`）；改项目默认时当场抓出旧 `.import`（实测抓出 24 个，删重导后通过）。

### 44. 共享输入的启动探针不能并行注入

- **症状**：headless 输入自检的低幅摇杆判据失败，HUD 判据却通过。
- **根因**：两个逐帧探针共享全局 Input 与门面；HUD 注入高幅扳机恰好跨入输入探针的漂移断言，合法设备切换被误归因给低幅摇杆。

### 45. 守卫只测了一种倍数，于是它报的建议是错的

- **症状**：2026-09-08 接作者第一批自绘角色帧，`ENG-10` 的放大件守卫拦下了它们（对的），但建议是「改用 160×160 的源尺寸」。真实源尺寸是 **32×32** —— 交付件是精确 10 倍放大件。
- **根因**：旧实现只判「整图每个 2×2 块是否同色」，判出来就按 2 倍报。10 倍放大件当然满足 2×2 同色，所以它拦对了、算错了。同一份实现还有第二个洞：遇到奇数宽高直接放过，于是「45×45 是 15×15 放大 3 倍」这种一条都查不出。
- **为什么危险**：**守卫报错报得不对，比不报更坏。** 照那条建议做会得到一张仍然放大 5 倍的图，而且下一轮守卫还会再拦一次、报的数还是错的 —— 人会开始怀疑守卫而不是怀疑素材。「拦住了」不等于「诊断对了」，而验收时很容易只看有没有拦住。
- **处理**：求**最大**的 n 使整图每个 n×n 块同色，报真实倍数与真实源尺寸。判据对因子封闭（n 成立则 n 的任一因子也成立），所以从 1 出发只往当前最优倍数的整数倍上试即可，不必全枚举。纯色图天然满足任意倍数，色数 < 2 直接返回 1。
- **可推广的判据**：**守卫的输出也是产物，也要有反证。** 只证明「坏的被拦下」不够，还要证明「报出来的数对」—— 造一个已知倍数的样本，断言它报的就是那个倍数。
- **守卫**：代码仓 `tools/check_assets.py` 的 `upscale_factor`（`ENG-10`）。自证在 `tools/selfcheck_verify.py`：10 倍件必须报「10 倍、源 32×32」、15×15 放 3 倍的奇数边长件必须被拦、31×31 的真 1 倍件不许被误判。

### 46. 手绘的对齐基准线逐帧不一致，跨动作就对不齐，而且不报错

- **症状**：2026-09-08 接 10 个动作 74 帧逐帧件。每帧底部有一条作者画的灰色地面参考线，用来定脚底锚点。实测各帧参考线**中心**的摆动：待机与奔跑 0px（正例），行走 2.5px、轻击 4.5px、重击 7px。
- **根因**：手绘的线每帧长短与起点都不完全一样。对齐算法只能取各帧线中心的中位数当水平锚点（取平均会随帧数抖），所以**逐帧的差消不掉** —— 它不是对齐算法能修的东西。
- **为什么危险**：它**没有任何报错**。尺寸对得上、像素规格全过、登记表也一致，唯一的表现是「切换动作时角色轻微上下或左右跳」，属于要盯着看才发现的那类；发现之后还无法定位到某一张图，因为每张单看都是对的。按画布中心对齐（最容易想到的替代做法）更坏：不同动作的脚底会差 1–4 个像素，同样静默。
- **处理**：把「脚底在哪」变成作者标出来的事实而不是推测 —— 要求每帧同一行、同起点、同长度，接仓时整行去掉。线按**形状**识别（整行只有一种不透明颜色、连成一段、长度 ≥4、位于画布底部五分之一内），不认颜色：作者的 `hit` 闪白帧连参考线都是白的，写死灰色会漏掉它们、把线留在图里变成角色脚下一条灰边。
- **可推广的判据**：**凡是靠「人手画的标记」定位的自动化，都要先问这个标记本身稳不稳**。稳不了就得把不稳的量报出来让人回去改画，而不是在算法里挑一个「看起来居中」的值糊过去。
- **守卫**：代码仓 `tools/import_role_sheets.py`（`ART-6`）逐帧报出线的行、跨度、颜色与中心，并把横向落位逐动作打出来；规范写在设计仓 [像素绘制原则 §12](../production/像素绘制原则.md)。
- **后续（2026-09-09 已解决）**：中位数那套是**将就**，不是解法。真解法是让作者在线上再标一个**单像素锚点**（纯品红 `#FF00FF`），横向由它精确给出、纵向仍由线给出。改完摆动问题从根上不存在了 —— 91 帧的锚点全部落在同一列。同时暴露了下一条记录里那个更值得记的坑。

## 47. 给素材加了新约定，却没检查既有判据会不会把新约定判成违规

- **症状**：2026-09-09 作者按新约定在拉满的地面参考线中央嵌了一个品红锚点像素 —— **完全照要求做的**。结果导入器 13 个动作全部报「没有一行在所有帧里都像地面参考线，认不出脚底锚点」，一帧都接不进来。
- **根因**：参考线的旧判据是「整行只有一种不透明颜色」。锚点像素让那一行有了**两种**颜色，于是旧判据把它判成脏行。新约定与旧判据直接冲突，而两者都写在同一份规范里。
- **为什么值得记**：报错信息把矛头指向了**素材**（「认不出锚点」），而错在守卫。这类错报最贵的地方不是修起来难，是**它会让人回去改本来正确的东西** —— 如果当时顺着报错去让作者把锚点去掉，就等于用一个真缺陷换掉了一个真解法。
- **处理**：先实测再改判据。逐帧扫出锚点的确切颜色 `(255,0,255,255)`、出现次数（每帧恰好 1 次）与坐标（全部落在线所在行、全 91 帧同列），据实把判据改成「整行**除锚点像素外**只有一种颜色」，并补三条硬判据把锚点本身判死：一帧恰好一个、必须落在线所在行、同动作各帧坐标完全一致。
- **可推广的判据**：**每次给素材（或任何被守卫检查的东西）加一条新约定，都要同时问「现有哪条判据会把这个新约定判成违规」**。约定与判据是一对，只改一半必然对撞；而对撞的表现往往是「守卫指着无辜的一方报错」。
- **守卫**：`tools/import_role_sheets.py` 的 `line_candidates` 与 `anchor_pixels`（`ART-6`）；规范同步在 [像素绘制原则 §12](../production/像素绘制原则.md)。

## 48. 探针里写死的距离，实际上绑在一个会变的测量值上

- **症状**：素材替换后 `hit_feedback_dev.py` 的 `last-active-entry` 失败，而同一段里同距离同相位的 `pre-overlap` 却通过。
- **根因**：探针把木桩写死放在距主角 24px。重叠条件是「距离 ≤ 轻击伸展 + 受击框半宽」，而轻击伸展是**从美术量出来的**（`ART-6`）：旧素材 18px → 上界 27，有余量；新素材 15px → 上界 24，**正好等于那个写死的 24，余量为零**。首次命中的击退（`Hitbox.Resolve` 里会调 `dummy.Receive`）把木桩推开约 2px，就掉出框外了。另外探针用的是**相对**位移（`+= 100` / `-= 100`），于是击退漂移被累加进后面每一轮「回到近处」。
- **为什么危险**：写死的那个数当时是对的，而且**测试当时是绿的**。它的失效不由改动它的人触发，而由改美术的人触发 —— 两件事之间没有任何可见联系。
- **处理**：距离改由几何导出（`Hurtbox.WidthWorldPx`，两个同宽实体刚好不互插的最小间距）；进出改用**绝对**定位，漂移无法累加；再加一条前提判据 `probe-near-in-reach` 把「这个距离真的在轻击框内」判死，将来伸展再缩小时它会当场说清原因，而不是让下游某条判据莫名失败。顺带发现同一序列后面的 `refresh-distance` 测的是击退记账，木桩贴身时向左的击退会被主角实体挡住，于是给那一段单独挪到两侧有空地的位置。
- **可推广的判据**：**探针里的每个字面量都要问一句「它依赖的东西会变吗」**。依赖测量值的就从测量值算出来，并为「算出来的前提还成立吗」单独立一条判据 —— 前提判据的价值就是把「条件不成立」和「玩法坏了」分开报。

## 49. 拿引擎物理量做跨状态比较，容差是自己挑的

- **症状**：2026-09-09 `GP-15` 新加的 `depth-land-unlock` 失败，同一段里的 `depth-air-lock` 通过。判据名说的是「落地后纵深解锁」，读起来像纵深真的没解锁。
- **根因**：那条判据里顺手加了一句「跳跃轴要回到起跳前的 Y」，容差写的是 `< 0.001`。而角色**跳过一次又落地**之后的静止 Y 与起跳前差 0.025px —— 那是 `CharacterBody2D` 自己的碰撞安全边距（`SafeMargin`，引擎默认 0.08）留下的，不是缺陷。纵深那三个合取全都成立。
- **为什么值得记**：失败信息指向被测玩法（纵深没解锁），错在**量具的容差**，与第 47 条「守卫指着无辜的一方报错」同一族。而这里更容易走错一步：容差是自己挑的数，最省事的「修法」是把 0.001 调到刚好能过 —— 那等于用量具骗自己，下次真差了 0.5px 也照样绿。
- **处理**：先加临时诊断把每个合取的实测值打出来，定位到唯一不成立的是 Y；再把容差改成**引擎自报的那个量**（`actor.SafeMargin`），并补一条「竖速归零」把「真的落地静止了」判死；诊断输出删掉。
- **可推广的判据**：**跨物理状态比较引擎位置时，容差必须来自引擎自报的量（安全边距、贴地距离），不许自己挑一个数。** 挑不出来就说明这条比较不属于当前判据 —— 那就把它拆出去，而不是放宽它。
- **守卫**：`src/World/PlayerDev.cs` 的 `DepthProbe`（`GP-15`）；判据名与期望条数登记在 `tools/player_dev.py`。

## 50. 前提判据失败时，先去查下游判据

- **症状**：2026-09-09 `ENG-15` 途中跑 `player_dev.py`，一次报三条失败：`depth-back`、`depth-land-unlock`、`focus-kept`。前两条是玩法判据，而那一轮刚改过绘制结构，看起来正是改动引起的回归。
- **根因**：真正的原因就是第三条自己报的那件事 —— 窗口失焦。Godot 失焦时释放全部按下的动作，探针合成的「按住向后键」被悄悄松开，纵深于是停在半路，走不到带后沿。前两条是它的**下游**。
- **走了多少弯路**：先假设是自己的改动，往判据里加了诊断输出，重跑发现**诊断一次都没触发** —— 那一轮全过了。也就是说前一轮的失败与代码无关。同一轮里我还顺手修了一个真 bug（射线没排除宿主自己），差点把它误当成根因写进笔记。
- **为什么值得记**：`focus-kept` 这类前提判据的全部用处就是**把「这一轮不能算」与「玩法坏了」分开报**（`GP-13` 的类注释早写明了失焦会让需要持续输入的判据失败）。而我看到它失败却先去查玩法判据 —— 等于把量具的报警当噪音。
- **可推广的判据**：**前提判据失败时，那一轮的其余结论一律作废，先重跑，不要顺着下游判据查根因。** 下游判据在前提不成立时报什么都不能作为证据。反过来也成立：修完一个真 bug 之后，别把它当成上一次失败的根因 —— 要用一次干净的重跑来确认。
- **守卫**：`tools/player_dev.py` 与 `tools/depth_dev.py` 的 `PRECONDITIONS`（`tick-frame-1to1`、`focus-kept`）；相关观察记在 [`issue-ENG-14`](../spec/issues/issue-ENG-14-input-probe-isolation.md)。

## 51. 引擎日志里被守卫解析的那一行，是契约

- **症状**：2026-09-09 给启动日志的 `[GP12] Sheet idle=6` 那行后面追加了本体宽度，变成 `Sheet idle=6 bodyWidth=19 frames=[...]`。跑 `player_dev.py`：**46 项判据全部 PASS，入口却判失败**。
- **根因**：入口用 `^\[GP12\] Sheet (\w+)=(\d+)$` 解析那行，把引擎自报的帧数与登记表比对（引擎读不到登记表，那是两份真相唯一的会合点）。正则锚定行尾，追加任何东西都让它匹配不到 —— 于是帧数字典为空，比对判失败。**守卫做对了：读不到不等于通过。**
- **为什么值得记**：这是[第 47 条](#47-给素材加了新约定却没检查既有判据会不会把新约定判成违规)的同一族，而我在**同一轮里刚写完第 50 条又踩了它** —— 说明「加新约定要检查既有判据」这条的检查点还不够靠前：它得在「改任何被别人读的输出」这一刻触发，而不是只在改素材规范时。
- **系统性的洞**：项目里有七个守卫在读引擎日志（`player_dev`／`hit_feedback_dev`／`depth_dev`／`check_camera`／`check_hud`／`check_worldui`／`check_input_map`），它们解析的每一行都是契约，而**代码里绝大多数那样的 `GD.Print` 没有任何标记说明这件事**。下一个人照样会追加字段。
- **处理**：新信息另起一行，不动既有那行；并在那行上方写明它是谁的契约、行尾是锚定的。缓存那件事顺带也修了（见下）。
- **可推广的判据**：**改一行会被守卫解析的日志之前，先 `grep` 谁在读它。** 打日志的地方如果被守卫依赖，就在旁边写明依赖者与格式约束 —— 否则那份契约只存在于守卫的正则里。
- **顺带一条**：同一轮还发现每个角色实例都在重扫共享的精灵表（同屏 20 个角色 150 万像素）。**没有任何判据会报它**（只是载入变慢），发现它靠的是启动日志里同一行打了六遍。所以那行只在真正扫的时候打 —— **打的次数本身就是「扫了几次」的量具**。
- **守卫**：`tools/player_dev.py` 的 `SHEET_LINE` 与 `sheet_counts`；契约说明写在 `src/World/PlayerActor.cs` 打那行的地方。

## 52. 断言「没发生」时，得排除掉其它会让它没发生的原因

- **症状**：2026-09-11 `GP-16` 给命中判定加纵深条件，新判据 `depth-off-row-miss`（纵深错开一排 →
  `Resolve` 返回 0）**首次就 PASS**，而紧接着的 `depth-realign-hits-same-swing`（同一次挥击挪回同排 →
  返回 1）失败。看起来像「打空这一半对了，打中那一半坏了」。
- **根因**：两条其实都在说同一件事 —— **压根没打到过**。`Hitbox` 的每挥击去重集合靠 `Resolve`
  在**相邻两次调用之间**观察到的 Active 上升沿清空，也就是说它的生命周期挂在**调用节奏**上，不挂在
  挥击本身上。生产路径每个物理帧调一次所以正确；而探针手动驱动连段、只在需要时调 `Resolve`，跨挥击
  那次清空没发生，集合里还留着上一阶段命中过的受击框。于是那个 0 是**去重**挡的，不是纵深挡的。
- **为什么值得单列**：`depth-off-row-miss` 是一条**否定式**断言，而「返回 0」有三个来源（横向查询里
  没这个候选、纵深超差、本次挥击已经打过它）。只看返回值的判据说不清自己测到了哪一个，于是它可以在
  被测特性**完全不存在**的情况下全绿 —— 反证时把纵深条件整个删掉，它照样会 PASS。这比第 47、49 条更
  隐蔽：那两条是判据指错了对象，这条是判据根本没碰到对象。
- **处理**：先加临时诊断把候选、各自纵深与 `alreadyHit` 打出来（一次就定位，`hitSetSize=1`
  `alreadyHit=True`），据实定位后删掉诊断；然后三件事一起做 ——（1）探针在换挥击前让判定框看见一个
  非 Active 帧，并把这件事本身写成前提判据 `depth-probe-fresh-swing`；（2）`Hitbox` 暴露
  `RejectedAsAlreadyHit`（上一次因去重被驳回的候选数）当量具，让否定式判据能加一句「这个 0 不是去重
  造成的」；（3）把调用契约写进 `Resolve` 的注释 —— 它原先只存在于代码的执行顺序里。
- **可推广的判据**：**写「某件事没发生」的判据时，先列出所有会让它没发生的原因，再为不想要的那些各
  加一句排除。** 排除不了就说明缺量具 —— 那就先把量具做出来（被测系统自报一个计数），而不是让判据
  带着歧义过关。配套的一条：**一条否定式判据，必须能在「被测特性整个不存在」时变红**；做不到就不算
  执行体。
- **守卫**：`tools/hit_feedback_dev.py` 的 `DEPTH_TOLERANCE`（`depth-probe-fresh-swing`
  ＋ `depth-off-row-miss` 里的 `RejectedAsAlreadyHit == 0`）；量具本体是 `src/World/Hitbox.cs` 的
  `RejectedAsAlreadyHit`，调用契约写在同文件 `Resolve` 的注释里；遗留记在
  [`issue-GP-16`](../spec/issues/issue-GP-16-depth-hit-tolerance.md) 的「待确认」。

## 53. 自证里硬引用的常量值与资源路径会随被测系统漂移，而它不在验收链里所以没人发现

- **症状**：2026-09-11 接三段轻击、跑 `selfcheck_verify.py` 自证判定框守卫时，两处**一开就失败**：判定框注入用例的 `_patch_cs` 抛「找不到 `LightHitboxWidthWorldPx = 18`」（该常量 09-09 已由 18 改到 15），单色帧用例的 `Image.open(hit.png)` 抛 `FileNotFoundError`（`hit` 09-09 已拆成 `light_hit`／`heavy_hit`、仓里已无 `hit.png`）。两处都**不是本轮改动引起** —— 09-09 那两次变更当时就该同步，但没人发现，潜伏了两周。
- **根因**：自证代码里硬编码引用了具体的常量字面值（`= 18`）与具体资源路径（`hit.png`）。被引用的东西一改，自证要么 patch 不到、要么打不开文件。而 `selfcheck_verify.py` **不在 `verify.py` 常规验收链里**（约定是「改了 verify.py 才跑」），于是它自己烂了没有任何常规检查会碰到 —— 失效窗口 = 两次「有人主动跑它」之间的全部时间。
- **为什么值得单列**：这是 [第 48 条](#48-探针里写死的距离实际上绑在一个会变的测量值上)的更隐蔽变体。#48 的探针在验收链内，绑错了当轮就红、当场可见；本条的自证不在链内，绑错了**静默**，直到下一个人因为别的事跑它才炸，而那时根因（09-09 的改名/改值）早已淹在历史里。**「守卫的守卫」比守卫更容易腐烂，正因为没人天天看它。**
- **处理**：本轮把两处引用重指到现存的常量与资源（注入改成 `Light3HitboxWidthWorldPx` 16→15、`HIT_SHEET` 指到 `light_hit.png`、帧宽 46→44），`selfcheck_verify.py` 恢复 32/32。注意 `_patch_cs` 找不到旧串就 `raise` 本身是对的（读不到不等于通过），问题不在它、在「没人跑」。
- **可推广的判据**：**自证里出现的每个魔法值/路径，都要问「它在别处被改一次，我这条自证是当场 FAIL，还是 crash／skip」** —— crash 或 skip 就是静默失效，等于没有这条自证。以及：**一个不在常规验收链里的自证，其失效窗口等于两次触发之间的全部时间**，所以要么把它挂进链、要么让被它覆盖的守卫（及那些守卫依赖的常量/资源）改动时一并跑它。
- **守卫**：只能人工留意（自证的自证会无限递归）。可观察形式：改常量或资源名后，把引用它的自证也跑一遍。本条两处已重指，见 `ART-6` 的 2026-09-11 笔记。

## 动手前快速检查

- 当前页面的数据变化后是否会重绘？
- 新状态是否完成 `Capture → JSON → Rebuild`？
- 随机源是否从 `Rng` 进入并传到最深层？
- 探针是否证明到达目标，而不只是进程存活？
- 守卫是否强制重建并用真实缺陷形状自证？
- 只处理一部分的优化，是否打印了实际覆盖量与应覆盖量？
- 测试报告里的测试**数量**是否等于预期数量，而不只是看它说没说「通过」？
- 提交信息的标题后面是否空了一行，`git log -1 --format=%s` 复核过标题长度？
- 注入型自证还原之后，是否看过版本库状态，确认没留下被测系统的副产物？
- 判定不成立时，是否先核了「这个量的定义对不对」，才去调参数？
- 注入型探针是否先证明了注入真的生效，才去报被测量？
- 只有人读的「为什么」，是否放在了不会被工具重写的文件里？
- 比较引擎位置用的容差，是引擎自报的量，还是自己挑的一个数？
- 前提判据（失焦、帧对齐）失败时，是先重跑了，还是顺着下游判据查了根因？
- 判据只覆盖了某个量的一侧（只有正、只有负）吗？让它跨过零点了吗？
- 机器判据全绿之后，看过截图吗？
- 改一行日志之前，`grep` 过谁在解析它吗？
- 断言「某件事没发生」时，排除过其它会让它没发生的原因吗？它能在被测特性整个不存在时变红吗？
- 同一份只读数据，是每个实例各算一遍，还是算一次共享？
- 设完布局属性后，是否把实际几何读回来核过，而不只是「我设了铺满」？
- 自适应／拉伸布局的缩放校验，是否只钉了不变量（整数、两轴倍数相等、逻辑尺寸下限），而不是某个窗口下的定值倍数？
- 改的是配置还是最终生效的产物？有中间产物的话，判据是否取自运行时实际值？
- 纯 2D 像素项目里，带 `detect_`／`compress`／`mipmap` 的导入默认是否都关了（它们会在导入期静默毁像素）？
- 用 git 取文件清单时，是否关掉了 `core.quotepath`？
- 守卫拦下东西之后，是否核过它**报出来的那个数对不对**（而不只是「拦住了」）？
- 靠人手画的标记做自动定位时，是否先量过那个标记本身稳不稳？
- 改了某个常量值或资源名后，引用它的自证（尤其不在验收链里的）是会当场 FAIL 还是会 crash／skip 静默失效？
- 探针的**前提**（时钟对齐、窗口有焦点、注入真的生效）是否也写成了判据，而不是默认成立？
- 自动检查通过后，是否仍安排了必要的实机观感验收？

### 主角物理探针的输入边沿与精灵脚点（GP-12）

- **实测**：在物理回调内直接注入动作时，持续移动成立但跳跃/攻击边沿未被同帧读取；角色推进后用 deferred 注入、下一物理帧断言后，图形探针由 5/11 变为 11/11，后增控制器替换为 12/12。不要把探针注入时点失败直接当输入门面缺陷。
- **表现**：96 像素画布不是角色脚点，四张表非透明底边在81/82行。以画布底部对齐碰撞体导致悬空，改以待机底边81对齐，截图复核脚贴地。执行体在代码仓 `tools/player_dev.py --probe`，日志与截图落 `logs/player/`；手感仍需作者确认。
- **规则接入**：两台独立状态机单测通过不等于组合排他性成立。使用单一仲裁入口，碰撞反馈不得重复 Tick；`ActorCombatStateTests` 覆盖同帧跳闪攻击、闪避退出帧及落地/撞顶计时不重复。
- **速度输出边界**：Tick退出相位不等于本次速度已被物理引擎消费；退出时清零会让18帧只产生17帧位移。动作早返回还可能绕开重力。必须同时验逐帧输出、积分总位移与真实离台碰撞，不能仅看相位结束或单测全绿。GP-12以规则逐Tick断言和图形18帧50.4px/离台落地探针覆盖；碰撞反馈只校正，不再推进时钟。
- **两个时钟不同步（2026-09-08）**：断言按**物理帧**计数，注入走 `CallDeferred`，那是主循环迭代末尾才刷的队列。默认一次迭代最多补跑 8 个物理帧，于是「第 65 帧按下、第 66 帧松开」可能落在同一次刷里 —— 按下与松开一起生效，动作压根没起来。表现是同一份代码连跑三次各失败一条**不同**的判据（`move`／`jump`+`air-attack`／`dodge-exclusive`），而失败信息指向运动学。处理：探针里把 `Engine.MaxPhysicsStepsPerFrame` 钉成 1（放弃追赶，探针不需要），并逐帧核渲染帧号有没有前进，末尾报一条 `tick-frame-1to1`。**别去抬各条判据的阈值** —— 那会把「注入晚了」伪装成「位移够了」。
- **失焦会松开按住的键（2026-09-08）**：Godot 在窗口失焦时释放全部已按下的动作，于是探针合成的「按住右移／按住冲刺」被悄悄松开，`move`／`dash`／`held-input-survives` 失败，而原因是别的窗口抢了焦点。处理：数 `NotificationApplicationFocusOut`，末尾报一条 `focus-kept`。前提判据的价值不在于它会不会过，而在于**它不成立时不许别的判据替它失败**。
- **静态判据不许插进计时序列（2026-09-08）**：把「逐像素核精灵表脚底行」放在第 5 个物理帧，那一帧长到引擎开始追赶物理步，第 20 帧的位移判据当场失败（阈值 10px、正常值 11.27px）。移到 `_Ready` 仍然坏，多带坏一条无敌判据。真正的修法是位置而不是速度：静态判据挪到 `Capture()` 里、物理已停之后再跑，**快多少都不该插进去**。

### 命中帧、冻结帧与实际颜色（GP-13）

- **机制**：新状态若在本帧角色推进之前施加，会立刻少一帧；冻结计时若随角色一起停，会永不恢复。统一外层物理时钟先消费旧冻结，非冻结帧先运动再命中，新状态从下一次推进开始消费。
- **执行体**：代码仓 `tools/hit_feedback_dev.py --probe` 的首Active、fresh-stun、freeze判据同时检查命中帧满时长、之后恰N帧双方/相机固定与外层计时递减；不是只核最终返回待机。
- **颜色**：彩色纹理乘白色不会变白。本轮几何受击者直接输出白色，以真实视口像素和恢复色断言自证；渲染效果不能只检查Modulate或布尔开关。
