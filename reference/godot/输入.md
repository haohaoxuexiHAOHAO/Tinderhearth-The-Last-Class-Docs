# 输入

> 本篇回答：**按键怎么绑**、**代码怎么问「玩家按了什么」**、**键鼠与手柄怎么自动切提示**，以及本项目
> 一条实测出来的硬约束 —— **玩法代码不许直接轮询输入**。
>
> ⚠️ **本项目不在编辑器的输入映射面板里配按键**，理由在第三节。所以你打开那个面板会看到它是空的，
> 那不是没配。前置是[脚本与节点接线](./脚本与节点接线.md)。总纲在[本目录索引](./README.md)。

---

## 一、引擎的输入模型：动作，不是按键

Godot 不让玩法代码问「W 键按了没有」，而是问「`move_up` 这个**动作**按了没有」。中间隔一层
**动作**（Action）：

```
物理按键／手柄按钮／摇杆轴   →   动作名   →   玩法代码
   W、摇杆上推                move_up
```

好处是改键只改绑定表，玩法代码一个字不动；同一个动作能同时绑键盘、手柄、鼠标好几个来源。

**动作的注册表叫 `InputMap`**，它是全局的、运行时可改。

## 二、三种问输入的方式

| 方式 | 形状 | 什么时候用 |
| --- | --- | --- |
| **事件回调** | `_Input(InputEvent e)` / `_UnhandledInput(e)` | 一次性的事：按返回键、打开面板 |
| **轮询** | `Input.IsActionPressed("跳")` | 逐帧的事：移动、按住格挡 |
| **二维量** | `Input.GetVector(左, 右, 上, 下)` | 移动方向，自带死区与归一化 |

事件回调那一对要分清：

- **`_Input`** 先收到，适合「不管界面在不在都要处理」的东西。
- **`_UnhandledInput`** 在界面控件处理完之后才收到，适合玩法。**优先用它** —— 界面开着的时候玩法不该
  再收到那次输入。
- **`GetViewport().SetInputAsHandled()`** 表示「这次输入我收了，别往下传」。

⚠️ 下面第九节会说一件要紧的事：**`SetInputAsHandled` 只挡事件流，挡不住轮询。**

## 三、本项目为什么不用编辑器的输入映射面板

默认绑定表写在代码里（`rules/UI/InputBindings.cs` 是那张表，`src/UI/InputMapInstaller.cs` 把它灌进
`InputMap`）。两条理由：

1. **两份来源必然漂移。** 编辑器面板里配一份、代码里再配一份，改了一处另一处不报错。
2. **手柄的修饰键组合写不进那个面板。** 实测：`InputEventJoypadButton` 与 `InputEventJoypadMotion`
   直接继承 `InputEvent`，**一个修饰键字段都没有**（而 `InputEventKey` 有四个）。所以「按住扳机再按
   面键」这种组合只能自己解算。

**代价写明**：编辑器的输入映射面板会是空的。**留下的纪律是不要在那里手加动作** —— 那是造出第二份
来源，而那种漂移不会报错。

⚠️ **也不要在 `project.godot` 里加 `[input]` 段。** 同一个理由。

## 四、动作名是常量，不是字符串字面量

`rules/UI/InputActions.cs` 里每个动作名都是一个常量：

```csharp
public const string AttackLight = "attack_light";
```

**为什么**：拼错一个动作名不会报错，只会表现为「这个键没反应」，而排查时你分不清是没绑、绑错还是
名字打错。常量让拼错变成编译失败。

### 本项目的动作清单

| 动作 | 说明 |
| --- | --- |
| 四向移动 | 侧视关卡只用左右，俯视场景四向都用。**是四个动作而不是一个二维量**，因为 `InputMap` 的单位就是动作 |
| 奔跑 | **按住期间的移动即为奔跑**，不是一个独立的位移键 |
| 轻攻击、重攻击、防御、闪避、跳跃、交互 | 正典点名的战斗动作 |
| 两个技能组修饰键 | 手柄上是左右扳机；键鼠上不用 |
| 六个技能位 | 顺序即编号 |

两条命名上的口径值得记住，因为它们是有理由的：

- **闪避与奔跑是两个动作**，不合并。
- **叫「奔跑」而不是「冲刺」是语义问题**：本作这个机制是「按住键持续加速移动」，那是奔跑；
  dash 在动作游戏里通常指一次性短距突进。地面移动因此只有行走与奔跑两档。

**界面动作刻意不自己定义**：返回、确认与焦点移动用引擎内置的 `ui_*`（`src/UI/UIRoot.cs` 在用
`ui_cancel`），重复定义一套只会多一份要维护的东西。

## 五、键盘绑物理键位，不绑字符

```csharp
// src/UI/InputMapInstaller.cs
private static InputEventKey Key(Key key) => new() { PhysicalKeycode = key };
```

**为什么用 `PhysicalKeycode` 而不是 `Keycode`**：AZERTY 键盘上 WASD 的物理位置是 ZQSD，按字符绑会让
那批玩家的移动键散开成四个不相邻的键。物理位在任何布局下都是同四个键。

**副作用是好的**：将来的改键界面显示的是玩家键盘上实际印着的字。

## 六、手柄：三件事要知道

### 面键编号是布局中立的

引擎按**位置**编号而不是按字母：底、右、左、上。所以同一份绑定在 Xbox 与 PlayStation 手柄上都对得上
（Xbox 的 A 与 PS 的叉都是「底」）。代码里对应 `JoyButton.A` / `B` / `X` / `Y` 这几个名字 —— 名字来自
Xbox 布局，但含义是位置。

### 摇杆与扳机是模拟轴

摇杆四向要**同一个轴的正负两个方向各绑一条事件**；扳机**只绑正方向**（它从 0 压到 1，没有负半轴）。

```csharp
private static InputEventJoypadMotion Axis(JoyAxis axis, float value) =>
    new() { Axis = axis, AxisValue = value };
```

### 死区

模拟轴有个**死区**（deadzone）：推不过这个值就不算按下。摇杆搁在桌上会有零点几的漂移，死区就是为它
存在的。

本项目的做法是**死区没登记就用引擎默认值，不在代码里再写一个数出来** —— 那会变成第二个要维护的默认值。

## 七、引擎内置的 `ui_*`：只追加，绝不先擦

本项目给内置界面动作补了手柄绑定，**补法是只追加**：

```csharp
// src/UI/InputMapInstaller.cs
if (!InputMap.ActionHasEvent(action, e))
{
    InputMap.ActionAddEvent(action, e);
}
```

**为什么不能先擦再建**：擦掉会把 `ui_accept` 的回车与空格、`ui_cancel` 的 Esc 一起带走，**键鼠玩家
就退不出面板了** —— 那是「修好手柄反而弄坏键鼠」的典型形状。

**为什么必须补**：实测 Godot 4.7.2 的默认值里 `ui_accept` 与 `ui_cancel` **一条手柄事件都没有**
（方向那四个有）。也就是说不补的话，手柄玩家打开面板之后按不了确认也退不出来。

⚠️ 本作自己的动作则是**先擦再建**。理由相反：跳过的话第二次调用会静默保留上一次的绑定，将来做
「恢复默认」时会得到两套叠在一起的绑定。

## 八、动作用完要能自证：新增符号忘了翻译当场抛

物理位符号（哪个键、哪个按钮、哪个轴）在本项目里是一个枚举，翻译成引擎事件的地方写成一个 `switch`，
**最后一臂是抛而不是兜底**：

```csharp
_ => throw new ArgumentOutOfRangeException(
    nameof(symbol), $"没有为这个物理位写翻译：{symbol}"),
```

**加了新符号却忘了翻译时它当场响。** 静默漏一条绑定的表现是「这个键没反应」，而那要试半天。

⚠️ **翻译得对不对编译器管不了。** 枚举名写错编不过，但 `PadTriggerRight` 到底落在轴 4 还是轴 5 这种
事，只能**改完绑定实机按一遍**。原先有守卫起真引擎核对，随 ADR-0009 删除了。

## 九、输入门面：玩法代码不许直接轮询

**这是本篇最要紧的一条，而且它是实测出来的。**

`src/UI/InputRouter.cs` 是唯一允许调 `Input.IsActionPressed` 的地方，玩法代码一律通过它问输入。

**实测现象**：在 `_Input` 里对面键事件调了 `SetInputAsHandled()` 之后，`Input.IsActionPressed` 与
`IsActionJustPressed` **仍然返回 true**。

**也就是说「拦下事件」只挡住了事件流，挡不住轮询。** 任何直接轮询的代码都会在玩家按住扳机挑技能时
照旧看到轻攻击被按下 —— 打出一次没打算打的攻击。**这种失效不报错。**

所以遮挡要做两半，合起来才完整：

- **事件流那一半**：`SetInputAsHandled()`。
- **轮询那一半**：门面自己在 `IsPressed` / `IsJustPressed` 里判一次「这个动作现在被修饰键遮住了吗」。

⚠️ 原先有守卫扫 `src/` 里除门面之外的 `Input.IsActionPressed` 调用并判失败，它随
[ADR-0009](../../decisions/ADR-0009-编辑器主导的开发模式.md) 删除。**现在这条只是约定，没有门禁。**

### 移动不受遮挡

```csharp
public Vector2 MoveDirection() => Input.GetVector(左, 右, 上, 下);
```

**挑技能的时候还得能走位**，所以移动那一路刻意不过遮挡判定。

## 十、修饰键组合：扳机加面键换出技能位

手柄只有四个面键，而技能位有六个。方案是**两个扳机各带一组，每组三个面键**。

解算流程（都在 `src/UI/InputRouter.cs` 里）：

1. **认出修饰键的按下与松开**，更新「现在哪一组生效」。
2. **修饰键按住时，把面键的按下与松开翻译成技能位的按下与松开**，用 `InputEventAction` 合成一个事件
   丢回引擎（实测：合成之后 `Input.IsActionPressed` 与 `IsActionJustPressed` 都为真，且 `_Input`
   会收到它一次）。
3. **把原事件消费掉。**

这样技能位对下游而言就是个**普通动作**，下游不必知道它是组合出来的。

⚠️ **扳机是模拟轴，越过死区之后同一次按住会持续来事件**，所以「按下」那一步必须可以重复调用而不出错。

### 被遮住的是哪几个动作

修饰键按住时，三个面键上原本的动作（轻攻击、重攻击、跳跃）失效。**闪避刻意不在其中** —— 正典把它
定为唯一带无敌帧的脱身手段，所以它占第四个面键并且永远可用。

**那一份清单同时是两件事的唯一来源**：哪些动作被遮住，以及「修饰键加第几个面键」对应哪个技能位。
写成两份必然漂移。

### 合成的事件不再回炉

```csharp
if (@event is InputEventAction)
{
    return;
}
```

**为什么**：自己合成的动作事件不属于任何物理设备，拿它去判「最后用的是哪个设备」会把结论污染成上一次
组合用的设备。

## 十一、失去焦点要把修饰键松开

```csharp
// src/UI/InputRouter.cs
if (what is (int)NotificationApplicationFocusOut or (int)NotificationWMWindowFocusOut)
{
    // 把按住的修饰键全部松开，并给被它驱动的技能位补发松开事件
}
```

**不做的后果**：玩家按住扳机去切窗口，回来时修饰键还是「按住」状态，而被它驱动的技能位永远收不到
松开 —— 表现是**一个技能卡在按下不放**。

这类「窗口焦点」通知是引擎给的 `Notification*` 常量，在 `_Notification(int what)` 里收。

## 十二、键鼠与手柄怎么自动切提示

`rules/UI/InputDeviceTracker.cs` 用三条规则判「现在该显示哪一族按键图标」：

1. **离散按下一定切换。** 玩家按了键或按钮，那就是他在用的设备，没有歧义。
2. **模拟轴要过阈值才切换。** 阈值必须高于摇杆死区，否则手柄搁在桌上的漂移会持续把提示从键鼠抢过去
   —— 玩家会看到图标自己跳。
3. **纯移动永远不切换。** 鼠标被碰一下不代表玩家换了设备；真要用鼠标玩他会点下去，而点击算离散按下。
   这条同时省掉一个「多少像素才算移动」的拍脑袋阈值。

**为什么这三条在规则层**：它的失效方式是**图标闪烁**，而闪烁只在特定条件下出现（手柄摇杆漂移、鼠标
被碰一下），实机随手试是试不出来的。做成三条规则加一个阈值，就能用单元测试把三种情形都钉住。

**阈值与扳机死区取同一个数**：「够得上当修饰键」与「够得上换图标」是同一个门槛，两个数会分叉。

**初始值取键鼠**：发行目标是 Steam 的 Windows PC 端，玩家还没输入任何东西时先按键鼠显示，比显示
「未知」有用。

## 十三、暂停时输入门面还要跑

```csharp
ProcessMode = ProcessModeEnum.Always;
```

**为什么**：弹窗要求暂停世界，而那时界面还得能操作。`ProcessMode` 设成 `Always` 的节点在
`GetTree().Paused` 为真时照常收输入与跑回调。

⚠️ **玩法节点不要设 `Always`。** 它们就该在暂停时停住 —— 手柄上「下面键既是跳跃也是界面确认」那个
共用物理位的歧义，正是靠「面板开着时玩法节点根本不在跑」消掉的。

`ProcessMode` 的其他取值（`Inherit` / `Pausable` / `WhenPaused` / `Disabled`）平时不用碰，默认继承
父节点就对。

## 十四、4.7 里两件与输入有关的新东西

- **键鼠事件现在也带设备标识。** 以前只有手柄输入有设备编号，现在键盘与鼠标事件也有（各有一个专门的
  常量值）。用途是区分「这次是键盘来的还是别的设备来的」。
- **项目设置里多了一项「窗口未聚焦时忽略手柄输入」。** 默认情况下手柄输入不管窗口有没有焦点都会进来，
  这会导致意外操作。需要的话在项目设置里打开它。

这两条的完整说明在 [4.7 发布说明](https://godotengine.org/releases/4.7/)（原文英文；本节是概括）。

## 十五、动手练习：绑一套键并看见「轮询挡不住」

目标是把动作、绑定、事件与轮询走一遍，并亲手复现第九节那条实测。大约四十分钟。

1. **新建场景**，根节点 `Node` 改名 `InputLab`，挂一个脚本。
2. **在 `_Ready` 里用代码建两个动作**：一个叫 `lab_fire` 绑键盘 `J`（用 `PhysicalKeycode`），一个叫
   `lab_mod` 绑键盘左 Shift。
3. **在 `_Process` 里打印** `Input.IsActionPressed("lab_fire")`。跑起来按 `J`，确认打出 true。
4. **在 `_Input` 里加一段**：如果这次事件是 `lab_fire` 按下、并且 `lab_mod` 正按着，就调
   `GetViewport().SetInputAsHandled()` 并打印「已拦下」。
5. **跑起来按住 Shift 再按 `J`**。你会看到「已拦下」，**同时 `_Process` 里那行仍然打 true** ——
   这就是「消费只挡事件流不挡轮询」。这一步是这个练习的重点，请务必亲手看到。
6. **加一层遮挡**：在 `_Process` 那行外面包一个判断「`lab_mod` 按着时就当 `lab_fire` 没按」。再跑，
   这回两边一致了。这就是门面在做的事。
7. **把 `lab_fire` 改绑手柄底面键**，插上手柄试一次。再把它绑到右扳机上（记得是轴、只取正方向），
   感受一下死区。
8. **试 `Input.GetVector`**：绑四向，在 `_Process` 里打印返回的向量，看斜推摇杆时它是不是归一化的。
9. **失焦测试**：按住 Shift 不放，切到别的窗口再切回来，打印 `lab_mod` 的状态 —— 如果它还是 true，
   你就看到了第十一节那个「卡住」。

做完你会有两个直觉：**拦事件与拦轮询是两件事**，以及为什么本项目一定要有一个输入门面。

## 十六、这一篇里只能你实机看的

- **改了绑定之后每个键实机按一遍。** 符号翻译对不对没有机器判据 —— 某个轴编号错了只表现为「这个键
  没反应」。
- **手柄上按住扳机挑技能时，会不会误触一次攻击。** 这是第九节那条约束的验收点。
- **修饰键按住那零点几秒里，跳跃与轻重攻击失效会不会碍事。** 这是修饰键方案本身的代价，已接受 ——
  但手感上碍不碍事只有你按得出来。
- **图标会不会自己跳。** 手柄搁在桌上别动，看键鼠图标会不会被摇杆漂移抢走。
- **切窗口回来有没有键卡住。** 按住扳机切出去再切回来。
- **键鼠玩家退不退得出面板、手柄玩家按不按得动确认。** 这两条是同一处补丁的两侧，容易只测一侧。
- **键位布局好不好按。** 六个技能位挪到右手那一批的最终判据就是你实机按一遍。
