# 时间与帧推进

> 本篇回答：**两个循环各管什么**、**为什么玩法时长以帧记而不是以秒记**、**顿帧与暂停是两件不同的
> 事**、**需要「过一会儿再做」时该用什么**。
>
> ⚠️ **本项目不用 `Timer` 节点表达游戏内时间**，理由与替代形状在第六与第七节。前置是
> [脚本与节点接线](./脚本与节点接线.md)。总纲在[本目录索引](./README.md)。

---

## 一、两个循环

| 回调 | 多久一次 | `delta` 是什么 |
| --- | --- | --- |
| `_PhysicsProcess(delta)` | **固定** 60 次每秒 | 恒等于 1/60，不随机器性能变 |
| `_Process(delta)` | 每画一帧一次，次数不固定 | 上一帧到这一帧真实过去了多久 |

**一句话判据**：会影响判定结果的东西放物理帧，纯表现放渲染帧。

**为什么**：物理帧是固定步长的，同样的输入在任何机器上走出同样的结果。渲染帧不是 —— 一台 144Hz 的
机器与一台 60Hz 的机器，`_Process` 被调的次数差一倍多。把玩法放渲染帧里，掉帧时角色会走得更慢、
判定窗口会变宽，而这**不报错**。

物理帧率可以读也可以改（`Engine.PhysicsTicksPerSecond`），但本项目**锁在 60** —— 而且启动时就校验：

```csharp
// src/World/PlayerActor.cs
if (Engine.PhysicsTicksPerSecond != CombatFeel.PhysicsTicksPerSecond)
{
    throw new InvalidOperationException("Combat requires 60 physics ticks per second");
}
```

**为什么当场抛**：全部手感帧数都是按 60Hz 定的，改了物理帧率之后所有窗口的实际时长都变了，而画面上
只表现为「手感不对」。抛出来比让人猜便宜得多。

## 二、时长以帧记，不以秒记

本项目所有手感量的单位是**帧**（`rules/Combat/CombatFeel.cs` 里那一批），不是秒：

| 量 | 单位 |
| --- | --- |
| 前摇、命中窗、后摇、无敌窗、顿帧、硬直 | **帧** |
| 移动速度、跳跃初速、重力 | 世界像素／秒（引擎自己乘 delta） |
| 击退量、判定框尺寸 | 世界像素 |

**为什么用帧**：判定窗口与连段衔接都是逐帧的，秒会引入取整歧义 —— 「0.1 秒的无敌」在 60Hz 下是 6 帧
还是 7 帧，取决于取整方式，而差一帧在动作游戏里是能感觉到的。

**量纲一律写在成员名里**，读得出它是帧、是世界像素还是像素每秒。

## 三、顿帧：不是暂停，是「当帧不推进」

命中那一下画面卡住零点几秒（顿帧，hitstop）是打击感的主要来源。本项目的做法：

```csharp
// rules/Combat/HitstopTimer.cs：只计时，不冻结引擎
public bool Tick()
{
    if (!IsActive) { return false; }
    RemainingFrames--;
    return true;      // 这一帧必须冻结
}
```

调用契约是：**外层每个物理帧先调一次 `Tick`，返回真就跳过这一帧的战斗推进与相机推进。**

三条要点：

- **物理帧照常走，渲染照常走** —— 停的只是「战斗状态机往前走一步」这件事。
- **再次命中时用新值替换剩余时间**，不叠加。
- **顿帧计时器自己不能放进被顿帧跳过的那段逻辑里**，否则它永远不会递减。

### 为什么不用 `Engine.TimeScale`

`Engine.TimeScale = 0` 能让整个世界停住，但它同时冻住**一切** —— 包括那些必须照走的东西。本项目里有
一个具体的例子：命中白闪按**真实帧号**算（`Engine.GetPhysicsFrames()`），顿帧期间它要自己走完，
所以那一句写在顿帧判断之外。

**用帧号而不是「每帧减一的计数器」还躲开了一个顺序依赖**：命中当帧里「受击」与「自己推进」都会跑，
而两者的先后取决于节点树的顺序（父在子前）。计数器版本会在「命中当帧就被减掉一次」与「没被减掉」之间
摇摆 —— 白闪到底亮 1 帧还是 2 帧变成树结构的函数。帧号版本与调用顺序、调用次数都无关。

## 四、三种「玩家动不了」，只有一种是暂停

这四行是[界面控件](./界面控件.md)那张表的时间侧说法，值得在这里再列一次，因为它是最容易写错的地方：

| 情形 | 机制 | 世界在跑吗 |
| --- | --- | --- |
| 打开面板 | 导航栈非空 → `GetTree().Paused` | **停** |
| 命中顿帧 | 战斗推进当帧不走 | 跑（物理帧照走） |
| 硬直、失衡、被击倒 | 状态机里的一个姿态 | 跑 |
| 每日结算 | 一次转场 | 世界本来就不在跑 |

**判据是「界面接不接管输入」，不是「玩家操作得了吗」。**

## 五、`GetTree().Paused` 怎么工作

设成真之后，引擎按每个节点的 `ProcessMode` 决定它还跑不跑：

| `ProcessMode` | 暂停时 |
| --- | --- |
| `Inherit`（默认） | 跟父节点一样 |
| `Pausable` | 停 |
| `WhenPaused` | **只在暂停时跑** |
| `Always` | 一直跑 |
| `Disabled` | 一直不跑 |

本项目只显式用了一处：**输入门面设成 `Always`**（`src/UI/InputRouter.cs`），因为弹窗要求暂停世界，
而那时界面还得能操作。

⚠️ **玩法节点不要设 `Always`。** 它们就该在暂停时停住 —— 手柄上「下面键既是跳跃也是界面确认」那个
共用物理位的歧义，正是靠「面板开着时玩法节点根本不在跑」消掉的。

## 六、为什么不用 `Timer` 节点表达游戏内时间

`Timer` 是一个节点，设个秒数、到时候发一个信号。它适合表现（闪一下、延迟消失），**不适合玩法**。
三条理由：

1. **它按秒算，而玩法时长按帧算。** 两套单位混用就要来回换算，而换算点就是取整歧义的入口。
2. **它不认顿帧。** 顿帧期间战斗不推进，而 `Timer` 照走 —— 于是「硬直 20 帧」在被顿帧打断之后实际
   短了几帧，而这不报错。
3. **它在暂停时的行为取决于 `ProcessMode`**，于是「这个计时器暂停时走不走」变成一个要逐个节点确认的
   事，而漏掉一个不报错。

**更要紧的一条**：游戏内的「天」不是真实时间。按天发生的事挂在**每日结算那串固定步序**上，而不是
挂在一个计时器上。

## 七、需要「过一会儿再做」时用什么

按这三种情形选，不要默认伸手去拿 `Timer`：

### 甲：玩法上的「N 帧之后」→ 自己数帧

状态机里存一个「还剩几帧」，每个**未被顿帧跳过的**物理帧减一。本项目的硬直、无敌窗、前后摇全是这个
形状。要「从某一刻起算 N 个真实帧」（白闪这种不受顿帧影响的），就存一个截止帧号：

```csharp
_flashUntilFrame = Engine.GetPhysicsFrames() + (ulong)CombatFeel.HitFlashFrames;
// 判断：Engine.GetPhysicsFrames() < _flashUntilFrame
```

### 乙：纯表现上的「等一会儿」→ 一次性计时器

不想为一次淡出建一个 `Timer` 节点时，用场景树给的一次性计时器：

```csharp
await ToSignal(GetTree().CreateTimer(0.2), SceneTreeTimer.SignalName.Timeout);
```

⚠️ **只用在表现上。** 它按秒算、不认顿帧，而且 `async` 里抛的异常会被吞掉（见
[脚本与节点接线](./脚本与节点接线.md)那一节）。

### 丙：游戏内日期上的「第几天」→ 挂结算步，或者存一个日期后补算

**挂结算步**：按天发生的事（作物生长、建造进度、债务计息）都并进每日结算那串步序里已有的某一步。
**那串步序的步数一个不增一个不减**，这是结构约束 —— 要加一件按天做的事，是把它挂进某一步，不是加
一步。

**存日期后补算**：不占结算任何一步的做法。商店刷新就是这个形状 —— 存一个「上次刷新在哪天」，玩家
**进店时**按过了几天补算。订货在途单同理：存「下单那天」，日期到了货就出现在送达点。

**这两种形状的判据**：这件事必须在那一天当场发生（作物必须在那天长大）→ 挂结算步；这件事只在玩家
看它的时候才需要正确（商店货架）→ 存日期后补算。

## 八、读条怎么做

读条（采集、用道具、劳作、转场、钓鱼）是本项目最常见的一种「持续若干帧的动作」。它有三种不同的
中断规则，**别用同一套实现**：

| 哪一类 | 受击时 | 移动时 | 消耗 |
| --- | --- | --- | --- |
| 采集、开箱、用道具、劳作 | **中断** | **取消** | 中断时不消耗 |
| 关卡转场 | **不中断，只延长** | 打不断 | —— |
| 按住跳过演出 | 不适用 | 不适用 | —— |

三条实现口径：

- **进度按帧数，不按秒。** 时长是手感量，归实机调。
- **进度条画在执行者身上**，不画在屏幕角落 —— 所以它挂世界空间那一层（见[界面控件](./界面控件.md)）。
- **读条不接管输入，所以世界不暂停。** 它是世界里的动作。

⚠️ **转场那条「受击不中断只延长」有一条硬要求**：延长量不得大到在一屏敌人齐打时把它推成走不掉。这一条
只能实机验。

## 九、真实时间只用在两处

`Time` 这个单例给的是真实世界时间（`Time.GetUnixTimeFromSystem()`、`Time.GetDatetimeStringFromSystem()`
这些）。本项目只在两种地方用它：

- **诊断输出的时间戳。**
- **存档位摘要里的「上次玩是什么时候」。**

**玩法一个地方都不读它。** 游戏内的日期是游戏自己的状态，不是真实日期的函数。

## 十、帧步进：调手感的主要工具

本项目自己有一个调试工具（`ENG-6` 交的那个），它把顿帧那个「当帧不推进」的闸门复用成**手动帧步进**：
按一下走一帧，配合判定框与受击框的叠层，能逐帧看「这一帧判定框开着吗、画面上拳脚伸到哪了」。

**这是 `GP-6`（手感实机收敛）唯一可行的工作方式。** 详细用法在调试那一篇（还没写）。

⚠️ **手动驱动帧推进的调用方有一条契约要守**：判定框的去重集合是靠「相邻两次调用之间观察到 Active 上
升沿」清空的。稀疏调用（只在命中帧调、跨挥击不调）会让集合停在上一次挥击的内容里，**表现是攻击静默
不生效** —— 返回 0、无报错，看起来像判定框或纵深出了问题。

## 十一、动手练习：做一个认顿帧的读条

目标是把物理帧、帧计数、顿帧闸门走一遍，并看出「用 `Timer` 会错在哪」。大约四十分钟。

1. **新建场景**，根节点 `Node2D` 改名 `ChargeLab`，挂一个脚本。加一个 `ProgressBar` 子节点（先挂在
   世界里，位置随便）。
2. **在 `_PhysicsProcess` 里做一个读条**：按住某个键时 `_frames++`，读条长度 = `_frames / 总帧数`。
   松开键就把 `_frames` 归零（这就是「移动即取消」的简化版）。总帧数先写 60（一秒）。
3. **跑起来按住键**，确认一秒填满。
4. **加一个假顿帧**：加一个 `_freezeFrames` 字段，按另一个键时设成 30。在 `_PhysicsProcess` 开头判
   「如果 `_freezeFrames > 0` 就减一并 `return`」。再跑：读条中途按那个键，读条应该停半秒再继续。
   **这就是顿帧闸门。**
5. **换成 `Timer` 再试一次**：加一个 `Timer` 节点、`WaitTime` 设 1 秒，按住键时 `Start()`。跑起来在
   读条中途触发顿帧 —— **`Timer` 不会停**，它照样一秒后发信号。这就是第六节第二条理由的样子。
6. **打印帧号对比**：在 `_PhysicsProcess` 里同时打 `Engine.GetPhysicsFrames()` 与你自己那个
   `_frames`。顿帧期间前者继续涨、后者不涨 —— 这就是「真实帧」与「逻辑帧」的差别。
7. **打印两个 delta**：在 `_Process` 与 `_PhysicsProcess` 里各打一次 `delta`，跑起来对比。把
   `Engine.MaxFps` 设成 30 再跑一次，看哪一个变了。
8. **试一次性计时器**：用 `await ToSignal(GetTree().CreateTimer(0.5), ...)` 让读条满了之后延迟半秒
   再重置，感受它与帧计数在写法上的差别。

做完你会有三个直觉：物理帧与渲染帧的差别、顿帧闸门是怎么「停一部分」的、`Timer` 为什么不认顿帧。

## 十二、这一篇里只能你实机看的

- **顿帧几帧最带感。** 太短没感觉，太长像卡顿。这是全项目最该逐帧试的一个数。
- **读条被取消那一下看不看得出来。** 玩家要能立刻明白「我这次没采到」，而不是以为卡了。
- **转场读条被打断时的延长量合不合理。** 一屏敌人齐打时它还走得完吗。
- **无敌窗与前后摇。** 闪避能不能躲过那一招、后摇会不会长到像掉帧。
- **跳过演出要按住多久。** 按住的进度必须看得见，否则会被读成没反应。
- **掉帧时手感有没有变。** 把机器压一下（开几个占 GPU 的窗口）再打一场，判定应该不受影响 —— 如果
  受了，说明某处把玩法写进了渲染帧。
