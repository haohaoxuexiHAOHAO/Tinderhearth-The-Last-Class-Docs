# 编辑器与场景

> 本篇是地基：**Godot 里的四个基本词**、编辑器几块地方各管什么、一个场景从零到能跑、素材怎么进来。
> 读完这一篇之后，别篇就可以直接说「在场景里摆一个 `Area2D`」而不用再解释「场景」是什么。
>
> 总纲与四条口径在[本目录索引](./README.md)。

---

## 一、四个词先分清

Godot 的整套心智模型只有四个词，其中两个 Java 里没有对应物。

| 词 | 是什么 | 在磁盘上 | 大致对得上的东西 |
| --- | --- | --- | --- |
| **节点**（Node） | 一个有能力的零件：会画图的、会碰撞的、会放声音的 | 不单独存 | 一个对象实例 |
| **场景**（Scene） | **一棵节点树**，加一个根节点 | `.tscn` 文件 | 一个可复用的组件 |
| **实例**（Instance） | 把一个场景当成一个节点，塞进另一棵树 | 引用，不是拷贝 | `new` 一个组件 |
| **资源**（Resource） | 一坨数据：图、字体、音频、动画帧表、你自定义的表 | `.tres`／`.res`，或就是 `.png` 这类原件 | 一个不可变的数据对象 |

三件事值得单独说明，因为它们是新手最容易卡住的地方：

**「场景」不是「关卡」。** 一个角色是一个场景，一个按钮是一个场景，一颗子弹是一个场景。它只是
「一棵可以整体复用的节点树」，与规模无关。本项目里训练房是一个场景，主角也会是一个场景。

**节点没有「组件」这一层。** Unity 那种「一个 GameObject 挂五个 Component」在 Godot 里是「一个父
节点带五个子节点」。所以角色的碰撞形状是它的**子节点**，不是它的一个字段。这也是为什么本项目的
脚本要「取子节点」而不是「读字段」。

**资源是共享的。** 两个节点指向同一个 `.png`，内存里只有一份。所以改一个资源会同时改到所有用它
的地方 —— 这正是想要的（换一张图全场生效），但也意味着「我只想改这一个」时要先点资源旁边那个
「使其唯一」（Make Unique）。

## 二、编辑器几块地方

打开工程后屏幕分四块，每块回答一个不同的问题。

| 位置 | 面板 | 回答什么 |
| --- | --- | --- |
| 左上 | **场景**（Scene） | 这个场景由哪些节点组成、谁是谁的子节点 |
| 左下 | **文件系统**（FileSystem） | 工程里有哪些文件（这就是 `res://` 那棵树） |
| 右侧 | **检查器**（Inspector） | 当前选中的那个节点／资源有哪些格子可以填 |
| 中间 | **2D／3D／Script 视图** | 画面本身。本项目只用 2D 与 Script |
| 底部 | **输出**（Output）／**调试器**（Debugger） | 游戏打印了什么、报了什么错 |

几条对本项目有用的操作：

- **加节点**：场景面板上那个 `+`，或 `Ctrl+A`。搜框里打类名的前几个字母就能筛到。
- **换根节点类型**：右键根节点 → 更改类型。搭错了不用重建。
- **跑**：`F5` 跑整个工程（从 `project.godot` 里指定的主场景起），`F6` 只跑当前打开的这一个场景。
  **调一块片段或一个界面时用 `F6`**，不必每次从主场景走进去。
- **底部那两个面板是唯一的报错出口。** C# 抛的异常、`GD.PushError` 打的东西都在那里。画面上少了
  一块东西时先看它 —— 本项目的脚本被要求「缺子节点就报错说清缺谁」，那句话就打在这里。

2D 视图左上角那排是变换模式（选择、移动、旋转、缩放、标尺等），鼠标悬停在按钮上会显示它的快捷键。
**像素游戏里几乎只用「选择」与「移动」**：旋转与缩放会让像素落在非整数位置上，糊边是肉眼看得
出来的。

## 三、一个场景从零到能跑

以本项目要搭的第一个东西为例：训练房。步骤对任何场景都一样。

1. **新建场景**，给它一个根节点。根节点的类型决定这个场景「本质上是什么」：
   - 世界里的东西（关卡、片段、基地、角色）→ `Node2D`
   - 一页界面 → `Control`
   - 纯逻辑容器（很少用）→ `Node`
2. **给根节点改名**。名字就是脚本里取它的路径，所以取个稳定的名字，别留 `Node2D2`。
3. **往下加子节点**，一层一层搭出结构。
4. **`Ctrl+S` 存成 `.tscn`**，落在 `res://scenes/` 下。
5. **挂脚本**：选中某个节点 → 检查器顶上那个卷轴图标，或右键 → 附加脚本。详见
   [脚本与节点接线](./脚本与节点接线.md)。
6. **`F6` 跑一下**，看底部输出有没有报错。

存盘时注意 **`.tscn` 是文本格式**，能进 git、能 diff、冲突能手改。`.scn` 是同一个东西的二进制版本，
只在导出的发行包里出现（导出时引擎自己转）。所以**永远存 `.tscn`，别存 `.scn`**。

### 节点树怎么分层

一条经验规则：**一个节点只做一件事，位置由父节点带着走。** 本项目的角色大致会是这个形状（真正
的树由你搭，这里只示意层级关系）：

```
Player            (CharacterBody2D)   ← 位置、速度、碰撞由它持有
├── Body          (CollisionShape2D)  ← 实体碰撞形状
├── Visual        (Node2D)            ← 纵深偏移与影子挂这里
│   └── Sprite    (AnimatedSprite2D)  ← 逐帧动画
├── Hurtbox       (Area2D)            ← 受击范围
│   └── Shape     (CollisionShape2D)
└── Hitbox        (Area2D)            ← 攻击判定范围
    └── Shape     (CollisionShape2D)
```

为什么要多一层 `Visual` 而不把精灵直接挂在角色下面：本项目的纵深（第三个轴）要把整个可视部分
往上抬，而碰撞形状不许跟着抬。多一层就让「抬」只有一个落点。这类「为什么多一层」的理由会写在
各篇对应的地方，不在这里堆。

## 四、把一个场景当节点用（实例化）

搭好的场景可以整棵塞进另一个场景，这是复用的唯一方式。

- **加进来**：从文件系统面板把 `.tscn` 拖进场景树，或场景面板上那个链条图标（实例化子场景）。
- **实例是引用，不是拷贝。** 改原场景，所有实例跟着变。这正是「摆二十个敌人，改一次动画全改」
  的机制。
- **单个实例要微调**：右键那个实例 → **可编辑子节点**（Editable Children）。打开之后它内部的
  节点就露出来、可以单独改；改过的格子旁边会出现一个「还原」箭头，点它回到原场景的值。
- **想让一批东西共享结构但各自不同**：场景 → **新建继承场景**（New Inherited Scene）。继承场景
  等于「以那个场景为基类」，改基类会影响全部子类。敌人那一批适合这么做。

⚠️ **一个陷阱**：实例化之后在检查器里改的每一个格子都会被记进**外层场景**的 `.tscn`。所以「改一个
数就能全场生效」与「我在这个实例上改过」是两件事 —— 后者会盖住前者且不报错。摆位之外的东西
（尺寸、参数）尽量改原场景，别在实例上覆盖。

## 五、名字与「唯一名」

脚本要找到你搭的节点，靠的是**路径**：`Visual/Sprite` 这种。路径由名字拼出来，所以**改名会断掉
脚本的引用**。

Godot 给了一个办法让路径不随层级变：**右键节点 → 作为唯一名称访问**（Access as Unique Name）。
之后它在场景树里前面会多一个 `%`，脚本用 `%Sprite` 就能拿到它，**不管它被挪到哪一层**。

**本项目的口径**：会被脚本读的节点尽量都开唯一名。理由是你在编辑器里重排层级（这是你该自由做的
事）不应该让代码坏掉，而层级路径会让它坏掉。唯一名在同一个场景里不许重名，编辑器会拦。

## 六、位置、层级与画的先后

`Node2D` 及其派生类在检查器里有一组变换格子：

| 格子 | 单位 | 改了会怎样 |
| --- | --- | --- |
| **Position** | 像素（相对父节点） | 挪位置。本项目是像素游戏，**尽量填整数** |
| **Rotation** | 度 | 旋转。像素素材基本不用 |
| **Scale** | 倍数 | 缩放。像素素材基本不用，见下面那条 |
| **Z Index** | 整数 | 同一层里谁画在上面。数字大的盖住小的 |
| **Y Sort Enabled** | 开关 | 开了之后，**子节点按各自的 Y 坐标决定先后**（低的画在上面） |

三条本项目的硬约定：

- **不缩放像素素材。** 侧视与俯视各画一套素材、按各自需要的大小直接画出来（[ADR-0020](../../decisions/ADR-0020-侧视不拉近而把角色画大一档.md)），
  不靠 `Scale` 放大。缩放会让一个像素跨到两个屏幕像素上，糊边肉眼可见。
- **不靠 `Y Sort` 排侧视战斗的前后。** 侧视的前后关系归纵深轴，它的值在规则层持有，引擎层按它算
  `Z Index`。俯视场景才可能用 `Y Sort`。
- **位置尽量落在整数像素上。** 相机也有同样的约束（相机那一篇会说）。

## 七、素材是怎么进来的

这条链是作者最常走的，也是本项目坑最多的一条。

### 导入那一步在做什么

往 `res://` 下丢一个 `.png`，Godot 会**自动导入**它：读原图 → 按一组参数处理 → 存一份引擎能用的
中间产物，同时在原图旁边生成一个同名的 `.import` 文件。

**那个 `.import` 文件就是这张图的导入参数，它要进 git。** 选中图片之后，检查器旁边会多一个
**导入**（Import）页签，改完点「重新导入」。

### 项目级默认值：本项目覆盖了四项

前三项在 `project.godot` 的 `[importer_defaults]` 里，第四项在渲染设置里。**理由写在代码仓
`ARCHITECTURE.md` 而不是那个文件的注释里** —— 实测过：在编辑器里打开一次工程，Godot 会重写
`project.godot` 并**把注释整段删掉**，不报错也不提示。

| 参数 | 本项目取值 | 为什么 |
| --- | --- | --- |
| 压缩模式 | 无损 | 有损压缩会让像素图发花，而画面只是「有点脏」，不报错 |
| 发现用于 3D 时重新压缩 | 关 | 纯 2D 项目理论上不触发，一旦触发就是像素图被有损压缩 |
| 生成 Mipmap | 关 | 缩小级别对像素风没有意义 |
| 默认纹理过滤 | 最近邻 | 线性过滤会把像素糊掉 |

⚠️ **项目级设置只影响「将来新导入」的文件。** 已经导入过的素材各自把参数固化在自己的 `.import`
里了。所以从别处拷进来一批已带 `.import` 的素材时，要逐个确认，或者删掉 `.import` 让它重新导入。

⚠️ **不要在节点上覆盖纹理过滤。** `CanvasItem` 有一个 `Texture Filter` 格子，默认是「继承项目
设置」。改成线性过滤的表现是那一个节点的像素糊掉，而项目照常跑（`ENG-13`）。

### 改了导入参数一定要重新导入

**这一条有实测代价。** 改了字体的 `.ttf.import` 参数却没重新导入，游戏读到的还是上一次烘出来的
产物 —— 抗锯齿仍是灰度，12px 中文多一圈半透明脏边，**一句报错都没有**。重新导入的两个办法：在
编辑器里对那个文件点「重新导入」，或跑一次 `<Godot> --headless --path . --import`。

### 逐帧素材的切法

一张图里横排若干帧的做法，在动画那一篇里写（`AtlasTexture` 与 `SpriteFrames`）。这里只记一条与
导入有关的：**进仓的表里不要出现整帧单色的帧**。命中闪白由代码持有（`ART-6`），烧进图里会让闪白
时长改不了。

## 八、`res://` 与 `.gdignore`

- **`res://`** 是工程根目录。`res://scenes/Main.tscn` 就是工程里那个文件。
- **`user://`** 是玩家的数据目录（存档、mod）。文件读写那一篇会说它为什么必须是这个而不是 exe
  同级目录。
- **`.gdignore`** 放进某个目录，Godot 的资源扫描就跳过它。本项目在 `rules/`、`tests/`、`tools/`
  下各放了一个，否则源码与编译中间产物会被打进发行包（实测过：包从 8.5 KB 变成 182 KB）。

**新增 `res://` 下不含 Godot 类型的目录时，同时放一个 `.gdignore`。** 这一条有执行体：验收入口会
解开发行包逐条比对，泄漏当场判失败 —— 而泄漏本身不会报错。

## 九、场景文件长什么样，代码怎么用它

这一节偏代码侧。你不必自己写，但看懂 `.tscn` 之后，git 里的改动你就读得出来了 —— 那是「我在编辑器
里到底改了什么」唯一看得见的地方。

### `.tscn` 就是一份文本清单

`scenes/TrainingRoom.tscn` 现在整份就这么几行（本项目还没搭树，所以它只有一个节点）：

```ini
[gd_scene format=3 uid="uid://ctrnroomgp14a"]

[ext_resource type="Script" uid="uid://d1dcwsduekkp4" path="res://src/World/TrainingRoom.cs" id="1"]

[node name="TrainingRoom" type="Node2D" unique_id=748131779]
script = ExtResource("1")
```

三个部分：

- **`[gd_scene]`** 是文件头。`uid://` 是这个场景的稳定标识，别人引用它用的是这个而不是路径 ——
  所以**移动或改名一个场景不会断掉引用**。
- **`[ext_resource]`** 列这个场景用到的外部东西（脚本、图、别的场景），每样给一个局部编号。
- **`[node]`** 是节点本身。下面跟着的每一行都是**你在检查器里改过的那一格**；没改过的格子根本
  不会出现在文件里。

**最后那条是读 diff 的关键**：文件里出现一行，就意味着「这一格被显式设成这个值了」。所以看一次
`git diff` 就知道刚才在编辑器里动了什么，包括手滑动的那些。

### 代码里怎么加载与实例化

```csharp
// 加载一个场景，拿到的是模板而不是实例
var enemyScene = GD.Load<PackedScene>("res://scenes/Enemy.tscn");

// 造一个出来，再挂进树
var enemy = enemyScene.Instantiate<Enemy>();
AddChild(enemy);
enemy.Position = new Vector2(120, 0);
```

三条本项目的口径：

- **路径不写死在代码里**，改成 `[Export] public PackedScene? EnemyScene { get; set; }` 让你在检查器
  里拖进去。写死路径的坏处是改名不报错 —— `GD.Load` 找不到时返回 `null`，然后在下一行炸出一个跟
  真正原因无关的空引用。
- **`Instantiate<T>()` 带类型参数**，拿到的直接是要的类型，省一次强制转换；类型不对当场抛，而这
  正是想要的。
- **`AddChild` 之后位置才有意义。** 实例刚造出来时还不在树里，`GlobalPosition`、`IsOnFloor()` 这些
  都要进树之后才算得对。

### `GD.Load` 与后台加载

`GD.Load<T>(path)` 是同步加载：调用它就卡住，直到读完。小东西（一张图、一个小场景）无所谓；大东西
要用 `ResourceLoader.LoadThreadedRequest` 那一套在后台读。本项目现在全是前者，关卡片段那一批到时候
再定 —— 判据是「切片段时会不会卡出一帧」，而那只能实机看。

## 十、4.7 里三样对你有用的新东西

本项目的引擎基线是 4.7.2，下面这几样在 4.6 及更早的教程里查不到。

- **2D 场景画笔**（Scene Paint Mode，2D 视图里默认按 `B`）：像刷瓦片一样把**场景实例**刷进场景 ——
  刷收集物、敌人、装饰件都行。与瓦片地图的场景瓦片不同，它刷出来的是**真正的节点**，事后可以在
  编辑器里单独选中和修改，也不受网格限制。摆基地装饰与关卡片段里那些零碎件会用到它。
- **检查器整节复制粘贴**：右键检查器里的一个分类或分组，可以把那一整节的值一次性复制到另一个
  节点上。给二十个敌人配同一组参数时省事。
- **`Control` 的偏移变换**：现在可以位移、旋转、缩放一个界面控件而**不影响容器里其他控件的排布**
  （容器排序不会再把它抹掉）。界面做出现与淡出动效时用它。

更多见 [4.7 发布说明](https://godotengine.org/releases/4.7/)（原文英文；本节是概括，不是逐句翻译）。

## 十一、本项目现在有哪几个场景

`scenes/` 下两个：`scenes/Main.tscn` 是启动场景（现在只是把「内容加载 → 规则层」这条链走通一遍的
临时脚手架），`scenes/TrainingRoom.tscn` 是训练房。

**两个都还是「一个节点、六行」的形状** —— 节点树是空的，东西全在 `_Ready()` 里用代码建。把训练房
改成你搭树、脚本挂上去读，是待办台账里 `GP-14`；其余场景跟着 `ENG-21` 走。

## 十二、动手练习：搭一个能跑的空房间

目标是把这一篇用到的每一样各碰一次。大约二十分钟，做完不用保留。

1. **新建场景**，根节点 `Node2D`，改名 `Sandbox`，存成 `res://scenes/Sandbox.tscn`。
2. **加一个 `Sprite2D` 子节点**，改名 `Ground`，从文件系统拖一张图进它的 `Texture` 格子
   （`assets/self-drawn/` 下随便一张）。把它的 `Position` 填成整数。
3. **把它的 `Scale` 改成 3**，`F6` 跑一下，凑近看边缘 —— 记住糊边长什么样。然后**改回 1**。
4. **再加一个 `Sprite2D`**，改名 `Thing`，摆在 `Ground` 上面一点。给两个节点填不同的 `Z Index`，
   跑起来看谁盖住谁；把两个值互换，再看一次。
5. **把 `Thing` 单独存成一个场景**（右键那个节点 → 将分支保存为场景），然后**实例化三份**回 `Sandbox` 里，
   摆成一排。回到 `Thing` 那个场景换一张图，再跑 —— 三份应该一起变了。
6. **在其中一份实例上改一格**（比如 `Modulate` 调成红色），存盘，然后在 git 里看
   `res://scenes/Sandbox.tscn` 的 diff —— 那一行就是「我在这个实例上覆盖过」的痕迹。
7. **给 `Thing` 开唯一名**（右键 → 作为唯一名称访问），看它前面多出来的 `%`。

做完你会对四件事有直觉：实例是引用不是拷贝、覆盖会被记进外层场景、缩放会糊、`.tscn` 的 diff 读得懂。

## 十三、这一篇里只能你实机看的

机器判不了下面这些，全靠 `F6` 跑一下自己看：

- **像素有没有糊。** 过滤被覆盖成线性、或者素材被缩放过，表现都是边缘发虚。放到最大看一眼。
- **脚底有没有贴地。** 精灵往上抬多少由「帧内地面行」决定，改错一像素的表现是脚陷进地面或者
  悬空，而纹理尺寸照样对得上、日志照样干净。
- **层级前后对不对。** 角色走到物件后面时该被挡住的有没有被挡住。
- **实例上有没有误覆盖。** 一批敌人里有一个参数跟别人不一样，最常见的原因是在那个实例上手滑
  改过。检查器里带「还原」箭头的格子就是被覆盖过的。
