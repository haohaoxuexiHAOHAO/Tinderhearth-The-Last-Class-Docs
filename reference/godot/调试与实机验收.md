# 调试与实机验收

> 本篇回答：**跑起来之后怎么看里面发生了什么**、**出问题时先看哪里**、**哪些事只有你看得出来**。
>
> 这一篇是整套文档的收尾，因为本项目的验证分工就落在这里：**机器只判在 Godot 里看不出来的东西**
> （规则层逻辑、发行包泄漏、字体授权、数值平衡），**看得出来的一律交给你实机看**。图形探针那一套已经
> 随 [ADR-0009](../../decisions/ADR-0009-编辑器主导的开发模式.md) 删除。总纲在[本目录索引](./README.md)。

---

## 一、出问题时的排查顺序

按这个顺序走，绝大多数问题在开头那几项就定位了。

1. **看底部「输出」面板。** 脚本打印的诊断、警告、报错都在这里。本项目的脚本被要求「缺子节点／缺配置
   就报错说清缺谁」，那句话就打在这里。
2. **看底部「调试器」面板。** 抛出来的异常连堆栈都在这里，而且游戏会停在那一行。
3. **开「可见碰撞形状」再跑一次。** 「该挡住却穿过去」「明明打中了却没判定」这类问题看一眼就清楚。
4. **切到「远程」场景树。** 看跑起来时真实的节点树长什么样、每个节点此刻的属性值是多少。
5. **用帧步进逐帧看。** 手感与时序问题只能这么看。

## 二、输出面板：脚本在说什么

| 写法 | 显示成 |
| --- | --- |
| `GD.Print(...)` | 普通文字 |
| `GD.PushWarning(...)` | 黄色警告 |
| `GD.PushError(...)` | 红色错误 |
| `throw new ...` | 跳到调试器面板，游戏停住 |

**本项目的口径**：缺配置与缺子节点一律**抛**，不打警告继续跑 —— 警告会被滑过去，而滑过去的后果是画面
上少一块东西、你以为是自己没摆。

**启动日志是有意留的。** 现在跑起来会打印界面层级、排版单位、精灵表帧数这些。**它们不是契约**（原先
有探针按格式解析，探针已删），但对着精灵表核一眼「帧数对不对」很方便。

⚠️ **排查缺陷时允许临时加诊断输出**，但**事后要删掉**。留着的诊断会在下一次排查时变成噪声。

## 三、远程场景树：跑起来时的真实状态

游戏跑起来之后，**场景面板顶上会多一个「远程」页签**。切过去能看到运行时真实的节点树 —— 包括代码
建出来的节点。

**两个用法值得专门记住：**

- **点一个远程节点，检查器里显示它此刻的属性值。** 「这个值到底被设成多少了」不用打印，直接看。
- **在检查器里改值，游戏里立刻生效。** 这是调手感最快的路子 —— 改一个数、眼睛看、再改。

⚠️ **远程改的值不会存回场景文件。** 试出满意的值之后要回到「本地」页签手动填一遍，否则重启就没了。

⚠️ **「远程」页签只在游戏跑着的时候有。** 停了就回到本地树。

## 四、调试菜单里那几个可视化开关

菜单栏 →「调试」下面有一批开关，勾上之后**下一次跑**生效：

| 开关 | 画出什么 | 什么时候开 |
| --- | --- | --- |
| **可见碰撞形状** | 所有碰撞体与区域的形状 | 穿模、判定不生效、交互点范围不对 |
| **可见导航** | 导航网格 | 本项目不做寻路，用不上 |
| **可见路径** | `Path2D` 那类路径 | 本项目现在没有 |
| **同步场景更改** | 编辑器里改场景，跑着的游戏跟着变 | 调摆位很快，但会有意外 |
| **同步脚本更改** | 改脚本自动重载 | C# 支持有限，别依赖 |

**「可见碰撞形状」是这一批里最常用的一个**，遇到任何「位置对不上」先开它。

## 五、剖析器：慢的时候看它

调试器面板里有几个页签是性能相关的：

- **剖析器**（Profiler）：每一帧各部分花了多少时间（物理、脚本、渲染）。
- **监视器**（Monitors）：帧率、物理帧时长、内存、绘制调用数随时间的曲线。
- **显存**（Video RAM）：哪些纹理占了多少显存。

**本项目现在用不上它**，但有一件事将来要靠它量：满编场景（一屏十几个敌人加角色加物件）会不会掉帧。
那条账记在[待办台账](../../spec/issues/README.md)的 `ENG-16` 旁边。

⚠️ **先测量再优化。** 本项目的约定是优先写清楚的代码（比如优先用 LINQ 而不是手写循环），**除非性能
测量显示有问题**。

## 六、本项目自己的帧步进与判定框叠层

这是 `ENG-6` 交付的工具，也是调手感唯一可行的方式：

- **判定框与受击框画出来**：读的是与命中查询**同一份**形状，所以画出来的框就是命中真正用的那个，不会
  各算一份而漂移。
- **帧步进**：复用顿帧那个「当帧不推进」的闸门，按一下走一帧。

**配合起来能回答这个问题**：这一帧判定框开着吗、画面上拳脚伸到哪了、两者对得上吗。

⚠️ **手动驱动帧推进有一条契约**：判定框的去重集合靠「相邻两次调用之间看到命中窗的上升沿」清空。只在
命中帧调、跨挥击不调，会让集合停在上一次挥击的内容里 —— **表现是攻击静默不生效**（返回 0、无报错，
看起来像判定框或纵深坏了）。

## 七、命令行：不开编辑器也能跑

```
<Godot 可执行文件> --path .                              跑这个工程
<Godot 可执行文件> --headless --path . --import          只重新导入素材，不开窗口
<Godot 可执行文件> --headless --export-release "Windows Desktop"   导出
```

几个有用的参数：`--headless`（不开窗口）、`--log-file <路径>`（把引擎日志写到文件）、`--verbose`
（详细日志）、`--quit`（跑一帧就退）。

**`--import` 那条值得记住**：改了素材的导入参数之后要重新导入，而这条命令能一次做完（也可以在编辑器
里对那个文件点「重新导入」）。不重新导入的话游戏读到的还是上一次烘出来的产物，**一句报错都没有**。

## 八、验收总入口：`python tools/verify.py`

在**代码仓根目录**跑这一条，它把五步串起来：行尾 → 构建 → 测试 → 导出 → 跑产物。逐步日志落到
`logs/verify/` 下带时间戳的目录里，同目录写一份摘要。

**失败即停** —— 后一步依赖前一步的产物，硬跑下去只会产出误导性的失败。

**标准输出每步只有一行**，详细的东西都在日志里。

两个附带用法：`--upto eol|build|test|export` 只跑到某步（前置步骤一定跟着跑）；`--manifest` 不跑任何
步骤、只把发行包里的清单打出来。

**日常改场景不用跑它** —— 它验的是代码那一侧。你改了场景之后要跑的是 `F6`，看画面。

### 为什么每步都另找一个量具

**退出码骗过人。** 这五步的退出码都不足以证明成功，所以每步都另核一样东西：

| 步骤 | 除退出码之外还核什么 |
| --- | --- |
| 行尾 | 认不出行尾检查工具的输出形状就判失败 |
| 构建 | 自己数错误行，认不出构建输出的形状就判失败 |
| 测试 | 运行器报的条数**等于**从测试源码静态数出来的条数（两个独立来源） |
| 导出 | 先清空产物目录再导，于是「文件存在」＝「本轮生成」；再解开包逐条看清单查泄漏 |
| 跑产物 | 真启动导出的可执行文件，从引擎日志确认代码跑到了内容载入完成 |

⚠️ **这条脚本自己没有自证入口了。** 代价要写明：**一个什么都不检的脚本也会全绿**，所以它坏了没有东西
能发现。复核的省事办法是临时弄坏一样东西（改反一个文件的行尾、往包里塞一个源码文件），确认它真的报
出来再改回去。

⚠️ **退出码 0 不等于成功，要同时看脚本自己打印的摘要。** 这一条对设计仓那两个入口同样成立。

## 九、机器判什么、你判什么

这张表是整套文档的总纲的另一面：

| 机器判 | 你判 |
| --- | --- |
| 规则层逻辑（判定、结算、状态机流转） | 手感（顿帧几帧、前后摇、跟随死区） |
| 发行包里有没有泄漏源码 | 画面（像素糊不糊、脚底贴不贴地、边角拼得像不像手画的） |
| 字体有没有带许可证 | 可读性（12 像素中文读不读得清、一屏文字挤不挤） |
| 数值平衡（那几条不等式） | 交互（提示看不看得出说的是哪个东西、手柄走不走得通每一页） |
| 文档断链、编号、引用纪律 | 声音（打击音与画面爆点是不是同一帧） |

**判断一个新的检查入口该不该存在，用同一把尺子**：**它判的东西在 Godot 里看不看得出来。** 看得出来的
交给你，看不出来的才写成入口。

## 十、实机验收清单：按类别汇总

各篇末尾都有自己那一节，这里按「打开游戏之后从哪看到哪」重排一遍，当一次完整验收的走查单用。

### 画面基础

- **像素糊不糊。** 放大看边缘。糊了先查两处：纹理过滤有没有被谁覆盖、素材有没有被缩放。
- **走动时画面抖不抖。** 抖了就是某处落在了半像素上（先看相机有没有开位置平滑）。
- **脚底贴不贴地。** 站着、走动、跳起落地各看一次。
- **层级前后对不对。** 角色走到物件后面该被挡住；侧视里跳起来的角色不该突然跑到别人身后。

### 窗口与取景

- **把窗口从最窄拉到最宽**，每一页界面都看一遍 —— 错位只在某些宽度下出现。
- **地图四个角各走一次**，看边缘有没有露白；再把窗口拉宽重看一遍。
- **跟随跟得舒不舒服。** 小幅走动镜头不动、走远了跟上来但不甩。

### 战斗手感

- **顿帧几帧最带感。** 这是最该逐帧试的一个数。
- **判定框与画面对不对齐。** 开帧步进与叠层，拳脚伸到最远那一帧框应该开着。
- **受击框高度对不对。** 从头顶掠过的攻击不该判中（这一条曾经错过，而它不报错）。
- **该挡住的挡住了吗。** 四个方向各走一次，**侧视记得也用上下键在纵深上走进去试**。
- **绕行走得通吗。** 走到物件跟前、纵深挪开、再往前走。
- **打击音与画面爆点是不是同一帧。**

### 界面

- **只用手柄能不能走完每一页。** 进页有初始焦点、每个可操作项都到得了、返回键有反应。
- **纯装饰件有没有挡住点击。** 每个按钮都点一次。
- **12 像素中文读不读得清。**
- **冷却遮罩是不是不透明色而不是压暗。**
- **读条在不在执行者身上**（钉在屏幕角上就是挂错层了）。
- **关卡里打开面板时敌人是不是完全不动。**

### 经营与地形

- **边角拼得像不像手画的。** 每一对会挨着的地形都要看。
- **每种地形有没有挡住人**（漏配物理层不报错）。
- **耕地的干湿两套色带一屏之内分不分得出来。**
- **有没有整体偏半格**（通常是把格中心当左上角用了）。
- **交互点范围合不合手**：该能用的地方能用、明显够不着的地方不误触发。

### 配置与报错

- **每个导出格子的名字读不读得懂**，单位清不清楚。
- **故意留空一格跑一下**，报错说不说得清是哪个节点的哪一格。
- **换一份参数资源跑起来有没有真的变**（没变说明代码里还留着默认值在偷偷胜出）。

### 存档

- **存档位列表读不读得出「这一位是哪条世界线」。**
- **写入失败那句话说不说得清「这一天有没有推进」。**
- **缺 mod 的清单说不说得清「装回哪个 mod」。**

## 十一、怎么把结果贴回来

**我看不到你的屏幕，也跑不了 Godot 编辑器。** 所以实机结果是我唯一拿不到的证据，贴回来的质量直接决定
我能不能定位。

**最有用的三样，按有用程度排：**

1. **底部输出面板与调试器面板的全文。** 直接全选复制，不要只贴你觉得相关的那一行 —— 报错前面几行常常
   是真正的原因。
2. **你看到的画面，用「该怎样／实际怎样」两句话说。** 例：「该被挡住，实际直接穿过去了」比「碰撞有
   问题」能定位得多。
3. **复现步骤。** 每次都这样还是偶尔一次；从哪个场景进去、按了什么。

**如果是偶发的**，告诉我「十次里大概几次」—— 那个比例本身就是线索（每次都错、一半的时候错、极偶尔错，
三者的成因完全不同）。

⚠️ **如果我定不出根因，我会加临时诊断输出让你再跑一次，据实定位之后再精准修，事后删掉那些诊断。**
我不会在不确定根因的情况下连着改 —— 那样改坏了也看不出来是哪一下。

## 十二、动手练习：制造三个缺陷并各用一种工具抓住它

目标是把输出面板、可见碰撞形状、远程场景树各用一次。大约四十分钟。

1. **准备**：拿[物理与碰撞](./物理与碰撞.md)那个练习的场景（一个会走的角色、一面墙、一片地）。
2. **缺陷甲：空引用。** 在脚本里导出一个 `Texture2D?`，不填就直接用它。跑一下 —— **在调试器面板里
   看到异常与堆栈**，双击堆栈那一行会跳到出错的代码。
3. **把它改成「在 `_Ready` 里判空并抛一句说清是哪一格」**，再跑 —— 对比两次报错，哪一个让你更快知道
   该改哪里。
4. **缺陷乙：穿模。** 把角色的碰撞掩码清空。跑一下 —— 它穿过墙，**什么都不报**。现在**开「可见碰撞
   形状」**再跑，看到两个框但没有反应，于是你知道问题在层与掩码而不在形状。
5. **缺陷丙：值不对。** 在脚本里把某个导出属性在 `_Ready` 里悄悄改掉（模拟「代码里还留着默认值」）。
   跑起来切到**远程场景树**，点那个节点看检查器 —— 显示的是被改后的值，而本地场景里填的是另一个。
   **这就是「两份来源，场景那份被静默盖掉」的样子。**
6. **在远程检查器里改一个数**（比如移动速度），感受一下立刻生效。然后停掉游戏，确认那个改动没有留下。
7. **打印一行诊断**（`GD.Print` 当前速度与位置），跑起来看输出面板。**然后删掉它** —— 练一下「事后要
   删」这个习惯。
8. **跑一次 `python tools/verify.py`**（在代码仓根目录）。看它每步一行的输出，再去
   `logs/verify/` 下打开那份摘要。**注意退出码与摘要是两样东西。**

做完你会知道：什么症状该开哪个工具、远程场景树能做什么、一句好的报错值多少。

## 十三、最后一条

**没有机器判据不等于可以不判。** 这套文档里每一篇末尾那张「只能你实机看的」清单，就是那些判据的存放
处 —— 它们不是提醒，是这个项目验证链条里真实的一环。

**看不出来的时候说出来**：某一项你看不出该怎么判（比如「这个动画切得顺不顺」到底看什么），那说明那一条
写得不够具体，告我一声我改。清单本身也是活的。
