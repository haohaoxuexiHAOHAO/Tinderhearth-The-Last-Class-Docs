# 文件读写与存档

> 本篇回答：**文件该读哪个路径**、**内容与存档各走哪一套文件 API**、**怎么保证写坏了不丢档**。
>
> **全项目只有存档这一处真正写文件**，所以这一篇里作者要做的事最少（存档系统的「作者填」那一格是
> 空的），但它是**最不能出错的一处** —— 存档写坏了玩家会丢进度，而那是唯一无法挽回的缺陷。前置是
> [资源与内容数据](./资源与内容数据.md)。总纲在[本目录索引](./README.md)。

---

## 一、三种路径前缀

| 前缀 | 指向 | 能不能写 |
| --- | --- | --- |
| `res://` | 工程根目录。导出后是打进 `.pck` 包里的那些东西 | 包内的条目**改不了** |
| `user://` | 玩家的数据目录（Windows 上在用户的应用数据目录下） | 能写 |
| 绝对路径 | 本机真实路径 | 看权限 |

本项目用到的三个位置都在 `src/Platform/ModPaths.cs` 里写成常量：基础内容 `res://data`、
mod `user://mods/<名字>/`、存档 `user://saves`。

**代码里不要出现第四个位置**，也不要把这三个字符串再抄一遍 —— 那是给它们开第二个家。

## 二、内容走引擎的文件 API，存档走 .NET

```csharp
// 读内容：对
using var handle = FileAccess.Open(path, FileAccess.ModeFlags.Read);

// 读内容：错，导出后读不到
var text = System.IO.File.ReadAllText(path);
```

**为什么内容必须走引擎**：导出后 `res://` 的内容打进 `.pck` 包里，**只有 Godot 自己的 `FileAccess` 能读**。
`user://` 是真实目录，两种读法都行；内容那一侧统一走 `FileAccess`，免得两套路径两种行为。

**存档是唯一的例外，读写都走 .NET 的 `System.IO`**：存档要写坏了不丢档，而 Godot 的改名在 Windows 上
先删旧档、`Flush()` 也不保证到盘（源码与做法在「七、原子替换：写坏了不丢档」）。存档只在 `user://` 下、
不进 `.pck`，所以 .NET 读得到它；读与写走同一套，存档只有一条路。代码在 `src/Platform/SaveStore.cs`。

### 一个 C# 特有的小坑

`ImplicitUsings` 会引入 `System.IO`，于是 `FileAccess` 在 `Godot.FileAccess` 与
`System.IO.FileAccess` 之间歧义、编译报 `CS0104`。本项目的处理是在用到它的那个文件顶上取别名：

```csharp
// src/Platform/GodotContentSource.cs
using FileAccess = Godot.FileAccess;
```

**取别名而不是关掉 `ImplicitUsings`**：这样歧义只在真正用到它的文件里解决一次，读代码的人也能看出用的
是哪一个。`src/Platform/SaveStore.cs` 不引用 Godot，那里的 `FileAccess` 就是 `System.IO` 那一个，不用取别名。

## 三、`FileAccess` 用法，以及 C# 里必须 `using`

```csharp
const string path = "user://lab/data.json";

// 读
using var f = FileAccess.Open(path, FileAccess.ModeFlags.Read);
if (f is null)
{
    throw new FileNotFoundException(
        $"读不到：{path}（Godot 错误 {FileAccess.GetOpenError()}）");
}
string text = f.GetAsText();

// 写
using var w = FileAccess.Open(path, FileAccess.ModeFlags.Write);
w.StoreString(json);
```

四条要点：

- **打不开返回 `null`，不抛。** 所以每次 `Open` 之后都要判，并且**把 `GetOpenError()` 写进报错里** ——
  「读不到」有很多原因（不存在、没权限、被占用），不写错误码就等于把排查甩给下一个人。
- **C# 里必须 `using`。** 官方文档写明：引擎侧的 `FileAccess` 在对象被释放时自动关闭，而**在 C# 里要
  自己释放** —— `using` 语句或者显式 `Dispose()`。不写的话文件句柄什么时候关取决于垃圾回收，而那会让
  「写完马上读」偶发读到旧内容。
- **`Flush()` 只把缓冲交给系统。** 它在 Windows 上就是一次 `fflush`：数据进了系统缓存，不保证到盘；
  关闭时也会做一次。存档要的是落盘，所以存档不走它（见「七、原子替换：写坏了不丢档」）。
- **文本一律 UTF-8**，`GetAsText()` 按 UTF-8 解。

## 四、`DirAccess`：目录操作

常用的都是静态方法（名字带 `Absolute` 的那些只吃绝对路径或带前缀的路径）：

```csharp
DirAccess.DirExistsAbsolute(path)            // 目录在不在
DirAccess.MakeDirRecursiveAbsolute(path)     // 建目录，连中间层一起
DirAccess.GetFilesAt(path)                   // 目录下的文件名
DirAccess.GetDirectoriesAt(path)             // 目录下的子目录名
DirAccess.RenameAbsolute(from, to)           // 改名或移动
DirAccess.RemoveAbsolute(path)               // 删（目录必须为空）
```

⚠️ **`RenameAbsolute` 不能拿来换存档。** 目标已存在时，它在 Windows 上先删掉目标、再改名，中间有一刻
盘上一份都没有（见「七、原子替换：写坏了不丢档」）。

它们返回一个 `Error` 值，**要判**：

```csharp
// src/Platform/ModPaths.cs
if (DirAccess.MakeDirRecursiveAbsolute(path) != Error.Ok)
{
    return false;     // 失败不抛 —— 调用方要能把它报给玩家
}
```

⚠️ **列目录的顺序不确定。** 官方文档点明：逐项遍历那套接口返回的顺序**不保证**，会随操作系统变。要
稳定顺序就用 `GetFilesAt` / `GetDirectoriesAt`（它们是排好序的），或者自己排一次。

**这一条对 mod 加载很要紧**：mod 的叠加顺序决定谁覆盖谁，靠目录遍历顺序就等于让覆盖结果随机。

## 五、纠正一条流传很广的说法

**「导出后 `res://` 只读」是错的。** 这条曾经写在本项目文档里。

用导出产物实测（Windows、非嵌入 pck）：往 `res://` 写文件**会成功** —— 句柄非 null、错误码正常，文件
落在**可执行文件同级目录**。只有已经打进 `.pck` 的条目才真正改不了；`res://` 这个前缀本身是可写的。

**所以「mod 与存档放 `user://`」的理由不是「res:// 写不了」**，而是这三条（都写在
`src/Platform/ModPaths.cs` 里）：

1. **exe 同级目录不按用户区分。** 多用户共享一份安装时，一个人装的 mod 会影响所有人。
2. **真实安装位置常常写不了或会被抹掉。** `C:\Program Files` 下要提权；Steam 库目录即使可写，
   「验证文件完整性」也会清掉不在清单里的文件 —— 玩家的 mod 会莫名消失。
3. **Steam 云存档要求一个可预测的按用户位置**，`user://` 正是它。

## 六、把 `user://` 交给规则层：`GlobalizePath`

规则层**不引用 Godot**，所以它不认识 `user://` 这个前缀。存档的分片收集与解析都在规则层，而读写文件
在引擎层，交界面是**一个绝对路径字符串**：

```csharp
// src/Platform/ModPaths.cs
public static string ResolveUserPath(string godotPath) =>
    ProjectSettings.GlobalizePath(godotPath);
```

**所以存档那条链的形状是**：引擎层把 `user://saves` 解析成本机绝对路径 → 规则层只吃字符串与字典 →
真正的读写回到引擎层做。

**这也是给玩家说明「mod 放哪」的唯一办法** —— 得告诉他一条他在文件管理器里点得到的路径。

## 七、原子替换：写坏了不丢档

**直接往目标文件上写是错的。** 写到一半断电、崩溃或磁盘满，目标文件就是半份 —— 而半份存档读出来的
世界比没有存档更糟。

正确的形状：

1. **写临时文件**，与目标文件**同目录**（本项目是 `slot_01.json.tmp`）。
2. **落盘**：内容真的写到盘上，而不是停在系统缓存里。
3. **一次带覆盖的改名**：把临时文件改名成目标文件，目标在就替换掉它；是一次调用，而不是先删目标、再改名。

**为什么临时文件要与目标同目录**：跨盘或跨文件系统的改名不是原子操作（系统会退化成「复制加删除」），
那就又回到「写到一半」的风险上。

⚠️ **不要用引擎那个「建临时文件」的便捷方法来做这件事** —— 它把文件建在系统临时目录里，改名就跨了
文件系统。

**中间任何一步失败，目标文件一个字都没动。** 这就是「事务」的含义。

### 为什么存档不用 Godot 那一套

读的是 Godot 4.7.2-stable 的源码：

- **`DirAccess.RenameAbsolute` 先删目标、再改名。** 目标已存在时，它在 Windows 上先删掉目标，再调
  `MoveFileW`（[dir_access_windows.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/windows/dir_access_windows.cpp)）。
  删完、改名之前断电，盘上一份存档都没有；改名失败时旧档已经删了。
- **`FileAccess.Flush()` 在 Windows 上只调 `fflush`**（[file_access_windows.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/windows/file_access_windows.cpp)）：
  数据进了系统缓存，不保证到盘。
- **Godot 自己那套安全保存默认关着。** 它写临时文件、关闭时用 `ReplaceFileW` 换上去，但只在 `backup_save`
  打开时生效，而它默认关（[file_access.h](https://github.com/godotengine/godot/blob/4.7.2-stable/core/io/file_access.h)）。

### 本项目的做法：.NET 写临时文件、落盘、带覆盖地改名

```csharp
// src/Platform/SaveStore.cs 的 Write，省掉了出错时删临时文件、报出路径那一段
System.IO.Directory.CreateDirectory(Directory);
using (var stream = new FileStream(temporary, FileMode.Create, FileAccess.Write, FileShare.None))
{
    stream.Write(bytes);
    stream.Flush(flushToDisk: true);              // 落盘
}

File.Move(temporary, Path, overwrite: true);      // 一次带覆盖的改名
```

- **`Flush(true)` 把中间缓冲也写到盘上**（[微软文档](https://learn.microsoft.com/dotnet/api/system.io.filestream.flush)）。
- **`File.Move` 带覆盖，在 Windows 上是一次 `MoveFileExW`**，带着 `MOVEFILE_REPLACE_EXISTING`
  （[dotnet/runtime v10.0.0 源码](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Common/src/Interop/Windows/Kernel32/Interop.MoveFileEx.cs)）。
  同一处还带着 `MOVEFILE_COPY_ALLOWED`：跨盘时它悄悄退化成复制加删除，这是临时文件必须同目录的又一个理由。
- **不重试。** 刚写完的文件可能被杀毒软件读着、锁住，改名就失败：Godot 那套安全保存为此重试上千次，
  注释写的就是这件事（上面那份 file_access_windows.cpp 的 `_close`）。这里失败就走「这一天没有推进」，
  那是安全的一侧。

以上几处内容为合规做过改写。

### 怎么故意让它写不上

**把存档文件设成只读**（右键那个文件 → 属性 → 勾「只读」）：改名被拒，`File.Move` 抛
`UnauthorizedAccessException`，目标一字不动，临时文件也删掉了；去掉只读再写一次就成了（实测，本机
Windows、.NET 10）。

**给存档目录打只读属性挡不住**，替换照样成功（实测，用的是 Python 的 `os.replace`，底下是同一个
`MoveFileExW`）。要设的是文件，不是目录。

### 本项目刻意不留备份

**不另留玩家读得到的备份文件。** 理由是那等于偷偷做了一个「手动存档」的替代品，而本作的存档时机
只有睡眠一处 —— 留备份会让玩家发现「原来可以读回上一天」，那改变了设计。

## 八、事务边界：提交点在哪

每日结算加自动存档**是一次事务**，而**提交点是存档写入成功那一刻**。

三条推论：

- **跑一半就一步都不生效。** 不能出现「作物长了但钱没结算」。
- **写入失败等于整天没推进。** 玩家仍在睡前，而提示要说清这一点 —— 「保存失败」不够，要说「这一天
  没有推进」。
- **被中断则回到睡前。**

**摘要产出在提交之前，弹出在提交之后** —— 所以写入失败时那份摘要一次都不会被弹出来。

## 九、存档的形状：分片

存档**不是一个大对象**，是若干**分片**的集合，每个分片由持有它的系统自己声明。所以存档系统本身
**不持有任何字段清单**。

| 分片声明的四格 | 说明 |
| --- | --- |
| 叫什么 | 分片标识 |
| 进哪一侧 | 正式存档，还是临时续玩点。**只有两个取值，没有「两边都进」** |
| 缺字段时补什么 | 老存档里没有这一格时的处置 |
| 谁持有它 | 那个系统 |

**进哪一侧只有一条判据**：**跨过一次睡眠还成立的进正式存档。** 当天的计数器、关卡进度、在哪张图、
气泡冷却池这些进续玩点。

### 四条结构约束

- **显式注册，没有自动发现。** 忘了注册就是忘了存 —— 而那要能被看出来。
- **载入顺序无关。** 全部分片读完之后才统一解析标识。反证是「任意顺序读出同一结果」。
- **派生量不单独存。** 反证是「改基底之后派生量跟着变」。
- **判兼容排在处理缺字段之前**，而且被拒时**任何分片都不许交给持有者** —— 不许读出半份世界。

### 续玩点是全量快照

临时续玩点**带着那些家在正式存档里的分片一起存**，所以它是一份完整世界。它按存档位各一份、读取后
即失效、睡眠成功时作废当前那一份，而且**不跑定时器** —— 按时机写（进出场景、关卡内某些节点）。

## 十、缺 mod 的内容：隔离，不删除

存档里存的一律是**标识**，所以「缺了那个 mod」的表现是**解析不到**。

处置是**隔离而不是删除**：标成不可用、**不进任何计数**（编队、名册容量、仓库格数、遍历都要跳过它），
装回 mod 之后一件不少。写回存档时**原样写回读不懂的标识**。

⚠️ **这一条要求存档里记「写档时启用了哪些 mod」**，否则说不出缺的是哪一个。

## 十一、玩家级偏好是第三样东西

音量、键位、分辨率这类**不属于任何存档位**：换存档位它们不变。所以它们：

- **不进任何存档文件**，与存档位平级；
- **不走分片注册**；
- **缺字段一律补默认值、不报错** —— **与存档侧刻意相反**。

**为什么相反**：缺一项偏好的后果是「音量回到默认」，玩家自己改回来就行；缺一项存档字段的后果是
「世界状态不对」，那必须被发现。

## 十二、JSON 用哪一个

| 场合 | 用什么 |
| --- | --- |
| 规则层解析内容与存档 | **`System.Text.Json`**（规则层不引用 Godot） |
| 引擎层偶尔要读一个小配置 | 也用 `System.Text.Json`，保持一致 |
| Godot 自己的 `Json` 类 | **本项目不用** |

**为什么不用引擎那个**：它产出的是 Godot 的字典与数组（`Variant` 那一套），传进规则层要先转一遍；而
`System.Text.Json` 直接反序列化成 C# 类型，还能靠 `required` 属性让**缺键当场报错**（见
[资源与内容数据](./资源与内容数据.md)）。

本项目的解析入口是 `rules/Foundation/Content/ContentJson.cs`，全项目共用它，**枚举按名字读写**。

## 十三、存档位摘要不要读整份存档

存档位列表要显示「这是第几周目、玩到哪一天、上次玩是什么时候」。**那些放在文件最外层**，读前面几行
就够 —— 不要为了画一个列表把五个存档全部反序列化一遍。

⚠️ **也不另存一个索引文件。** 那是同一份事实的第二个家：索引与存档分叉之后，列表显示的和读出来的
不是同一个东西，而它不报错。

## 十四、动手练习：写一个不会写坏的存档

目标是把 `FileAccess`、`DirAccess`、原子替换、失败处置走一遍。大约一小时。

1. **新建场景**，根节点 `Node` 改名 `SaveLab`，挂脚本。这个脚本两套文件接口都用，`FileAccess` 会撞名
   （见「一个 C# 特有的小坑」），所以写全名：`Godot.FileAccess` 与 `System.IO.FileAccess`。
2. **确保目录存在**：`_Ready` 里调 `DirAccess.MakeDirRecursiveAbsolute("user://lab")`，判返回值，
   失败就打印而不是抛。
3. **写一个文件**：用 `Godot.FileAccess.Open("user://lab/data.json", ModeFlags.Write)` 写一段 JSON。
   **记得 `using`。** 跑一下。
4. **找到它**：打印 `ProjectSettings.GlobalizePath("user://lab/data.json")`，去文件管理器里打开那个
   路径，确认文件真在那儿、内容是你写的。**这一步让 `user://` 变成一个你摸得到的地方**，后面 .NET 那几步
   吃的也是这个绝对路径。
5. **读回来**：`ModeFlags.Read` 打开、`GetAsText()`，打印出来对比。
6. **制造打不开**：把路径改成一个不存在的目录下的文件，跑一下 —— 确认 `Open` 返回 `null` 而不是抛，
   并把 `FileAccess.GetOpenError()` 打出来。
7. **原子替换**：照「七、原子替换：写坏了不丢档」里那段代码改成 .NET 的三步 —— 用 `FileStream` 写
   `data.json.tmp`、`Flush(true)`、`File.Move(临时文件, data.json, overwrite: true)`，路径都用「找到它」
   那一步打出来的绝对路径。跑几次，确认目标文件每次都是完整的。
8. **故意在中间失败**：在 `Flush(true)` 之后、改名之前抛一个异常。跑一下，然后去看 `data.json` ——
   **它应该还是上一次的完整内容**，而 `data.json.tmp` 留在那儿。这一步是这个练习的重点。
9. **对比直接写**：改回「直接往 `data.json` 写」，在写到一半时抛异常（写一半字符串后抛），再看那个
   文件 —— 这回它是半份。**记住这个差别。**
10. **设成只读**：在文件管理器里把 `data.json` 设成只读，再走一次原子替换 —— `File.Move` 抛
    `UnauthorizedAccessException`，`data.json` 一字不动。去掉只读再走一次，这回换上去了。
11. **列目录**：在 `user://lab` 下建三四个文件，用 `DirAccess.GetFilesAt` 打印出来，看顺序。

做完你会摸清：`user://` 到底在哪、`using` 为什么不能省、原子替换挡住的是什么、「写不上」该设在哪。

## 十五、这一篇里只能你实机看的

- **存档位列表读不读得出「这一位是哪条世界线」。** 摆两个不同周目的存档看一眼。
- **写入失败那句话说不说得清「这一天有没有推进」。** 这是最要紧的一条 —— 玩家必须知道自己要不要重睡
  一次。想试就临时把存档文件设成只读；设在目录上挡不住，见「七、原子替换：写坏了不丢档」。
- **缺 mod 的清单说不说得清「装回哪个 mod」与「继续之后会怎么样」。** 只说「有内容不可用」不够。

- **读档界面在主菜单而不在手环上。** 主角不在世界里选存档位。
