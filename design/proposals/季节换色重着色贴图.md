# 季节换色在换季那一刻重着色贴图，改轮廓的才画素材

## 摘要

四季要改变画面的颜色。我们把这件事按一条判据拆成三条互不重叠的路 —— **这一季的变化改不改轮廓**：只换颜色的，在换季那一刻用 CPU 把贴图重新着色一次；改了轮廓的（物件顶上的积雪、光秃的树、冰面裂纹），画成季节变体素材；只有每帧都在变的才用着色器。

**最重要的那个承诺是：新增一样素材的默认季节成本为零。** 画一版就能跟着换色，只有真需要积雪那几个才多画一版。由此季节数增加不带来素材量增加 —— 加第五种季相只是往色板加一条色带。

## 背景与动机

作者确认四季要换色之后，第一个成形的想法是写一个片元着色器把植被那条色带换掉。我们照这个想法做了一个一次性试验件（一个 `.gdshader`，挂在农场场景的地形显示层上，一个整数 uniform 切季），作者在编辑器里实机看过：**画面确实变了**，换色的观感成立。

但试验同时暴露了两笔原先算错的账。

**第一笔：着色器跑在哪个分辨率上。** 我们一度按逻辑分辨率 640×360 的二十三万像素估开销。那是错的 —— 项目用的是 `canvas_items` 拉伸模式，片元着色器跑在**窗口分辨率**上。按换四条色带约二十四次比较重算：

| 显示分辨率 | 像素数 | 每帧比较次数 | 60fps 每秒 |
| --- | --- | --- | --- |
| 1920×1080 | 2.1M | 50M | 3.0G |
| 2560×1440 | 3.7M | 89M | 5.3G |
| 3840×2160 | 8.3M | 199M | 12G |

独显无感，核显在 4K 下吃掉个位数百分比的预算。不致命，但不再是可忽略的量。

**第二笔：这件事到底多久变一次。** 换季是一年四次。让 GPU 每秒算六十遍同一个答案，算的全是同一批像素的同一个结果。

而真正把方案推翻的是第三件事：**着色器变不出形状。** 雪覆盖地面、树枝落光、水面结冰，这些是「多了一层东西」或「少了一块东西」，不是换色。着色器对它们一点办法都没有，所以原先那个「全部交给着色器」的设想从一开始就只能覆盖一半问题。

## 上游约束

- [像素绘制原则 · 硬边、抗锯齿与点绘](../../production/像素绘制原则.md)：透明度只用完全透明或完全不透明，导出与引擎显示均用最近邻过滤。**这一条约束本设计否掉换季过渡动画** —— 插值会算出色板外的颜色，而淡入淡出就是插值。
- [像素绘制原则 · 色带与色相偏移](../../production/像素绘制原则.md)：同一素材族复用色带，内容素材可扩展项目色彩家族但要记录原因。**这一条约束换色表的形状** —— 换色是「整条色带换成另一条」，不是逐色随手改。
- [像素绘制原则 · 统一视角与光源](../../production/像素绘制原则.md)：外部光源统一来自右上。**这一条约束季节变体素材的雪该堆在哪一侧。**
- [场景绘制约定 · 动态水：静态瓦片加逐格帧动画，不写扰动着色器](../../production/场景绘制约定.md)：那一侧刻意否掉了噪声扰动着色器，理由是扰动采样落在非整数像素上。**这一条给本设计划了边界** —— 否掉那条的理由是「动采样位置」，而换色不动采样位置，所以那条理由套不到换色上；但它同时说明项目对着色器的态度是「只在它真正擅长的事上用」。
- [场景绘制约定 · 耕地要干与湿两套](../../production/场景绘制约定.md)：干湿形状相同只换色带，而且明说不许用代码统一压暗。**这一条是本设计的先例** —— 「形状相同、只换色带」正是本设计处理季节的同一个形状。
- [玩法定位 · 像素基准](../../canon/gameplay/玩法定位.md)：逻辑分辨率 640×360、两种视角都不缩放。**这一条是上面那张开销表的前提**，也说明逻辑分辨率不是本设计可以动的量。
- [时间与经营 · 结算顺序（固定，不得改动）](../../canon/gameplay/时间与经营.md)：那串步序标着不得改动，而且换季枯死必须排在按天推进之前。**这一条约束换季换色挂在哪里** —— 挂进已有的换季那一步，结算步数一个未增。
- [ADR-0009](../../decisions/ADR-0009-编辑器主导的开发模式.md)：参数唯一来源是场景与资源，代码不留能用的默认值；表现由作者实机验收。**这一条约束「这个物件冬天盖不盖雪」那处声明必须显式，以及本设计的观感项只能由作者判。**

## 当前事实与证据

- **色板在代码仓 `assets/self-drawn/palette.gpl`**，它是色值的唯一来源。四季要用的色带已经在里面（`moss` 当夏、另有春秋冬三条）。
- **贴图在本项目读得回来，不是推断**：`src/World/PlayerActor.cs` 已经在用 `texture.GetImage()` 逐帧扫身体边界；项目的导入默认是无损（`project.godot` 的 `compress/mode` 为 0），所以取回的像素就是原值。
- **着色器那条路的换色观感成立** —— 作者在编辑器里实机确认画面变了。这同时排掉了「引擎交给着色器的颜色值是不是贴图原值」那处色彩空间疑虑。
- **逻辑分辨率整数命中四档主流分辨率**：640×360 的二、三、四、六倍分别是 1280×720、1920×1080、2560×1440、3840×2160，一档都不用小数缩放。
- **待验证**：CPU 重着色一次要多久。三张地形图各 64×64、合计约一万二千格，按量级应当远低于一帧，但**没有实测**。验证办法是落地后在换季那一下打一条耗时日志。
- **待验证**：动画精灵逐帧重着色的总耗时。树与作物的帧数现在还没有，所以这个量现在量不出来。

## 设计

### 一条判据把三条路分开，而且不重叠

| 变化类型 | 走哪条 | 例 |
| --- | --- | --- |
| 只换颜色 | 换季那一刻 CPU 重着色贴图 | 春草更嫩、秋叶变黄、冬天大面被雪压白 |
| 改轮廓 | 画成季节变体素材 | 物件顶上的雪、光秃的树、冰面裂纹 |
| 每帧都在变 | 才用着色器 | 命中闪白（已有，在 `PlayerActor.cs`） |

判据只有一个问句：**这一季的变化改不改轮廓？** 它对每一样素材各问一次，所以答案是按素材给的，不是按季节给的 —— 这正是「新增素材默认零成本」的来源。

### 重着色就是把贴图当一张可改的网格

一张 PNG 载入内存之后是一个逐格存颜色的网格，可读可写。换季那一刻做三步：取回内存、逐格查表替换、做成新贴图装回去。装回去之后引擎画的就是新图，它不知道发生过换色。

```csharp
/// <summary>按一张换色表重新着色一张贴图。换季时跑一次，不是每帧。</summary>
/// <remarks>
/// 键取 8 位整数而不是 <c>Color</c>：那是四个浮点数，直接比相等很脆，而贴图里的值与色板里
/// 的值本该逐位相同。转成整数之后「贴图里那个绿」和「色板里那个绿」一定对得上。
/// </remarks>
private static ImageTexture Recolored(Texture2D source, Dictionary<uint, Color> swap)
{
    Image image = source.GetImage();
    for (var y = 0; y < image.GetHeight(); y++)
    {
        for (var x = 0; x < image.GetWidth(); x++)
        {
            if (swap.TryGetValue(image.GetPixel(x, y).ToRgba32(), out Color replacement))
            {
                image.SetPixel(x, y, replacement);
            }
        }
    }
    return ImageTexture.CreateFromImage(image);
}
```

用它换一层地形：

```csharp
atlasSource.Texture = Recolored(_baseSheet, SwapFor(season));
```

**瓦片图集的布局一个字不动。** 冬季那张图画在同一个 4×4 模板上，第几格是哪种收边完全一样，所以地图数据、地形集与双网格那张映射表都不受影响 —— 换的只是那张贴图本身。

### 四条落地时会咬人的边界

**每一季都从原图算，不从上一季算。** 夏到秋是一次换色，而秋到冬若拿已经是秋色的图再换一次，查表就对不上（秋的颜色不在「植被原色」那张表里）。所以原图留着不动，每季都从它生成。

**换色表从色板读，不写死在代码里。** 写死就是给同一个事实开第二个家，而色板改了而代码没跟着改**不报错**，表现只是某一季的颜色不对。这个错我们在双网格守卫上刚踩过一次：那个脚本原先硬写着四种地形的 RGB，素材一换它就把对的素材判成错的。

**「这个物件冬天盖不盖雪」必须是显式三态。** 盖哪一件、明确不盖、未声明当场报错。若它是个默认为假的布尔，「忘了填」与「故意不盖」长得一模一样，而忘了填**不报错** —— 表现只是冬天那块石头光秃秃的。

**动画精灵要逐帧换。** `AnimatedSprite2D` 的每一帧各是一张贴图，所以树与作物要遍历 `SpriteFrames` 把帧各换一次。

### 挂 `[Tool]` 之后编辑器里就能看

重着色是一次性调用，所以给那段脚本加 `[Tool]` 标注、让它在编辑器里也跑，作者改一个季节枚举就当场看到画面。**这一条是承重的** —— 季节观感没有机器判据，看不见就等于盲调。

## 理由与取舍

**我们没选「每季一套全素材」。** 星露谷走的是这条（它按季各备一张图块表），这是业界成熟做法，而且最直白。否掉它的理由是边际成本：新增一样素材要画四版（或至少两版），而季节数增加会线性放大整个素材库。本设计把这个成本压到「只有改轮廓的那几样才多画一版」。

**我们没选「全部交给片元着色器」。** 四条代价叠起来：每帧重算同一个答案（4K 下每秒约 120 亿次简单运算）；每个要换色的节点都得挂上材质，而漏挂一个**不报错**，表现只是「秋天了但那棵树还是绿的」；颜色要经一次引擎的色彩空间处理，多一处会出错而又不报错的地方；最要紧的是**它变不出形状**，所以它至多只能解决一半问题。

**我们没选「通用雪帽叠加件」。** 这个想法是我们自己提出又自己否掉的：在十六到三十二像素这个尺度上，雪盖在哪几个像素上取决于那个物件自己的轮廓 —— 同一个雪帽贴到圆石头、方木箱与栅栏上，三处都会错位。叠加件是三维或高分辨率下才成立的做法。

**我们没选换季过渡动画。** 作者明确不要过渡，而就算要也走不通：两个颜色之间插值会产出色板外的中间色，与硬 alpha 和整数缩放三条纪律直接冲突。想要过渡只能画中间季相的色带，那是额外素材。

**重着色不是只为季节存在，这一点加强了它值得建的理由。** 土元素把敌人**石化**，而石化在画面上就是把那个敌人重着色成石头那条色带 —— 同一套机制，零新素材、零新色带。换季那一刻与中一次土系技能，走的是同一段代码。一个只服务一处的机制值得掂量，一个已经有第二处用途的机制不必再争。

**我们没选查表贴图（LUT）。** 它是着色器那条路的优化形态（一次纹理采样代替二十多次比较），但本设计把换色挪出了每帧路径，所以它优化的那个开销已经不存在。记下它是因为它仍是一条已知的退路：真有一天需要每帧换色，LUT 是那时该走的路，而且最近邻采样的查表只产出色板里的颜色、不破像素纪律。

## 兼容性

**纯增量，不破坏任何既有东西。** 季节本来就是玩法数据，本设计不改存档格式、不加结算步骤、不动已有素材。原图保持原样正是本设计要求的前提，所以现有那几张地形图一个像素都不用动。

一处要写明的代价：**冬季变体素材进来之后，双网格守卫要连它们一起判。** 那个脚本现在只认三套交接，冬季那几张的外圈拼接规则与夏季完全相同，但它不会自己去看。不改的话冬季素材的拼接没有任何东西在守。

## 实现与过渡

1. **换色表从色板读出来**：解析 `palette.gpl`，按色带名取出 `moss`、`spring`、`autumn`、`winter` 四条，组成三张换色表。这一步自带一条校验 —— 色带名拼错或档数对不上当场报错。
2. **写重着色那一段**，带 `[Tool]`，作用在地形显示层上。先只接地形，作者看一眼观感。
3. **接动画精灵**：遍历 `SpriteFrames` 逐帧换。
4. **接进换季那一步**：挂在已有的换季处，不新增结算步骤。
5. **季节变体素材的声明**：定「这个物件冬天盖不盖雪」那处三态声明，缺声明报错。
6. **双网格守卫按季分**：`SETS` 那张表加季节维度。

一到二步做完就能让作者判观感，所以观感风险在最前面就暴露，不会压到最后。

## 边界与非目标

- **不定四季各自的主题色。** 色值在色板里，由作者在暗色实机背景下校准。
- **不定哪些物件需要冬季变体。** 那是逐素材按判据问出来的，归各自的美术条目。
- **不碰逻辑分辨率。** 640×360 由中文可读性与整数缩放两条定下，本设计只是它的下游。
- **不做昼夜换色。** 全库没有一句说画面要表现昼夜，所以它不在本设计之内 —— 但它与季节是同一类问题，真要做时套同一条判据即可。
- **不做室内与城区的季节表现。** 星露谷的室内与地下不受季节影响，本设计先照这个范围走。

## 验收

**可自动验证项**

- 换色表解析不出预期的色带名或档数时当场报错，有用例。
- 「这个物件冬天盖不盖雪」缺声明时当场报错，有用例。
- 双网格守卫对冬季那几套素材执行与夏季相同的外圈检查，`python tools/verify.py` 全绿。
- 重着色之后的贴图里不出现色板外的颜色 —— 这一条由色板检查入口判。

**必须实机确认项**

- 四季各自的观感：切到每一季各看一遍，判它像不像那个季节。
- 冬天大面被雪压白之后，玩家还分不分得出草地与裸土的边界。
- 季节变体素材与重着色过的大面放在一起协调不协调（雪帽的白与被压白的地面要是同一套白）。
- 换季那一下的突变能不能接受。

**完成边界**

四季在基地场景里切得过去、观感由作者确认、冬季变体那条声明有报错兜着，这份设计就算落地。城区与侧视关卡的季节表现不在其内。
