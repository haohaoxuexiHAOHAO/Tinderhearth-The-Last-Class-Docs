# 专项设计

限定范围的**活跃方案**：比一份需求文档大、但还没稳定到进正典的系统设计。由 `/to-design` 产出，写成设计提案的形状 —— 摘要、背景、设计、理由与取舍、兼容性、实现。

| 条目 | 内容 |
| --- | --- |
| [数值模型](./数值模型.md) | 属性、成长、判定、时间与体力、经济、容量的公式与判据。**值不在正文**，在 `numeric-model-params.json`；推演入口 `python tools/simulate_week.py` |
| [角色动作状态机](./角色动作状态机.md) | 互斥的姿态与流转：运动层、动作叠加层、生命周期终态、受击链与完整流转表、经营侧另一套动作机的原则。**不定效果、不定数值**；立项在 `GP-18` |
| [状态效果系统](./状态效果系统.md) | 能并存的修饰：三类（控制／参数／纯描述）、三种时长单位（帧／天／永久）、载体字段、显示与实际分离、跨场景与存档、与动作机的唯一接缝。**不定姿态、不定数值**；与动作机共用 `GP-18` |
| [推进与时间轴](./推进与时间轴.md) | 主线节点的解锁条件只有四类（前置节点／里程碑闩／天数下限／玩家主动触发）、债务与成长与繁荣度与信任度四条长期线如何收束成闩、繁荣度与共同体选择链的结构、结局判定时点。**不定数值**（归 `GP-2`）、不写剧情内容（归 `NR-1`／`NR-2`／`NR-3`） |

## 与正典、需求文档的分工

| 文档 | 回答什么 | 生命周期 |
| --- | --- | --- |
| [正典](../canon/world/世界观.md) | 产品**意图**：这个游戏应该是什么 | 稳定，长期有效 |
| 本目录 | 某个系统**怎么做成**，以及**为什么不选别的做法** | 活跃期维护，稳定后结论上升进正典 |
| [`spec/`](../spec/README.md) | 这**一次**改动做什么 | 一次需求，归档即结束 |

判断该写哪个：

- 只影响一次改动 → 需求文档，不要建专项设计。
- 一个系统的完整规则、会被多次改动反复引用 → 专项设计。
- 已经确定、不会再变的产品事实 → 直接进正典。

**建之前先找现有权威源。** 默认修改既有文档，不新建平行方案。真要新建就说明它的类型、上游来源、生命周期与替代关系，并接入 [README 文档地图](../README.md) —— 否则检查器会报「从 README 无法到达」。

## 设计稳定后要上升

设计稳定后把**已确定的产品事实上升进正典**，本目录只留仍在活跃调整的部分。

不做这一步就会出现两份说法不同的权威源，而且没有任何机制能发现 —— 检查器查断链，查不出两份文档对同一件事的描述已经分叉。

**已知的唯一例外是[数值模型](./数值模型.md)**：[玩法定位](../canon/gameplay/玩法定位.md)写明「数值一律不在正典」，所以它永久留在本目录，不上升。写在这里是为了以后没人来做一次错误的上升。
